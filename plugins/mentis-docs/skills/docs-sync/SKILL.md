# docs-sync

여러 레포를 **git pull** 하고, 각 레포의 **pull 전후 diff를 근거로 대응 문서를 자동 갱신**하는 스킬. 사용자가 선택한 동작은 **pull까지 수행 → 자동 반영 → 요약 보고**다.

> 핵심 원칙
> - **사실 기반**: 문서에 쓰는 모든 항목은 실제 diff(커밋 제목·변경 파일·코드)에서 확인한 것만. 추측·일반론 금지. 불명확하면 그 부분은 "미확인"으로 남긴다.
> - **비파괴**: 문서 전체를 다시 쓰지 않는다. 그 문서의 기존 구조와 서술을 그대로 둔 채 고칠 곳만 고친다.
> - **본문 정정은 선택이 아니다**: 변경 로그만 위에 쌓고 본문을 그대로 두면 문서는 겉만 최신이 된다.
>   diff 로 본문 서술이 틀렸다고 **확인되면** 그 서술을 고친다. 이건 비파괴 원칙을 어기는 게 아니다.
>   비파괴는 "멀쩡한 곳을 건드리지 마라"는 뜻이지 "틀린 곳을 놔둬라"는 뜻이 아니다.
> - **문서 컨벤션 존중**: 각 문서가 이미 쓰는 형식(예: 상단 "master pull 보강" 블록, "최근 변경사항" 표, "분석 갱신일")을 그대로 따른다.

## 설정 (첫 실행 시)
작업 시작 전 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md`의 "설정 절차"를 그대로 따른다**: `~/.config/mentis-docs/config.env`를 source 해 환경 변수를 불러온다. 파일이 없으면 그 절차대로 기본값을 확인·저장한 뒤 진행한다. 이하 경로는 `$DOCS_REPOS_ROOT`·`$DOCS_ROOT` 기준.

## 사용법
- `/docs-sync` — `$DOCS_REPOS_ROOT` 하위 모든 대상 레포를 pull·갱신.
- `/docs-sync {레포...}` — 지정한 레포만. 예: `/docs-sync wadiz-frontend app-api`.
- `/docs-sync pull=off` — pull은 건너뛰고, 각 레포의 최근 미반영 변경(`ORIG_HEAD..HEAD` 또는 최근 N개 커밋)만 문서화. 이미 pull 해둔 경우에 사용.

## 절차

### 1. 대상 레포 선정
`$DOCS_REPOS_ROOT`의 하위 항목 중 다음을 **제외**한다: 디렉터리가 아닌 것, `.git`이 없는(=git 저장소 아님) 폴더, `$DOCS_ROOT` 자신, `DOCS_SYNC_EXCLUDE` 목록. 인자로 레포를 지정했으면 그 교집합만.

### 2. 레포별 pull 전후 스냅샷 (핵심 — 정확한 diff 범위 확보)
각 레포에서 순서대로:

```bash
cd "$DOCS_REPOS_ROOT/{repo}"
BRANCH=$(git rev-parse --abbrev-ref HEAD)
BEFORE=$(git rev-parse HEAD)
# pull=off 가 아니면:
git pull --ff-only 2>&1 || git pull 2>&1   # ff 불가 시 일반 pull. 충돌/에러는 그대로 기록하고 그 레포는 갱신 건너뜀
AFTER=$(git rev-parse HEAD)
```

- `BEFORE == AFTER` → **변경 없음**, 그 레포는 스킵(요약에 "변경 없음"만).
- pull이 **충돌/실패**하면 문서를 건드리지 말고 요약에 오류로 보고(사용자가 직접 해결).
- `pull=off`면 `BEFORE`는 `git rev-parse ORIG_HEAD`(있으면) 또는 최근 커밋 기준으로 잡고, 없으면 그 레포는 "범위 불명"으로 보고.

> `execute_all git pull`을 한 번에 돌리지 않고 **레포별로 pull 전 HEAD를 기록**하는 이유: 정확한 `BEFORE..AFTER` 범위를 알아야 "이번 pull로 실제 들어온 변경"만 문서화할 수 있다.

### 3. 변경 내용 수집 (사실 근거)
변경이 있는 레포마다:

```bash
git log --no-merges --format='%h %s' "$BEFORE..$AFTER"     # 커밋 제목(이슈키 포함)
git diff --stat "$BEFORE..$AFTER"                           # 변경 파일 규모
```

- 커밋 제목에서 **이슈키**(예 `FE1-1234`, `QA-22345`, `CLIENT-101`)를 추출한다.
- 문서에 쓸 "무엇이 바뀌었나"가 제목만으로 불명확하면 **해당 파일의 실제 diff를 더 읽어** 사실을 확인한다(`git diff "$BEFORE..$AFTER" -- <경로>`). 추측 금지.
- (선택·있으면) 이슈키로 Jira 제목을 조회해 요약을 보강한다. Jira 접근이 없으면 커밋 제목만 쓴다.
- 변경 커밋이 많으면(예 30개 초과) 레포별로 서브 에이전트에 "이 범위 diff를 읽고 문서 갱신용 변경 테마 목록(테마·이슈키·대표 파일경로)을 뽑아라"라고 위임해도 된다.

### 4. 레포 → 문서 매핑
`reference/config.md`의 "레포 → 문서 매핑 규칙"을 따른다: `DOCS_SYNC_MAP` → `$DOCS_ROOT/{repo}.md` → `$DOCS_ROOT/{repo}/`(폴더면 대표 문서) 순. 없으면 **"문서 없음(신규 후보)"** 로 분류하고 새 문서를 만들지 않는다(요약에만).

- 폴더형 문서(예 `wadiz-frontend/`)는 변경 파일 경로를 보고 **가장 관련 있는 하위 문서**를 고른다. 대표/인덱스 문서에 변경 로그가 모여 있으면 거기에 쓴다. 애매하면 인덱스 문서에 기록한다.

> ⚠️ **대표 문서 하나로 끝내지 않는다.** 한 저장소의 파일을 인용하는 문서는 여럿이다.
> 실측하면 `wadiz-frontend` 를 인용하는 문서는 20개인데 대표 문서는 1개뿐이다.
> 나머지 19개는 지금까지 한 번도 갱신되지 않았고, `_flows/` 문서들이 152일째 멈춘 이유가 이것이다.
>
> 그래서 이 단계에서 정하는 것은 **변경 로그 블록을 쓸 대표 문서 하나**뿐이다.
> **어느 문서를 고칠지는 5단계의 영향 목록이 정한다.** 대표 문서 밖에도 작업이 나온다.

### 5. 무엇을 고칠지 뽑기 (도구 둘)

경로는 `${CLAUDE_PLUGIN_ROOT}/scripts/`. 그 변수를 못 쓰면 이 스킬 파일 기준 `../../scripts/`.

#### 5-1. 영향 목록 — 이번 diff 가 어느 문서를 건드리는가 (저장소마다)

변경이 있었던 저장소마다 한 번씩 돌린다. **이게 6단계의 작업 지시서다.**

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/impact.py" {repo} "$BEFORE" "$AFTER"
```

파일 이름으로 문서의 인용을 역추적한다. 대표 문서가 아닌 문서도 함께 나온다.
결과가 두 층으로 갈린다.

| 층 | 무엇이 들어오나 | 어떻게 하나 |
|---|---|---|
| **확정** | 삭제(`D`)·이름변경(`R`), 인용한 줄과 겹치는 수정(`M`), 열거 목록에 빠진 추가(`A`) | **반드시 고친다.** 근거가 diff 에 있다 |
| **확인** | 문서가 인용한 파일이 수정됨. 줄번호가 없어 겹침을 못 따짐 | 해당 부분을 읽고 아직 맞는지 본다 |

- **이름변경은 새 경로까지 알려 준다.** `git` 의 이름 추적을 쓰기 때문이다.
  경로만 바꾸면 되는 것을 "기능이 사라졌다"고 잘못 쓰지 않게 해 준다.
- 확인 층은 **바뀐 비율**(바뀐 줄 ÷ 파일 줄 수)로 줄을 세운다.
  줄 수로만 세우면 큰 설정값 파일이 작은 템플릿을 밀어낸다.
  실제로 `authz-policy.yaml`(86% 바뀜)이 그렇게 묻혔던 적이 있다.
- 문서마다 5건까지, 전체 60건까지 낸다. `--per-doc`·`--max-review` 로 조절한다.
- 확정이 0건이고 확인만 있으면, 그 저장소는 **변경 로그만 쓰고 본문은 안 고쳐도 된다.**
  다만 8단계 보고에 "확정 0건"이라고 적는다.

#### 5-2. 낡음 검사 — 이번 diff 와 무관하게 벌어진 문서 (전체 1회)

모든 저장소의 pull 이 끝난 뒤 한 번만 돌린다. 5초쯤 걸린다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check-stale.py" --top 25
```

이쪽은 이번 diff 를 보지 않는다. **문서의 현재 상태가 코드와 얼마나 벌어졌는지** 점수만 낸다.
오래 방치된 문서를 찾는 용도다. 세 가지를 본다.

| 신호 | 무엇을 보는가 | 왜 |
|---|---|---|
| 소실 인용 | 문서가 `경로.확장자` 로 인용한 파일이 지금 저장소에 있는가 | 없으면 그 서술은 성립할 수 없다. 확정 증거다 |
| 본문 방치 | 인용블록(`>`)이 아닌 줄이 마지막으로 바뀐 날 | 변경 로그만 쌓이고 본문이 멈춘 문서를 잡는다 |
| 낡은 표현 | `$DOCS_ROOT/_tools/obsolete-terms.tsv` 의 표현이 남아 있는가 | 파일이 안 지워지는 변화(도메인 이전 등)를 잡는다 |

결과 활용:

- 이번 pull 로 **변경이 있었던 레포**의 문서가 목록에 있으면, 6단계에서 **그 문서의 본문을 먼저 확인**한다.
- 변경이 없던 레포의 문서는 이번 회차에 고치지 않는다. 8단계 보고에만 "본문 점검 권장"으로 올린다.
- 사전에 새 항목을 넣어야 할 낡은 표현을 발견하면 `obsolete-terms.tsv` 에 한 줄 추가한다. 근거를 같이 적는다.
- 검사기가 **[경고]** 를 출력하면 그 신호는 무효다. 점수를 믿지 말고 경고 내용을 보고에 그대로 옮긴다.

#### 두 도구의 역할 구분

| 도구 | 보는 것 | 언제 |
|---|---|---|
| `impact.py` | **이번에 들어온 변경**이 문서 어디를 건드리는가 | 저장소마다 |
| `check-stale.py` | **지금까지 쌓인 어긋남**이 어느 문서에 큰가 | 전체 1회 |

`impact.py` 가 이번 회차의 필수 작업을 정한다.
`check-stale.py` 는 이번 회차에 안 해도 되는, 밀린 숙제를 보여 준다.

### 6. 문서 갱신 (자동 반영)
대상 문서를 **읽고 그 문서의 기존 형식을 파악한 뒤** 그 형식대로 갱신한다:

- **갱신일/버전 표기**가 있으면 오늘 날짜로 갱신한다(오늘 날짜는 대화 컨텍스트의 현재 날짜를 쓴다. 셸에서 날짜를 새로 만들지 않는다).
- **변경 로그 섹션**(예 "최근 변경사항" 표, 상단 "pull 보강" 블록)이 있으면 그 형식에 맞춰 이번 변경 테마를 **이슈키·대표 파일경로와 함께** 추가한다.
- 그런 섹션이 없으면 문서 맨 위(개요 다음)에 간결한 "최근 변경사항 (YYYY-MM-DD pull 기준)" 블록을 새로 만들되, **그 문서의 톤과 서식**(한국어/존댓말, 표/불릿 스타일)을 맞춘다.
- 본문의 서술이 이번 변경으로 **사실과 달라졌으면**(예: 삭제된 기능·바뀐 경로) 해당 서술만 정정한다. 관련 없는 부분은 건드리지 않는다.
- 커밋이 순수 리팩터/포맷/빌드설정처럼 **문서에 반영할 사용자 의미가 없으면** 문서를 바꾸지 않고 요약에만 "문서 반영 불필요"로 남긴다.

**작업 순서.** 변경 로그 블록을 쓰기 전에 5-1 의 영향 목록부터 처리한다.

1. **확정 층을 위에서부터 전부 처리한다.** 항목마다 문서와 줄번호가 찍혀 있다.

   | 표시 | 하는 일 |
   |---|---|
   | `[삭제됨]` | 그 서술을 지운다. 대체 기능이 diff 안에 있으면 그것으로 바꾼다 |
   | `[이름바뀜]` | **경로만** 새 것으로 고친다. 서술은 그대로 둔다 |
   | `[내용바뀜]` | 인용한 줄이 바뀌었다. 그 줄의 지금 내용을 읽고 서술을 맞춘다 |
   | `[추가됨]` | 그 폴더를 열거한 목록이므로 새 항목을 넣는다 |

2. **확인 층을 읽는다.** 파일을 열어 인용한 부분이 아직 맞는지 본다.
   맞으면 아무것도 하지 않는다. 틀리면 고치고, 애매하면 "확인 필요"로 남긴다.

3. **문서 첫머리의 한 줄 요약과 개요**를 이번 diff 에 비추어 다시 읽는다.
   여기가 틀리면 아래 내용 전부가 틀린 전제 위에 선다. 영향 목록에 안 나와도 본다.
   `_flows/store-detail.md` 가 넉 달 동안 틀린 채 있었던 이유가 이것이다.

4. 그러고 나서 변경 로그 블록을 쓴다.

5. 고칠 근거가 diff 에 없으면 고치지 않는다. 대신 문서에 "확인 필요"로 남긴다.

> **대표 문서가 아닌 문서도 고친다.** 영향 목록은 저장소 이름과 무관하게
> 인용을 따라간다. `helm-charts` 를 받았는데 `nicepay-api.md` 가 나올 수 있다.
> 그게 정상이다. 그 문서도 이번 회차에 고친다.

> ⚠️ **변경 로그만 쌓는 것은 실패다.** 이 스킬이 실제로 그렇게 퇴화한 적이 있다.
> 2026-08-21 부터 7회 연속으로 본문 수정이 전체의 1~7% 에 그쳤고, 본문 삭제는 0~5줄이었다.
> 그 사이 어떤 문서는 변경 로그가 46줄에서 511줄로 늘고 본문은 501줄에서 529줄로만 늘었다.
> 8단계 보고의 **본문 정정 칸이 전부 0 이면 그 회차는 의심해야 한다.**

> 문서 저장소(`$DOCS_ROOT`) 반영(브랜치·커밋·푸시·main PR)은 아래 **7단계에서 자동 수행**한다. 원본 레포(source)는 pull 외에 절대 수정하지 않는다.

### 7. 문서 저장소 반영 (브랜치 → 커밋 → 푸시 → main PR)
문서 갱신이 끝나면 `$DOCS_ROOT`(git 저장소)에 자동 반영한다. **문서 수정이 0건이면 이 단계 전체를 건너뛰고** 요약에만 "반영 없음"으로 남긴다.

1. **브랜치**: `feature/{오늘날짜}`(예 `feature/2026-07-22` — 날짜는 **대화의 현재 날짜**, 셸 `date`로 새로 만들지 않는다). 현재 브랜치가 이미 그것이면 그대로 두고, 그 이름의 브랜치가 있으면 체크아웃, 없으면 현재 상태(문서 수정 포함)에서 `git -C "$DOCS_ROOT" checkout -b feature/{오늘날짜}`.
2. **커밋**: 이번에 고친 문서만 스테이지해 `git -C "$DOCS_ROOT" commit --no-verify -m "docs: {오늘날짜} 문서 동기화 — {레포 요약}"`. (커밋 메시지에 이슈키를 함께 넣어도 좋다.)
3. **푸시**: `git -C "$DOCS_ROOT" push -u origin feature/{오늘날짜}`.
4. **main PR 생성**: `gh pr create --base main --head feature/{오늘날짜} --title "docs: {오늘날짜} 문서 동기화" --body "{레포·이슈키 요약}"`. **같은 브랜치의 열린 PR이 이미 있으면**(`gh pr view feature/{오늘날짜}` 확인) 새로 만들지 않고 그 PR에 커밋이 얹히게 둔다. gh가 없거나 실패하면 커밋·푸시는 유지하고 PR은 수동 생성하도록 링크만 안내한다.

⛔ **main으로의 머지는 하지 않는다**(PR 생성까지만 — 머지는 사용자). 브랜치·커밋은 `$DOCS_ROOT`에만 만들고 원본 레포엔 만들지 않는다.

### 8. 요약 보고
마지막에 레포별 결과를 표로 보고한다:

| 레포 | 변경 커밋 | 이슈키 | 문서 | 로그 추가 | 본문 정정 | 처리 |
|---|---|---|---|---|---|---|
| wadiz-frontend | 12 | FE1-1234 외 | wadiz-frontend/… | O | 2곳 | 갱신함 |
| app-api | 3 | QA-22345 | app-api.md | O | 없음 | 갱신함 |
| helm-charts | 5 | — | (문서 없음) | — | — | 신규 후보 |
| nicepay-api | 0 | — | nicepay-api.md | — | — | 변경 없음 |
| co.wadiz.fep | 2 | — | co.wadiz.fep.md | — | — | 문서 반영 불필요(리팩터) |

**본문 정정 칸은 비워 두지 않는다.** 고친 게 없으면 "없음"이라고 쓴다.
한 회차에서 모든 레포가 "없음"이면, 그 사실을 보고 맨 앞에 적고 왜 그런지 한 줄 덧붙인다.

영향 목록 처리 결과를 따로 한 줄 적는다.

```
영향 목록: 확정 31건 중 31건 처리, 확인 48건 중 12건 반영 · 관련 문서 19개
```

**확정 건수와 처리 건수가 다르면 그 차이를 설명한다.** 못 한 것이 있으면 무엇인지 적는다.

- 문서를 실제로 고친 파일 목록과, pull 충돌/실패 레포, "문서 없음(신규 후보)" 레포를 각각 명확히 나열한다.
- **본문 점검 권장 목록**을 따로 낸다. 5단계 검사기 상위 항목 중 이번에 손대지 못한 문서다.
  문서 경로·점수·소실 인용 수·본문 방치일을 함께 적는다. 고칠지는 사용자가 정한다.
- 7단계 반영 결과를 명시한다: **브랜치명 `feature/{오늘날짜}`·커밋 해시·푸시 여부·생성된(또는 기존) main PR 링크**. 문서 수정 0건이면 "반영 없음".

## 주의
- pull은 `--ff-only`를 먼저 시도한다. 로컬 커밋·충돌이 있는 레포는 **자동 병합하지 않고** 오류로 보고한다(사용자 데이터 보호).
- 문서 저장소가 아닌 원본 레포의 소스는 **절대 수정하지 않는다**. 이 스킬은 pull(읽기 갱신)과 문서(docs) 수정만 한다.
- 오늘 날짜는 대화의 현재 날짜를 사용한다(스킬 실행 환경에 따라 셸 날짜 생성이 제한될 수 있다).
