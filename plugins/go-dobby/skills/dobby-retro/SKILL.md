# dobby-retro

한 오더(dobby-order 1건)를 **회고**해, 작업 중 생긴 **버그·디자인 불일치·반복 재작업의 원인을 에이전트별로 정리**하고 **개선 방향(스킬/개발 방법/사용자 인풋)** 을 제안하는 비파괴 스킬. `$ORCHESTRATION_META/{키}/retro.md` **한 파일만** 만든다(다른 것은 건드리지 않음).

> 핵심 원칙: **실제 산출물에 남은 사실만** 근거로 쓴다(리뷰 findings·이벤트 로그·라운드 수 등). 추측·일반론은 쓰지 않는다. 근거가 없으면 "근거 부족"으로 명시한다.

## 설정 (첫 실행 시 확인)
작업을 시작하기 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md`의 "설정 절차"를 그대로 따른다**: `~/.config/go-dobby/config.env`를 source 해 환경 변수를 불러온다. 이하 메타 경로는 `$ORCHESTRATION_META` 기준.

## 사용법
`/dobby-retro {키} [regen]` — {키}는 이슈 키 또는 `TASK-{slug}`. 대상 폴더는 `$ORCHESTRATION_META/{키}/`.
- **인자 없음(기본)**: `retro.md`가 없으면 생성, 있으면 그대로 둔다(재작성 안 함).
- **`regen`**: 최신 산출물을 다시 읽어 **처음부터 덮어쓰기**(라운드가 더 쌓인 뒤 재회고 등).

## 입력(근거) — 있는 것만 읽는다 (⛔ 사실 기반, 지어내기 금지)
1. `reviews/round-*/*.md` — **라운드별 리뷰 findings**(심각도 blocker/major/minor·`파일:라인`·수정 제안). **가장 중요** — 무슨 버그/불일치가 몇 라운드에 걸쳐 고쳐졌는지의 1차 근거.
2. `orchestration.md` `## 이벤트 로그` — 재작업·**디자인 리뷰 불일치**·반복 수정의 타임라인(에이전트·라운드·사유).
3. `orchestration.md` `## 에이전트 상태표` + `agents/{슬러그}.md` 계약 — 에이전트별 오너십·최종 라운드 수.
4. `analysis.md`·`implementation.md`(또는 `implementation-*.md`)·`produce.md` — 무엇을 어떻게 만들었나(원인 파악).
5. `side-effects.md`·`decisions.md` — 부작용·미결정·추정으로 남긴 값.
6. (있으면) `jira-issue.md`·`jira-comments.md` — QA에서 잡힌 버그.

> 근거가 부족하면 코드/문서를 더 읽어 사실을 확인한다. 그래도 불명확하면 단정하지 말고 "미확인"으로 둔다. **이 오더가 dobby-order 없이 진행돼 리뷰/이벤트가 거의 없으면**, 억지 분석 대신 `## 회고 근거 부족`으로 그 사실만 적는다.

## 분석 방법

### A. 문제 수집 (사실)
리뷰 findings·이벤트 로그에서 실제로 발생한 것을 모은다:
- **버그**: 리뷰 blocker/major, 회귀, null/경계값, 비동기/에러 처리 누락 등.
- **디자인 불일치**: 디자인 리뷰의 색상/spacing/shadow/blur/레이아웃 불일치.
- **반복/낭비**: 같은 항목이 여러 라운드에 걸쳐 재수정, blocker=0까지 걸린 라운드 수.

### B. 원인 분류 (태그)
각 문제에 원인 태그를 붙인다(복수 가능):
- `분석부족` — 활성 경로 오판·기획/요구 오해.
- `스펙모호` — 디자인 정확값(hex·spacing 등) 미제공 → **추정**으로 구현 후 재작업.
- `규칙미준수` — 기존 규칙 위반(트래킹 누락·SCSS flat·범위 이탈 등).
- `docs미참조` — 참고 문서를 안 봐서 배경/계약을 놓침.
- `인풋부족` — 오더 시작 시 사용자가 줬으면 예방됐을 정보 부재(피그마 정확값·앵콜 데이터 유무·엣지케이스).
- `리뷰지연` — 늦게 발견돼 재작업 폭이 커짐.

### C. 에이전트별 귀속
각 문제를 **담당 에이전트(오너십)** 에 귀속한다. 상태표 슬러그·계약 화이트리스트·리뷰 대상으로 판단한다. 오케스트레이터 인라인 구현(에이전트 로그가 세션 ID를 가리키는 슬러그)도 하나의 에이전트로 본다.

### D. 개선 제안 (3방향)
원인을 줄일 방향을 제안한다:
- 🛠 **스킬 수정** — go-dobby 스킬/레퍼런스에 넣을 규칙.
- 🔁 **개발 방법** — 워크플로 개선(리뷰 시점 앞당김·프로토타입·병렬 등).
- 🙋 **사용자 인풋** — 오더 시작 시 제공하면 좋았을 것.

## 산출: `$ORCHESTRATION_META/{키}/retro.md`

아래 구조로 **한국어**로 쓴다.


### 톤·품질
- **사실 기반**: 산출물에 있는 것만. 없으면 단정하지 않는다.
- 🛠 스킬 제안은 **대상 파일·섹션·넣을 문장·근거**를 반드시 갖춰, 다른 세션이 바로 적용할 수 있게 한다. 막연한 "잘하자"류 금지 — **구체적 규칙 문장**으로.
- 제안은 **이번 오더의 실제 원인에서 도출**한다(일반 베스트프랙티스 나열 금지).

## 갱신 방식
- `retro.md`가 없으면 생성. 이미 있으면 기본은 그대로 두고, `regen` 인자를 받으면 최신 산출물로 **덮어쓰기**.

## 비파괴
- `retro.md`만 생성/갱신한다. 워크트리·다른 메타·Jira·코드·스킬은 **건드리지 않는다**(스킬 반영은 사용자가 별도 세션에서 실행).

## 자동 실행
- 사용자가 대시보드 "회고" 탭의 생성 버튼으로 실행한다(`/dobby-retro {키}`). dobby-order가 자동 호출하지는 않는다(완료 후 회고는 사용자 판단).
