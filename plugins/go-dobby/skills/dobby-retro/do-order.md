# /do 오더 회고

회고는 두 가지를 이 순서로 본다.

1. **잘못한 판단(먼저, 자세히)** — 이슈를 분석하고 진행하면서 잘못 판단한 곳을 찾는다. 판단마다 왜 그랬는지, 다시 안 그러려면 어떻게 할지, 스킬·서버·사람 중 어디를 고쳐야 하는지 적는다.
2. **토큰 사용(그다음)** — 단계마다 세션을 새로 연 선택과 이어 쓴 선택이 토큰·시간에서 이득이었는지 재고, 이어 쓰기 기준을 바꿀지 본다.

결과는 `$ORCHESTRATION_META/{키}/retro.json` 하나다. 숫자는 헬퍼가 쓰고, 세션은 판단만 쓴다. 숫자를 옮겨 적지 않는다(토큰이 들고 틀린다).

## 순서

1. `dobby_retro_office {키} start` — 사무실에서 담당자들이 회고 탁자에 앉는다.
2. `dobby_retro_measure {키}` — 세션 기록을 재서 `retro.json` 을 새로 쓴다(`basis`·`measure`). **출력된 요약만 읽는다.** 토큰 분석은 4단계에서 한다.
3. `dobby_retro_digest {키}` 로 잘못한 판단을 찾는다(아래 "1. 잘못한 판단"). 근거가 더 필요하면 요약이 가리키는 파일의 그 부분만 읽는다. **이 단계에 가장 공을 들인다.**
4. 토큰 사용을 판단한다(아래 "2. 토큰 사용"). 전환 하나를 더 봐야 하면 `jq '.measure.segments[] | select(.when == "…")' retro.json` 처럼 그 줄만 꺼낸다.
5. 판단 내용을 임시 파일(`$TMPDIR` 아래)에 JSON 으로 쓰고 `dobby_retro_put {키} {파일}` 로 합친다.
6. `dobby_retro_lint {키}` 가 통과할 때까지 고쳐 다시 합친다.
7. `dobby_retro_office {키} end` — 기획자가 회고록을 회고 책장에 꽂는다. 2~6 중 하나라도 끝내 실패하면 `dobby_retro_office {키} end 실패` 를 보내고, 실패 이유를 출력하고 끝낸다.

## 1. 잘못한 판단

### 무엇을 찾나

| 찾는 것 | 예 |
|---|---|
| 이슈를 분석할 때 잘못 짚은 것 | 이슈에 없는 값을 사람에게 묻지 않고 관례로 정함, 쓰이지 않는 코드 경로를 고침 |
| 설계에서 빠뜨린 것 | 영향 받는 화면을 빠뜨림, 시험 기대값을 잘못 정해 검증이 실패로 나옴 |
| 구현 결함 | 「새 버그」 변경, 검증 실패 중 코드 결함, 리뷰의 `[blocker]`·`[major]` |
| 진행하면서 잘못 고른 것 | 처음 설계 범위 안을 바로잡은 「수정 지시」, 검증 실패 원인을 잘못 짚어 다시 고침, 멈춰 물었어야 할 곳에서 그냥 감 |

빼는 것: 「추가 설계」, 처음 범위 밖을 더한 「수정 지시」(요구 변경), 「이어받기」, 환경 문제(접속·설치·데이터 준비).

### 판단마다 적는 것

| 칸 | 내용 |
|---|---|
| `title` | 한 줄 제목. 무엇이 틀렸는지 바로 보이게 |
| `what` | 무엇을 잘못 판단했나. 한두 문장 |
| `why` | 왜 그렇게 판단했나. 근거에서 확인한 사실만 |
| `prevent` | 다시 안 그러려면 어떻게 하나. 누가 언제 무엇을 하는지로 |
| `foundAt` | 실제로 잡힌 단계 |
| `couldAt` | 잡을 수 있었던 가장 이른 단계. 근거가 없으면 `"미확인"` |
| `causes` | 원인 표시. `분석부족`·`스펙모호`·`규칙미준수`·`docs미참조`·`리뷰지연`·`시험계획오류` 중에서 고른다 |
| `fixes` | 고칠 곳 목록. 항목마다 `where`(`스킬`·`서버`·`사람` 중 하나), `target`(파일 경로, 사람이면 빈 값), `change`(무엇을 바꾸는지 한 문장) |
| `evidence` | 근거 파일 |

`foundAt`·`couldAt` 은 다음 단계 이름 중 하나로 쓴다. 대시보드가 이 이름으로 단계 띠 그림을 그린다.

`설계` → `구현` → `리뷰` → `통합` → `배포` → `검증` → `사람 확인`

(`사람 확인` 은 사람이 변경을 요청하거나 QA 에서 잡은 경우다.)

- `서버` 는 대시보드(mentis-dashboard-v2)·사무실(agent-office)·헬퍼(`reference/dobby-lib.sh`)·훅처럼 코드로 고치는 곳이다. `스킬` 은 스킬 문서(`SKILL.md`·`steps/*.md`)다.
- 고칠 곳은 실제로 그 파일을 열어 해당 절이 있는지 확인하고 쓴다. 넣을 문장이 길면 `proposals` 에 그대로 쓰고, `fixes` 에는 한 문장만 둔다.
- 잘못한 판단이 없으면 `defects` 를 빈 배열로 두고, `summary` 에 "잘못한 판단은 찾지 못했습니다"와 무엇을 살폈는지 쓴다.

## 2. 토큰 사용

헬퍼가 세션이 바뀐 지점마다 실제 선택(새로 / 이어 씀)과 반대 선택의 추정 비용·시간을 계산해 판정을 붙인다.

| 판정 | 뜻 |
|---|---|
| 맞음 | 고른 쪽이 쌌거나, 차이가 작고 시간도 손해가 없었다 |
| 속도 손해 | 비용 차이가 `fastPct`(10%) 미만인데 반대쪽이 더 빨랐다 |
| 틀림 | 반대쪽이 `fastPct` 이상 쌌다 |
| 리뷰는 새로(독립) | 리뷰는 앞 세션의 생각을 이어받지 않아야 해서 비교하지 않는다 |
| 앞 세션 진행 중 | 바로 앞 세션이 아직 일하는 중에 새 세션이 시작됐다. 이어 쓸 수 없었으므로 비교하지 않는다 |
| 측정 불가 | 세션 기록이 없거나 호출이 없다 |

이어 쓴 전환은 같은 세션의 직전 구간과, 새로 연 전환은 바로 앞 줄의 세션과 비교한다.

세션이 할 일:
- `틀림`·`속도 손해` 전환마다 **왜 그렇게 됐는지** 적는다. 쓸 수 있는 근거는 전환 줄의 값뿐이다 — 간격(`gap`)과 캐시 유지 시간(`ttl`), 직전 끝 문맥, 시작 문맥, 첫 호출 비용.
- 같은 이유가 되풀이되면 묶어서 하나의 발견으로 쓴다.
- 이어 쓰기 기준값(`reference/dobby-lib.sh` 의 `DOBBY_REUSE_MAX_CTX`·`DOBBY_REUSE_MAX_GAP`)이나 단계별 예외를 바꿀지 제안한다. 근거 문서 `skills/do/session-reuse.md` 의 가정이 이 오더의 실측과 다르면 그것도 제안한다. 기존 기준이 맞았으면 "바꾸지 않음"도 제안이다.
- 추정의 한계를 숨기지 않는다. 전환을 하나씩 따로 계산했으므로 앞 선택이 바뀌면 뒤 문맥도 바뀐다는 점은 계산에 없다.

## 쉬운 글로 쓰기 (검사가 막는다)

사람이 읽는 글이다. 대시보드와 사무실 책에 그대로 나온다.

- 한 문장은 60자 안팎으로 끊는다. 100자를 넘는 문장은 `dobby_retro_lint` 가 거부한다.
- 한 문장에 원인과 결과를 같이 넣지 않는다. `→` 로 흐름을 압축하지 않는다.
- 어려운 말은 풀어 쓴다.
  - 문맥 → "세션이 지금까지 쌓은 대화 양"
  - 캐시 → "앞서 읽은 내용을 싸게 다시 읽게 해 두는 저장"
  - 환산 토큰 → "비용(토큰 기준)"
- 숫자는 "만" 단위로 쓰고, 한 문장에 숫자를 셋 넘게 넣지 않는다.
- 단계 코드·에이전트 슬러그·`round-N` 같은 내부 용어는 풀어 쓴다("3차 리뷰").
- `summary` 는 세 문장 이하다. 첫 문장은 잘못한 판단, 둘째 문장은 고칠 곳, 셋째 문장은 토큰 사용 결과다.

## 판단 부분의 형식 (`dobby_retro_put` 에 넘기는 JSON)

```json
{
  "summary": "수집 태그 분류를 묻지 않고 정한 판단이 1건 있었습니다. 설계 요약에서 관례로 정한 값을 따로 묻도록 스킬을 고칩니다. 토큰은 모두 새 세션으로 열었을 때보다 7% 더 썼습니다.",
  "defects": [
    { "title": "수집 태그 분류를 묻지 않고 정했습니다", "change": 3, "foundAt": "사람 확인", "couldAt": "설계",
      "what": "이슈에 분류 규칙이 없는데 기존 관례대로 나눴습니다.",
      "why": "설계 요약에 관례로 정한 값을 따로 보여 주는 칸이 없었습니다.",
      "prevent": "설계 요약 때 이슈에 없는 값은 표로 모아 사람에게 묻습니다.",
      "causes": ["스펙모호"],

      "evidence": ["jira-issue.md", "design.md"] }
  ],
  "proposals": [
    { "type": "스킬|서버|진행 방법|사용자 입력", "title": "…", "target": "plugins/go-dobby/skills/do/steps/review.md",
      "section": "…", "text": "넣을 문장 그대로", "evidence": ["reviews/round-3/review-agent.md"] }
  ],
  "sessionFindings": [
    { "title": "…", "segments": ["2026-11-05 07:18"], "why": "…", "impact": 2900000, "evidence": ["retro.json"] }
  ],
  "ruleProposals": [
    { "title": "…", "target": "plugins/go-dobby/reference/dobby-lib.sh", "value": "DOBBY_REUSE_MAX_CTX=120000 → 80000",
      "why": "…", "evidence": ["retro.json"] }
  ],
  "evidence": ["retro.json", "design.md"]
}
```

- 근거 경로는 오더 폴더 기준 상대 경로로 쓴다. `dobby_retro_lint` 가 실제로 있는지 확인한다.
- `basis`·`measure` 는 넘기지 않는다(헬퍼가 거부한다).

## 하지 않는 것

- 진행 중인 오더를 회고하지 않는다(시작 전 검사가 막는다).
- `retro.json` 밖의 파일을 고치지 않는다. 고칠 곳은 제안으로만 남기고, 반영은 사람이 따로 시킨다.
- 세션 기록 파일을 통째로 읽지 않는다. 숫자는 측정 헬퍼가 이미 냈다.
