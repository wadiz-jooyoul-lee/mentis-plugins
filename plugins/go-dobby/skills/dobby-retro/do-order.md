# /do 오더 회고

`/do` 오더는 단계마다 세션을 새로 연다. 세션을 새로 열면 쌓인 문맥을 다시 읽지 않아 싸지만, 새로 여는 첫 호출 비용과 시작 시간이 든다. 이 회고는 그 선택이 실제로 이득이었는지 재서, 다음 오더의 세션 전환 기준을 다듬는 것이 **주 목적**이다. 요구를 구현하다 잘못 판단한 곳을 찾는 것은 **보조**다.

결과는 `$ORCHESTRATION_META/{키}/retro.json` 하나다. 숫자는 헬퍼가 쓰고, 세션은 판단만 쓴다. 숫자를 옮겨 적지 않는다(토큰이 들고 틀린다).

## 순서

1. `dobby_retro_office {키} start` — 사무실에서 담당자들이 회고 탁자에 앉는다.
2. `dobby_retro_measure {키}` — 세션 기록을 재서 `retro.json` 을 새로 쓴다(`basis`·`measure`). **출력된 요약만 읽는다.** 전환 하나를 더 봐야 하면 `jq '.measure.segments[] | select(.when == "…")' retro.json` 처럼 그 줄만 꺼낸다.
3. 세션 전환 손익을 판단한다(아래 "주: 세션 전환 손익").
4. `dobby_retro_digest {키}` 로 판단 실수를 정리한다(아래 "보조: 판단 실수"). 근거가 더 필요하면 요약이 가리키는 파일의 그 부분만 읽는다.
5. 판단 내용을 임시 파일(`$TMPDIR` 아래)에 JSON 으로 쓰고 `dobby_retro_put {키} {파일}` 로 합친다.
6. `dobby_retro_lint {키}` 가 통과할 때까지 고쳐 다시 합친다.
7. `dobby_retro_office {키} end` — 기획자가 회고록을 회고 책장에 꽂는다. 2~6 중 하나라도 끝내 실패하면 `dobby_retro_office {키} end 실패` 를 보내고, 실패 이유를 출력하고 끝낸다.

## 주: 세션 전환 손익

헬퍼가 세션이 바뀐 지점마다 실제 선택(새로 / 이어 씀)과 반대 선택의 추정 비용·시간을 계산해 판정을 붙인다.

| 판정 | 뜻 |
|---|---|
| 맞음 | 고른 쪽이 쌌거나, 차이가 작고 시간도 손해가 없었다 |
| 속도 손해 | 비용 차이가 `fastPct`(10%) 미만인데 반대쪽이 더 빨랐다 |
| 틀림 | 반대쪽이 `fastPct` 이상 쌌다 |
| 리뷰는 새로(독립) | 리뷰는 앞 세션의 생각을 이어받지 않아야 해서 비교하지 않는다 |
| 앞 세션 진행 중 | 바로 앞 세션이 아직 일하는 중에 새 세션이 시작됐다. 이어 쓸 수 없었으므로 비교하지 않는다 |
| 측정 불가 | 세션 기록이 없거나 호출이 없다 |

이어 쓴 전환은 같은 세션의 직전 구간과, 새로 연 전환은 바로 앞 줄의 세션과 비교한다.

세션이 할 일:
- `틀림`·`속도 손해` 전환마다 **왜 그렇게 됐는지** 적는다. 쓸 수 있는 근거는 전환 줄의 값뿐이다 — 간격(`gap`)과 캐시 유지 시간(`ttl`), 직전 끝 문맥, 시작 문맥, 첫 호출 비용. 예: "직전 끝 문맥 25만을 이어 써서 호출마다 2만씩 더 읽었다", "간격이 캐시 유지 시간을 넘겨 문맥 전체를 다시 캐시에 썼다".
- 같은 이유가 되풀이되면 묶어서 하나의 발견으로 쓴다.
- 이어 쓰기 기준값(`reference/dobby-lib.sh` 의 `DOBBY_REUSE_MAX_CTX`·`DOBBY_REUSE_MAX_GAP`)이나 단계별 예외(예: 검증 묶음 사이, 변경 접수 뒤)를 바꿀지 제안한다. 근거 문서 `skills/do/session-reuse.md` 의 가정(새 세션 첫 호출 비용 등)이 이 오더의 실측과 다르면 그것도 제안한다. 기존 기준이 맞았으면 "바꾸지 않음"도 제안이다.
- 네 합계(`totals.actual`·`allNew`·`rule`·`best`)를 한 문장으로 비교해 `summary` 첫머리에 쓴다.
- 추정의 한계를 숨기지 않는다. 전환을 하나씩 따로 계산했으므로 앞 선택이 바뀌면 뒤 문맥도 바뀐다는 점, 호출마다 응답 속도가 문맥 크기에 따라 달라지는 점은 계산에 없다.

## 보조: 판단 실수

대상과 제외:

| 대상 | 제외 |
|---|---|
| 「새 버그」 변경, 검증 실패 중 코드 결함, 리뷰의 `[blocker]`·`[major]`, 처음 설계 범위 안을 바로잡은 「수정 지시」 | 「추가 설계」, 처음 범위 밖을 더한 「수정 지시」(요구 변경), 「이어받기」, 환경 문제(접속·설치·데이터 준비) |

결함마다 처음 잡힌 단계(`foundAt`), 잡을 수 있었던 가장 이른 단계(`couldAt`, 근거가 없으면 `"미확인"`), 잘못된 판단 한 문장, 원인 표시, 근거를 쓴다. 원인 표시는 `분석부족`·`스펙모호`·`규칙미준수`·`docs미참조`·`리뷰지연`·`시험계획오류` 중에서 고른다.

## 판단 부분의 형식 (`dobby_retro_put` 에 넘기는 JSON)

```json
{
  "summary": "한두 문장. 네 합계 비교 + 가장 큰 발견",
  "sessionFindings": [
    { "title": "…", "segments": ["2026-11-05 07:18"], "why": "…", "impact": 2900000, "evidence": ["retro.json"] }
  ],
  "ruleProposals": [
    { "title": "…", "target": "plugins/go-dobby/reference/dobby-lib.sh", "value": "DOBBY_REUSE_MAX_CTX=120000 → 80000",
      "why": "…", "evidence": ["retro.json"] }
  ],
  "defects": [
    { "title": "…", "change": 1, "foundAt": "검증", "couldAt": "리뷰", "judgment": "잘못된 판단 한 문장",
      "causes": ["리뷰지연"], "evidence": ["test-runs/20261104-154429/result.md", "reviews/round-1/review-agent.md"] }
  ],
  "proposals": [
    { "type": "스킬|진행 방법|사용자 입력", "title": "…", "target": "plugins/go-dobby/skills/do/steps/review.md",
      "section": "…", "text": "넣을 문장 그대로", "evidence": ["reviews/round-3/review-agent.md"] }
  ],
  "evidence": ["retro.json", "design.md"]
}
```

- 근거 경로는 오더 폴더 기준 상대 경로로 쓴다. `dobby_retro_lint` 가 실제로 있는지 확인한다.
- `basis`·`measure` 는 넘기지 않는다(헬퍼가 거부한다).
- 사람이 읽는 글이다. 한국어로 쉬운 말을 쓰고, 단계 코드·에이전트 슬러그·`round-N` 같은 내부 용어는 풀어 쓴다("3차 리뷰").

## 하지 않는 것

- 진행 중인 오더를 회고하지 않는다(시작 전 검사가 막는다).
- `retro.json` 밖의 파일을 고치지 않는다. 제안은 제안으로만 남기고, 스킬 반영은 사람이 따로 시킨다.
- 세션 기록 파일을 통째로 읽지 않는다. 숫자는 측정 헬퍼가 이미 냈다.
