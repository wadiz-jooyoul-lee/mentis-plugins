# dobby-qa

개발이 상위 브랜치로 통합(dobby-order P7)된 뒤 진입하는 **QA 감시 모드**. Jira를 주기적으로 폴링해 이 오케스트레이션에 속하는 버그 이슈를 잡아, **원래 그 기능을 구현한 에이전트가 고치고 담당 리뷰어가 리뷰**한 뒤, **모아서 배포하고 검증하고 Jira에 보고**하는 데까지 한 루프에서 간다. 라우팅·수정·리뷰 절차는 dobby-order **P8(후속 작업 재개)** 규칙을, 배포 절차는 **dobby-ship** 을 그대로 따른다.

```
dobby-order (개발·통합)  →  ★dobby-qa (감시·수정·배포·검증·보고)★  →  dobby-end
                                    ├ 폴링 세션(5분마다): 폴링 → 트리아지 → 슬랙 응답 확인 → 작업 결과 알림 → 작업 세션 기동
                                    └ 작업 세션(새 프로세스): 수정 → 리뷰 → 루트 머지 → 배포 → 검증 → Jira 코멘트 → 결과 파일
```

**세션을 둘로 나눈다.** 폴링 세션은 예약으로 같은 세션에서 계속 돌기 때문에, 수정·검증 기록까지 쌓이면 문맥이 금방 커진다. 그래서 폴링 세션은 가벼운 일(Q0~Q3, QW, Q9)만 하고, 편입된 버그는 `work.sh` 가 띄운 **새 작업 세션**(`claude -p "/dobby-qa {루트키} work"`)이 Q4~Q8 을 처리한 뒤 프로세스째 사라진다. 폴링 세션은 작업 세션의 결과 파일 몇 줄만 읽는다.

**브랜치는 대표 QA 브랜치 하나다.** 루트 브랜치에서 `bugfix/{루트키}-QA` 를 처음 한 번만 따고, 그 작업 폴더를 틱마다 다시 쓴다. 버그는 브랜치가 아니라 **커밋**으로 나눈다 — 커밋 하나가 버그 하나다. 버그마다 작업 폴더를 새로 만들면 에이전트가 규약 문서·코드 탐색을 버그 수만큼 반복해 토큰이 크게 든다.

```
cloud_live
 └─ feature/FE1-1800              ← 루트 브랜치(통합 지점)
      └─ bugfix/FE1-1800-QA       ← 대표 QA 브랜치. 처음 한 번만 따고 계속 쓴다
           ├─ fix: QA-1 ...       ← 버그마다 커밋 하나
           ├─ fix: QA-2 ...
           └─ 틱 끝에 루트로 한 번 머지 → 루트에서 {환경} PR 한 번 → 빌드 → 배포
```

> ⛔ **dobby-ship 을 부르지 않는다.** 배포 절차를 이 스킬 안에서 직접 밟되, 안전장치인 **`dobby_ship_*` 헬퍼는 반드시 경유**한다. 생 `gh pr create` 를 치면 `cloud_live` 로 새는 길이 열리고 리뷰어 자동 부착도 사라진다.

> **동작 전제(중요)**: 감지(Jira 폴링)·문의(Slack)는 원격 MCP만 있으면 되지만, **실제 수정(워크트리·git·dobby-impl)과 검증(chrome-devtools)은 로컬 PC/세션이 떠 있어야** 한다. 그래서 이 스킬은 **로컬 세션 루프(모드 A)**로 동작한다 — 폴링 세션을 닫으면 다음 작업 세션도 뜨지 않는다. 이미 뜬 작업 세션은 별도 프로세스라 끝까지 간다.

## 설정 (첫 실행 시 확인)

작업을 시작하기 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md`의 "설정 절차"를 그대로 따른다**: `~/.config/go-dobby/config.env`를 source 해 환경 변수를 **읽기만** 한다. ⛔ **이 스킬은 config.env를 저장·수정·생성하지 않는다**(값 변경은 `dobby-init` 전용 — config.md '비파괴 원칙'). config.env 파일이 아예 없으면 멈추고 `/dobby-init`을 먼저 실행하도록 안내한다. 메타 루트 `ORCHESTRATION_META`, 폴더 배치(워크트리 `$ORCHESTRATION_WORKSPACE/subtree/` · 메타 `$ORCHESTRATION_META/`), `$JIRA_BASE_URL`은 그 문서에 있다. 이하 메타 경로는 `$ORCHESTRATION_META` 기준. **공용 헬퍼(config.md '공용 헬퍼', 이미 source됨)**: 상태표 전이는 `dobby_agent_state 키 슬러그 상태 [라운드]`(상태·라운드·착수/갱신을 `## 에이전트 상태표`에 반영), 이벤트 로그 1줄은 `dobby_event 키 "사건 — 설명"`으로 남긴다(어느 값을 넣을지·문구는 LLM이 정하고, 표·로그 편집만 헬퍼가 한다). ⛔ 폴링(Q1)·다음 폴 예약(Q7)은 Jira MCP·`ScheduleWakeup` 몫이라 헬퍼가 아니다.

## 원칙 (필수 — 시작 전 숙지)

- 분석·수정 에이전트를 스폰할 때 프롬프트 상단에 **`${CLAUDE_PLUGIN_ROOT}/reference/analysis-discipline.md` 원칙 0·1·2·3·4**(이중경로면 1)을 넣고, 그 뒤에 **`${CLAUDE_PLUGIN_ROOT}/reference/role-personas.md`의 역할 블록**(수정=「구현 에이전트」, 리뷰=「리뷰 에이전트」)을 삽입한다.
- **사실 기반·추측 금지**: 버그가 이 오케스트레이션 소관인지, 어느 에이전트 담당인지는 **계약 화이트리스트·코드로 확인한 사실**로만 판단한다. 애매하면 자동 편입하지 말고 슬랙으로 문의한다(기준 ③).

## 사전 조건

- `$ORCHESTRATION_META/{루트키}/` 가 존재해야 한다(`orchestration.md` · `agents/{슬러그}.md` 계약 · `review-agent.md`). 없으면 "먼저 dobby-order로 개발·통합하라"고 알리고 중단한다.
- **루트 브랜치**가 살아 있어야 수정 가능하다. 워크트리가 정리됐어도 브랜치는 dobby-end가 보존하므로, 아래 Q4 3항에서 QA 작업 폴더를 그 브랜치 위에 만든다.

## 입력 / 중단

```
/dobby-qa {루트키} [env=rc4] [parent=QA부모키] [bugs=키,키] [interval=5m]
/dobby-qa stop {루트키}     # 감시 종료
/dobby-qa {루트키} work     # 작업 세션 — work.sh 가 띄운다. 사람이 치지 않는다
```

- **`work` 가 붙으면 작업 세션이다.** Q4~Q8 만 하고 끝낸다. 폴링(Q1~Q3)·알림(QW)·예약(Q9)은 하지 않고, `ScheduleWakeup` 도 부르지 않는다.

- `{루트키}`: QA를 붙일 오케스트레이션(방금 개발·통합한 이슈/에픽).
- `env=`: 고친 것을 다시 내보낼 환경(`dev`·`rc1`·`rc4`·`stage`). **QA 버그는 대개 배포된 환경에서 발견되므로 그 환경으로 되돌려 보내야 QA가 재확인할 수 있다.**
- `parent=`: 기준 ①의 부모 QA 이슈. 그 하위 버그를 후보로 본다.
- `bugs=`: 기준 ②로 "같은 컨텍스트에서 처리"할 버그 키를 사용자가 명시.
- `interval=`: 폴링 주기(기본 `5m`). 초로 환산해 다음 폴을 예약한다.

**`env=` 를 안 주면 짐작하지 않고 이 순서로 찾는다.**

| 순서 | 어디서 |
|---|---|
| 1 | `env=` 인자 |
| 2 | `status.md` 의 `## 배포` 표에서 **마지막으로 `검증 완료`** 가 된 환경 |
| 3 | 못 찾으면 — 결과 파일에 적고(폴링 세션이 슬랙으로 알린다) **그 작업 세션은 배포·검증을 건너뛴다**(수정·리뷰는 계속한다). 다음 작업 세션이 다시 찾는다 |

3번에서 감시를 멈추지는 않는다. 고쳐 둔 것은 루트 브랜치에 모여 있으므로, `env` 가 정해지면 다음 틱에 한 번에 나간다.

## 절차 (Phase — 매 폴링 틱마다 반복)

전이는 객관적 조건으로 자율 진행한다.

| 세션 | 순서 |
|---|---|
| 폴링 세션 | **Q1 폴링 → Q2 트리아지 → Q3 슬랙 응답 확인 → QW 작업 결과 알림·작업 세션 기동 → Q9 다음 폴 예약** |
| 작업 세션 | **Q4 수정 → Q5 리뷰 → Q6 루트 머지 → Q7 배포 → Q8 검증·보고 → QR 결과 파일** |

**사용자를 부르지 않는다.** 머지·빌드도 묻지 않는다(dobby-auto 와 같은 근거 — 되돌리기 쉬운 환경이고, 막는 것은 헬퍼와 훅이 이미 하고 있다). 사람을 부르는 곳은 맨 아래 "확인 게이트"뿐이다. 작업 세션은 사람이 없는 프로세스라 **아무것도 묻지 않는다** — 혼자 못 하는 버그는 그 버그만 보류해 결과 파일에 적고, 폴링 세션이 슬랙 본인 DM으로 알린다(작업 세션에는 슬랙 도구가 없다 — `work.sh` 가 크롬 도구만 붙인다).

### Q0. 진입 (최초 1회)
- `status.md`에 `## QA` 표(아래 "산출물")를 만든다.
- ⛔ **현재 단계는 건드리지 않는다.** 단계 정본은 `착수·분석·구현·리뷰·통합·검증·해결·종료` 여덟뿐이고(`DOBBY_PHASES`), 정본 밖 값(예전의 `QA감시중`)을 넣으면 두 곳이 깨진다 — **`dobby_ship_*` 이 배포를 거부**하고(허용: `통합 검증 해결 종료 완료`), **대시보드가 단계를 `unknown` 으로 읽어** 배지가 회색이 된다. QA 진행은 `## QA` 표와 `qa-watch.md` 로만 드러낸다(대시보드 QA 탭이 그 둘을 읽는다).
- `qa-watch.md`(폴링·트리아지 이력)를 없으면 생성한다. **이 파일이 있으면 대시보드에 QA 탭이 생긴다.**
- `env`를 위 "입력"의 순서로 확정해 `qa-watch.md` 머리에 적는다.
- `parent=`/`bugs=` 인자를 기록한다. 사용자가 "같은 컨텍스트에서 처리"를 구두로 지시한 버그가 있으면 그것도 `bugs=`에 준한다.

### Q1. 폴링 (Jira 조회)
- **JQL**(할당 *시각* 기준 최근 24h, 진행중 포함):
  ```
  assignee = currentUser()
  AND issuetype = Bug
  AND assignee CHANGED TO currentUser() AFTER "-1d"
  ORDER BY updated DESC
  ```
  `twg jira workitem query --jql "…" --fields summary,status,assignee,parent,issuetype --limit 20` 으로 조회한다(Jira 명령은 `${CLAUDE_PLUGIN_ROOT}/reference/jira-twg.md`). `assignee CHANGED TO`로 "**나에게 할당된 시각**" 기준을 쓴다(생성/수정 시각이 아니라). 진행중이어도 제외하지 않는다 — "할당 24h 이내 + 아직 한 번도 확인 안 한" 것을 잡기 위함이다.
- **중복 제거**: `qa-watch.md`에 이미 있는(=이전 틱에서 트리아지한) 이슈는 건너뛴다. 남은 것만 **신규 후보**로 Q2로 넘긴다.

### Q2. 트리아지 (이 오케스트레이션 소관인가)
신규 후보마다 아래 순서로 판정한다. **①②는 자동 편입**, **③은 슬랙 문의 후 편입**. 결과를 `qa-watch.md`에 남긴다.

- **① 부모/하위 관계 → 자동 편입**: 버그가 `parent=`로 받은 부모 QA의 하위 이슈이거나, **루트키의 버그 타입 하위 이슈**(`parent = {루트키} AND issuetype = Bug`)이면 편입.
- **② 사용자 명시 → 자동 편입**: `bugs=`에 포함되거나 사용자가 같은 컨텍스트 처리로 지정한 버그이면 편입.
- **③ 내용 기반 판단 → 슬랙 문의**: ①②에 안 걸리면 버그 내용(`twg jira workitem get {버그키} --fields summary,status,parent,labels` 와 `dobby_jira_desc {버그키}`)을 읽고, **이 오케스트레이션 에이전트의 계약 화이트리스트에 속한 파일/기능과 관련되는지**를 코드로 확인한다. 관련된다고 판단되면 **자동 진행하지 말고 슬랙으로 문의**한다(Q3). 관련 없으면 `qa-watch.md`에 `무관`으로 남기고 종료.

**③ 슬랙 문의** — 본인 DM(Slack User ID `U03SRUFP97W`)으로 `mcp__claude_ai_Slack__slack_send_message` 발송, 반환된 메시지 `ts`를 `qa-watch.md`에 저장한다.
```
🐞 QA 버그가 현재 개발 건과 관련돼 보입니다. 이 컨텍스트에서 처리할까요?
• 현재 이슈: {루트키} — {제목}  {$JIRA_BASE_URL/browse/{루트키}}
• 버그 이슈: {버그키} — {제목}  {$JIRA_BASE_URL/browse/{버그키}}
• 판단 근거: {관련 파일/기능 + 담당 에이전트 슬러그}
→ :넵: 이면 처리, :아니오: 이면 넘어갑니다.
```
상태를 `qa-watch.md`에 `문의대기`로 남긴다.

### Q3. 슬랙 응답 확인 (지난 틱의 `문의대기` 처리)
- `문의대기`인 각 건에 대해 저장한 `ts`로 `mcp__claude_ai_Slack__slack_get_reactions`를 호출해 이모지를 확인한다.
  - `:넵:` → **편입**(Q4로). `qa-watch.md` `편입(③)`.
  - `:아니오:` → `보류`로 남기고 **다시 문의하지 않는다**.
  - 반응 없음 → 그대로 `문의대기` 유지(다음 틱에 재확인). 재문의 메시지는 보내지 않는다.

### QW. 작업 결과 알림 → 작업 세션 기동 (폴링 세션)

1. **작업 세션이 도는 중인지 본다**: `qa/work.pid` 의 프로세스가 살아 있으면 2·3을 건너뛰고 Q9로 간다. 이번 틱에 편입된 버그는 `편입` 으로 남아 다음 작업 세션이 함께 처리한다.
2. **지난 작업 결과 반영**: `qa/work-result.md` 에 `- **알림**:` 줄이 없으면 그 표만 읽고(코드·로그는 읽지 않는다) 버그마다 `qa-watch.md` 판정을 고친다 — `해결`·`배포완료`·`보류` 는 그 값으로, `재시도` 는 `편입` 그대로 둔다. `보류` 가 있으면 슬랙 본인 DM(`U03SRUFP97W`)으로 한 번에 알린다:
   ```
   ⏸ {루트키} QA 작업 세션이 혼자 고치지 못한 버그가 있습니다.
   • {버그키} — {제목}  {$JIRA_BASE_URL/browse/{버그키}}
     사유: {보류 사유} / 필요한 것: {사람이 할 일}
   ```
   보낸 뒤 결과 파일 끝에 `- **알림**: {YYYY-MM-DD HH:MM}` 를 붙인다. 같은 결과를 두 번 알리지 않기 위해서다.
3. **작업 세션 기동**: `qa-watch.md` 에 판정 `편입` 인 버그가 있으면
   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/skills/dobby-qa/work.sh" {루트키}
   ```
   출력 `started {pid}` 를 확인하고 `dobby_event {루트키} "QA: 작업 세션 기동 — {버그키 목록}"`. 폴링 세션은 작업 세션을 기다리지 않는다.

⛔ 폴링 세션은 Q4~Q8 을 직접 하지 않는다. 작업 세션이 실패해도 폴링 세션에서 대신 고치지 않는다 — 다음 틱에 다시 띄운다.

### Q4. 수정 — 담당 에이전트가 대표 QA 브랜치에서 고친다 (작업 세션 · dobby-order P8 준용)

`qa-watch.md` 에서 판정이 `편입` 인 버그마다(작업 세션은 이 파일을 읽기만 하고 고치지 않는다 — 판정은 폴링 세션이 QW 2항에서 고친다):

0. **혼자 고칠 수 있는지 먼저 가른다.** 아래에 해당하면 고치지 않고 **그 버그만 보류**해 결과 파일(QR)에 사유와 사람이 할 일을 적는다. 다른 버그는 계속 진행한다.

   | 보류 사유 | 왜 혼자 못 하나 |
   |---|---|
   | 다국어 문구 추가·수정이 필요함 | 원본이 스프레드시트라 JSON 을 직접 고치면 안 된다(동기화로 덮인다) |
   | 기획 판단이 필요함 | 기대 동작이 이슈·설계 문서에 없거나 둘 이상으로 읽힌다 |
   | 디자인 자료가 필요함 | 이미지·피그마 자료가 이슈에 없다 |
   | 다른 저장소 수정이 필요함 | 백엔드나 `com.wadiz.web` 을 고쳐야 한다(이 스킬은 `wadiz-frontend` 만 다룬다, Q7) |
   | 재현·원인 특정이 안 됨 | 코드로 원인을 `파일:라인` 까지 잡지 못했다 — 짐작으로 고치지 않는다 |

1. **담당 에이전트 특정 — 묻지 않고 정한다**: 버그를 분석해 고쳐야 할 파일을 `파일:라인`으로 잡고, 그 파일이 어느 에이전트의 **계약(`agents/{슬러그}.md`) 화이트리스트**에 속하는지로 담당을 정한다. 에이전트가 하나뿐이면 그 에이전트가 담당이다. 여러 계약에 걸치면 고칠 줄이 가장 많은 파일의 계약을, 어느 계약에도 안 들어가면 그 기능과 가장 가까운 계약을 담당으로 하고, 판단 근거를 `qa/{버그키}/analysis.md` 에 적는다.
2. **버그 이슈 진행중 전환**: `dobby_jira_start_transition {버그키}`. 이어서 `${CLAUDE_PLUGIN_ROOT}/reference/jira-start.md` 를 따라 시작 날짜를 적고 상위 이슈 레이블을 더한다.
3. **브랜치·워크트리 — 대표 QA 브랜치 하나를 계속 쓴다** (틱마다 한 번, 버그마다가 아니다):
   ```bash
   WT="$(dobby_setup_worktree {repo} {루트키}-QA bugfix {루트브랜치} {루트키})"
   #                                  ↑ bugfix/{루트키}-QA       ↑ 베이스   ↑ docs 게이트는 루트에서 검사
   dobby_record_branch {루트키} {repo} bugfix/{루트키}-QA "$WT"
   git -C "$WT" pull --ff-only origin {루트브랜치}
   ```
   - 키에 `-QA` 를 붙이는 이유: 헬퍼는 작업 폴더를 `subtree/{repo}-{키}` 로 정해, 루트키를 그대로 넘기면 루트 작업 폴더를 돌려준다.
   - 헬퍼는 브랜치를 `{루트키}-QA` 의 status.md 에 적으려다 없어서 넘어간다. 그래서 `dobby_record_branch` 로 루트 status.md 에 직접 적는다.
   - 폴더가 이미 있으면 헬퍼가 그대로 돌려준다. 마지막 줄은 지난 틱 뒤 루트에 쌓인 변경(배포 리뷰 반영 등)을 먼저 받는다.
   - 베이스는 **언제나 루트 브랜치**다(`$ORCHESTRATION_DEFAULT_BASE` 가 아니다). 루트 브랜치는 `status.md` 의 브랜치 표에서 찾는다.
4. **상태 선(先)갱신**(P8 규칙): 작업 전에 담당 에이전트를 `완료 → 구현`(재분석이 필요하면 `분석`), **라운드 +1**. → `dobby_agent_state 루트키 슬러그 구현 라운드` + `dobby_event 루트키 "QA: {슬러그} 버그 {버그키} 편입(기준 ①/②/③) — {요약}"`.
5. **수정 실행 — 담당 에이전트별로 묶어 차례대로**: 이 틱의 편입 버그를 담당 슬러그별로 묶고, 슬러그마다 `dobby-impl` 을 **한 번만** 기동해 자기 버그를 차례대로 고치게 한다. 고치는 중에 0항의 보류 사유가 드러나면 그 버그의 변경을 버리고 보류한다. 컨텍스트는 담당 슬러그의 계약·`implementation.md`·`analysis.md`, 프롬프트에 analysis-discipline + role-personas「구현 에이전트」주입.
   - **버그 하나를 고칠 때마다 커밋 하나**: `fix: {버그키} ...`. 커밋 메시지의 버그키가 버그를 가르는 유일한 표식이다.
   - **동시에 고치지 않는다.** 작업 폴더가 하나라 두 에이전트가 함께 고치면 변경이 섞인다. 한 슬러그가 끝난 뒤 다음 슬러그를 기동한다.
   - 푸시는 **`bugfix/{루트키}-QA` 에만** 한다.

### Q5. 리뷰 (담당 리뷰어 — dobby-order P5 준용)

- **틱마다 리뷰 에이전트를 한 번** 기동한다(`review-agent.md` 계약 + role-personas「리뷰 에이전트」, 리뷰어≠구현자). 대상은 이 틱의 커밋 전체(`git log -p origin/{루트브랜치}..HEAD`)이고, 커밋별로 적대적으로 리뷰한다. 루브릭 A~E는 dobby-order P5와 동일.
- 지적은 **버그키별로 나눠** `$ORCHESTRATION_META/{루트키}/qa/reviews/{YYYYMMDD-HHMM}-round-{n}.md`에 심각도·`파일:라인`·수정 제안으로 남긴다.
- 지적받은 버그만 담당 에이전트가 고쳐 `fix: {버그키} ...` 커밋을 더하고, 다음 라운드는 **그 버그들만** 다시 본다. 통과한 버그는 다시 보지 않는다.
- blocking(blocker·major)=0이 될 때까지 반복(**최대 3라운드**). 넘기면 그 버그의 커밋을 `git revert` 로 되돌리고(메시지 `revert: {버그키} ...`) 결과 파일에 보류로 적는다. 다른 버그는 그대로 진행한다.
- 매 전이 `dobby_agent_state 루트키 슬러그 리뷰`·`… 구현`(리뷰 에이전트 행도 `dobby_agent_state 루트키 review-agent 리뷰`).

### Q6. 루트 브랜치로 모으기

- 리뷰가 끝나면 `bugfix/{루트키}-QA` 를 **루트 브랜치로 한 번 머지·푸시**한다. → `dobby_merge_root {루트워크트리} {루트브랜치} bugfix/{루트키}-QA`
  - 루트 작업 폴더에서 한다. 헬퍼가 그 폴더를 루트 브랜치로 체크아웃하므로, QA 작업 폴더에서 부르면 다음 틱에 QA 브랜치가 아닌 곳에서 고치게 된다.
  - 루트 작업 폴더가 지워졌으면 QA 작업 폴더에서 부르고, 끝나면 `git -C "$WT" checkout bugfix/{루트키}-QA` 로 되돌린다.
- 버그마다 머지·배포하지 않는다 — 한 틱에 6건이 편입된 적이 있고(FE1-1316), 그만큼 PR·빌드가 돌면 낭비다.
- 담당 에이전트 상태 `구현 → 완료`(→ `dobby_agent_state 루트키 슬러그 완료`).
- 머지가 충돌하면 **멈추지 말고** 양쪽 변경 이력을 근거로 푼다. 근거로도 어느 쪽이 맞는지 확정되지 않으면 그 버그를 되돌리고 결과 파일에 보류로 적는다.

### Q7. 배포 — `dobby-ship` 을 부르지 않고 그 절차를 밟는다

Q6에서 루트에 모인 것이 있을 때만 돈다. `env` 가 정해지지 않았으면(입력 3번) 건너뛴다.

⛔ **생 `gh` 를 치지 않는다.** 아래 헬퍼가 `cloud_live` 차단·리뷰어 자동 부착·충돌 브랜치·중복 PR 방지를 대신 지켜 준다.

| 순서 | 하는 일 | 헬퍼 |
|---|---|---|
| 1 | **PR 생성** — 루트 브랜치 → `{env}`. `dev` 를 뺀 환경엔 `wadiz-fe/fe1-team` 리뷰어가 자동으로 붙는다 | `dobby_ship_pr {루트키} {워크트리} {루트브랜치} {env} "{제목}" "{본문}"` |
| 2 | **자동 코드리뷰** — `rc1`·`rc4` 는 기다렸다 반영, `stage` 는 기다리지 않되 달려 있으면 읽어 반영, `dev` 는 충돌만 본다 | `dobby_ship_round {루트키} wadiz-frontend {env}` |
| 3 | **머지** — ⛔ **묻지 않는다** | `dobby_ship_merge {루트키} wadiz-frontend {PR번호}` |
| 4 | **빌드** — ⛔ **묻지 않는다**. 바뀐 경로로 번들을 가린다(공용 꾸러미를 고쳤다고 전부 빌드하지 않는다) | `dobby_ship_build` |
| 5 | **배포 확인** — 우리가 건 빌드(`gh run watch`)와 슬랙 배포 알림을 함께 본다. 빌드 3분 뒤부터 1분 간격, 최대 15분 | `dobby_ship_verify` |

- 각 단계마다 `dobby_ship_stage {루트키} {저장소} {env} "{단계}"` 로 `## 배포` 표를 갱신한다. 다음 틱이 그 표를 보고 **이어서** 한다.
- **이 스킬은 `wadiz-frontend` 만 다룬다.** 헬퍼가 저장소를 인자로 받게 된 것은 `dobby-ship` 이 `com.wadiz.web` 까지 맡기 때문이고, 여기서는 언제나 `wadiz-frontend` 를 넘긴다. QA 버그가 `com.wadiz.web` 을 건드리면 그 수정은 `/dobby-ship` 으로 따로 내보낸다.
- PR 제목은 `{루트키} QA 수정 — {버그키 목록}`, 본문에 버그별 한 줄 요약.
- **`stage` 와 `cloud_live` 는 훅 G1 이 머지를 막는다.** `stage` 면 PR 까지만 만들고 주소를 결과 파일에 적은 뒤 그 작업 세션을 끝낸다(시점은 사람이 고른다). `cloud_live` 는 애초에 `env` 로 받지 않는다.
- 빌드·배포가 실패하면 결과 파일에 적고 `## 배포` 표에 단계를 남긴다. 다음 작업 세션이 그 지점부터 다시 한다.

### Q8. 검증 → Jira 보고

배포 확인이 끝나면 검증한다.

```
/dobby-test {루트키} {env}
```

결과를 **버그마다** 세 갈래로 가른다. 가르는 기준은 `test-runs/{시각}/` 의 그 시나리오 결과다.

| 결과 | 하는 일 |
|---|---|
| **통과** | Jira 코멘트(수정 완료) → **이슈를 해결 상태로 전환** → `## QA` 표 `해결` |
| **검증이 어려움**(재현 불가·테스트 데이터 없음·외부 설정 의존 등) | Jira 코멘트에 **배포 완료 + 검증이 어려운 사유**를 함께 적고 → **여기까지를 프로세스 종료로 본다** → `## QA` 표 `배포완료` |
| **실패**(고쳤는데 그대로임) | ⛔ **코멘트를 달지 않는다.** 담당 에이전트를 `구현` 으로 되돌리고(`dobby_agent_state`) 결과 파일에 `재시도` 로 적는다. 다음 작업 세션이 다시 고친다 |

실패인데 "수정 완료" 코멘트가 남으면 QA 를 오히려 방해한다. 그래서 실패는 조용히 되돌린다.

**Jira 코멘트** — `twg jira workitem comment create --issue-id {버그키} --body-format markdown --body "…" -o json --output-summary none --select data.id`. ⛔ 내부 용어(에이전트 슬러그·라운드·단계 코드·메타 경로·세션 ID)와 소감·아바타는 **적지 않는다**. 나중에 이슈만 읽어도 뜻이 통해야 한다.

통과:
```markdown
## 수정 완료

- **원인**: {무엇이 잘못돼 있었는지 한 줄}
- **수정**: `{파일경로}` — {무엇을 바꿨는지}
- **반영**: {env} 배포 완료 (PR #{번호})
- **검증**: {시나리오} 통과 ({YYYY-MM-DD HH:MM})
```

검증이 어려울 때:
```markdown
## 수정 완료 (검증 보류)

- **원인**: {무엇이 잘못돼 있었는지 한 줄}
- **수정**: `{파일경로}` — {무엇을 바꿨는지}
- **반영**: {env} 배포 완료 (PR #{번호})
- **검증 보류 사유**: {왜 확인하지 못했는지 — 재현 조건·데이터·외부 설정 등}
  → 배포는 끝났으니 QA 환경에서 확인 부탁드립니다.
```

- 같은 이슈에 이 스킬이 남긴 `## 수정 완료` 코멘트가 이미 있으면 **새로 달지 말고 그것을 수정**한다. `comment query … --output-file {파일}` 로 받아 찾고, `comment update --id {코멘트 번호} --issue-id {버그키}` 로 고친다.
- **이슈 상태 전환은 코멘트가 성공한 뒤에** 한다(`twg jira workitem transitions query --id {버그키}` 의 `완료` 묶음에서 도착 상태 `해결됨` 의 번호를 골라 `twg jira workitem transition --id {버그키} --transition-id {번호}`). 순서가 바뀌면 "왜 닫혔는지" 모르는 이슈가 남는다.
- ⛔ `dobby-resolve` 를 쓰지 않는다 — 그 스킬은 **Jira 를 건드리지 않고** 메타만 바꾸며, 버그 이슈는 메타 폴더가 없어 애초에 거부된다.

### QR. 결과 파일 (작업 세션의 마지막 일)

작업 세션은 끝나기 전에 `qa/work-result.md` 를 **새로 써서** 이번에 맡은 버그 전부의 결과를 남기고 끝난다. 폴링 세션은 이 표만 읽는다(QW 2항).

```markdown
# {루트키} QA 작업 결과 ({YYYY-MM-DD HH:MM})

| 버그키 | 결과 | 사유 | 사람이 할 일 |
|--------|------|------|--------------|
| QA-1 | 해결 | - | - |
| QA-2 | 보류 | 다국어 문구 추가 필요(`funding.reward.soldout`) | 다국어 시트에 문구 추가 |
| QA-3 | 재시도 | 검증 실패 — 품절 표시가 그대로 | - |
```
- 결과값: `해결`(검증 통과) · `배포완료`(검증 보류) · `보류`(Q4 0항·리뷰 상한·충돌) · `재시도`(검증 실패·빌드 실패·`env` 미정).
- 버그와 무관한 일(예: `stage` PR 주소)은 표 아래 한 줄로 적는다.

### Q9. 다음 폴 예약 (또는 종료) — 폴링 세션

- 종료 조건이 아니면 **`ScheduleWakeup`으로 `interval`(기본 300초) 뒤 같은 `/dobby-qa {루트키} ...` 재실행을 예약**한다(reason에 "QA 폴링" 명시).
- **종료 조건**: `/dobby-qa stop {루트키}` 수신, 또는 루트 이슈가 정식 배포 베이스로 머지/종료됨. 종료 시 `ScheduleWakeup stop:true`로 루프를 끊고 이벤트 로그에 종료 1줄(`dobby_event`). **단계는 들어올 때 건드리지 않았으므로 되돌릴 것도 없다.**

## 산출물 (기존 메타 폴더 확장)

```
$ORCHESTRATION_META/{루트키}/
├── qa-watch.md                    # 폴링·트리아지 이력 — 이 파일이 있으면 대시보드에 QA 탭이 생긴다
├── qa/{버그키}/                    # 버그별 처리 산출물
│   ├── analysis.md                #   원인(파일:라인)·담당 에이전트 판정
│   └── implementation.md          #   수정 요약(담당 에이전트가 기록)
├── qa/reviews/{YYYYMMDD-HHMM}-round-{n}.md  # 틱별 리뷰 결과(버그키별로 나눠 적음)
├── qa/work-result.md              # 마지막 작업 세션 결과(QR) — 폴링 세션이 읽고 알림
├── qa/work.pid                    # 도는 중인 작업 세션 번호. 끝나면 지워진다
├── qa/work-session.txt            # 마지막 작업 세션 아이디(복기: claude --resume {아이디})
└── (기존 orchestration.md · agents/ · status.md …)
```

**`qa-watch.md`** — 대시보드 QA 탭이 이 파일을 읽는다. 표 모양을 바꾸지 않는다.
```markdown
# {루트키} QA 감시 로그

## 폴링
- **주기**: {interval} · **마지막 폴**: {YYYY-MM-DD HH:MM}
- **환경**: {env} · **parent**: {키 또는 -} · **bugs**: {키들 또는 -}

## 트리아지
| 버그키 | 제목 | 판정 | 기준 | 담당 슬러그 | 브랜치 | 슬랙 ts | 갱신 |
|--------|------|------|------|-------------|--------|---------|------|
| QA-1 | 로고 사이즈 상이 | 편입 | ① | wadiz-edition | bugfix/FE1-1800-QA | - | 2026-10-01 14:20 |
```
- 판정값: `편입` · `무관` · `문의대기` · `보류` · `배포완료` · `해결`.
- `브랜치`는 Q4의 대표 QA 브랜치 `bugfix/{루트키}-QA`. 편입되지 않았으면 `-`. 버그별 수정은 이 브랜치의 `fix: {버그키}` 커밋으로 찾는다.

**`status.md`에 추가하는 `## QA` 표**:
```markdown
## QA
| 버그키 | 편입 기준 | 담당 슬러그 | 상태 | 리뷰 라운드 | 갱신 |
```
- 상태값: `구현` · `리뷰` · `머지완료` · `배포중` · `검증중` · `배포완료` · `해결`.
- `배포완료` = 고쳐서 내보냈지만 **검증이 어려워 거기서 끝낸 것**(Q8 두 번째 갈래). `해결` = 검증까지 통과한 것.
- ⛔ `QA감시중` 같은 값을 **현재 단계에 쓰지 않는다**(Q0 참조). 이 표의 상태값과 오더의 단계는 다른 축이다.

**`## 배포` 표**는 `dobby_ship_stage` 가 갱신한다(dobby-ship 과 같은 표를 쓴다) — QA 수정분이 어느 환경까지 갔는지가 여기 남고, 다음 틱이 이 표를 보고 이어서 한다.

## 확인 게이트 (좁음 — 이때만 사용자를 부른다)

1. **기준 ③ 편입 여부**: 내용상 관련돼 보이지만 ①②로 확정 못 하는 버그 → 슬랙 문의(:넵:/:아니오:). 폴링 세션이 한다.
2. **정식 배포 베이스(`$ORCHESTRATION_DEFAULT_BASE`, 현재 `cloud_live`) 반영**: 확인이 아니라 **금지**. `stage` 머지도 훅 G1 이 막는다 — PR 까지만 만들고 알린다.

담당 에이전트 정하기와 머지 충돌은 묻지 않는다 — 작업 세션이 근거를 적고 스스로 정하거나(Q4 1항), 정하지 못하면 보류한다(Q6).

**묻지 않고 알리기만 하는 것** — 작업 세션이 결과 파일에 적고, 폴링 세션이 슬랙 본인 DM으로 알린다. 그 버그만 보류하거나 다음 작업 세션에서 다시 한다.

| 상황 | 결과 파일 값 |
|---|---|
| Q4 0항의 보류 사유(다국어 시트·기획 판단·디자인 자료·다른 저장소·원인 특정 불가) | `보류` |
| 근거로 풀 수 없는 머지 충돌 | `보류` |
| 진짜 충돌(헬퍼가 거부) — 충돌 해결은 `/merge-branch` 몫 | `보류` |
| 빌드·배포 실패 | `재시도` (`## 배포` 표에 단계를 남긴다) |
| `env` 를 못 정함 | `재시도` (배포·검증만 건너뛴다) |
