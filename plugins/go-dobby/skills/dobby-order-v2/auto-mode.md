# dobby-order-v2 auto 모드 설계 (구현 전)

설계 확정부터 배포 환경 테스트까지 사람 없이 이어 가는 실행 방식의 설계다. 이 문서는 구현 전에 합의한 내용을 적은 것이다. 구현하면서 바뀌는 곳은 이 문서를 먼저 고친다.

## 지금과 무엇이 다른가

| 구분 | 지금(기본 실행) | auto 모드 |
|---|---|---|
| 끝나는 곳 | 통합(작업 브랜치 커밋·푸시)까지 | 배포 환경 테스트 통과까지 |
| 배포 | 사람이 `/dobby-ship {키} {환경}` 실행 | 시작할 때 받은 환경으로 자동 실행 |
| 테스트 | 사람이 `/dobby-order-v2 {키}` 로 검증 세션 실행 | 배포가 끝나면 자동 실행 |
| 테스트 실패 | 수정 세션을 사람이 다시 띄움 | 알림을 보내고, 분석해서 고친 뒤 다시 배포·테스트 |
| PR 생성 | 하지 않음 | 배포에 필요한 PR 만 dobby-ship 이 만든다 |

## 시작하는 법

```
/dobby-order-v2 {키} auto env={dev|rc1|rc4}
```

- `env` 는 시작할 때 한 번만 받는다. 중간에 묻지 않는다.
- `stage` 는 받지 않는다. dobby-ship 이 stage 는 PR 까지만 만들고 사람이 머지·배포하기 때문이다.
- `cloud_live` 는 어떤 경우에도 가지 않는다(dobby-ship 규칙 그대로).

### 시작 전에 미리 확인하는 것

중간에 멈추지 않으려면 사람이 필요한 준비를 처음에 다 확인한다. 하나라도 안 되면 시작하지 않고 무엇이 빠졌는지 알린다.

| 확인 | 왜 |
|---|---|
| argocd 로그인 상태 | com.wadiz.web 배포는 argocd sync 가 있어야 끝난다 |
| 테스트 계정(테스트 계획의 사전 준비) | 로그인이 막히면 테스트가 처음부터 실패한다 |
| 환경 값이 dev·rc1·rc4 중 하나 | 잘못된 환경으로 배포하는 것을 막는다 |
| 알림 채널(슬랙 DM, Gmail) 사용 가능 | 실패와 판단 요청을 사람에게 전할 길이다 |

## 전체 흐름

```
설계(auto) → 구현 → 리뷰 ⇄ 수정 → 통합(커밋·푸시)
  → 배포(dobby-ship {env}) → 테스트(dobby-test)
      통과 → 완료 알림 → 끝
      실패 → 실패 알림 → 실패 분석 → (원인별 처리, 아래 표)
```

부모는 지금처럼 `run.sh` 다. 단계마다 새 세션을 띄우고, 세션 이어 쓰기는 SKILL.md "세션 이어 쓰기 판정"을 따른다.

## 테스트가 실패했을 때

**실패해도 멈추지 않는다.** 먼저 알리고, 원인을 분석해서 고칠 수 있으면 고친다.

### 원인 분류

실패 분석 세션은 테스트 기록(`test-runs/{시각}/`)과 배포 표를 읽고 원인을 아래 중 하나로 고른다.

| 원인 | 어떻게 알아보나 | 처리 |
|---|---|---|
| 배포가 덜 됐다 | 배포된 버전이 통합 커밋과 다르다 | 다시 배포한 뒤 테스트만 다시 |
| 코드 결함 | 실패가 이번 변경 부분에서 재현된다 | 수정 → 리뷰 → 통합 → 배포 → 테스트 |
| 테스트 계획이 틀렸다 | 기대 결과가 설계 문서와 어긋난다 | 사람 판단 요청 |
| 환경·데이터 문제 | 이번 변경과 무관한 곳에서 실패한다 | 사람 판단 요청 |
| 원인을 모르겠다 | 위 어느 것에도 확신이 없다 | 사람 판단 요청 |

테스트 계획과 설계는 사람이 확정한 것이라, 자동으로 고치지 않는다.

### 수정 상한

**테스트 실패를 고치는 시도는 2번까지다.** 2번 고쳤는데도 실패하면 사람 판단 요청으로 넘어간다. 리뷰 라운드 상한(3차)과는 따로 센다.

## 알림

알림은 세 가지다. 슬랙 DM 과 Gmail 로 같이 보낸다. 보내는 데 실패해도 이벤트 로그와 대시보드에는 남긴다.

| 알림 | 언제 | 담는 것 |
|---|---|---|
| 실패 알림 | 테스트가 실패할 때마다 | 실패한 시나리오, 몇 번째 시도인지, "분석해서 고치는 중" |
| 판단 요청 | 사람 판단이 필요할 때 | 아래 "판단 요청에 담는 것" |
| 완료 알림 | 테스트를 전부 통과했을 때 | 배포 환경, 통과한 시나리오 수, 남은 일(`/dobby-resolve {키}`) |

### 판단 요청에 담는 것

사람이 메타를 열어 보지 않고도 결정할 수 있게 자세히 쓴다.

1. 무엇이 실패했는지: 시나리오 이름, 기대한 것, 실제로 본 것
2. 지금까지 한 것: 수정 시도 횟수와 각각 무엇을 바꿨는지
3. 분석: 원인을 무엇으로 보는지와 그 근거, 확인하지 못한 것
4. 선택지와 권장: 2~3개, 각각 무엇이 일어나는지
5. 이어 가는 법: `/dobby-order-v2 {키}` 로 답하면 된다는 안내

판단 요청을 보낸 뒤에는 상태 문서의 단계를 `보류` 로 바꾸고 `## 확인이 필요했던 것` 에 같은 내용을 적고 멈춘다.

## 사람이 답한 뒤 다시 이어 가기

1. 사람이 `/dobby-order-v2 {키}` 를 실행해 답한다.
2. 그 세션이 답을 설계 문서 `## 결정과 근거` 에 적는다. 테스트 계획을 고치기로 했으면 고친다.
3. 단계를 되돌리고 자동 실행을 다시 띄운다(`dobby_v2_autorun {키}`).

## 구현 전에 풀어야 할 것

| 항목 | 지금 상태 | 해야 할 일 |
|---|---|---|
| dobby-ship 의 확인 질문 | 머지·빌드·argocd sync 를 매번 사람에게 묻는다 | auto 실행에서는 시작할 때 받은 승인으로 대신하게 한다(`--approve-commit` 처럼 지시로 덧붙임). 훅이 막는 것은 그대로 둔다 |
| 리뷰봇 대기 | dobby-ship 세션 안에서 30초마다 최대 10분 기다린다 | 기다리는 동안에도 문맥을 다시 읽어 토큰이 든다. `run.sh` 가 기다렸다가 새 세션으로 이어 가게 바꿀지 정한다 |
| 헤드리스 브라우저 테스트 | 검증 세션은 지금까지 모두 대화형이었다. 헤드리스 세션에 chrome-devtools 도구가 보이는 것까지만 확인했다 | 실제 오더 하나로 헤드리스 테스트를 시험한다 |
| 재배포 표시 | `## 배포` 표는 머지된 PR 을 끝난 것으로 본다 | 수정 뒤 다시 배포할 때 새 행을 여는 헬퍼가 필요할 것으로 본다(추측: 지금 표 구조만 보고 판단했고, 실제로 막히는지는 시험하지 않았다) |
| 캐시 유지 시간 | 대화형 5분, 헤드리스 1시간이 관측됐다 | 헤드리스가 늘 1시간이면 이어 쓰기 기준 시간을 늘릴 수 있다 |
