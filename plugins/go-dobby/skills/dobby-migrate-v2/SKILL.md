# dobby-migrate-v2

`dobby-order` 로 진행하던 오더를 `/do` 로 옮긴다. 옮긴 뒤에는 `/do {키}` 로 이어간다.

**이 스킬은 상태만 만든다.** 진행 중인 오더에서 무엇이 끝났고 무엇이 남았는지는 판정하지 않는다. 그 판정과 남은 작업 설계는 `/do` 의 "이어받기 설계" 절이 기존 설계 문서와 작업 브랜치를 보고 한다. 여기서 문서를 채우면 옛 범위를 기준으로 채워진다. dobby-order 는 설계 뒤에 범위가 바뀌어도 설계 문서를 다시 쓰지 않는 일이 있기 때문이다.

## 언제 쓰나

| 쓴다 | 쓰지 않는다 |
|---|---|
| 남은 단계가 길다(구현이 안 끝났거나, 리뷰와 수정이 몇 번 더 돌 것 같다) | 통합이나 검증만 남았다 — dobby-order 로 끝내는 편이 싸다. 옮기는 데도 세션 하나가 든다 |
| 지금 dobby-order 세션의 문맥이 커서 호출마다 비싸다 | 해결, 종료, 완료, 보류 단계다 — 헬퍼가 거부한다 |
| | 설계 문서 없이 분석 단계를 넘어갔다 — 헬퍼가 거부한다. v2 의 뒷세션은 설계 문서를 기준으로 일하기 때문이다 |
| | 착수 단계다 — 옮길 것이 없다. `/do {키}` 로 바로 시작한다 |

## 설정 (첫 실행 시 확인)

작업 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md` 의 "설정 절차"를 그대로 따른다**(config.env 는 읽기만). 이하 메타 경로는 `$ORCHESTRATION_META` 기준이고, 헬퍼는 `${CLAUDE_PLUGIN_ROOT}/reference/dobby-lib.sh` 의 `dobby_*` 를 쓴다.

v2 의 규칙은 `${CLAUDE_PLUGIN_ROOT}/skills/do/SKILL.md` 와 단계별 본문 `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/` 가 정본이다. 아래에서 "v2 의 1-4" 처럼 설계 단계의 절을 가리키면 `steps/design.md` 의 그 절을 읽고 따른다.

## 1. 떠 있는 세션 확인

같은 오더를 맡은 dobby-order 세션이 아직 떠 있으면, 두 세션이 같은 메타 문서를 동시에 고친다. 그래서 **가장 먼저 사람에게 그 세션을 닫았는지 묻는다.** 닫지 않았다면 닫은 뒤 다시 실행하라고 알리고 끝낸다.

## 2. 옮길 수 있는지 검사

```
dobby_migrate_v2_check {키}
```

아무것도 고치지 않는다. 결과는 "항목, 값" 줄이다.

| 항목 | 뜻 |
|---|---|
| `단계` | 지금 단계값 |
| `불가` | 옮길 수 없다. 이유가 함께 나온다. 이 줄이 있으면 이유를 알리고 끝낸다 |
| `개발담당` | 상태표에서 이름이 "분석/개발자" 인 행. 없으면 전환 때 `v2-dev` 행을 만든다 |
| `진행중행` | 상태가 분석, 구현, 리뷰인 행. 전환 때 전부 대기로 돌린다 |
| `마지막리뷰` | 가장 최근 리뷰의 차수, 결과 파일 수, 막는 지적(`[blocker]`·`[major]`) 수 |
| `다음` | 옮긴 뒤 다음 `/do` 세션이 할 일 |
| `필요` | 통합·검증 단계에서 옮길 때만 나온다. 검증 세션이 읽는데 지금 없는 테스트 계획이다. 4절에서 채운다 |

결과를 **쉬운 말로 풀어** 사람에게 보여 준다. 사람이 진행하라고 하면 3절로 간다.

## 3. 기계적인 전환

```
WT="$(dobby_migrate_v2_apply {키})"
```

헬퍼가 하는 일은 아래와 같다.

| 하는 일 | 왜 |
|---|---|
| 상태 문서의 워크트리마다 `dobby_ensure_worktree` 를 부른다. 적힌 브랜치와 폴더를 그대로 쓰고, 폴더가 지워졌으면 그 브랜치로 되살린다. 새 브랜치는 만들지 않는다 | 이어받은 작업은 이전 작업 브랜치에서 계속한다 |
| 개발 담당 행이 없으면 `v2-dev` 행을 만든다 | v2 의 개발 세션은 이 행의 슬러그를 쓴다 |
| `dobby_session_log` 로 `## 지난 세션` 표를 만든다. 원래 세션 아이디는 "이전 세션" 줄로 옮겨진다 | 이 표가 v2 오더의 표지다. 원래 세션은 나중에 `claude --resume` 으로 복기할 수 있다 |
| 진행 중인 행을 전부 대기로 돌린다 | 세션 사이의 빈 시간에 보드가 "정체"로 경고하지 않게 한다 |
| 분석·구현·리뷰 단계이고 설계 문서가 있으면, 단계를 `분석` 으로 두고 `## 현재 단계` 에 `- **이어받기**: 설계 필요 (전환 전 단계 …)` 줄을 넣는다 | dobby-order 의 `구현` 은 "구현 중", v2 의 `구현` 은 "구현을 마쳤다"는 뜻이다. 그대로 두면 남은 일을 건너뛴다. 이 표시를 보고 `/do` 가 이어받기 설계를 고른다 |
| 이벤트 로그에 전환 사실과 전후 단계를 남긴다 | 보드에서 언제 옮겼는지 보인다 |

이어받기 표시는 `/do` 의 이어받기 설계를 사람(또는 `auto`)이 확정할 때 `dobby_design_ack` 가 지운다. 표시가 남아 있는 동안에는 자동 실행(`run.sh`)이 설계가 확정되지 않은 것으로 보고 멈춘다.

헬퍼가 실패하면 오류 문장을 그대로 사람에게 보여 주고 멈춘다. 특히 "git 에 등록되지 않은 폴더" 오류는 사람이 그 폴더를 확인해야 한다.

## 4. 테스트 계획 채우기 (통합·검증 단계에서 옮길 때만)

2절의 `필요` 줄이 있을 때만 한다. 분석·구현·리뷰 단계에서 옮겼으면 건너뛴다. 그때는 이어받기 설계가 테스트 계획을 맞춘다.

v2 의 1-4 형식대로 `test-plan.md` 를 쓴다.
- 각 시나리오의 `- **조건**:` 값은 상태 문서의 `## 닫히는 조건 항목` 표에서 가져온다.
- 그 표가 없으면 설계 문서의 `## 닫히는 조건` 을 보고 `dobby_add_condition {키} "{조건 한 줄}"` 로 먼저 만든다.
- 이미 테스트를 돌린 기록(`test-runs/`)이 있으면, 그때 확인한 시나리오와 실패한 시나리오를 빠짐없이 옮긴다.

v2 의 1-5 표 중 테스트 계획 행으로 점검하고 `dobby_lint {키}` 를 돌려 걸리는 것을 고친다. 끝나면 이벤트를 남긴다.

```
dobby_event {키} "v2 전환 테스트 계획 작성"
```

## 5. 세션 닫기

v2 의 "세션을 닫는 법" 형식 그대로 알리고 **더 이상 아무것도 하지 않는다.** "다음" 칸에는 아래 표에서 전환 뒤 상태에 맞는 줄을 쓴다.

| 전환 뒤 상태 | 다음 `/do` 세션이 하는 일 |
|---|---|
| 분석 + 이어받기 표시 | 이어받기 설계. 기존 설계와 작업 브랜치를 보고 끝난 것과 남은 것을 가른 뒤, 남은 작업을 설계해 사람과 확정한다. "확정"하면 구현부터 통합까지 자동 실행이 이어진다 |
| 분석 (설계 문서 없음) | 분석 문서부터 다시 설계하고 사람과 확정한다 |
| 통합 | 검증(배포가 끝난 뒤에) |
| 검증 | 검증 결과에 따라 수정 또는 끝 |

## 하지 않는 것

- **설계하지 않는다.** 끝난 것과 남은 것의 판정, 남은 작업 설계, 리뷰 항목은 `/do` 의 이어받기 설계가 한다.
- **코드를 고치지 않는다.** 구현과 수정은 v2 의 뒷세션이 한다.
- **커밋하지 않는다.**
- **새 브랜치를 만들지 않는다.** 이전 작업 브랜치를 그대로 쓴다.
- **기존 설계 문서, 리뷰 결과, 구현 문서, 이벤트 로그를 지우거나 고쳐 쓰지 않는다.**
- **`dobby-order` 스킬 문서를 고치지 않는다.**
- **다음 단계를 이어서 하지 않는다.** 이 세션은 옮기는 데까지만 쓴다.
