# dobby-summary

테스트까지 끝난 오더를 **처음 보는 사람도 한 장으로 이해할 수 있게** 정리해 아티팩트로 게시한다.

```
/dobby-summary {키}
   → 테스트 결과가 있는지 확인 → 기록 파일 읽기 → 설계·이슈와 실제 구현 대조
   → 담을 내용 확인받기 → (고르면) 설계 문서·이슈 설명 맞추기 → 원고 작성 → 금지어 자동 검사(스스로 고쳐 재검사) → 게시 → 링크 기록·보고
```

## 비슷한 스킬과 다른 점

| | 근거 | 하는 일 |
|---|---|---|
| dobby-share | `outcome.md`·`explainer.md` 한 문서 | 그 문서를 그대로 옮긴다 |
| dobby-artifact | 이번 대화에서 한 일 | 요구사항에 맞춰 새로 쓴다 |
| **dobby-summary** | **오더 기록 파일 여러 개** | **정해진 여덟 절로 새로 쓴다** |

## 설정 (첫 실행 시 확인)
작업 시작 전 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md`의 "설정 절차"를 그대로 따른다**: `~/.config/go-dobby/config.env`를 source 해 환경 변수를 **읽기만** 한다(config.env 없으면 `/dobby-init` 먼저). 이하 메타 경로는 `$ORCHESTRATION_META` 기준.

## 입력

```
/dobby-summary {키}
```

{키}는 이슈 키 또는 `TASK-{slug}`. 대상 폴더 `$ORCHESTRATION_META/{키}/`.

## 글 쓰는 규칙 — dobby-artifact 를 따른다

**`${CLAUDE_PLUGIN_ROOT}/skills/dobby-artifact/SKILL.md`를 먼저 읽고** 아래 절을 그대로 따른다. 이 문서에 다시 적지 않는다.

- "기본 3규칙" — 목차, 쉬운 용어, 도구 이야기 완전 배제(바꿔 쓰는 법 포함)
- "A2. 원고 작성"의 CSP(외부 호스트 금지·CSS 인라인)와 mermaid 대체
- "A3. 자동 검사" — `dobby_tooling_lint`·`dobby_terms_lint`, 최대 2회 고쳐 재검사
- "A4. 게시"·"A5. 기록" — 단, 아래 "슬러그"·"게시" 절이 정한 값을 쓴다

**⛔ dobby-artifact 의 "A0. 근거 모으기"(이번 대화에서 한 일만)는 따르지 않는다.** 이 스킬의 근거는 아래 "근거" 표의 기록 파일이다.

## 슬러그

`summary` 로 고정한다. 원고는 `$ORCHESTRATION_META/{키}/artifacts/summary.html`.

- `artifact-share.md`의 `## 아티팩트` 표에 `summary` 행이 **있으면 갱신** — 그 행의 URL을 Artifact 도구 `url` 인자로 넘기고 `dobby_artifact_touch {키} summary "{무엇을 바꿨나}"`.
- **없으면 신규** — `url` 없이 게시하고 `dobby_artifact_add {키} summary "{제목}" {URL}`.
- **⛔ 다른 슬러그 행의 URL로 게시하지 않는다** — 그 아티팩트가 덮여 이전 링크가 죽는다.

## 근거 — 절마다 어디서 가져오나

| 절 | 가져올 곳 | 없을 때 |
|---|---|---|
| 1. 이슈 제목 | `status.md` `## 이슈/작업`의 제목 | 키만 쓴다 |
| 2. 이슈 링크 | `${JIRA_BASE_URL}/browse/{키}` | `TASK-` 작업이면 절을 뺀다 |
| 3. 요구사항 | `jira-issue.md`(이슈 원문). 설계 문서 `## 닫히는 조건`을 "완료로 보는 기준"으로 덧붙인다 | `jira-issue.md`가 없으면 `dobby_jira_desc {키}` 로 설명을 화면으로 조회한다(파일로 저장하지 않는다). `TASK-`면 설계 문서 `## 한 장 요약`의 "무엇이 문제인가" |
| 4. 기획·디자인·참고문서 | 이슈 원문과 `design.md`에 나온 링크(피그마·컨플루언스·구글 문서 등). 링크마다 무엇인지 한 줄 | 링크가 하나도 없으면 "연결된 문서 없음" 한 줄 |
| 5. 설계 | `design.md`의 `## 한 장 요약`·`## 현재 동작`·`## 문제가 되는 코드와 원인`·`## 작업 순서`·`## 결정과 근거`, 그리고 `## 변경 N` 절이 있으면 각각의 `### 무엇을 왜` | 설계 문서가 없으면 `analysis.md` |
| 6. 구현 | `implementation.md`의 `## 건드린 파일`·`## 핵심 설계 결정`(설계와 달라진 것). `outcome.md`가 있으면 함께 | 둘 다 없으면 절에 "구현 기록 없음" |
| 7. 테스트 내용 | `test-plan.md`의 `## 사전 준비`(환경·데이터)와 시나리오마다 무엇을 어떻게 눌러 무엇을 보면 통과인지 한두 줄 | 계획이 없으면 결과 표의 "확인 항목"·"기대" 칸 |
| 8. 테스트 결과 | `test-runs/` 의 **가장 최근 회차** `result.md` — 통과·실패·보류 건수, 시나리오별 판정, 보류 사유, `## 변경 밖 관찰` | — (없으면 시작 단계에서 멈춘다) |

- **⛔ `docs-refs.md`는 쓰지 않는다.** 낱말로 자동 검색한 목록이라 관련 없는 문서가 섞인다.
- 회차가 여럿이면 지난 회차는 "언제·몇 건 통과/실패"만 한 줄씩 적는다.
- 위 파일에 없는 내용은 쓰지 않는다. 따로 조사하거나 지어내지 않는다.

## 절차

### S0. 준비 상태 확인
`$ORCHESTRATION_META/{키}/test-runs/*/result.md`가 하나도 없으면 **멈추고** "테스트를 먼저 마친 뒤 다시 부르라"고 알린다.

### S1. 근거 읽기
위 "근거" 표의 파일만 읽는다. 설계 문서는 길 수 있으므로 표에 적힌 절만 읽는다(`## 고칠 코드` 같은 코드 전문은 읽지 않는다).

### S1-1. 설계·이슈와 실제 구현 대조
설계 문서와 이슈 설명이 실제 코드와 어긋난 곳을 찾는다. 코드는 `status.md` `## 워크트리 / 브랜치` 표의 경로·브랜치에서 읽는다. `TASK-` 작업이면 이슈 대조는 뺀다.

어긋남을 찾는 단서는 두 가지다.

1. `implementation.md` `## 핵심 설계 결정` 의 "설계와 달라진 것" 항목.
2. 브랜치에만 있는 커밋(`git log --oneline origin/{기준 브랜치}..HEAD`). 테스트 중에 고친 커밋은 구현 기록에 없는 경우가 많다. 커밋마다 `git show --stat` 으로 바뀐 내용을 본다.

단서마다 아래를 확인한다.

- **설계 문서** — `## 고칠 코드` 에서 그 부분만 찾아 읽는다(S1의 "코드 전문은 읽지 않는다"의 예외). 옛 계획이 남아 있거나, 커밋이 바꾼 내용이 아예 없으면 어긋남이다. `## 결정과 근거` 표에 반영됐어도 `## 고칠 코드` 가 옛 계획이면 어긋남으로 센다.
- **이슈 설명** — 이슈 화면에서 지금 설명을 다시 조회한다(`jira-issue.md` 는 예전 사본일 수 있다). 요구사항으로 적힌 문구·수치·동작이 실제 코드와 다르면 어긋남이다.

**⛔ 추측으로 어긋남을 만들지 않는다.** 어긋남마다 실제 코드의 파일 경로·줄 번호나 커밋 번호를 근거로 단다. 확인하지 못한 것은 "확인 못 함"으로 따로 적는다.

### S2. 담을 내용 확인받기 (게시 전 유일한 확인 지점)
여덟 절의 제목과 절마다 넣을 요지를 한두 줄씩 보여 주고 확인을 받는다. 다음이 있으면 함께 표시한다.

- 사내 민감 정보 — 계정 메일, 비밀번호, 키, 고객 데이터. 테스트 계획의 로그인 계정이 흔한 예다.
- 최근 회차의 실패·`SKIP(미비)` — 결과 절에 그대로 드러난다는 것.
- **S1-1에서 찾은 어긋남** — 설계 문서와 이슈 설명을 나눠 표로 보여 준다. 칸은 "위치", "지금 적힌 내용", "실제 코드(근거)". 그리고 각각 실제 구현에 맞출지 묻는다. 어긋남이 없으면 묻지 않는다.

### S2-1. 설계 문서·이슈 설명 맞추기 (S2에서 고른 것만)
**설계 문서** — `design.md` 의 해당 부분을 실제 코드대로 고친다.

- `## 고칠 코드` 의 코드 조각과 설명, `## 결정과 근거` 표를 함께 고친다. 커밋에만 있던 변경은 알맞은 단계에 새 항목으로 넣는다.
- 최종 사실만 쓴다. "구현 중 발견 —", "검증 중 발견(…) —" 같은 경위 머리말과 "설계에 없었음" 같은 지난 이야기는 지우고 이유만 남긴다.

**이슈 설명** — 설명 본문을 실제 구현에 맞게 고친다.

1. 지금 설명을 조회한 뒤 고칠 문단만 바꾼 새 본문을 만든다. 나머지 문단은 그대로 둔다.
2. 바꾸는 문단마다 "고치기 전"과 "고친 뒤"를 나란히 보여 주고 **한 번 더 확인받는다.** 이슈는 다른 사람도 보는 곳이라 되돌리기 어렵다.
3. 설명에 그림, 첨부, 표, 피그마 같은 끼워 넣은 내용이 있으면 본문을 통째로 바꿀 때 사라질 수 있다. 이런 내용이 있으면 고치지 말고 멈춘 뒤, 어느 문단을 어떻게 바꿀지만 사용자에게 건넨다.
4. 반영은 `twg jira workitem update --id {키} --description-format markdown --description "{새 본문}"` 으로 한다. 반영한 뒤 다시 조회해 바꾼 문단이 들어갔는지 확인한다. 그다음 `jira-issue.md` 를 새 본문으로 바꾼다.

맞춘 뒤의 원고에서는 6절(구현)의 표 제목을 "구현에서 정한 세부 사항"으로 쓴다. 설계 문서와 실제 구현이 같아졌으므로 "설계와 달라진 점"이라고 쓰지 않는다. 맞추지 않기로 했으면 "설계와 달라진 점"으로 쓴다.

### S3. 원고 작성
여덟 절을 위 순서대로 쓴다. 각 절의 제목에 `id`를 단다.

- **목차는 왼쪽 열에 둔다.** 화면 폭 1000px 이상이면 본문 왼쪽 220px 열에 붙어, 본문을 내려도 따라온다. 그보다 좁으면(휴대폰) 제목 아래에 그대로 둔다. 원고는 `.wrap` 안에 머리글, 목차(`nav.toc`), 여덟 절 순서로 두고 아래 규칙을 스타일 끝에 넣는다. `span 9` 는 머리글 하나와 여덟 절을 더한 수다.

```css
@media (min-width: 1000px) {
  .wrap { max-width: 1160px; display: grid; grid-template-columns: 220px minmax(0, 1fr); column-gap: 40px; row-gap: 28px; }
  .wrap > * { grid-column: 2; min-width: 0; }
  .wrap > .toc { grid-column: 1; grid-row: 1 / span 9; align-self: start; position: sticky; top: calc(env(safe-area-inset-top, 0px) + 24px); max-height: calc(100vh - 48px); overflow-y: auto; }
}
```

- **설계 절에 흐름도를 넣는다.** 사용자가 무엇을 하면 화면·코드·서버가 어떤 순서로 움직이는지를 인라인 SVG로 그린다. 그림으로 옮길 흐름이 없으면 번호 매긴 단계 목록으로 대신한다. 그림은 `artifact-diagramming` 스킬 지침을 따른다.
- **결과 절은 결론부터** — 맨 위에 "통과 N · 실패 N · 보류 N (환경)" 한 줄. 실패·보류는 시나리오 이름과 사유를 함께, 통과는 시나리오 이름만.
- 파일을 언급할 때는 저장소 안 경로를 밝힌다. 작업 폴더의 절대 경로(`/Users/…/subtree/…`)는 쓰지 않는다.

### S4. 자동 검사
dobby-artifact "A3. 자동 검사"를 원고에 그대로 적용한다.

### S5. 게시
`artifact-design` 스킬 지침에 따라 Artifact 도구로 publish 한다.

- `title`: 아래 "문서 제목" 규칙으로 정한 제목. 원고의 `<title>`·맨 위 제목, 기록 헬퍼의 `"{제목}"`에도 같은 값을 쓴다.

#### 문서 제목

`{이슈 제목} 구현 내용` 이 기본이다. 이슈 제목이 아래 중 하나면 그대로 쓰지 않고, 이슈 원문과 설계 문서의 한 장 요약을 보고 **무엇을 만들었는지 드러나게 다듬은 뒤** ` 구현 내용`을 붙인다.

- 너무 길다 — 다듬은 주제가 25자 안팎이 되게 줄인다.
- 전체 뜻을 담지 못한다 — 일부 화면·증상만 적었거나, 배경(법 개정·요청 부서)만 적었거나, `[Web]`·`[QA]` 같은 머리표·키 번호가 붙은 경우.

```
[Web] 전자상거래법 개정에 따른 사용후기 기준 공개 적용  →  사용후기 기준 공개 구현 내용
```

키 번호만으로 제목을 만들지 않는다.
- `description`: 무엇을 고쳤고 테스트가 어떻게 끝났는지 한 문장
- `icon`: `document` (첫 게시 때만)

### S6. 기록·보고
위 "슬러그" 절대로 `dobby_artifact_add` 또는 `dobby_artifact_touch` 로 기록한다(파일을 직접 쓰지 않는다). 사용자에게 링크와, 근거에서 무엇을 뺐는지(도구 이야기 N곳, 민감 정보 등) 한 줄을 알린다. 대시보드 아티팩트 탭에서도 열린다고 안내한다.

## 비파괴
- `artifacts/summary.html`과 `artifact-share.md`의 `summary` 행만 만들거나 갱신한다.
- 다른 슬러그의 행·원고, 기록 파일, 워크트리, 코드, Jira는 건드리지 않는다.
- 예외: S2에서 사용자가 맞추기를 고른 경우에만 `design.md`, 이슈 설명, `jira-issue.md` 를 고친다(S2-1). 코드는 이때도 고치지 않는다.

## 주의
- **대화형 전용**: 헤드리스/백그라운드에서는 Artifact 도구·claude.ai 인증이 없어 실패한다. 대시보드 버튼으로 자동화하지 않는다.
- 아티팩트는 기본 **비공개**로 게시된다(사용자가 claude.ai에서 공유 여부를 결정).
