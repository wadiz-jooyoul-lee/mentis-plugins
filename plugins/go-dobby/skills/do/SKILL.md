# do

한 오더(이슈·작업)를 **여러 세션에 나눠** 진행하는 오케스트레이터다. `dobby-order` 를 대체하지 않는다 — 둘은 같은 메타 형식을 쓰고 목적만 다르다.

| | dobby-order | do |
|---|---|---|
| 한 번 실행에 하는 일 | 착수부터 통합까지 전부 | **한 단계만** |
| 세션 수 | 1개(서브 에이전트는 그 안에서) | 단계마다 새 세션 |
| 끝낼 때 | 다음 단계로 이어감 | **결과를 적고 세션을 닫으라고 알린 뒤 끝** |
| 사람에게 묻기 | 게이트에서 묻는다 | **설계 세션에서만** 요약을 보여 주고 함께 고친다. 나머지 세션은 묻지 않는다(판단이 필요하면 문서에 적고 멈춘다) |
| 적합한 때 | 짧고 한 번에 끝나는 작업 | 길고 문맥이 커지는 작업 |

## 왜 이렇게 하나 (바꾸면 안 되는 근거)

모델을 한 번 부를 때마다 **그때까지 쌓인 대화 전부**가 입력으로 다시 들어간다. 그래서 비용은 "결과물의 크기"가 아니라 **"문맥의 크기 × 호출 횟수"** 로 정해진다.

한 오더를 실측한 숫자다.

| 주체 | 호출 수 | 평균 문맥 | 문맥 재읽기 누적 | 비중 |
|---|---|---|---|---|
| 메인 세션 1개 | 1,563회 | 444,372 토큰 | 684,000,000 토큰 | **96.6%** |
| 서브 에이전트 15명 전부 | 328회 | 57,000~98,000 토큰 | 24,400,000 토큰 | 3.4% |

**일을 누구에게 보내느냐는 거의 차이가 없다. 오케스트레이터 세션이 얼마나 오래 크게 살아 있느냐가 전부다.** 그래서 이 스킬은 자기 자신을 빨리 죽이는 것을 최우선으로 한다.

세션을 끊는 비용은 한 번뿐이다 — 새 세션 시작 약 70,000 토큰 + 메타 문서 읽기 약 20,000 토큰 = 약 90,000 토큰. 반면 안 끊으면 **호출 한 번마다** 44만 토큰이 다시 들어간다. 호출을 한 번이라도 더 할 거면 끊는 쪽이 이미 이득이다.

## 설정 (첫 실행 시 확인)

작업 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md` 의 "설정 절차"를 그대로 따른다**(config.env 는 읽기만). 이하 메타 경로는 `$ORCHESTRATION_META` 기준이고, 헬퍼는 `${CLAUDE_PLUGIN_ROOT}/reference/dobby-lib.sh` 의 `dobby_*` 를 쓴다.

분석할 때는 **`${CLAUDE_PLUGIN_ROOT}/reference/analysis-discipline.md` 원칙을 따른다**(추측 금지, 사실 확인, 모르면 docs 참조).

## 사용법

```
/do {이슈키|URL} [base={브랜치}] [step={단계}] [auto [env={dev|rc1|rc4}]]
/do {이슈키} 변경 {무엇을 바꾸거나 더할지}
```

- `step` 을 주지 않으면 **지금 어느 단계인지 스스로 판정**한다(아래 "단계 판정").
- `base` 는 첫 세션에서만 쓴다. 안 주면 `$ORCHESTRATION_DEFAULT_BASE`.
- 같은 명령을 세션마다 그대로 다시 치면 그 다음 단계가 진행된다.
- `auto` 를 주면 설계 세션에서도 사람에게 묻지 않는다. 대시보드가 사람 없이 띄우는 실행(헤드리스 실행)용이다. 안 주면 설계 세션은 사람과 대화하며 설계를 확정한다(아래 "1-6. 사람과 함께 설계 고치기").
- `auto env={환경}` 을 주면 통합에서 멈추지 않고 그 환경 배포와 검증까지 사람 없이 간다(**자동 배포 오더**). 상태 문서 `## 현재 단계` 의 `- **자동 배포 환경**: {환경}` 줄이 표지다. stage·cloud_live 는 받지 않는다. 설계와 근거는 이 폴더의 `auto-mode.md`.
- `변경 {내용}` 을 주면 단계와 상관없이 **변경 접수**를 한다(아래 "변경 접수"). 어느 단계의 세션에서든, 사람이 대화로 수정을 지시하거나 새 버그·추가 설계를 말해도 같다.

### 설계 확정 뒤 자동으로 끝까지 돌리기

설계를 사람과 확정한 뒤에는 이 스킬 폴더의 `run.sh` 로 남은 단계를 자동으로 돌릴 수 있다. 단계마다 `claude -p "/do {키}"` 를 새로 실행한다. 실행이 끝나면 그 프로세스가 사라지므로 사람이 세션을 닫을 일이 없다.

**설계 세션이 "자동 실행" 답을 받으면 이 자동 실행을 직접 띄운다**(1-6). 그래서 사람은 설계만 확정하면 구현부터 통합(작업 브랜치 커밋·푸시)까지 손댈 일이 없다. 띄우는 일은 `dobby_v2_autorun {키}` 가 대시보드의 '자동 실행'을 불러서 한다. 대시보드가 띄워야 터미널을 닫아도 실행이 살아 있고, 진행이 대시보드 오더 화면에 보인다.

**부모는 `run.sh` 이고, Claude 세션이 아니다.** 부모가 하는 일은 상태 문서의 단계값을 읽고 다음 세션을 띄우는 것뿐이라 판단이 필요 없다. 셸이 맡으면 부모 몫의 토큰이 0이다. Claude 세션이 부모가 되면 자식이 끝날 때마다 깨어나 자기 문맥 전체를 다시 읽는다(설계 세션 문맥 실측 17만~27만 토큰, 단계마다 약 2회). Agent 도구의 서브 에이전트를 자식으로 쓰면 자식의 세션 아이디가 부모와 같아져 `## 지난 세션` 표와 `claude --resume` 복기가 깨진다.

```bash
run.sh {키} [--mode {권한 모드}] [--max {최대 세션 수}] [--with-test] [--approve-commit]
```

| 인자 | 뜻 | 기본값 |
|---|---|---|
| `--mode` | `claude` 의 `--permission-mode` 값. 화면 없는 실행은 권한 확인 창을 띄울 수 없어서 미리 정한다 | `auto` |
| `--max` | 이번 실행에서 띄울 세션 수의 상한 | 10 (자동 배포 오더는 20) |
| `--with-test` | 통합 뒤 검증까지 돈다. 검증은 배포된 화면을 보므로 배포가 끝난 뒤에 준다 | 없음(통합에서 멈춤) |
| `--approve-commit` | 사람이 커밋·푸시를 미리 승인한 실행이다. 세션마다 그 승인을 지시로 덧붙인다(`--append-system-prompt`). 없으면 통합 세션이 사용자 지침에 따라 동의를 묻고 멈출 수 있다. 승인 범위는 오더 작업 브랜치의 커밋·푸시뿐이다 | 없음 |

멈추는 경우는 아래와 같다. 멈출 때는 이유와 함께, 마지막 세션을 다시 여는 `claude --resume {세션 아이디}` 명령을 알려 준다.

| 멈추는 경우 | 이유 |
|---|---|
| 설계가 확정되지 않았다 | 설계는 사람과 함께 확정해야 한다 |
| 통합까지 끝났다(`--with-test` 없음) | 검증은 배포 뒤에 해야 의미가 있다 |
| 검증을 전부 통과했다 | 할 일이 끝났다 |
| 세션이 끝났는데 아무것도 바뀌지 않았다 | 사람 판단이 필요해 스킬이 멈췄을 가능성이 크다 |
| 세션이 오류로 끝났다 | 원인을 사람이 봐야 한다 |
| 세션 수 상한에 닿았다 | 끝없이 도는 것을 막는다 |
| (자동 배포 오더) 배포 표에 막힘(⚠)이 있다 | 배포 세션이 스스로 풀지 못한 일이다 |
| (자동 배포 오더) 리뷰봇 리뷰가 30분, 빌드가 30분 동안 끝나지 않았다 | 기다려도 오지 않을 가능성이 크다 |

자동 배포 오더는 위에서 멈출 때 슬랙 DM 과 메일로 알린다(`dobby_v2_notify`). 리뷰봇과 빌드는 세션이 아니라 `run.sh` 가 기다린다(`dobby_v2_ship_next` 가 `wait-review`·`wait-build` 를 내는 동안). 세션마다 배포 승인 지시도 덧붙인다.

세션이 끝날 때마다 이벤트 로그에 "자동 실행 세션 N 종료 — 시작 단계, 지금 단계, 새 세션인지 이어 쓴 세션인지, 세션 아이디"를 한 줄 남긴다. 세션 안에서도 공통 규칙 "세션 기록"대로 아이디를 남긴다.

#### 세션 이어 쓰기 판정

기본은 단계마다 새 세션이다. 다음 일이 수정이고, 직전 세션 문맥이 12만 토큰 이하이며, 5분 안일 때만 이어 쓴다(`dobby_v2_reuse_ok`). 근거와 비용은 이 폴더의 `session-reuse.md` 에 있다.

자동 배포 오더(배포·테스트까지 사람 없이 돌리기)의 설계와 근거는 이 폴더의 `auto-mode.md` 에 있다.

## 단계 판정 (실행하면 가장 먼저 하는 일)

`$ORCHESTRATION_META/{키}/status.md` 의 `## 현재 단계` 를 읽고 아래 표대로 고른다. 메타 폴더가 없으면 **설계** 다.

**먼저 v2 오더인지 본다.** v2 오더의 표지는 상태 문서의 `## 지난 세션` 표다. 설계 세션이 1-1 의 5번(`dobby_session_log`)에서 만든다. 이 표가 없고 단계가 `착수` 도 아니면 `dobby-order` 가 만든 메타다. 그때는 아무것도 고치지 않고 멈춘다. 사람에게 "이 오더는 dobby-order 로 진행한 오더라 dobby-order 로 이어가거나, `/dobby-migrate-v2 {키}` 로 v2 로 옮긴 뒤 이어가야 한다"고 알린다. 두 스킬이 한 오더를 번갈아 맡으면 서로의 상태 기록을 엉뚱하게 읽는다. 단계가 `착수` 인데 표가 없으면, v2 설계 세션이 1-1 도중에 끊긴 것이다. 그때는 설계부터 다시 한다.

| status.md 현재 단계 | 추가로 보는 것 | 이번 세션에서 할 일 |
|---|---|---|
| (폴더 없음) · 착수 | — | **설계** |
| 분석 | `## 현재 단계` 에 `- **이어받기**:` 줄이 있다 (dobby-order 에서 진행 중에 옮겨 온 오더) | **이어받기 설계** (아래 "이어받기 설계" 절). 승인 기록보다 먼저 본다 — dobby-order 가 남긴 옛 승인 기록에 걸려 구현으로 넘어가지 않게 |
| 분석 | 설계 문서가 없다 (dobby-order 에서 옮겨 온 오더) | **설계** (1-1 의 4·5번만 하고 1-2 부터 이어감) |
| 분석 | 설계 승인 기록이 없다 | **설계 수정 대화** (1-6 부터 이어감) |
| 분석 | 설계 승인 기록이 있고 지금 설계와 같은 버전이다 | **구현** |
| 분석 | 설계 승인 기록이 있지만 그 뒤에 설계가 바뀌었다 | **설계 수정 대화** (바뀐 곳을 보여 주고 다시 확정받는다) |
| 구현 | — | **리뷰** |
| 리뷰 | 최신 라운드 리뷰 파일이 없다 | **리뷰** |
| 리뷰 | 리뷰 파일이 있고 `dobby_blocking` 집계 > 0 | **수정** |
| 리뷰 | 리뷰 파일이 있고 `dobby_blocking` 집계 = 0 | **통합** |
| 통합 | `자동 배포 환경` 줄이 없다 | **검증** |
| 통합 | 줄이 있다 — `dobby_ship_reopen {키}` 를 부른 뒤 `dobby_v2_ship_next {키}` 의 첫 칸이 `ship` | **배포** (세션 5-2) |
| 통합 | 위 첫 칸이 `verify` | **검증** |
| 통합 | 위 첫 칸이 `wait-review`·`wait-build`·`blocked` | 멈춘다. 기다림은 `run.sh` 몫이다. 무엇을 기다리는지(또는 무엇이 막혔는지) 알린다 |
| 검증 | 검증 결과가 전부 통과 | 끝 — `dobby-resolve` 를 안내하고 멈춘다 |
| 검증 | 실패가 있고 `자동 배포 환경` 줄이 없다 | **수정** |
| 검증 | 실패가 있고 줄이 있다 | **실패 처리** (세션 6-2) |
| 해결 · 종료 · 완료 | — | 끝난 오더다. 그 사실만 알리고 멈춘다 |
| 보류 | `자동 배포 환경` 줄이 있다 | **판단 답 받기** (세션 6-3) |
| 보류 | 줄이 없다 | 멈춘다. 다시 진행하려면 사람이 상태 문서의 단계를 되돌려야 한다고 알린다 |
| 그 밖의 값 | — | 멈춘다. 모르는 단계값이라고 알리고 상태 문서를 확인해 달라고 한다 |

**변경 요청이 먼저다.** 인자에 `변경` 이 있거나, 이 세션에서 사람이 수정 지시·새 버그·추가 설계를 말하면 위 표와 상관없이 **변경 접수**를 한다. 끝난 오더(해결·종료·완료)와 검증을 통과한 오더도 마찬가지다.

"수정"은 `dobby_norm_phase` 가 `리뷰` 로 접기 때문에 단계값만으로는 리뷰와 갈리지 않는다. 그래서 리뷰 결과 파일의 유무와 blocking 집계로 가른다.

"설계 승인 기록"은 `$ORCHESTRATION_META/{키}/design-ack.json` 의 `사용자` 또는 `auto` 항목이다. 그 값이 `dobby_design_rev {키}`(지금 설계 문서의 지문, 내용이 바뀌면 달라지는 짧은 값)와 같으면 승인된 설계 그대로다.

최신 라운드 번호는 `$ORCHESTRATION_META/{키}/reviews/` 의 `round-N` 폴더 중 가장 큰 N 이다. 폴더가 하나도 없으면 1 이다.

**수정 세션은 끝날 때 다음 라운드의 빈 폴더를 연다**(`reviews/round-{N+1}/`). 그래서 수정 뒤에는 "최신 라운드 리뷰 파일이 없다"가 되어 다음 세션이 다시 리뷰를 한다. 이 폴더를 열지 않으면 지적이 남은 옛 리뷰 파일이 최신으로 남아, 판정이 계속 "수정"으로 돌아간다.

# 세션 1 · 설계

**이 세션이 v2 의 전부다.** 뒤따르는 세션들은 여기서 만든 문서만 읽고 일한다. 문서가 부족하면 뒷세션이 코드를 다시 뒤져야 하고, 그러면 세션을 나눈 의미가 사라진다.

## 1-1. 골격과 착수

1. `dobby_bootstrap {키} "{임시제목}" 개발 "{키워드1|키워드2}"` — 폴더·골격·종류·세션·docs 게이트를 한 번에 깐다.
2. Jira 이슈를 조회한다(작업 키 `TASK-` 면 건너뛴다). 조회 직후 **그 자리에서** 두 가지를 한다.
   - `dobby_set_title {키} "{실제 이슈 요약}"` — 임시 제목을 실제 요약으로 바꾼다.
   - Jira 상태를 진행 중으로 전환한다. 이어서 `${CLAUDE_PLUGIN_ROOT}/reference/jira-start.md` 를 따라 시작 날짜를 적고 상위 이슈 레이블을 더한다.
3. 워크트리를 준비한다 — `dobby_ensure_worktree {저장소} {키} {prefix} {base}`. `prefix` 는 버그면 `bugfix`, 그 밖은 `feature` 다(빗금은 헬퍼가 붙인다). 이 헬퍼는 상태 문서에 이미 적힌 워크트리가 있으면 그것을 쓰고, 폴더가 지워졌으면 남은 브랜치로 되살리고, 아무것도 없을 때만 새로 만든다. git 에 등록되지 않은 폴더가 같은 자리에 있으면 지우지 않고 멈춘다. 그때는 사람에게 그 폴더를 확인해 달라고 알린다.
4. `dobby_agent_add {키} {슬러그} "분석/개발자" "{작업 한 줄}" 분석 0` — 상태표에 담당 한 행을 넣는다. 마지막 0 은 수정 횟수다(아래 "보드의 상태표"). 슬러그는 `dobby_slug` 로 만든다.
5. `dobby_session_log {키} {슬러그} design 설계 {워크트리경로}` — 이 세션의 아이디를 기록한다(공통 규칙 "세션 기록").

## 1-2. 분석 → `analysis.md`

`dobby_scaffold_doc {키} analysis` 로 틀을 깔고 채운다. 틀은 **하한선**이다 — 필요한 만큼 길게 쓰고, 틀에 맞추려고 분석을 줄이지 않는다.

- 코드를 직접 읽어 원인을 `파일:라인` 으로 짚는다. 증상 서술로 끝내지 않는다.
- 현재 저장소에서 알 수 없는 외부 참조가 나오면 **도서관**(`$ORCHESTRATION_DOCS_ROOT`)을 먼저 뒤진다.
- 레거시 앱이나 별도 번들로 뜨는 앱이면 `## 이 앱에 없는 것` 절을 반드시 채운다(국제화 초기화 여부, 같은 주소로 닿는 API 경로, 공용 패키지 재사용 가능 여부).

## 1-3. 설계 → `design.md`

`dobby_scaffold_doc {키} design` 으로 틀을 깔고 채운다. 규칙은 `dobby-design` 스킬의 design.md 규칙을 그대로 따른다.

**v2 에서 달라지는 것은 읽는 사람이다.** 기존에는 사용자가 읽고 승인하는 문서였다. v2 에서는 **다음 세션의 개발 담당이 이것만 보고 코드를 쓰는 작업 지시서**다. 그래서 아래를 더 한다.

### 반드시 더 적는 것

1. **작업 순서** — 고칠 파일이 둘 이상이면 어느 것부터 손대야 하는지와 그 이유. 의존이 있으면(A 를 바꿔야 B 가 컴파일된다) 명시한다.
2. **건드리지 않을 것** — 범위 밖인데 눈에 띌 파일을 미리 적는다. 적지 않으면 개발 담당이 "겸사겸사" 고친다.
3. **검증 명령** — 구현 담당이 자기 작업을 확인할 실제 명령을 적는다. 예: `npm run lint -- {경로}`, `npm run build`, `npx tsc --noEmit`. 저장소마다 다르므로 **실제로 있는 명령인지 확인하고** 적는다.
4. **확인하지 못한 것** — 모른 채 남은 것을 전부 적는다. 각 항목마다 **구현 담당이 어떻게 해야 하는지**까지 적는다(예: "이 값이 null 로 오는 경우가 있는지 확인 못 했다. 방어 코드를 넣고 주석으로 남길 것"). 빈칸으로 두면 뒷세션이 멈춘다.

**A/B 테스트(실험군 분기)를 넣는 요청이면** `ab-test-design` 스킬(wadiz-client 플러그인)을 불러 그 규칙대로 design.md·test-plan.md 의 실험 내용을 채운다. 설치돼 있지 않으면 설계를 확정하지 않고 "ab-test-design 스킬 필요"를 확인할 것으로 남긴다.

### `## 리뷰 항목` 절 (v2 고유 · design.md 맨 끝에 덧붙인다)

리뷰 담당 세션이 읽을 확인 목록이다. **별도 파일로 만들지 않는다** — 대시보드는 파일 이름을 하드코딩해 읽기 때문에 새 파일은 보이지 않는다. design.md 안에 두면 "설계/결과" 탭이 그대로 보여 준다.

설계를 막 끝낸 지금이 **이 변경에서 무엇이 틀리기 쉬운지 가장 잘 아는 시점**이다. 그 지식을 넘긴다.

```markdown
## 리뷰 항목

### 이 변경에서 틀리기 쉬운 곳
| 확인할 것 | 어디를 | 왜 위험한가 |
|---|---|---|
| (한 줄) | `경로:라인` | (설계할 때 망설였던 이유) |

### 영향받는 호출부
| 바뀌는 것 | 부르는 곳 | 확인할 것 |
|---|---|---|
| `함수명`의 반환 형태 | `경로:라인` | (이 호출부가 무엇을 기대하는가) |

- 소비처가 없으면 "소비처 없음 — {어떻게 확인했는지}" 라고 적는다. 안 적으면 안 본 것과 구별되지 않는다.

### 이 저장소에서 지켜야 할 규약
- (CLAUDE.md·NAMING·GLOSSARY 에서 이번 변경에 걸리는 것만)
```

**호출부를 찾는 법**: 내보내는 이름·공개 메서드 이름만으로는 부족하다. 지우는 줄의 **문자열 값**과 **파일 이름**까지 찾는다. 이름을 쪼개 만드는 참조(`'reward-' + name`)와 설정 파일이 간접으로 부르는 것은 이름 검색으로 안 잡히므로 따로 본다.

## 1-4. 테스트 케이스 → `test-plan.md`

`dobby_scaffold_doc` 에 test-plan 틀은 없다. 아래 형식으로 직접 쓴다.

**검증 담당 세션이 이 문서만 보고 브라우저를 열어 테스트하고, 통과인지 실패인지 혼자 판정할 수 있어야 한다.**

**⛔ 시나리오를 쓰기 전에 영향 번들부터 판정한다.** `${CLAUDE_PLUGIN_ROOT}/reference/bundle-scope.md` 를 따라 네 번들(`static`, `static-global`, `static-account`, `studio`)이 이번 변경에 닿는지 가리고, 결과를 `## 영향 번들` 표로 적는다. 그다음 영향인 번들마다 그 번들의 화면에서 확인하는 시나리오를 만든다. 이슈에 적힌 화면 하나만 보고 시나리오를 쓰면, 같은 코드를 쓰는 다른 번들의 화면이 확인 없이 나가기 때문이다.

```markdown
# {키} 테스트 계획

## 사전 준비
- 테스트 환경: {주소}
- 로그인 계정: {아이디} (비밀번호는 config.env 의 TEST_LOGIN_PW)
- 필요한 데이터 상태: (예: 종료된 펀딩 프로젝트 1건, 알림 신청 이력 있는 계정)

## 영향 번들
| 번들 | 판정 | 근거 | 확인 시나리오 |
|---|---|---|---|
| static | 영향 / 제외 / 해당 없음 | (`파일:라인` 또는 찾은 명령과 결과) | S1 |
| static-global | | | |
| static-account | | | |
| studio | | | |

## S1. {시나리오 이름}
- **조건**: C1
- **번들**: static
- **대상 주소**: https://{환경}/{경로}
- **사전 상태**: (이 시나리오를 시작하기 전에 갖춰져야 할 것)
- **조작 단계**:
  1. (사람이 그대로 따라 할 수 있는 동작 하나)
  2. ...
- **통과 기준**: (무엇이 화면에 보이면 통과인가 — 눈으로 판정 가능한 문장으로)
- **실패로 보는 것**: (어떤 모습이면 실패인가)
- **남길 증거**: (화면 캡처 / 개발자 도구 콘솔 / 네트워크 요청 중 무엇을)
```

- **`- **조건**: C1`** 은 `status.md` 의 `## 닫히는 조건 항목` 표에서 가져온다. 대시보드 검증 탭이 "조건 몇 가지 중 몇 가지 확인"을 이 값으로 센다.
- 사전 준비의 데이터(프로젝트 번호, 계정 등)를 dev·rc4 DB 에서 골라야 하면 `wadiz-shared:cloud-db-query` 스킬로 조회한다(`analysis-discipline.md` 6). 고른 값과 그 값을 찾은 조회문을 함께 적는다.
- **통과 기준은 "정상 동작한다" 로 쓰지 않는다.** 무엇이 보이면 통과인지 적는다. 예: "버튼 아래에 '마감된 프로젝트입니다' 라는 회색 문구가 보인다".
- 데이터 수집(수집 태그·수집 스크립트)이나 광고 노출을 건드렸으면 그 시나리오를 반드시 넣는다. 화면에는 안 보이게 깨지기 때문이다.
- 기존 기능이 망가지지 않았는지 보는 **회귀 확인 시나리오를 최소 하나** 넣는다. 영향 번들이 둘 이상이면 회귀 확인도 번들마다 둔다.
- **`- **번들**:`** 은 그 시나리오가 확인하는 번들이다. `## 영향 번들` 표의 "확인 시나리오" 칸과 맞춘다.
- **로그인·로그아웃은 조작 단계에 버튼으로 적는다.** 로그인 화면이나 로그아웃 주소를 직접 여는 단계는 쓰지 않는다. 검증 담당이 적힌 그대로 따라 하기 때문이다.
  - 로그인: PC 는 메인 화면 헤더의 **로그인** 버튼, 모바일은 **마이 와디즈**의 **로그인**을 눌러 로그인 화면으로 간다.
  - 로그아웃: **마이 와디즈** 맨 아래 **로그아웃** 버튼을 누른다.

## 1-5. 자족성 점검 (이 세션을 닫기 전 필수)

아래를 스스로 묻고, 하나라도 "아니오"면 그 자리를 채운 뒤에 끝낸다.

| 문서 | 점검 질문 |
|---|---|
| design.md | 고칠 파일 경로가 **전부** 적혀 있나 (말줄임·"등" 금지) |
| design.md | 파일마다 "지금 / 고친 뒤 / 왜" 가 **코드로** 있나 |
| design.md | 검증 명령이 **실제로 있는 명령**인가 |
| design.md | `## 확인하지 못한 것` 의 각 항목에 **구현 담당이 어떻게 할지**가 적혀 있나 |
| design.md | `## 리뷰 항목` 의 호출부 표가 비어 있다면 "소비처 없음 + 확인 방법" 이 적혀 있나 |
| test-plan.md | 각 시나리오에 **주소·사전 상태·통과 기준**이 다 있나 |
| test-plan.md | 통과 기준이 **눈으로 판정 가능한 문장**인가 |
| test-plan.md | 회귀 확인 시나리오가 있나 |
| test-plan.md | `## 영향 번들` 표에 네 번들이 **모두** 있고, 판정마다 근거가 있나 |
| test-plan.md | 영향인 번들마다 **그 번들의 화면**에서 확인하는 시나리오가 있나 |

`dobby_lint {키}` 와 `dobby_terms_lint $ORCHESTRATION_META/{키}/design.md` 를 돌려 걸리는 것을 고친다.

## 1-6. 사람과 함께 설계 고치기 (`auto` 가 없을 때)

자족성 점검까지 마치면 먼저 상태를 적어 둔다. 이 대화가 길어져 세션이 끊겨도, 새 세션이 "설계는 있고 승인은 없다"를 보고 이 절부터 이어가게 하기 위해서다.

```
dobby_phase {키} 분석
dobby_agent_state {키} {슬러그} 분석
dobby_event {키} "설계 초안 완료 — 사람 확인 대기"
```

그다음 사람에게 아래 요약을 보여 준다. 문서를 통째로 붙여 넣지 않는다. 사람이 판단할 수 있을 만큼만 추린다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{키} · 설계 초안

한 장 요약
  (무엇이 문제이고, 어떻게 고치는지 3~5줄)

고칠 파일

```

요약 끝의 자동 실행 안내는 빼지 않는다. 커밋과 푸시는 사람의 동의가 있어야 하는 일이라, 사람이 "자동 실행"이 무엇을 시작하는지 알고 답해야 그 답이 동의가 된다.

사람이 고칠 곳을 말하면 아래를 지킨다.

1. **설계 문서를 고친다.** 결정이 바뀌면 `## 결정과 근거` 표의 해당 줄도 함께 바꾼다.
2. **설계가 바뀌면 딸린 문서도 맞춘다.** 고칠 파일이나 동작이 바뀌면 `## 리뷰 항목` 과 테스트 계획의 시나리오·통과 기준도 같이 고친다. 설계만 바꾸고 두 문서를 두면 뒷세션이 서로 다른 문서를 보고 일한다.
3. **고칠 때마다 1-5 자족성 점검을 다시 돈다.** 대화로 고친 내용은 빠뜨리기 쉽다.
4. 바뀐 곳만 짧게 다시 보여 주고 "자동 실행"인지 "직접 실행"인지 묻는다.

사람이 **"자동 실행"** 이나 **"직접 실행"** 이라고 하면 승인을 기록한다.

옛 낱말도 같은 뜻으로 받는다. "확정"은 "자동 실행", "확정만"은 "직접 실행"으로 본다.

```
dobby_design_ack {키} 사용자
dobby_agent_state {키} {슬러그} 대기
dobby_event {키} "설계 확정 — 구현 세션으로 넘김"
```

**"자동 실행"이면 이어서 자동 실행을 띄운다.** 승인 기록 뒤에 불러야 한다. 대시보드가 시작 전에 "설계가 확정됐는가"를 다시 보기 때문이다.

```
dobby_v2_autorun {키}
```

| 결과 | 할 일 |
|---|---|
| 0 (시작함) | "세션을 닫는 법"의 **자동 실행을 띄웠을 때** 형식으로 알리고 끝낸다. 대시보드 오더 실행 탭이 띄운 세션(`DOBBY_V2_CHAINED`)이면 실제로 띄우지 않고 0 을 돌려준다. 이 세션이 끝나면 같은 잡이 이어서 실행한다 |
| 1 (대시보드가 거부) | 출력된 이유를 그대로 전하고, 기본 형식으로 알리고 끝낸다. 이 세션 자체가 대시보드 잡으로 떠 있으면 "이미 실행 중"으로 거부된다. 그때는 이 세션을 닫은 뒤 오더 화면의 "자동 실행" 버튼을 누르라고 안내한다 |
| 2 (대시보드에 닿지 못함) | 출력된 직접 실행 명령을 그대로 전하고, 기본 형식으로 알리고 끝낸다 |

⛔ **이 세션에서 `run.sh` 를 직접 띄우거나 다음 단계를 이어서 하지 않는다.** 이 세션 아래에서 띄운 프로세스는 세션이 닫힐 때 함께 끝날 수 있고, 이어서 하면 세션을 나눈 의미가 없어진다.

**"직접 실행"이면** 자동 실행을 띄우지 않고 기본 형식으로 알리고 끝낸다.

수정 대화는 확정될 때까지 이 세션에서 그대로 이어간다. 대화 길이 때문에 중간에 끊지 않는다.

사람이 확정하지 않고 세션을 닫았다면, 새 세션은 단계 판정에서 "승인 기록이 없다"를 보고 이 절부터 다시 시작한다. 이때는 1-1 부터 1-5 까지를 다시 하지 않는다. `dobby_session_log {키} {슬러그} design 설계 {워크트리경로}` 로 세션만 기록하고, 설계 문서와 테스트 계획을 읽어 바로 요약을 보여 준다.

## 1-7. 마무리 (`auto` 가 있을 때)

사람에게 묻지 않는다. 사람만 정할 수 있는 결정이 있으면 공통 규칙 "사람에게 묻지 않는다"의 2번대로 멈춘다(승인을 기록하지 않는다). 그런 결정이 없으면 아래를 하고 끝낸다.

```
dobby_phase {키} 분석
dobby_design_ack {키} auto
dobby_agent_state {키} {슬러그} 대기
dobby_event {키} "설계 완료(자동 확정) — 구현 세션으로 넘김"
```

`env=` 가 없으면 그다음 아래 "세션을 닫는 법"대로 알리고 끝낸다.

**`env=` 가 있으면** 승인을 기록하기 전에 아래를 확인한다. 하나라도 안 되면 승인을 기록하지 않고, 무엇이 빠졌고 어떻게 채우는지 알리고 끝낸다. 중간에 사람이 필요해 멈추지 않도록 처음에 다 본다.

| 확인 | 어떻게 |
|---|---|
| 환경이 dev·rc1·rc4 중 하나 | 인자 |
| 고칠 저장소가 wadiz-frontend·com.wadiz.web 안에 있다 | 워크트리 표. 다른 저장소는 배포 절차가 없다 |
| gh 로그인 | `gh auth status` |
| argocd 로그인(고칠 저장소에 com.wadiz.web 이 있을 때만) | `dobby_ship_argo {키} {환경} check` 가 세션 만료로 거부하지 않는다. 재로그인은 브라우저 인증이라 자동으로 못 한다 |
| 테스트 계정 | 테스트 계획 `## 사전 준비` 의 계정이 있고, config.env 에 `TEST_LOGIN_PW` 가 있다 |

통과하면 승인 기록 앞에 `dobby_v2_set_env {키} {환경}` 을 부르고, 승인 기록 뒤에 1-6 과 같이 `dobby_v2_autorun {키}` 를 부른다(결과 처리도 1-6 표와 같다).

# 세션 2 · 구현

## 읽을 것 (이것만 읽는다)

1. `$ORCHESTRATION_META/{키}/design.md` — **작업 지시서다. 이 문서가 정본이다.**
2. `$ORCHESTRATION_META/{키}/status.md` — 워크트리 경로와 현재 단계.

**`analysis.md` 는 읽지 않는다.** 설계 문서에 필요한 것이 다 옮겨져 있다. 분석 문서까지 읽으면 문맥만 커진다. 설계 문서를 읽다가 근거가 더 필요할 때만 그 부분을 찾아 읽는다.

**설계 문서에 `## 변경 {M}` 절이 있고 그 상태가 `구현 대기` 면, 그 절들만 구현한다.** 앞의 본문은 이미 통합된 내용이다. 배경으로만 읽고 다시 구현하지 않는다. 아래 2~5번의 `## 고칠 코드`, `## 작업 순서`, `## 건드리지 않을 것`, `## 검증 명령` 은 그 변경 절 안의 같은 이름 소절로 읽는다. 워크트리에 이미 반영된 부분(아직 커밋 전인 앞 변경)이 있으면 다시 하지 않는다.

## 하는 일

1. `dobby_session_log {키} {슬러그} impl 구현 {워크트리경로}` 그리고 `dobby_agent_state {키} {슬러그} 구현`. 변경을 구현하면 하위 키를 `impl-change-{M}`, 단계 이름을 `"변경 {M} 구현"` 으로 쓴다.
2. 워크트리로 이동해 `design.md` 의 `## 고칠 코드` 를 그대로 구현한다.
3. `## 작업 순서` 가 있으면 그 순서를 지킨다.
4. `## 건드리지 않을 것` 에 적힌 파일은 손대지 않는다.
5. `## 검증 명령` 을 돌려 통과시킨다.
6. **커밋하지 않는다.** 리뷰는 커밋 전 변경을 본다.

## 설계가 틀렸을 때

구현하다 보면 설계대로는 안 되는 경우가 있다. 그때는 멈추지 말고 **고치되 반드시 기록한다.**

`design.md` 의 `## 결정과 근거` 표에 행을 추가한다.

| 결정한 것 | 고른 답 | 왜 | 검토한 대안 |
|---|---|---|---|
| (설계와 달라진 것) | (실제로 한 것) | **구현 중 발견 — (설계대로 안 되는 이유를 코드 근거로)** | (설계안) |

기록하지 않으면 리뷰 담당이 "설계와 구현이 다르다"를 결함으로 올린다.

## 마무리

`implementation.md` 를 쓴다(`dobby_scaffold_doc {키} implementation`). 바꾼 파일, 핵심 결정, 설계와 달라진 점, 검증 명령 결과를 적는다. 변경을 구현했으면 덮어쓰지 않고 `## 변경 {M} 구현` 절로 덧붙인다.

```
dobby_phase {키} 구현
dobby_agent_state {키} {슬러그} 대기
dobby_event {키} "구현 완료 — 리뷰 세션으로 넘김"
```

# 세션 3 · 리뷰

## 읽을 것

1. `design.md` 의 **`## 리뷰 항목`** 절 — 설계 담당이 넘긴 확인 목록. `구현 대기` 인 `## 변경 {M}` 절이 있으면 그 절의 `### 리뷰 항목` 을 본다.
2. `dobby_review_brief {워크트리}` 의 출력 — 바뀐 것, 지운 파일, 변경 본문, 저장소 금지 규칙 검사 결과, 사라진 것들의 소비처 표가 한 번에 나온다.

**직접 `git diff` 를 치기 전에 `dobby_review_brief` 를 먼저 쓴다.** 리뷰 비용은 읽는 양이 아니라 **왕복 횟수**다. 한 번 부를 때마다 그때까지 쌓인 문맥을 다시 읽기 때문이다. 미리 받아 두면 그만큼 왕복이 준다.

## 시작할 때

리뷰는 개발 담당과 다른 행으로 보드에 올린다. 구현한 쪽과 리뷰하는 쪽을 보드에서 구별하기 위해서다. 슬러그는 라운드가 바뀌어도 `review-agent` 하나를 쓴다. 라운드마다 새 슬러그를 만들면 보드에 같은 리뷰어가 여러 명 생긴다.

```
dobby_agent_add {키} review-agent "리뷰어" "{N}차 리뷰" 리뷰 {N}
dobby_agent_state {키} review-agent 리뷰 {N} "{N}차 리뷰"
dobby_session_log {키} review-agent round-{N} "{N}차 리뷰" {워크트리경로}
```

첫 줄은 행이 이미 있으면 아무것도 하지 않는다. 그래서 2차 리뷰부터는 둘째 줄이 상태, 라운드, 설명을 바꾼다(다섯째 인자가 설명 칸이다).

## 리뷰 기준

`## 리뷰 항목` 을 먼저 전부 확인하고, 그다음 아래를 본다.

| 보는 것 | 무엇을 |
|---|---|
| 정확성 | 버그, 논리 오류, 빈 값·경계값 처리, 비동기와 오류 처리, 설계와 구현의 불일치 |
| 호출부 영향 | 내보내는 것·반환 형태가 바뀌었으면 부르는 곳마다 어떤 영향인지. **브리프의 소비처 표에 있는 것을 다시 찾지 않는다.** 표가 못 잡는 것(이름을 쪼개 만드는 참조, 물려받은 메서드, 설정 파일이 부르는 것)만 직접 본다 |
| 규약 | 브리프에 검사 결과가 붙은 저장소 금지 규칙은 다시 보지 않는다. 그 밖의 이름·용어·구조 규약만 |
| 재사용 | 새로 적은 타입·유틸·조립이 이미 저장소에 있는지 **찾아본다. 판단이 아니라 절차다** |
| 범위 | 설계의 `## 건드리지 않을 것` 을 지켰는지 |

## 결과 쓰기

`dobby_review_path {키} {N} review-agent` 가 알려 준 경로에 쓴다. N 은 단계 판정에서 구한 최신 라운드 번호다. 첫 리뷰면 1 이고, 수정 뒤의 리뷰면 수정 세션이 열어 둔 빈 폴더의 번호다.

각 지적은 **`## [blocker|major|minor|nit] {제목 한 줄}`** 카드로 시작한다. 이 머리글을 `dobby_blocking` 이 센다. 카드 머리글이 없으면 그 파일은 결함 1건으로 세어진다.

본문에는 근거 `파일:라인`, 재현 조건, 수정 제안을 적는다. 본문의 길이와 형식에는 제한이 없다.

**지적이 없는 영역도 적는다** — "확인함 — 문제 없음" 또는 "해당 없음 — {왜 닿지 않는지}". 안 적으면 안 본 것과 구별되지 않는다.

## 마무리

```
dobby_review_lint {키} {N}
dobby_blocking {키} {N}
dobby_phase {키} 리뷰
dobby_agent_state {키} review-agent 완료
```

`dobby_blocking` 결과를 알린다. 0 이면 다음은 통합, 0 보다 크면 다음은 수정이다.

# 세션 4 · 수정

## 읽을 것

1. 최신 라운드의 리뷰 결과 파일 — `$ORCHESTRATION_META/{키}/reviews/round-{N}/review-agent.md`. dobby-order 에서 옮겨 온 오더는 파일 이름이 다를 수 있다(예: `inline-dev.md`). 그 폴더의 `.md` 파일을 전부 읽는다.
2. `design.md` — 설계 기준.

검증 실패로 들어온 경우에는 리뷰 파일 대신 `test-runs/{시각}/` 의 실패 기록을 읽는다.

## 하는 일

1. `dobby_session_log {키} {슬러그} fix-{N} "{N}차 수정" {워크트리경로}` 그리고 `dobby_agent_state {키} {슬러그} 구현 "$(dobby_fix_count {키} {슬러그})"`. 검증 실패로 들어왔으면 하위 키를 `fix-test-{시각}`, 단계 이름을 `"검증 실패 수정"` 으로 쓴다.
2. 워크트리에서 `[blocker]` 와 `[major]` 를 전부 반영한다. `[minor]` 와 `[nit]` 은 판단해서 처리하고, 안 할 거면 이유를 적는다.
3. 반영한 내용을 `implementation.md` 에 덧붙인다.
4. **커밋하지 않는다.**

## 지적을 반영하지 않기로 할 때

"드물다"·"엣지 케이스다" 같은 **빈도 추정은 근거가 아니다.** 그 상태를 만드는 코드 경로를 `파일:라인` 으로 전수 확인해 **0건임을 증명**했을 때만 기각한다. 1건이라도 남으면 반영한다. 증명하지 못하면 반영한다.

## 마무리

```
dobby_review_path {키} {N+1} review-agent >/dev/null   # 다음 라운드 빈 폴더를 연다(파일은 만들지 않는다)
dobby_phase {키} 리뷰
dobby_agent_state {키} {슬러그} 대기
dobby_event {키} "{N}차 지적 반영 완료 — 재리뷰 세션으로 넘김"
```

**반영했으면 반드시 다시 리뷰한다.** 다음 세션은 리뷰다(라운드 번호가 하나 올라간다).

**라운드가 3을 넘으면 멈춘다.** 3차 리뷰의 지적을 반영하는 수정 세션이면, 4차 폴더를 열지 않는다. 변경을 리뷰하는 중이면 그 변경 절의 `리뷰 시작 차수` 부터 센다. 예를 들어 시작 차수가 4차면 6차가 마지막이다. 무엇이 왜 안 닫히는지 이벤트 로그에 적고 사람에게 넘긴다. 검증 실패로 들어온 수정은 이 셈에 넣지 않는다.

---

# 세션 5 · 통합

## 하는 일

1. `dobby_session_log {키} {슬러그} integrate 통합 {워크트리경로}` 로 세션을 기록하고, 리뷰 결과가 0 건인지 다시 확인한다 — `dobby_blocking {키} {N}`.
2. 커밋하고 푸시한다 — `dobby_commit_push {워크트리} {브랜치} "{메시지}"`.
   - 메시지는 `fix: {키} {무엇을 고쳤는가}` 또는 `feat: {키} {무엇을 만들었는가}`.
   - **오케스트레이션 내부 용어를 넣지 않는다**(라운드 번호, 슬러그, 단계 코드, "리뷰 반영").
   - 저장소가 금지하는 서명을 넣지 않는다.
3. 에이전트 브랜치가 루트 브랜치와 다르면 머지한다 — `dobby_merge_root {워크트리} {루트브랜치} {에이전트브랜치}`.
4. `outcome.md` 를 쓴다 — `dobby_scaffold_doc {키} outcome` 후 설계 대비 결과 표와 구현 내용을 채운다. 내부 용어와 줄임말을 쓰지 않는다(`dobby_terms_lint` 로 확인).
5. `dobby-explain {키}` 를 실행해 비전공자용 구현 내용 문서를 만든다.
6. 변경을 통합했으면 설계 문서의 그 `## 변경 {M}` 절 상태를 `통합됨 ({커밋 해시 7자리})` 로 바꾼다. `outcome.md` 는 덮어쓰지 않고 `## 후속 {YYYY-MM-DD} — {변경 요약}` 절을 덧붙인다. 상태를 바꾸지 않으면 다음 변경 때 구현 세션이 이미 통합된 변경을 다시 구현하려 한다.

**정식 배포 브랜치로 PR 을 만들거나 머지하지 않는다.** 그것은 `dobby-ship` 이 할 일이다.

## 마무리

```
dobby_agent_state {키} {슬러그} 완료
dobby_phase {키} 통합
dobby_event {키} "통합 완료 — 검증 세션으로 넘김"
```

자동 배포 오더면 다음은 배포 세션이다. 이벤트 문구의 "검증 세션"을 "배포 세션"으로 바꿔 적는다.

---

# 세션 5-2 · 배포 (자동 배포 오더만)

단계는 `통합` 그대로 둔다. 진행은 상태 문서 `## 배포` 표가 나타낸다.

1. `dobby_session_log {키} {슬러그} ship-{YYYYMMDD-HHMM} 배포 {워크트리경로}`
2. `dobby-ship` 스킬 절차를 `{키} {자동 배포 환경}` 으로 따른다. 그 스킬의 **"자동 실행에서"** 절대로 한다 — 머지·빌드·sync 를 묻지 않고, 리뷰봇과 빌드를 기다리지 않고, 검증은 하지 않는다.
3. 기다릴 자리(`리뷰 대기`·`빌드 대기`·`배포 대기`)나 `배포 확인` 에 닿으면 끝낸다. 다음 세션은 `run.sh` 가 정한다.

막혀서 못 나아가면 그 행의 비고에 무엇이 왜 막혔는지 적는다(`dobby_ship_stage` 의 비고 칸). 비고가 있으면 `run.sh` 가 멈추고 사람에게 알린다.

---

# 세션 6 · 검증

## 읽을 것

`test-plan.md` **하나만 읽는다.** 설계 문서도 구현 문서도 읽지 않는다. 테스트 계획이 자족적이지 않으면 그것 자체가 설계 세션의 결함이므로, 그 사실을 기록하고 멈춘다.

## 하는 일

`dobby_session_log {키} {슬러그} verify 검증 {워크트리경로}` 로 세션을 기록한 뒤 `dobby-test {키}` 를 실행한다(자동 배포 오더는 `dobby-test {키} {자동 배포 환경}`). 검증은 보드에 행을 따로 만들지 않는다. 그래서 세션 기록도 개발 담당 슬러그 아래에 남긴다(보드에 없는 슬러그로 기록하면 대시보드가 정체 모를 에이전트로 표시한다). 그 스킬이 브라우저를 열어 시나리오를 돌리고 결과를 `test-runs/{시각}/` 에 남긴다.

## 마무리

```
dobby_phase {키} 검증
```

- 전부 통과: 끝났음을 알리고 `dobby-resolve {키}` 를 안내한다. 배포가 필요하면 `dobby-ship {키} {환경}` 을 안내한다.
- 실패가 있음: 다음은 수정 세션이다. 무엇이 왜 실패했는지 알린다.

**자동 배포 오더는 더 한다.**

1. 테스트 전에 맡은 저장소마다 `dobby_ship_stage {키} {저장소} {환경} "검증 중"`. 전부 통과하면 `"검증 완료"`.
2. 브라우저 도구가 안 보이면 연결이 늦은 것이다. 잠시 뒤 다시 찾는다. 바로 "도구 없음"으로 끝내지 않는다.
3. 알린다(공통 규칙 "알림 보내는 법").
   - 전부 통과: **완료 알림** — 배포 환경, PR·빌드 번호(`## 배포` 표), 통과한 시나리오 수, 남은 일(`/dobby-resolve {키}` 로 해결 표시, Jira 보고). 해결 표시와 Jira 보고는 하지 않는다.
   - 실패가 있음: **실패 알림** — 실패한 시나리오, 몇 번째 시도인지(`dobby_v2_test_fixes {키}` + 1), "원인을 분석해서 고치는 중".

---

# 세션 6-2 · 검증 실패 처리 (자동 배포 오더만)

## 읽을 것

1. 마지막 `test-runs/{시각}/` 의 실패 기록
2. 상태 문서 `## 배포` 표
3. `design.md` — 원인이 코드 결함일 때만

## 하는 일

1. `dobby_session_log {키} {슬러그} triage-{YYYYMMDD-HHMM} "검증 실패 분석" {워크트리경로}`
2. **배포부터 의심한다.** 실패한 화면의 번들이 이번 커밋으로 나갔는지 `dobby_ship_verify`, com.wadiz.web 이면 `dobby_ship_argo {키} {환경} check` 로 본다.
3. 원인을 하나로 고르고 처리한다.

| 원인 | 어떻게 알아보나 | 처리 |
|---|---|---|
| 배포가 덜 됐다 | 빠진 번들이 있거나 argocd 가 `OutOfSync`·`Progressing` | `dobby_ship_stage` 로 그 행을 다시 할 단계(번들이 빠졌으면 `빌드 대기`, sync 가 덜 됐으면 `배포 대기`)로 되돌리고 `dobby_phase {키} 통합`. 다음은 배포 세션이다. 수정 횟수에 넣지 않는다 |
| 코드 결함 | 실패가 이번 변경 부분에서 재현된다 | `dobby_v2_test_fixes {키}` 가 2 이상이면 판단 요청으로 간다. 아니면 이 세션에서 세션 4(수정)를 검증 실패로 들어온 경우대로 한다(하위 키 `fix-test-{시각}`). 다음은 리뷰다 |
| 테스트 계획이 틀렸다 | 기대 결과가 설계 문서와 어긋난다 | 판단 요청. 테스트 계획과 설계는 확정된 것이라 고치지 않는다 |
| 환경·데이터 문제 | 이번 변경과 무관한 곳에서 실패한다 | 판단 요청 |
| 원인을 모르겠다 | 위 어느 것에도 확신이 없다 | 판단 요청 |

## 판단 요청

사람이 메타를 열지 않고도 정할 수 있게 자세히 쓴다.

1. 무엇이 실패했는지: 시나리오 이름, 기대한 것, 실제로 본 것
2. 지금까지 한 것: 수정 시도 횟수와 각각 무엇을 바꿨는지
3. 분석: 원인을 무엇으로 보는지와 그 근거, 확인하지 못한 것
4. 선택지와 권장: 2~3개, 각각 무엇이 일어나는지
5. 이어 가는 법: `/do {키}` 로 답하면 된다

같은 내용을 `design.md` 의 `## 확인이 필요했던 것` 에 적고, 알림으로 보내고(공통 규칙 "알림 보내는 법"), `dobby_phase {키} 보류` 로 멈춘다.

# 세션 6-3 · 판단 답 받기 (보류된 자동 배포 오더)

사람과 대화하는 세션이다. `design.md` 의 `## 확인이 필요했던 것` 마지막 항목을 보여 주고 답을 받는다.

1. `dobby_session_log {키} {슬러그} answer-{YYYYMMDD-HHMM} "판단 답" {워크트리경로}`
2. 답을 `## 결정과 근거` 에 적는다. 테스트 계획이나 설계를 고치기로 했으면 고치고 1-5 자족성 점검을 다시 돈다. 코드를 고쳐야 하면 변경 접수로 받는다(그 절이 단계를 되돌린다).
3. 코드를 안 고치고 배포나 검증을 다시 하기로 했으면 `dobby_phase {키} 통합` 으로 되돌린다. 배포부터 할지 검증부터 할지는 `run.sh` 가 배포 표를 보고 정한다. 막힘 비고가 남은 행은 사람이 풀었다는 답을 받은 뒤 `dobby_ship_stage` 로 비고 없이 다시 적는다.
4. 설계가 바뀌었으면 `dobby_design_ack {키} 사용자` 를 다시 부른다. 그다음 `dobby_v2_autorun {키}` 로 자동 실행을 다시 띄운다. `자동 배포 환경` 줄은 그대로라 배포와 검증까지 다시 간다.

# 이어받기 설계 (dobby-order 에서 진행 중에 옮겨 온 오더)

`dobby-migrate-v2` 는 진행 중(분석·구현·리뷰)인 오더를 옮길 때 기계적인 전환만 하고, 상태 문서에 `- **이어받기**: 설계 필요` 표시를 남긴다. 무엇이 끝났고 무엇이 남았는지는 이 세션이 가린다. dobby-order 의 `구현` 단계는 "구현 중"이라는 뜻이라, 단계값만 보고 넘어가면 남은 일을 건너뛴다.

**기존 작업 브랜치와 워크트리를 그대로 쓴다.** 상태 문서 `## 워크트리 / 브랜치` 표의 첫 행이 이 오더의 작업 브랜치다. 새 브랜치를 만들거나 브랜치를 바꾸지 않는다. 뒷세션의 구현, 리뷰, 통합도 그 브랜치에서 한다.

## 1. 기록

```
dobby_v2_change_open {키} check
dobby_session_log {키} {슬러그} takeover "이어받기 설계" {워크트리경로}
dobby_agent_state {키} {슬러그} 분석
```

슬러그는 상태표에서 이름이 "분석/개발자" 인 행의 것이다(전환 헬퍼가 없으면 `v2-dev` 로 만들어 둔다). 첫 줄이 거부하면 그 사실을 알리고 끝낸다.

## 2. 지난 설계와 경과를 읽는다

| 읽을 것 | 무엇을 얻나 |
|---|---|
| 설계 문서 | 처음에 정한 범위와 결정. 설계 뒤에 범위가 바뀌었는지는 이벤트 로그와 대조한다 |
| 상태 문서 `## 닫히는 조건 항목` 표 | 끝났는지 가를 기준. 표가 없으면 설계 문서의 `## 닫히는 조건` 을 보고 `dobby_add_condition` 으로 먼저 만든다 |
| 진행 보드 문서의 상태표와 이벤트 로그 | 누가 무엇을 언제 끝냈는지, 커밋 해시, 범위가 바뀐 시점 |
| 구현 기록(`implementation*.md`)과 리뷰 결과(`reviews/round-*/`) | 실제로 한 일, 남긴 지적, 미룬 것 |

분석 문서는 설계 문서만으로 근거가 모자랄 때 그 부분만 찾아 읽는다.

## 3. 작업 브랜치에서 끝난 것과 남은 것을 가린다

문서에 "완료"라고 적혀 있어도 브랜치로 확인한다. 문서와 브랜치가 다르면 브랜치를 따르고, 다르다는 사실을 표에 적는다.

```bash
git -C {워크트리} status --short                      # 커밋하지 않은 변경
git -C {워크트리} log --oneline @{u}.. 2>/dev/null     # 푸시하지 않은 커밋
git -C {워크트리} log --oneline --first-parent -30      # 작업 브랜치에 들어온 커밋과 머지
# 하위 작업 브랜치가 있으면 작업 브랜치에 들어왔는지
git -C {워크트리} merge-base --is-ancestor {하위 브랜치} HEAD && echo 머지됨 || echo 미머지
```

하위 작업 브랜치 이름은 상태 문서의 브랜치 표, 닫히는 조건, 이벤트 로그에 나오는 이슈 키에서 찾는다. 로컬에 없으면 `origin/` 을 본다. 둘 다 없으면 "브랜치 없음"이다.

닫히는 조건마다 한 행씩 판정한다.

| 판정 | 기준 |
|---|---|
| 끝남 | 그 일의 커밋이 작업 브랜치에 들어와 있다. 근거로 커밋 해시를 적는다 |
| 일부 | 커밋은 들어왔지만 문서에 남은 일(미룬 것, 반영 안 한 지적)이 적혀 있다 |
| 남음 | 브랜치가 없거나, 작업 브랜치에 머지되지 않았거나, 커밋하지 않은 변경으로만 있다 |

커밋하지 않은 변경이 있으면 그 파일 목록과 어느 조건의 일인지 적는다. 이 변경은 지우지 않는다. 남은 작업 설계에서 "이미 워크트리에 있음"으로 다룬다.

## 4. 남은 작업을 설계 문서에 변경 절로 덧붙인다

"변경 접수" 3절의 `## 변경 {M}` 형식으로 **설계 문서 맨 끝에** 덧붙인다. 앞의 본문은 고치지 않는다. 구현 세션은 `구현 대기` 인 변경 절만 구현하고 본문은 이미 된 일로 읽는다. 이어받기와 뜻이 같아서 이 장치를 그대로 쓴다.

- `- **종류**:` 는 `이어받기` 로 쓴다.
- `- **요청**:` 에는 "dobby-order 에서 옮겨 온 오더의 남은 작업"이라고 쓴다.
- `### 무엇을 왜` 맨 앞에 `#### 끝난 것과 남은 것` 표를 둔다. 3번의 판정 표를 조건 번호, 판정, 근거(커밋 해시나 파일)로 옮긴다.
- 나머지 소절은 남은 작업에 대해서만 쓴다. 규칙은 1-3 의 "반드시 더 적는 것"과 `## 리뷰 항목` 절과 같다.
- 남은 작업이 하위 작업 브랜치를 쓰는 방식이었다면(예: 하위 이슈마다 브랜치를 따서 작업 브랜치로 머지), 그 방식을 `### 작업 순서` 에 그대로 적는다. 바꾸려면 `## 결정과 근거` 표에 이유와 함께 적는다.

설계 뒤에 범위가 바뀌었는데 본문에 없으면(이벤트 로그에만 있으면), 바뀐 범위를 `### 무엇을 왜` 에 적는다. 리뷰 담당과 검증 담당이 옛 범위로 판정하지 않게 하기 위해서다.

## 5. 테스트 계획을 맞춘다

`test-plan.md` 가 1-4 형식(`## 영향 번들` 표, `## S{n}.` 시나리오와 `- **조건**:` 줄)이 아니거나, 조건 번호가 상태 문서의 표와 어긋나면 1-4 형식으로 다시 쓴다. 영향 번들 표가 없으면 작업 브랜치의 변경 파일로 새로 판정한다.
- 다시 쓰기 전에 `cp test-plan.md test-plan.md.bak` 로 옛 계획을 남긴다.
- 옛 계획의 확인 항목은 빠짐없이 새 시나리오로 옮긴다.
- 끝난 조건은 회귀 확인 시나리오로, 남은 조건은 `(변경 {M})` 을 붙인 시나리오로 쓴다.

형식이 맞으면 "변경 접수" 4절대로 남은 작업의 시나리오만 더한다.

## 6. 점검과 확정

1-5 자족성 점검을 이 변경 절과 테스트 계획에 대해 돈다. `dobby_lint {키}` 와 `dobby_terms_lint $ORCHESTRATION_META/{키}/design.md` 도 돌린다.

그다음 1-6 형식으로 요약을 보여 준다. 맨 앞에 두 가지를 더한다.
- 작업 브랜치: `{브랜치}` (`{워크트리}`)
- 끝난 것과 남은 것 표

확정과 그 뒤의 순서는 "변경 접수" 5절과 같다. 차례는 아래와 같다.
1. `dobby_v2_change_open` 을 부른다.
2. 출력된 리뷰 시작 차수를 변경 절에 적는다.
3. `dobby_design_ack {키} 사용자` 를 부른다. 이 승인이 이어받기 표시도 지운다.
4. `dobby_event {키} "이어받기 설계 확정 — 구현 세션으로 넘김"` 을 남긴다.

리뷰 차수는 그 시작 차수부터 센다. 그래서 dobby-order 에서 이미 3차까지 돌았어도 이어받은 작업은 처음부터 세 번의 리뷰를 받는다.

**"자동 실행"이면** 1-6 과 같이 `dobby_v2_autorun {키}` 를 부른다. **"직접 실행"이면** 부르지 않는다.

`auto` 가 있으면 묻지 않고 1-7 처럼 `dobby_design_ack {키} auto` 로 확정한다. 남은 작업의 범위를 사람만 정할 수 있으면 확정하지 않고 멈춘다(공통 규칙 "사람에게 묻지 않는다"의 2번).

확정하지 않고 세션을 닫으면 표시가 남는다. 그래서 다음 `/do` 가 이 절을 다시 고른다. 그때는 변경 절이 이미 있으면 2~5번을 다시 하지 않는다. 세션만 기록하고 바로 요약을 보여 준다.

모든 조건이 끝남이고, 커밋하지 않은 변경과 푸시하지 않은 커밋도 없으면, 변경 절을 만들지 않는다. v2 에서는 통합까지 끝난 상태다. 그 사실을 표와 함께 보여 주고, 사람에게 검증으로 넘길지 묻는다. 답을 받으면 아래를 차례로 한다.
1. `dobby_phase {키} 통합` (v2 의 `통합` 은 "통합을 마쳤다"는 뜻이라 다음 `/do` 가 검증을 한다)
2. `_v2_takeover_clear {키}`
3. 이벤트를 남긴다.

# 변경 접수 (진행 중에 새 요청이 들어왔을 때)

진행 중에 사람이 아래 같은 요청을 하면, **이 세션에서 바로 코드를 고치지 않는다.** 설계 문서와 상태를 고쳐 두고 끝낸다. 사람이 세션을 닫고 `/do {키}` 를 다시 치면 새 세션이 그 변경만 구현한다.

| 요청 | 예 |
|---|---|
| 수정 지시 | "버튼 문구를 바꿔 줘", "이 경우엔 숨겨 줘" |
| 새 버그 | 테스트나 확인 중에 새로 발견한 결함 |
| 추가 설계 | 디자인 변경, 이벤트(GA·GTM·Braze 수집) 추가 |

바로 고치지 않는 이유는 두 가지다. 이 세션의 문맥이 이미 크다(검증 세션은 끝날 때 10만~23만 토큰). 그리고 설계 문서를 거치지 않은 수정은 리뷰 항목과 테스트 계획에 빠져, 리뷰와 검증이 그 변경을 보지 못한다.

## 1. 기록과 사전 확인

```
dobby_v2_change_open {키} check
dobby_session_log {키} {슬러그} change-{M} "변경 {M} 접수" {워크트리경로}
```

첫 줄이 거부하면(자동 실행이 돌고 있음) 아무것도 쓰지 않고 그 사실을 알린 뒤 끝낸다. 자동 실행이 상태 문서와 설계 문서를 읽고 있는 중이라, 변경 절을 먼저 쓰면 돌고 있는 리뷰 세션이 구현도 안 된 변경을 리뷰하게 된다.

M 은 설계 문서에 있는 `## 변경 N` 절의 가장 큰 N 에 1 을 더한 값이다. 없으면 1 이다. 이 세션이 이미 다른 단계로 기록돼 있어도 한 줄 더 남긴다.

## 2. 분석

요청이 새 버그면 원인을 코드에서 찾는다. 분석 원칙(`analysis-discipline.md`)을 그대로 따른다. 추가 설계면 디자인이나 이벤트 명세를 먼저 읽는다. A/B 테스트를 넣는 요청이면 1-3 의 A/B 규칙을 따른다. 설계 세션(1-2)과 같은 깊이로 하되, **이번 요청에 닿는 곳만** 본다.

## 3. 설계 문서에 변경 절을 덧붙인다

`design.md` 의 `## 리뷰 항목` 절 **뒤에** 덧붙인다. 앞의 본문은 고치지 않는다. 이미 통합된 내용의 기록이기 때문이다.

```markdown
## 변경 {M} — {한 줄 요약}

- **상태**: 구현 대기
- **종류**: 수정 지시 | 새 버그 | 추가 설계
- **요청**: (사람이 한 말을 그대로, 또는 요청 출처)
- **접수**: {YYYY-MM-DD HH:MM}
- **리뷰 시작 차수**: (5번에서 받은 값)차

### 무엇을 왜
### 고칠 코드
### 작업 순서
### 건드리지 않을 것
### 검증 명령
### 확인하지 못한 것
### 리뷰 항목
```

소절의 규칙은 1-3 의 "반드시 더 적는 것"과 `## 리뷰 항목` 절과 같다. 결정이 바뀌었으면 `## 결정과 근거` 표에 행을 더한다.

## 4. 테스트 계획을 맞춘다

먼저 이 변경이 고칠 파일로 `## 영향 번들` 표를 다시 판정한다(`${CLAUDE_PLUGIN_ROOT}/reference/bundle-scope.md`). 새로 영향이 된 번들이 생기면 표를 고친다. 그다음 이 변경을 확인할 시나리오를 `test-plan.md` 에 더한다. 영향인 번들마다 하나씩 둔다. 제목에 `(변경 {M})` 을 붙인다. 이 변경 때문에 기존 시나리오의 통과 기준이 바뀌면 그 시나리오도 고친다. 검증 세션은 계획 전체를 다시 돌린다. 앞서 고친 것이 깨지지 않았는지도 함께 보기 위해서다.

그다음 1-5 자족성 점검을 이 변경 절에 대해 돈다.

## 5. 확인받고 상태를 되돌린다

1-6 과 같은 형식으로 **변경 절만** 요약해 보여 준다(한 장 요약, 고칠 파일, 테스트 시나리오, 리뷰 항목). 끝의 "자동 실행" 과 "직접 실행" 안내도 1-6 과 같다. 사람이 고칠 곳을 말하면 1-6 의 규칙대로 고친다.

`auto` 실행(사람 없는 실행)에서는 변경 접수를 하지 않는다. 변경은 사람이 요청하는 것이기 때문이다.

사람이 "자동 실행" 이나 "직접 실행" 이라고 하면(옛 낱말 "확정"·"확정만"도 같다) 아래 순서로 부른다.

```
dobby_v2_change_open {키}          # 출력값 = 리뷰 시작 차수. 설계 문서 변경 절에 적는다
dobby_design_ack {키} 사용자         # 변경 절을 적은 뒤에 불러야 한다(설계 지문이 바뀌므로)
dobby_agent_state {키} {슬러그} 대기
dobby_event {키} "변경 {M} 확정 — 구현 세션으로 넘김"
```

`dobby_v2_change_open` 이 하는 일은 아래와 같다.

| 하는 일 | 왜 |
|---|---|
| 자동 실행이 돌고 있으면 거부한다 | 그 실행이 같은 상태 문서를 고치고 있다. 거부되면 사람에게 그대로 전하고 끝낸다. 설계 문서의 변경 절은 남겨 둔다 |
| 단계가 해결이면 해결 표시를 무른다 | 다시 작업하는 오더가 "해결"로 남지 않게 한다 |
| 다음 리뷰 차수의 빈 폴더를 연다 | 안 열면 리뷰 세션이 지난 차수의 결과에 덮어쓰고, 지적 0건인 옛 결과 때문에 리뷰 없이 통합으로 넘어간다 |
| 단계를 분석으로 바꾼다 | 단계 판정이 "분석 + 지금 설계와 같은 승인 = 구현"으로 읽는다 |

**"자동 실행"이면** 1-6 과 같이 `dobby_v2_autorun {키}` 로 자동 실행을 띄운다. **"직접 실행"이면** 띄우지 않는다.

Jira 상태는 건드리지 않는다. 이미 '해결됨'이면 다시 열지는 사람이 정한다. 보고에 지금 Jira 상태를 적는다.

## 6. 마무리

"세션을 닫는 법" 형식으로 알린다. `다음` 칸은 아래로 쓴다.

```
다음
  - 이 세션을 닫아 주세요. (/clear 또는 터미널 종료)
  - 새 세션에서: /do {키}  ← 변경 {M} 을 구현합니다
```

자동 실행을 띄웠으면 "자동 실행을 띄웠을 때" 형식을 쓴다.

# 공통 규칙

## 세션을 닫는 법 (모든 단계 공통 · 마지막에 반드시 한다)

단계를 마치면 아래 형식 그대로 알리고 **더 이상 아무것도 하지 않는다.**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{키} · {이번 단계 이름} 완료

한 일
  - (무엇을 했는지 한 줄씩)

남긴 것
  - {파일 경로} — (무엇이 적혀 있는지)

다음
  - 이 세션을 닫아 주세요. (/clear 또는 터미널 종료)
  - 새 세션에서: /do {키}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`이 세션을 닫아 주세요` 문구는 바꾸지 않는다. 입력 검사 훅(`hooks/prompt-guard.sh`, G20)이 이 문구로 단계가 끝났는지 안다.

**설계 세션이 자동 실행을 띄웠을 때**(1-6 에서 `dobby_v2_autorun` 이 0 을 돌려줌)는 `다음` 칸만 아래로 바꾼다.

```
다음
  - 구현부터 통합(작업 브랜치 커밋·푸시)까지 자동 실행이 시작됐습니다.
  - 진행 상황은 대시보드 {키} 오더 화면에서 볼 수 있습니다. 이 세션은 닫아도 자동 실행은 계속됩니다.
  - 통합까지 끝나면 배포(/dobby-ship {키} {환경})와 검증(/do {키})은 직접 실행해 주세요.
```

자동 배포 오더면 마지막 줄을 "통합 뒤 {환경} 배포와 검증까지 자동으로 이어 갑니다. 끝나거나 멈추면 슬랙과 메일로 알립니다."로 바꾼다.

마무리 명령과 같은 셸 호출 끝에 `dobby_v2_next_hint {키}` 를 붙인다. 출력이 있으면 `다음` 칸을 그 출력으로 바꾼다. 없으면 위 형식 그대로다.

**다음 단계를 이어서 하지 않는다.** 이어서 하면 이 스킬을 쓸 이유가 없어진다.

세션을 닫으라고 알린 뒤에 사람이 수정 지시나 새 요청을 하면, 그 요청은 **변경 접수**로 받는다. 그 자리에서 코드를 고치지 않는다.

## 알림 보내는 법 (자동 배포 오더)

슬랙 DM 과 메일로 같은 본문을 보낸다. 받는 사람은 `dobby-lib.sh` 의 `DOBBY_NOTIFY_SLACK`·`DOBBY_NOTIFY_EMAIL` 이다.

| 어디로 | 도구 |
|---|---|
| 슬랙 DM | `mcp__claude_ai_Slack__slack_send_message` (channel_id 에 받는 사람 아이디) |
| 메일 | `mcp__claude_ai_Gmail__send_message` (제목 `[dobby] {키} {첫 줄}`) |

도구가 안 보이면 연결이 늦은 것이니 다시 찾는다. 보내지 못해도 세션을 멈추지 않는다. `dobby_event` 로 "알림 못 보냄"을 남긴다.

## 사람에게 묻지 않는다 (설계 세션의 수정 대화는 예외)

이 스킬은 대시보드가 띄우는 헤드리스 실행(사람과 대화하지 않는 실행)에서도 돌아야 한다. 그래서 **구현부터 검증까지는 세션 안에서 사람의 답을 기다리지 않는다.**

예외는 하나다. `auto` 없이 실행한 설계 세션은 "1-6. 사람과 함께 설계 고치기"대로 사람과 대화한다. 설계가 틀리면 뒤의 모든 세션이 틀리기 때문에, 사람이 볼 수 있는 유일한 자리를 여기에 둔다. 그 대화 중에도 사람만 정할 수 있는 결정은 요약의 "확인이 필요한 것"에 올려 답을 받는다.

판단이 필요한 일이 나오면 둘 중 하나를 한다.

1. **스스로 정할 수 있는 것**: 정하고 `design.md` 의 `## 결정과 근거` 표에 **고른 답과 이유**를 적는다. 이유 없는 결정은 남기지 않는다.
2. **사람만 정할 수 있는 것**(제품 결정, 디자인 결정, 지울지 말지 같은 되돌리기 어려운 선택): 멈춘다. `## 확인이 필요했던 것` 에 **무엇을 왜 못 정했는지와 선택지**를 적고, 세션 종료 알림에 그 사실을 적는다.

## 보드의 상태표 (모든 세션 공통)

대시보드 오케스트레이션 보드는 메타 폴더의 진행 보드 문서(`orchestration.md`)의 `## 에이전트 상태표` 를 읽어 그린다. 상태는 `대기`, `분석`, `구현`, `리뷰`, `완료` 다섯 가지다. 보드는 `분석`, `구현`, `리뷰` 상태로 **30분 넘게 갱신이 없으면 "정체"** 로 표시한다.

v2 는 단계 사이에 세션이 없는 시간이 있다. 그래서 **세션을 끝낼 때 자기 행을 `대기` 로 돌린다.** 그러지 않으면 다음 세션을 기다리는 동안 보드가 정체로 경고한다.

| 세션 | 상태표 행 | 시작할 때 | 끝낼 때 |
|---|---|---|---|
| 설계 | 개발 담당 (`{슬러그}`, 이름 "분석/개발자") | `분석` (행을 새로 넣음) | 확정 전에는 `분석` 유지, 확정하면 `대기` |
| 이어받기 설계 | 개발 담당 | `분석` | 확정 전에는 `분석` 유지, 확정하면 `대기` |
| 구현 | 개발 담당 | `구현` | `대기` |
| 리뷰 | 리뷰 담당 (`review-agent`, 이름 "리뷰어") | `리뷰` + 라운드 번호 | `완료` |
| 수정 | 개발 담당 | `구현` + 수정 횟수 | `대기` |
| 통합 | 개발 담당 | 바꾸지 않음 | `완료` |
| 배포·검증·검증 실패 분석·판단 답 받기 | 행 없음 | 바꾸지 않음 | 바꾸지 않음 |

개발 담당 행의 라운드 칸은 **수정 횟수**다(리뷰 지적 수정과 검증 실패 수정을 합친 수, `dobby_fix_count`). 리뷰 담당 행의 라운드 칸은 리뷰 차수다.

개발 담당 슬러그는 세션마다 새로 만들지 않는다. 상태표에서 이름이 "분석/개발자" 인 행의 슬러그를 그대로 쓴다.

## 세션 기록

세션은 단계마다 새로 열린다. 나중에 어느 단계에서 무슨 일이 있었는지 되짚을 수 있도록 **각 세션은 시작 직후 자기 아이디를 기록한다.** 세션 아이디는 손으로 적지 않는다. 헬퍼가 지금 세션의 아이디(`CLAUDE_CODE_SESSION_ID`)를 읽어 적는다.

```
dobby_session_log {키} {슬러그} {하위 키} {단계 이름} {워크트리경로}
```

이 한 줄이 세 군데에 남긴다.

| 어디에 | 무엇을 | 왜 |
|---|---|---|
| 상태 문서 `## 세션` | 세션 아이디와 작업 경로를 **지금 세션으로 바꿔** 적는다 | 대시보드 "이어가기"가 이 값을 읽어 가장 최근 세션을 연다 |
| 상태 문서 `## 지난 세션` 표 | 시각, 단계, 세션 아이디, 작업 경로 한 줄을 **덧붙인다** | 지나간 세션을 `claude --resume {세션 아이디}` 로 다시 열어 복기한다 |
| 에이전트 기록 목록 `agent-logs.json` | `{슬러그: {하위 키: 대화 기록 파일 경로}}` | 대시보드 콘솔에서 단계별 대화 기록을 골라 본다 |

| 세션 | 슬러그 | 하위 키 | 단계 이름 |
|---|---|---|---|
| 설계 | 개발 담당 | `design` | 설계 |
| 이어받기 설계 | 개발 담당 | `takeover` | 이어받기 설계 |
| 구현 | 개발 담당 | `impl` | 구현 |
| 리뷰 | `review-agent` | `round-{N}` | {N}차 리뷰 |
| 수정 | 개발 담당 | `fix-{N}` (검증 실패면 `fix-test-{시각}`) | {N}차 수정 |
| 통합 | 개발 담당 | `integrate` | 통합 |
| 배포 | 개발 담당 | `ship-{시각}` | 배포 |
| 검증 | 개발 담당 | `verify` | 검증 |
| 검증 실패 분석 | 개발 담당 | `triage-{시각}` | 검증 실패 분석 |
| 판단 답 받기 | 개발 담당 | `answer-{시각}` | 판단 답 |

같은 세션에서 두 번 불러도 표에는 한 줄만 남는다.

`## 지난 세션` 표의 머리는 "세션 아이디"로 쓴다. 대시보드는 문서에서 처음 나오는 `세션 ID:` 꼴을 최신 세션으로 읽기 때문에, 지난 세션 표에는 그 꼴을 쓰지 않는다.

## 메타 파일은 늘리지 않는다

대시보드는 읽을 파일 이름을 코드에 적어 두고 읽는다. **새 이름의 파일을 만들면 대시보드에 보이지 않는다.** 그래서 v2 는 파일을 새로 만들지 않고 기존 문서에 절을 더한다.

| 담는 내용 | 어디에 |
|---|---|
| 개발 작업 지시서 | `design.md` |
| 리뷰 확인 목록 | `design.md` 의 `## 리뷰 항목` 절 |
| 테스트 케이스와 통과 기준 | `test-plan.md` |
| 구현 기록 | `implementation.md` |
| 리뷰 결과 | `reviews/round-{N}/review-agent.md` |
| 지난 세션 아이디 | `status.md` 의 `## 지난 세션` 표 |
| 진행 상태 | `status.md`, `orchestration.md` |

## 글은 한국어로

상태, 로그, 요약, 산출 문서의 진행 서술은 한국어와 존댓말로 쓴다.

사람이 읽는 글에는 오케스트레이션 내부 용어를 쓰지 않는다. 메타 파일은 역할로 부르고(`design.md` → "설계 문서"), 라운드 번호는 "1차 리뷰"로 풀고, 단계 코드와 슬러그는 쓰지 않는다. 심각도 표시(`[blocker]`·`[major]`·`[minor]`·`[nit]`)와 실제 코드 경로는 그대로 쓴다.

# 하지 않는 것

- **다음 단계를 이어서 하지 않는다.** 한 번 실행에 한 단계다.
- **진행 중에 들어온 요청을 그 자리에서 고치지 않는다.** 변경 접수로 설계 문서에 적고, 새 세션이 구현한다.
- **서브 에이전트를 띄우지 않는다.** 서브를 기다리려면 이 세션이 살아 있어야 한다. 영역이 여럿이면 영역마다 세션을 나눈다(동시에 하려면 터미널을 여러 개 연다).
- **정식 배포 브랜치로 PR 을 만들거나 머지하지 않는다.** `dobby-ship` 의 일이다. 자동 배포 오더의 배포 세션만 `dobby-ship` 절차로 한다.
- **상태를 "해결"로 올리지 않는다.** `dobby-resolve` 의 일이다.
- **`dobby-order` 의 메타를 건드리지 않는다.** 같은 형식을 쓰되 같은 오더를 두 스킬이 번갈아 맡지 않는다. 옮기려면 `dobby-migrate-v2` 를 쓴다.
