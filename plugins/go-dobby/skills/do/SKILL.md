# do

한 오더(이슈·작업)를 **여러 세션에 나눠** 진행하는 오케스트레이터다. `dobby-order` 를 대체하지 않는다 — 둘은 같은 메타 형식을 쓰고 목적만 다르다.

| | dobby-order | do |
|---|---|---|
| 한 번 실행에 하는 일 | 착수부터 통합까지 전부 | **한 단계만** |
| 세션 수 | 1개(서브 에이전트는 그 안에서) | 단계마다 새 세션 |
| 끝낼 때 | 다음 단계로 이어감 | **결과를 적고 세션을 닫으라고 알린 뒤 끝** |
| 사람에게 묻기 | 게이트에서 묻는다 | **설계 세션에서만** 요약을 보여 주고 함께 고친다. 나머지 세션은 스스로 정하고, 꼭 필요할 때만 질문을 남기고 끝낸다(자동 실행이 답을 기다린다) |
| 적합한 때 | 짧고 한 번에 끝나는 작업 | 길고 문맥이 커지는 작업 |

## 왜 이렇게 하나 (바꾸면 안 되는 근거)

모델을 한 번 부를 때마다 **그때까지 쌓인 대화 전부**가 입력으로 다시 들어간다. 그래서 비용은 "결과물의 크기"가 아니라 **"문맥의 크기 × 호출 횟수"** 로 정해진다.

한 오더를 실측한 숫자다.

| 주체 | 호출 수 | 평균 문맥 | 문맥 재읽기 누적 | 비중 |
|---|---|---|---|---|
| 메인 세션 1개 | 1,563회 | 444,372 토큰 | 684,000,000 토큰 | **96.6%** |
| 서브 에이전트 15명 전부 | 328회 | 57,000~98,000 토큰 | 24,400,000 토큰 | 3.4% |

**일을 누구에게 보내느냐는 거의 차이가 없다. 오케스트레이터 세션이 얼마나 오래 크게 살아 있느냐가 전부다.** 그래서 이 스킬은 자기 자신을 빨리 죽이는 것을 최우선으로 한다.

세션을 끊는 비용은 한 번뿐이다 — 새 세션 시작 약 70,000 토큰 + 메타 문서 읽기 약 20,000 토큰 = 약 90,000 토큰. 반면 안 끊으면 **호출 한 번마다** 44만 토큰이 다시 들어간다. 호출을 한 번이라도 더 할 거면 끊는 쪽이 이미 이득이다.

## 설정 (첫 실행 시 확인)

작업 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md` 의 "설정 절차"를 그대로 따른다**(config.env 는 읽기만). 이하 메타 경로는 `$ORCHESTRATION_META` 기준이고, 헬퍼는 `${CLAUDE_PLUGIN_ROOT}/reference/dobby-lib.sh` 의 `dobby_*` 를 쓴다.

분석할 때는 **`${CLAUDE_PLUGIN_ROOT}/reference/analysis-discipline.md` 원칙을 따른다**(추측 금지, 사실 확인, 모르면 docs 참조).

## 사용법

```
/do {이슈키|URL} [base={브랜치}] [step={단계}] [auto [env={dev|rc1|rc4}]]
/do {이슈키} 변경 {무엇을 바꾸거나 더할지}
/do {이슈키} 전체 테스트
/do {이슈키} light [env={dev|rc1|rc4}] {미리 분석한 내용}
/do {이슈키} 답 "{사람의 답}"
```

- `step` 을 주지 않으면 **지금 어느 단계인지 스스로 판정**한다(아래 "단계 판정").
- `base` 는 첫 세션에서만 쓴다. 안 주면 `$ORCHESTRATION_DEFAULT_BASE`.
- 같은 명령을 세션마다 그대로 다시 치면 그 다음 단계가 진행된다.
- `auto` 를 주면 설계 세션에서도 사람에게 묻지 않는다. 대시보드가 사람 없이 띄우는 실행(헤드리스 실행)용이다. 안 주면 설계 세션은 사람과 대화하며 설계를 확정한다(아래 "1-6. 사람과 함께 설계 고치기").
- `auto env={환경}` 을 주면 통합에서 멈추지 않고 그 환경 배포와 검증까지 사람 없이 간다(**자동 배포 오더**). 상태 문서 `## 현재 단계` 의 `- **자동 배포 환경**: {환경}` 줄이 표지다. stage·cloud_live 는 받지 않는다. `TASK-` 작업은 `env=` 를 받지 않는다(통합에서 PR 을 만들고 끝난다). 설계와 근거는 이 폴더의 `auto-mode.md`.
- `변경 {내용}` 을 주면 단계와 상관없이 **변경 접수**를 한다(아래 "변경 접수"). 어느 단계의 세션에서든, 사람이 대화로 수정을 지시하거나 새 버그·추가 설계를 말해도 같다.
- 검증은 기본으로 **변경의 영향 범위만** 돈다(테스트 계획 `## 검증 범위` 표, `steps/change.md` 4). `전체 테스트` 를 주면 단계 판정 전에 `dobby_testplan_scope_all {키} "전체 테스트 인자"` 를 불러 범위를 전체로 바꾼 뒤 평소처럼 단계를 판정한다. 열린 회차가 있으면 범위 밖으로 건너뛴 시나리오도 남은 묶음으로 다시 돈다. 사람이 대화로 전체 테스트를 명시해도 같다. 사람이 명시하지 않았는데 스스로 전체로 넓히지 않는다.
- `답 "{내용}"` 을 주면 사람이 대화창 밖(화면의 답 입력 칸 등)에서 미리 적은 답을 가지고 사람 없이 도는 세션이다. 단계 판정은 평소대로 하고, 그 단계에서 사람에게 물을 자리에 이 내용을 사람의 답으로 쓴다. 다시 묻지 않는다. 판단 답 차례(보류)면 `steps/answer.md`, 설계 확인 차례면 `steps/design.md` 1-6 의 답 처리로 받는다. 내용이 묻는 것과 맞지 않아 정할 수 없으면 새 질문을 `## 확인이 필요했던 것` 에 적고 `판단요청` 으로 끝낸다. 이 쓰임은 보류된 옛 오더와 터미널 사용을 위한 것이다. 질문(`ask.json`)에는 대시보드나 오피스의 질문 창에서 답한다.
- `light` 를 주면 사람이 미리 분석한 가벼운 변경을 **세션 하나에서** 착수부터 배포·대상 시나리오 검증까지 한다. 리뷰는 하지 않는다. 사람 확인은 한 번이고 그 답이 커밋·배포 동의다. `env=` 가 없으면 그 확인 때 묻는다. 본문은 `steps/light.md`.

### 설계 확정 뒤 자동으로 끝까지 돌리기

설계를 사람과 확정한 뒤에는 이 스킬 폴더의 `run.sh` 로 남은 단계를 자동으로 돌릴 수 있다. 단계마다 `claude -p "/do {키}"` 를 새로 실행한다. 실행이 끝나면 그 프로세스가 사라지므로 사람이 세션을 닫을 일이 없다.

**설계 세션이 "자동 실행" 답을 받으면 이 자동 실행을 직접 띄운다**(1-6). 그래서 사람은 설계만 확정하면 구현부터 통합(작업 브랜치 커밋·푸시)까지 손댈 일이 없다. "전체 실행" 답이면 배포 환경을 물어 자동 배포 오더로 만든 뒤 띄워, 배포와 검증까지 간다. 띄우는 일은 `dobby_v2_autorun {키}` 가 대시보드의 '자동 실행'을 불러서 한다. 대시보드가 띄워야 터미널을 닫아도 실행이 살아 있고, 진행이 대시보드 오더 화면에 보인다.

**부모는 `run.sh` 이고, Claude 세션이 아니다.** 부모가 하는 일은 상태 문서의 단계값을 읽고 다음 세션을 띄우는 것뿐이라 판단이 필요 없다. 셸이 맡으면 부모 몫의 토큰이 0이다. Claude 세션이 부모가 되면 자식이 끝날 때마다 깨어나 자기 문맥 전체를 다시 읽는다(설계 세션 문맥 실측 17만~27만 토큰, 단계마다 약 2회). Agent 도구의 서브 에이전트를 자식으로 쓰면 자식의 세션 아이디가 부모와 같아져 `## 지난 세션` 표와 `claude --resume` 복기가 깨진다.

```bash
run.sh {키} [--mode {권한 모드}] [--max {최대 세션 수}] [--with-test] [--approve-commit]
```

| 인자 | 뜻 | 기본값 |
|---|---|---|
| `--mode` | `claude` 의 `--permission-mode` 값. 화면 없는 실행은 권한 확인 창을 띄울 수 없어서 미리 정한다 | `auto` |
| `--max` | 이번 실행에서 띄울 세션 수의 상한. 열린 회차를 잇는 검증 묶음 세션은 하나씩 더해 센다 | 10 (자동 배포 오더는 20) |
| `--with-test` | 통합 뒤 검증까지 돈다. 검증은 배포된 화면을 보므로 배포가 끝난 뒤에 준다. `TASK-` 작업에는 듣지 않는다 | 없음(통합에서 멈춤) |
| `--approve-commit` | 사람이 커밋·푸시를 미리 승인한 실행이다. 세션마다 그 승인을 지시로 덧붙인다(`--append-system-prompt`). 없으면 통합 세션이 사용자 지침에 따라 동의를 묻고 멈출 수 있다. 승인 범위는 오더 작업 브랜치의 커밋·푸시뿐이다 | 없음 |

멈추는 경우는 아래와 같다. 멈출 때는 이유와 함께, 마지막 세션을 다시 여는 `claude --resume {세션 아이디}` 명령을 알려 준다.

| 멈추는 경우 | 이유 |
|---|---|
| 설계가 확정되지 않았다 | 설계는 사람과 함께 확정해야 한다 |
| 판단 답 차례다(보류) | 사람만 정할 수 있는 일이 설계 문서 `## 확인이 필요했던 것` 에 있다(옛 방식으로 멈춘 오더) |
| 질문에 8시간 동안 답이 없다 | 질문은 남는다. 그 뒤 답하면 대시보드가 자동 실행을 다시 띄운다 |
| 켜진 담당자의 일이 모두 끝났다 | 테스터가 없는 오더(문서, 조사, 화면 확인이 필요 없는 개발)는 여기서 끝난다 |
| 통합까지 끝났다(`--with-test` 없음) | 검증은 배포 뒤에 해야 의미가 있다 |
| `TASK-` 작업의 통합이 끝났다 | 통합 세션이 PR 을 만들면 사람이 머지할 차례다. 검증은 하지 않는다 |
| 검증을 전부 통과했다 | 할 일이 끝났다 |
| 세션이 끝났는데 아무것도 바뀌지 않았다 | 사람 판단이 필요해 스킬이 멈췄을 가능성이 크다 |
| 세션이 오류로 끝났다 | 원인을 사람이 봐야 한다 |
| 세션 수 상한에 닿았다 | 끝없이 도는 것을 막는다 |
| (자동 배포 오더) 배포 표에 막힘(⚠)이 있다 | 배포 세션이 스스로 풀지 못한 일이다 |
| (자동 배포 오더) 리뷰봇 리뷰가 30분, 빌드가 30분 동안 끝나지 않았다 | 기다려도 오지 않을 가능성이 크다 |

**질문이 열리면 멈추지 않고 기다린다.** 세션이 질문을 남기고 끝나면 `run.sh` 가 셸에서 답을 기다린다(기다리는 동안 토큰 0). 답이 오면 테스터와 배포담당의 질문은 그 세션을 이어 띄우고(`claude -p --resume`, 문맥이 12만 토큰 이하일 때, 그 세션이 시작한 폴더에서), 기획자와 그 밖의 질문은 새 세션을 띄운다. 새 세션은 시작 헬퍼 결과로 질문과 답을 받는다.

멈추면 대시보드가 그 오더를 MY(사람이 할 일 있음)로 올리고 알림 카드를 띄운다. 리뷰봇과 빌드는 세션이 아니라 `run.sh` 가 기다린다(`dobby_v2_ship_next` 가 `wait-review`·`wait-build` 를 내는 동안). 세션마다 배포 승인 지시도 덧붙인다.

세션이 끝날 때마다 이벤트 로그에 "자동 실행 세션 N 종료 — 시작 단계, 지금 단계, 새 세션인지 이어 쓴 세션인지, 세션 아이디"를 한 줄 남긴다. 세션 안에서도 공통 규칙 "세션 기록"대로 아이디를 남긴다.

#### 세션 이어 쓰기 판정

기본은 단계마다 새 세션이다. 다음 일이 수정이고, 직전 세션 문맥이 12만 토큰 이하이며, 5분 안일 때만 이어 쓴다(`dobby_v2_reuse_ok`). 근거와 비용은 이 폴더의 `session-reuse.md` 에 있다.

자동 배포 오더(배포·테스트까지 사람 없이 돌리기)의 설계와 근거는 이 폴더의 `auto-mode.md` 에 있다.

## 시작과 끝 (실행하면 가장 먼저 하는 일 · 마지막에 하는 일)

이 스킬은 담당자 여섯 가운데 **오더에 켜진 담당자**가 차례로 일한다. 세션 하나가 담당자 하나의 일 하나를 한다.

| 담당자 | 상태표 슬러그 | 맡는 단계 | 원칙 |
|---|---|---|---|
| 기획자 | `analysis-agent` | 설계, 설계 확인, 변경 접수, 설계 다시 보기(검증 실패 분석 포함), 판단 답 | 설계를 정하고, 문제가 생기면 설계를 바꾼다. 설계를 바꾸는 것은 기획자뿐이다 |
| 개발자 | 개발 담당 슬러그(이름이 "개발자"인 행) | 구현, 수정 | 설계대로 구현한다. 설계의 동작과 범위를 바꾸지 않는다 |
| 산출자 | `produce-agent` | 산출, 산출물의 수정 | 문서와 조사를 만든다. 주장마다 출처를 적는다 |
| 리뷰어 | `review-agent` | 리뷰 | 설계를 기준으로 정확성과 다른 곳에 미치는 영향을 본다 |
| 배포담당 | `deploy-agent` | 통합(커밋·푸시, 문서 올리기), 배포 | 절차를 진행한다. 변경요청을 받으면 고치지 않고 넘긴다 |
| 테스터 | `test-agent` | 검증 | 배포 환경에서 화면을 확인한다 |

**켜진 담당자**는 설계 세션이 이슈를 읽은 직후 정해 상태 문서 `## 현재 단계` 에 `- **담당자**: 기획자, 산출자, 리뷰어` 한 줄로 적는다(`dobby_v2_set_roles`, `steps/design.md` 1-1-2). 종류를 고르지 않고 필요한 담당자를 켠다. 한번 켠 담당자는 끄지 않고, 일이 없어지면 "할 일 없음"과 이유를 남겨 끝낸다(`dobby_v2_role_skip`). 이 줄이 없는 오더(이 기능이 생기기 전의 오더)는 산출자를 뺀 다섯으로 본다.

| 오더 | 켜는 담당자 | 단계 |
|---|---|---|
| 개발 | 기획자·개발자·리뷰어·배포담당·테스터 | 착수 → 설계 → 설계 확인 → 구현 → 리뷰 ↔ 수정 → 통합 → 배포 → 검증 |
| 문서 | 기획자·산출자·리뷰어·배포담당 | 착수 → 설계 → 설계 확인 → 산출 → 리뷰 ↔ 수정 → 통합(문서 올리기 포함) |
| 조사 | 기획자·산출자(남이 쓰면 리뷰어도) | 착수 → 설계 → 설계 확인 → 산출 → (리뷰 ↔ 수정) |
| 가벼운 일 | — | 세션 하나(`light`) |

개발자와 산출자를 함께 켜면 산출물마다 **앞**(구현의 근거가 되는 조사 — 구현 전에 산출)인지 **뒤**(구현 결과를 쓰는 설명 문서 — 검증 뒤에 산출)인지를 설계 문서 `## 산출물` 표에 적는다.

**시작은 시작 헬퍼가 한다.** `/do {키} …` 를 입력하면 입력 검사 훅이 `dobby_v2_begin {키} {인자}` 를 먼저 부르고, 그 결과를 세션 문맥에 `[go-dobby 시작 헬퍼]` 로 붙인다. 결과가 붙어 있으면 다시 부르지 않는다. 붙어 있지 않으면(훅이 꺼졌거나 실패) 직접 한 번 부른다.

시작 헬퍼가 하는 일은 아래와 같다.

1. 단계 밖 변경을 반영한다(`dobby_v2_drift_apply`, 훅이 먼저 부른다).
2. 단계 판정 헬퍼(`dobby_v2_step`)로 이번 세션의 단계, 담당자, 지시 문서를 정한다.
3. 켜진 담당자의 행을 맞추고, 단계값을 적고, 세션을 기록하고, 자기 행을 `작업중` 으로 적는다.
4. 사람이 읽는 줄로 결과를 낸다. 끝에 두 가지가 더 붙을 수 있다.
   - `지킬 것:` — 이번 세션 담당자가 지킬 줄이다(개발자·리뷰어·산출자·배포담당). 그대로 따른다. 지시 문서에는 이 줄이 없다.
   - `질문과 답:` — 앞 세션이 남긴 질문에 사람이 답했다. 그 답을 사람의 답으로 쓰고 다시 묻지 않는다. 시작 헬퍼가 그 질문을 이미 닫았다.

| 첫 줄 | 뜻 | 할 일 |
|---|---|---|
| `시작함` · `이미 시작됨` | 이번 세션의 일이 정해졌다 | `지시 문서:` 줄의 파일 **하나만** 읽고 그대로 한다 |
| `시작 전(메타 없음)` | 처음 실행하는 오더다 | `지시 문서:` 줄의 문서를 읽고 처음부터 한다. 메타를 만든 뒤 그 문서가 말하는 자리에서 시작 헬퍼를 다시 부른다 |
| `멈춤` | 이 세션이 할 일이 없다(끝난 오더, 사람 차례, 기다림, dobby-order 오더, 모르는 단계값) | `이유:` 줄을 그대로 알리고 끝낸다 |
| `겹침` | 다른 세션이 이 오더를 작업 중이다 | 그 사실을 알리고 끝낸다. 아무것도 쓰지 않는다 |

다른 단계의 지시 문서는 읽지 않는다. 모든 세션이 모든 단계의 본문을 읽으면 호출마다 그만큼 다시 읽기 때문이다(나누기 전 이 파일 하나가 약 3만 3,800 토큰). 지시 문서는 `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/` 에 있다.

**인자가 판정을 바꾼다.** `light` 가 있으면 `light.md`, `변경` 이 있으면 `change.md` 가 나온다. 인자 없이 시작한 세션에서 사람이 수정 지시·새 버그·추가 설계를 말해도 `change.md` 를 읽고 **변경 접수**로 받는다. 끝난 오더와 검증을 통과한 오더도 마찬가지다.

**끝은 끝 헬퍼가 한다.** 지시 문서의 마지막 줄은 언제나 `dobby_v2_end {키} {결과}` 다. 끝 헬퍼는 고른 결과가 사실과 맞는지 확인한다. 예를 들어 구현 완료면 작업 폴더가 바뀌었는지, 리뷰 통과면 막는 지적이 0건인지 본다. 맞으면 상태를 다음 차례로 옮기고 세션 닫기 안내의 `다음` 칸을 낸다. 맞지 않으면 `거부: {이유}` 를 내고 아무것도 바꾸지 않는다. 그때는 빠진 일을 하고 다시 부른다. 거부를 피하려고 결과를 바꾸지 않는다.

| 단계 | 결과 | 다음 |
|---|---|---|
| 설계 · 설계 확인 | `사람확인` · `확정` · `변경접수` · `재배포` · `재검증` · `판단요청` | 확정이면 구현(앞에 만들 산출물이 있거나 개발자가 없으면 산출) |
| 설계 다시 보기(검증 실패 분석 포함) | `변경접수` · `재배포` · `재검증` · `돌려보냄 "{이유}"` · `판단요청` | 돌려보냄은 설계는 맞고 구현이 달랐을 때다. 변경 절 없이 수정(또는 구현·산출)으로 되돌린다 |
| 구현 · 수정 | `완료` (light 는 `통합완료`) · `설계문제 "{이유}"` | 설계문제는 설계대로 할 수 없거나 리뷰가 3번을 넘었을 때다. 기획자가 설계를 다시 본다 |
| 산출 | `완료` · `설계문제 "{이유}"` | 완료면 리뷰어(켜져 있으면). 아니면 구현(앞 산출물), 통합(커밋할 문서나 올릴 곳이 있음), 끝 |
| 리뷰 | `통과` · `지적 {건수}` | 지적이면, 막는 지적에 "설계대로 구현됨"이 하나라도 있으면 기획자, 아니면 만든 담당자의 수정 |
| 통합 | `완료` | 배포(산출물만 확정했으면 끝) |
| 배포 | `기다림` · `배포확인` · `사람승인` · `막힘` · `리뷰지적 "{지적 요약}"` | 리뷰지적은 변경요청으로 PR 을 닫았을 때다. 기획자가 설계를 다시 본다 |
| 검증 | `묶음남음` · `통과` · `실패` | 통과 뒤에 만들 산출물이 있으면 산출 |
| 어느 단계든 | `막힘 "{이유}"`(사람이 풀어야 함) · `넘김 "{이유}"`(다음 `/do` 가 이어 감) · `질문`(질문을 남김) | 질문이면 단계는 그대로 두고 자동 실행이 답을 기다린다 |

**단계값은 "지금 누구 차례인가"다.** 14가지다.

| 단계 | 차례 | 단계 | 차례 |
|---|---|---|---|
| 착수 | 기획자(설계 전) | 통합 | 배포담당(커밋·푸시, 문서 올리기) |
| 설계 | 기획자 | 배포 | 배포담당(사람의 `/dobby-ship` 또는 자동 실행) |
| 설계확인 | 사람(설계 요약에 답하기) | 검증 | 테스터 |
| 구현 | 개발자 | 실패분석 | 기획자(설계 다시 보기) |
| 산출 | 산출자 | 보류 | 사람(판단 답 — 옛 방식) |
| 리뷰 | 리뷰어 | 해결 · 종료 | 끝난 오더 |
| 수정 | 개발자(산출물이면 산출자) | | |

`실패분석` 은 기획자에게 넘어간 상태 전부를 가리킨다(검증 실패, 구현 중 설계대로 할 수 없음, 리뷰가 짚은 설계의 결함, 내부 리뷰가 3번을 넘김, PR 변경요청). 화면에는 "설계 다시 보기"로 보인다. 검증 실패가 아닌 이유로 넘어오면 상태 문서에 `- **다시 설계**: {이유}` 줄이 생기고, 기획자가 끝내면 지워진다.

**테스터가 없는 오더는 단계값이 끝을 말하지 않는다.** 켜진 담당자가 모두 `완료` 이고 답 없는 질문이 없으면 끝난 오더다. 단계 판정은 "할 일을 모두 마쳤습니다"로 멈추고, `/dobby-resolve {키}` 로 해결 처리한다. 테스터가 켜진 오더는 지금처럼 검증 통과가 끝이다.

옛 규칙의 오더(단계값이 "끝난 일"을 뜻하던 오더)는 시작 헬퍼나 대시보드가 처음 볼 때 한 번 옮긴다. 옮긴 오더에는 상태 문서에 `- **단계 규칙**: 다섯 담당자` 줄이 생긴다. 새 오더에도 같은 문구가 적힌다. 담당자가 여섯이 된 뒤에도 이 문구는 바꾸지 않는다(헬퍼와 대시보드가 이 글자를 그대로 찾는다).

**v2 오더의 표지는 상태 문서의 `## 지난 세션` 표다.** 이 표가 없고 단계가 `착수` 도 아니면 `dobby-order` 가 만든 메타라 시작 헬퍼가 멈춘다. 두 스킬이 한 오더를 번갈아 맡으면 서로의 상태 기록을 엉뚱하게 읽기 때문이다. `/dobby-migrate-v2 {키}` 로 옮긴 뒤 이어 간다.

"설계 승인 기록"은 `$ORCHESTRATION_META/{키}/design-ack.json` 의 `사용자` 또는 `auto` 항목이다. 그 값이 `dobby_design_rev {키}`(지금 설계 문서의 지문, 내용이 바뀌면 달라지는 짧은 값)와 같으면 승인된 설계 그대로다.

# 공통 규칙

## 세션을 닫는 법 (모든 단계 공통 · 마지막에 반드시 한다)

단계를 마치면 아래 형식 그대로 알리고 **더 이상 아무것도 하지 않는다.**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{키} · {이번 단계 이름} 완료

한 일
  - (무엇을 했는지 한 줄씩)

남긴 것
  - {파일 경로} — (무엇이 적혀 있는지)

다음
  - 이 세션을 닫아 주세요. (/clear 또는 터미널 종료)
  - 새 세션에서: /do {키}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`이 세션을 닫아 주세요` 문구는 바꾸지 않는다. 입력 검사 훅(`hooks/prompt-guard.sh`, G20)이 이 문구로 단계가 끝났는지 안다.

**설계 세션이 자동 실행을 띄웠을 때**(1-6 에서 `dobby_v2_autorun` 이 0 을 돌려줌)는 `다음` 칸만 아래로 바꾼다.

```
다음
  - 구현부터 통합(작업 브랜치 커밋·푸시)까지 자동 실행이 시작됐습니다.
  - 진행 상황은 대시보드 {키} 오더 화면에서 볼 수 있습니다. 이 세션은 닫아도 자동 실행은 계속됩니다.
  - 통합까지 끝나면 배포(/dobby-ship {키} {환경})와 검증(/do {키})은 직접 실행해 주세요.
```

자동 배포 오더면("전체 실행" 답 포함) 첫 줄을 "구현부터 {환경} 배포와 검증까지 자동 실행이 시작됐습니다."로, 마지막 줄을 "끝나거나 멈추면 대시보드에 알림이 뜹니다."로 바꾼다.

`TASK-` 작업이면 마지막 줄을 "통합에서 기준 브랜치로 PR 까지 만들고 끝납니다. PR 은 직접 머지해 주세요."로 바꾼다.

`다음` 칸은 끝 헬퍼가 낸 줄을 그대로 옮긴다. 끝 헬퍼는 이 단계가 끝난 상태를 기준점으로 남기고(다음 `/do` 가 이 기준점과 비교해 단계 밖 변경을 찾는다), 사람이 할 일이 있으면 그 명령을 함께 낸다.

**다음 단계를 이어서 하지 않는다.** 이어서 하면 이 스킬을 쓸 이유가 없어진다.

세션을 닫으라고 알린 뒤에 사람이 수정 지시나 새 요청을 하면, 그 요청은 `steps/change.md` 를 읽고 **변경 접수**로 받는다. 그 자리에서 코드를 고치지 않는다.

## 알림 보내는 법 (자동 배포 오더)

알림은 셸 한 줄로 남긴다.

    dobby_v2_notify {키} "{본문}"

이 헬퍼는 본문 첫 줄을 이벤트 로그에 남기기만 한다. 사람에게 띄우는 알림은 대시보드가 상태 문서를 읽어 만든다. 사람이 읽고 답해야 할 내용은 알림 본문이 아니라 질문에 자세히 적는다(아래 "사람에게 묻는 법").

슬랙·메일 도구는 찾지도 부르지도 않는다.

## 스스로 정하고, 꼭 필요할 때만 묻는다 (설계 세션의 수정 대화는 예외)

이 스킬은 대시보드가 띄우는 헤드리스 실행(사람과 대화하지 않는 실행)에서도 돌아야 한다. 그래서 **구현부터 검증까지는 세션 안에서 사람의 답을 기다리지 않는다.**

예외는 하나다. `auto` 없이 실행한 설계 세션은 "1-6. 사람과 함께 설계 고치기"대로 사람과 대화한다. 설계가 틀리면 뒤의 모든 세션이 틀리기 때문에, 사람이 볼 수 있는 유일한 자리를 여기에 둔다. 그 대화 중에도 사람만 정할 수 있는 결정은 요약의 "확인이 필요한 것"에 올려 답을 받는다.

판단이 필요한 일이 나오면 둘 중 하나를 한다.

1. **스스로 정한다(기본).** 기획자는 정하고 `design.md` 의 `## 결정과 근거` 표에 **고른 답과 이유**를 적는다. 사람의 확정 없이 스스로 정한 줄은 `왜` 칸을 `자동 결정 —` 으로 시작한다. 이유 없는 결정은 남기지 않는다. 기획자가 아닌 담당자는 설계를 바꾸는 판단을 하지 않고 기획자에게 넘긴다(끝 결과 `설계문제`, `리뷰지적`, 리뷰의 `지적`).
2. **사람에게 묻는다(아래 경우에만).** 질문을 남기고 끝낸다. 단계를 보류로 바꾸지 않는다. 자동 실행이 셸에서 답을 기다렸다가 이어 간다.

| 사람에게 묻는 경우 | 이유 |
|---|---|
| 이슈가 요구한 결과 자체를 바꿔야 풀린다 | 이슈의 목적은 세션이 바꿀 수 없다 |
| 되돌아간 횟수가 상한을 넘었다: PR 변경요청 3번, 검증 실패 2번, 기획자가 다시 설계한 뒤에도 내부 리뷰가 안 닫힘 | 같은 자리를 돌고 있다 |
| 사람만 할 수 있는 일이다: 로그인, 시험 데이터 값, 아티팩트로 올리기 | 세션에 수단이 없다 |
| 원인을 근거로 가를 수 없다 | 틀린 방향으로 고치게 된다 |
| 리뷰봇이나 빌드가 30분 넘게 오지 않는다 | 자동 실행(셸)이 묻는다 |

그 밖은 스스로 정한다. stage 와 cloud_live 는 지금처럼 훅과 헬퍼가 막는다.

## 사람에게 묻는 법

질문을 남겨야 할 때만 `${CLAUDE_PLUGIN_ROOT}/skills/do/ask.md` 를 읽고 그대로 한다. 일곱 칸(질문 한 줄, 무슨 일이 있었나, 왜 스스로 정하지 못했나, 지금까지 해 본 것, 방법들, 답하는 방식, 답한 뒤)을 채운 질문을 헬퍼로 남기고 끝 헬퍼를 부른다.

```
dobby_v2_ask {키} file {질문 초안 파일}
dobby_v2_end {키} 질문
```

- 단계는 그대로 둔다(보류로 바꾸지 않는다). 자동 실행이 셸에서 답을 기다리고, 답이 오면 이어 간다. 테스터와 배포담당의 질문은 그 세션이 이어서 띄워지고, 그 밖에는 새 세션이 띄워진다. 어느 쪽이든 시작 헬퍼 결과에 `질문과 답:` 이 붙는다.
- **대화형 세션(사람이 터미널에 있음)에서는 질문을 남기지 않고 그 자리에서 묻는다.**
- 옛 방식(설계 문서 `## 확인이 필요했던 것` 에 적고 `판단요청` 으로 끝내 단계를 보류로 바꾸는 것)과 `/do {키} 답 "…"` 은 보류된 옛 오더와 자동 실행 없이 터미널에서만 돌리는 오더를 위해 남아 있다. 자동 실행이 띄운 세션은 쓰지 않는다.

## 보드의 상태표 (모든 세션 공통)

대시보드 오케스트레이션 보드는 진행 보드 문서(`orchestration.md`)의 `## 에이전트 상태표` 를 읽어 그린다. 켜진 담당자가 한 행씩 있다(담당자 줄이 없는 오더는 다섯). 상태는 여섯 가지다.

| 상태 | 뜻 |
|---|---|
| 대기 | 차례가 아니다. 또는 차례가 왔지만 아직 세션이 없다 |
| 작업중 | 세션이 이 일을 하고 있다 |
| 기다림 | 자동 실행이 리뷰봇이나 빌드를 기다린다 |
| 사람 차례 | 사람이 할 일이 있다. `사람 할 일` 칸에 명령이 적힌다. 질문을 남긴 담당자도 답을 받을 때까지 이 상태다 |
| 막힘 | 스스로 풀지 못했다. 설명 칸에 이유, `사람 할 일` 칸에 할 일이 적힌다 |
| 완료 | 이 담당자의 일이 끝났다. 일이 없어진 담당자는 설명 칸이 "할 일 없음 — {이유}"다 |

**세션은 상태를 직접 바꾸지 않는다.** 시작 헬퍼가 자기 행을 `작업중` 으로, 끝 헬퍼가 자기 행과 다음 담당자 행을 바꾼다. 테스터 행의 진행(회차, 성공·실패 수)은 회차 헬퍼가, 배포담당 행의 진행은 배포 표 헬퍼(`dobby_ship_stage`)가 적는다.

세션이 끝 헬퍼를 부르지 않고 닫히면 작업 표시 훅이 그 행을 `사람 차례` "세션 끊김"으로 돌린다. `사람 할 일` 칸에는 `/do {키}` 와 `claude --resume {세션 아이디}` 가 적힌다. 자동 실행 중이면 자동 실행이 세션마다 남은 `작업중` 행을 `대기` 로 돌린다.

개발자 행의 라운드 칸은 수정 횟수(`dobby_fix_count`), 산출자 행은 산출물을 고친 횟수, 리뷰어 행은 리뷰 차수, 테스터 행은 회차 수다.

## 세션 기록

세션은 단계마다 새로 열린다. 나중에 어느 단계에서 무슨 일이 있었는지 되짚을 수 있도록 시작 헬퍼가 세션 아이디(`CLAUDE_CODE_SESSION_ID`)를 기록한다(`dobby_session_log`). 세션이 따로 부르지 않는다.

| 어디에 | 무엇을 | 왜 |
|---|---|---|
| 상태 문서 `## 세션` | 세션 아이디와 작업 경로를 **지금 세션으로 바꿔** 적는다 | 대시보드 "이어가기"가 이 값을 읽어 가장 최근 세션을 연다 |
| 상태 문서 `## 지난 세션` 표 | 시각, 단계, 세션 아이디, 작업 경로 한 줄을 **덧붙인다** | 지나간 세션을 `claude --resume {세션 아이디}` 로 다시 열어 복기한다 |
| 에이전트 기록 목록 `agent-logs.json` | `{슬러그: {하위 키: 대화 기록 파일 경로}}` | 대시보드 콘솔에서 단계별 대화 기록을 골라 본다 |

| 세션 | 슬러그 | 하위 키 | 단계 이름 |
|---|---|---|---|
| 설계 | 기획자 | `design` | 설계 |
| 이어받기 설계 | 기획자 | `takeover` | 이어받기 설계 |
| 변경 접수 | 기획자 | `change-{M}` | 변경 {M} 접수 |
| 검증 실패 분석 | 기획자 | `triage-{시각}` | 검증 실패 분석 |
| 설계 다시 보기(그 밖의 이유로 넘어옴) | 기획자 | `triage-{시각}` | 설계 다시 보기 |
| 판단 답 받기 | 기획자 | `answer-{시각}` | 판단 답 |
| 구현 | 개발자 | `impl` (변경이면 `impl-change-{M}`) | 구현 (변경 {M} 구현) |
| 수정 | 개발자 | `fix-{N}` | {N}차 수정 |
| 산출 | 산출자 | `produce` | 산출 |
| 산출물 수정 | 산출자 | `produce-fix-{N}` | {N}차 산출 수정 |
| 리뷰 | 리뷰어 | `round-{N}` | {N}차 리뷰 |
| 통합(문서 올리기 포함) | 배포담당 | `integrate` | 통합 |
| 배포 | 배포담당 | `ship-{시각}` | 배포 |
| 검증 | 테스터 | `verify-{묶음}` (예: `verify-V1`) | 검증 {묶음} |
| light | 개발자 | `light` | 가벼운 변경 |

같은 세션에서 두 번 불러도 표에는 한 줄만 남는다.

`## 지난 세션` 표의 머리는 "세션 아이디"로 쓴다. 대시보드는 문서에서 처음 나오는 `세션 ID:` 꼴을 최신 세션으로 읽기 때문에, 지난 세션 표에는 그 꼴을 쓰지 않는다.

## 메타 파일은 늘리지 않는다

대시보드는 읽을 파일 이름을 코드에 적어 두고 읽는다. **새 이름의 파일을 만들면 대시보드에 보이지 않는다.** 그래서 v2 는 파일을 새로 만들지 않고 기존 문서에 절을 더한다.

| 담는 내용 | 어디에 |
|---|---|
| 개발 작업 지시서 | `design.md` |
| 리뷰 확인 목록 | `design.md` 의 `## 리뷰 항목` 절 |
| 테스트 케이스와 통과 기준 | `test-plan.md` |
| 구현 기록 | `implementation.md` |
| 산출물 명세 | `design.md` 의 `## 산출물` 절 |
| 산출 기록 | `produce.md` (산출물이 여럿이면 `produce-{이름}.md`). 올린 주소는 `## 올린 곳` 절에 `- {종류}: {주소}` |
| 산출물 | 저장소 문서, 또는 `deliverables/` |
| 열린 질문 | `ask.json` (닫히면 `asks/`) |
| 켜진 담당자 | `status.md` 의 `- **담당자**:` 줄 |
| 리뷰 결과 | `reviews/round-{N}/review-agent.md` |
| 지난 세션 아이디 | `status.md` 의 `## 지난 세션` 표 |
| 진행 상태 | `status.md`, `orchestration.md` |

## 글은 한국어로

상태, 로그, 요약, 산출 문서의 진행 서술은 한국어와 존댓말로 쓴다.

사람이 읽는 글에는 오케스트레이션 내부 용어를 쓰지 않는다. 메타 파일은 역할로 부르고(`design.md` → "설계 문서"), 라운드 번호는 "1차 리뷰"로 풀고, 단계 코드와 슬러그는 쓰지 않는다. 심각도 표시(`[blocker]`·`[major]`·`[minor]`·`[nit]`)와 실제 코드 경로는 그대로 쓴다.

# 하지 않는 것

- **다음 단계를 이어서 하지 않는다.** 한 번 실행에 한 단계다. `light` 실행만 예외다(`steps/light.md`).
- **진행 중에 들어온 요청을 그 자리에서 고치지 않는다.** 변경 접수로 설계 문서에 적고, 새 세션이 구현한다.
- **서브 에이전트를 띄우지 않는다.** 서브를 기다리려면 이 세션이 살아 있어야 한다. 영역이 여럿이면 영역마다 세션을 나눈다(동시에 하려면 터미널을 여러 개 연다).
- **정식 배포 브랜치로 PR 을 만들거나 머지하지 않는다.** `dobby-ship` 의 일이다. 자동 배포 오더의 배포 세션만 `dobby-ship` 절차로 한다. `TASK-` 작업은 통합 세션이 기준 브랜치로 PR 을 만들기만 한다(머지하지 않는다).
- **상태를 "해결"로 올리지 않는다.** `dobby-resolve` 의 일이다.
- **`dobby-order` 의 메타를 건드리지 않는다.** 같은 형식을 쓰되 같은 오더를 두 스킬이 번갈아 맡지 않는다. 옮기려면 `dobby-migrate-v2` 를 쓴다.
