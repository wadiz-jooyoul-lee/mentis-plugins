# do

한 오더(이슈·작업)를 **여러 세션에 나눠** 진행하는 오케스트레이터다. `dobby-order` 를 대체하지 않는다 — 둘은 같은 메타 형식을 쓰고 목적만 다르다.

| | dobby-order | do |
|---|---|---|
| 한 번 실행에 하는 일 | 착수부터 통합까지 전부 | **한 단계만** |
| 세션 수 | 1개(서브 에이전트는 그 안에서) | 단계마다 새 세션 |
| 끝낼 때 | 다음 단계로 이어감 | **결과를 적고 세션을 닫으라고 알린 뒤 끝** |
| 사람에게 묻기 | 게이트에서 묻는다 | **설계 세션에서만** 요약을 보여 주고 함께 고친다. 나머지 세션은 묻지 않는다(판단이 필요하면 문서에 적고 멈춘다) |
| 적합한 때 | 짧고 한 번에 끝나는 작업 | 길고 문맥이 커지는 작업 |

## 왜 이렇게 하나 (바꾸면 안 되는 근거)

모델을 한 번 부를 때마다 **그때까지 쌓인 대화 전부**가 입력으로 다시 들어간다. 그래서 비용은 "결과물의 크기"가 아니라 **"문맥의 크기 × 호출 횟수"** 로 정해진다.

한 오더를 실측한 숫자다.

| 주체 | 호출 수 | 평균 문맥 | 문맥 재읽기 누적 | 비중 |
|---|---|---|---|---|
| 메인 세션 1개 | 1,563회 | 444,372 토큰 | 684,000,000 토큰 | **96.6%** |
| 서브 에이전트 15명 전부 | 328회 | 57,000~98,000 토큰 | 24,400,000 토큰 | 3.4% |

**일을 누구에게 보내느냐는 거의 차이가 없다. 오케스트레이터 세션이 얼마나 오래 크게 살아 있느냐가 전부다.** 그래서 이 스킬은 자기 자신을 빨리 죽이는 것을 최우선으로 한다.

세션을 끊는 비용은 한 번뿐이다 — 새 세션 시작 약 70,000 토큰 + 메타 문서 읽기 약 20,000 토큰 = 약 90,000 토큰. 반면 안 끊으면 **호출 한 번마다** 44만 토큰이 다시 들어간다. 호출을 한 번이라도 더 할 거면 끊는 쪽이 이미 이득이다.

## 설정 (첫 실행 시 확인)

작업 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md` 의 "설정 절차"를 그대로 따른다**(config.env 는 읽기만). 이하 메타 경로는 `$ORCHESTRATION_META` 기준이고, 헬퍼는 `${CLAUDE_PLUGIN_ROOT}/reference/dobby-lib.sh` 의 `dobby_*` 를 쓴다.

분석할 때는 **`${CLAUDE_PLUGIN_ROOT}/reference/analysis-discipline.md` 원칙을 따른다**(추측 금지, 사실 확인, 모르면 docs 참조).

## 사용법

```
/do {이슈키|URL} [base={브랜치}] [step={단계}] [auto [env={dev|rc1|rc4}]]
/do {이슈키} 변경 {무엇을 바꾸거나 더할지}
```

- `step` 을 주지 않으면 **지금 어느 단계인지 스스로 판정**한다(아래 "단계 판정").
- `base` 는 첫 세션에서만 쓴다. 안 주면 `$ORCHESTRATION_DEFAULT_BASE`.
- 같은 명령을 세션마다 그대로 다시 치면 그 다음 단계가 진행된다.
- `auto` 를 주면 설계 세션에서도 사람에게 묻지 않는다. 대시보드가 사람 없이 띄우는 실행(헤드리스 실행)용이다. 안 주면 설계 세션은 사람과 대화하며 설계를 확정한다(아래 "1-6. 사람과 함께 설계 고치기").
- `auto env={환경}` 을 주면 통합에서 멈추지 않고 그 환경 배포와 검증까지 사람 없이 간다(**자동 배포 오더**). 상태 문서 `## 현재 단계` 의 `- **자동 배포 환경**: {환경}` 줄이 표지다. stage·cloud_live 는 받지 않는다. `TASK-` 작업은 `env=` 를 받지 않는다(통합에서 PR 을 만들고 끝난다). 설계와 근거는 이 폴더의 `auto-mode.md`.
- `변경 {내용}` 을 주면 단계와 상관없이 **변경 접수**를 한다(아래 "변경 접수"). 어느 단계의 세션에서든, 사람이 대화로 수정을 지시하거나 새 버그·추가 설계를 말해도 같다.

### 설계 확정 뒤 자동으로 끝까지 돌리기

설계를 사람과 확정한 뒤에는 이 스킬 폴더의 `run.sh` 로 남은 단계를 자동으로 돌릴 수 있다. 단계마다 `claude -p "/do {키}"` 를 새로 실행한다. 실행이 끝나면 그 프로세스가 사라지므로 사람이 세션을 닫을 일이 없다.

**설계 세션이 "자동 실행" 답을 받으면 이 자동 실행을 직접 띄운다**(1-6). 그래서 사람은 설계만 확정하면 구현부터 통합(작업 브랜치 커밋·푸시)까지 손댈 일이 없다. 띄우는 일은 `dobby_v2_autorun {키}` 가 대시보드의 '자동 실행'을 불러서 한다. 대시보드가 띄워야 터미널을 닫아도 실행이 살아 있고, 진행이 대시보드 오더 화면에 보인다.

**부모는 `run.sh` 이고, Claude 세션이 아니다.** 부모가 하는 일은 상태 문서의 단계값을 읽고 다음 세션을 띄우는 것뿐이라 판단이 필요 없다. 셸이 맡으면 부모 몫의 토큰이 0이다. Claude 세션이 부모가 되면 자식이 끝날 때마다 깨어나 자기 문맥 전체를 다시 읽는다(설계 세션 문맥 실측 17만~27만 토큰, 단계마다 약 2회). Agent 도구의 서브 에이전트를 자식으로 쓰면 자식의 세션 아이디가 부모와 같아져 `## 지난 세션` 표와 `claude --resume` 복기가 깨진다.

```bash
run.sh {키} [--mode {권한 모드}] [--max {최대 세션 수}] [--with-test] [--approve-commit]
```

| 인자 | 뜻 | 기본값 |
|---|---|---|
| `--mode` | `claude` 의 `--permission-mode` 값. 화면 없는 실행은 권한 확인 창을 띄울 수 없어서 미리 정한다 | `auto` |
| `--max` | 이번 실행에서 띄울 세션 수의 상한. 열린 회차를 잇는 검증 묶음 세션은 하나씩 더해 센다 | 10 (자동 배포 오더는 20) |
| `--with-test` | 통합 뒤 검증까지 돈다. 검증은 배포된 화면을 보므로 배포가 끝난 뒤에 준다. `TASK-` 작업에는 듣지 않는다 | 없음(통합에서 멈춤) |
| `--approve-commit` | 사람이 커밋·푸시를 미리 승인한 실행이다. 세션마다 그 승인을 지시로 덧붙인다(`--append-system-prompt`). 없으면 통합 세션이 사용자 지침에 따라 동의를 묻고 멈출 수 있다. 승인 범위는 오더 작업 브랜치의 커밋·푸시뿐이다 | 없음 |

멈추는 경우는 아래와 같다. 멈출 때는 이유와 함께, 마지막 세션을 다시 여는 `claude --resume {세션 아이디}` 명령을 알려 준다.

| 멈추는 경우 | 이유 |
|---|---|
| 설계가 확정되지 않았다 | 설계는 사람과 함께 확정해야 한다 |
| 통합까지 끝났다(`--with-test` 없음) | 검증은 배포 뒤에 해야 의미가 있다 |
| `TASK-` 작업의 통합이 끝났다 | 통합 세션이 PR 을 만들면 할 일이 끝난다. 검증은 하지 않는다 |
| 검증을 전부 통과했다 | 할 일이 끝났다 |
| 세션이 끝났는데 아무것도 바뀌지 않았다 | 사람 판단이 필요해 스킬이 멈췄을 가능성이 크다 |
| 세션이 오류로 끝났다 | 원인을 사람이 봐야 한다 |
| 세션 수 상한에 닿았다 | 끝없이 도는 것을 막는다 |
| (자동 배포 오더) 배포 표에 막힘(⚠)이 있다 | 배포 세션이 스스로 풀지 못한 일이다 |
| (자동 배포 오더) 리뷰봇 리뷰가 30분, 빌드가 30분 동안 끝나지 않았다 | 기다려도 오지 않을 가능성이 크다 |

멈추면 대시보드가 그 오더를 MY(사람이 할 일 있음)로 올리고 알림 카드를 띄운다. 리뷰봇과 빌드는 세션이 아니라 `run.sh` 가 기다린다(`dobby_v2_ship_next` 가 `wait-review`·`wait-build` 를 내는 동안). 세션마다 배포 승인 지시도 덧붙인다.

세션이 끝날 때마다 이벤트 로그에 "자동 실행 세션 N 종료 — 시작 단계, 지금 단계, 새 세션인지 이어 쓴 세션인지, 세션 아이디"를 한 줄 남긴다. 세션 안에서도 공통 규칙 "세션 기록"대로 아이디를 남긴다.

#### 세션 이어 쓰기 판정

기본은 단계마다 새 세션이다. 다음 일이 수정이고, 직전 세션 문맥이 12만 토큰 이하이며, 5분 안일 때만 이어 쓴다(`dobby_v2_reuse_ok`). 근거와 비용은 이 폴더의 `session-reuse.md` 에 있다.

자동 배포 오더(배포·테스트까지 사람 없이 돌리기)의 설계와 근거는 이 폴더의 `auto-mode.md` 에 있다.

## 단계 판정 (실행하면 가장 먼저 하는 일)

`$ORCHESTRATION_META/{키}/status.md` 의 `## 현재 단계` 를 읽고 아래 표대로 고른다. 메타 폴더가 없으면 **설계** 다.

**먼저 v2 오더인지 본다.** v2 오더의 표지는 상태 문서의 `## 지난 세션` 표다. 설계 세션이 1-1 의 5번(`dobby_session_log`)에서 만든다. 이 표가 없고 단계가 `착수` 도 아니면 `dobby-order` 가 만든 메타다. 그때는 아무것도 고치지 않고 멈춘다. 사람에게 "이 오더는 dobby-order 로 진행한 오더라 dobby-order 로 이어가거나, `/dobby-migrate-v2 {키}` 로 v2 로 옮긴 뒤 이어가야 한다"고 알린다. 두 스킬이 한 오더를 번갈아 맡으면 서로의 상태 기록을 엉뚱하게 읽는다. 단계가 `착수` 인데 표가 없으면, v2 설계 세션이 1-1 도중에 끊긴 것이다. 그때는 설계부터 다시 한다.

**표를 보기 전에 `dobby_v2_drift_apply {키}` 를 부른다.** 지난 단계가 끝난 뒤 `/do` 밖에서 설계나 코드가 바뀌었으면 상태를 알맞게 되돌린다. 출력이 `design` 이면 단계가 분석으로 바뀌어 아래 표가 설계 수정 대화로, `code` 면 구현으로 바뀌어 리뷰로 보낸다. 그 밖의 출력(`none`, `nobase`, `kept`)은 상태를 그대로 둔다.

| status.md 현재 단계 | 추가로 보는 것 | 이번 세션에서 할 일 |
|---|---|---|
| (폴더 없음) · 착수 | — | **설계** |
| 분석 | `## 현재 단계` 에 `- **이어받기**:` 줄이 있다 (dobby-order 에서 진행 중에 옮겨 온 오더) | **이어받기 설계** (아래 "이어받기 설계" 절). 승인 기록보다 먼저 본다 — dobby-order 가 남긴 옛 승인 기록에 걸려 구현으로 넘어가지 않게 |
| 분석 | 설계 문서가 없다 (dobby-order 에서 옮겨 온 오더) | **설계** (1-1 의 4·5번만 하고 1-2 부터 이어감) |
| 분석 | 설계 승인 기록이 없다 | **설계 수정 대화** (1-6 부터 이어감) |
| 분석 | 설계 승인 기록이 있고 지금 설계와 같은 버전이다 | **구현** |
| 분석 | 설계 승인 기록이 있지만 그 뒤에 설계가 바뀌었다 | **설계 수정 대화** (바뀐 곳을 보여 주고 다시 확정받는다) |
| 구현 | — | **리뷰** |
| 리뷰 | 최신 라운드 리뷰 파일이 없다 | **리뷰** |
| 리뷰 | 리뷰 파일이 있고 `dobby_blocking` 집계 > 0 | **수정** |
| 리뷰 | 리뷰 파일이 있고 `dobby_blocking` 집계 = 0 | **통합** |
| 통합 | 키가 `TASK-` 로 시작한다 | 끝 — PR 주소를 알리고 머지와 `dobby-resolve` 를 안내한 뒤 멈춘다. 아래 세 줄보다 먼저 본다 |
| 통합 | `자동 배포 환경` 줄이 없다 | **검증** |
| 통합 | 줄이 있다 — `dobby_ship_reopen {키}` 를 부른 뒤 `dobby_v2_ship_next {키}` 의 첫 칸이 `ship` | **배포** (세션 5-2) |
| 통합 | 위 첫 칸이 `verify` | **검증** |
| 통합 | 위 첫 칸이 `wait-review`·`wait-build`·`blocked` | 멈춘다. 기다림은 `run.sh` 몫이다. 무엇을 기다리는지(또는 무엇이 막혔는지) 알린다 |
| 검증 | `## 테스트 실행 이력` 표의 마지막 회차가 `테스트중` | **검증** (남은 묶음을 잇는다. 아래 세 줄보다 먼저 본다 — 앞 묶음에 실패가 있어도 남은 묶음을 끝까지 돈다) |
| 검증 | 검증 결과가 전부 통과 | 끝 — `dobby-resolve` 를 안내하고 멈춘다 |
| 검증 | 실패가 있고 `자동 배포 환경` 줄이 없다 | **수정** |
| 검증 | 실패가 있고 줄이 있다 | **실패 처리** (세션 6-2) |
| 해결 · 종료 · 완료 | — | 끝난 오더다. 그 사실만 알리고 멈춘다 |
| 보류 | `자동 배포 환경` 줄이 있다 | **판단 답 받기** (세션 6-3) |
| 보류 | 줄이 없다 | 멈춘다. 다시 진행하려면 사람이 상태 문서의 단계를 되돌려야 한다고 알린다 |
| 그 밖의 값 | — | 멈춘다. 모르는 단계값이라고 알리고 상태 문서를 확인해 달라고 한다 |

**판정한 단계의 파일 하나만 읽는다.** 단계 본문은 이 폴더의 `steps/` 에 나눠 두었다. 다른 단계의 파일은 읽지 않는다. 모든 세션이 모든 단계의 본문을 읽으면 호출마다 그만큼 다시 읽기 때문이다(나누기 전 이 파일 하나가 약 3만 3,800 토큰).

| 이번 세션에서 할 일 | 읽을 파일 |
|---|---|
| 설계, 설계 수정 대화 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/design.md` |
| 이어받기 설계 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/takeover.md` (안에서 `design.md`, `change.md` 를 함께 읽으라고 안내한다) |
| 구현 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/impl.md` |
| 리뷰 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/review.md` |
| 수정 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/fix.md` |
| 통합 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/integrate.md` |
| 배포 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/ship.md` |
| 검증 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/verify.md` |
| 실패 처리 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/triage.md` |
| 판단 답 받기 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/answer.md` |
| 변경 접수 | `${CLAUDE_PLUGIN_ROOT}/skills/do/steps/change.md` |

**변경 요청이 먼저다.** 인자에 `변경` 이 있거나, 이 세션에서 사람이 수정 지시·새 버그·추가 설계를 말하면 위 표와 상관없이 **변경 접수**를 한다. 끝난 오더(해결·종료·완료)와 검증을 통과한 오더도 마찬가지다.

"수정"은 `dobby_norm_phase` 가 `리뷰` 로 접기 때문에 단계값만으로는 리뷰와 갈리지 않는다. 그래서 리뷰 결과 파일의 유무와 blocking 집계로 가른다.

"설계 승인 기록"은 `$ORCHESTRATION_META/{키}/design-ack.json` 의 `사용자` 또는 `auto` 항목이다. 그 값이 `dobby_design_rev {키}`(지금 설계 문서의 지문, 내용이 바뀌면 달라지는 짧은 값)와 같으면 승인된 설계 그대로다.

최신 라운드 번호는 `$ORCHESTRATION_META/{키}/reviews/` 의 `round-N` 폴더 중 가장 큰 N 이다. 폴더가 하나도 없으면 1 이다.

**수정 세션은 끝날 때 다음 라운드의 빈 폴더를 연다**(`reviews/round-{N+1}/`). 그래서 수정 뒤에는 "최신 라운드 리뷰 파일이 없다"가 되어 다음 세션이 다시 리뷰를 한다. 이 폴더를 열지 않으면 지적이 남은 옛 리뷰 파일이 최신으로 남아, 판정이 계속 "수정"으로 돌아간다.

# 공통 규칙

## 세션을 닫는 법 (모든 단계 공통 · 마지막에 반드시 한다)

단계를 마치면 아래 형식 그대로 알리고 **더 이상 아무것도 하지 않는다.**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{키} · {이번 단계 이름} 완료

한 일
  - (무엇을 했는지 한 줄씩)

남긴 것
  - {파일 경로} — (무엇이 적혀 있는지)

다음
  - 이 세션을 닫아 주세요. (/clear 또는 터미널 종료)
  - 새 세션에서: /do {키}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`이 세션을 닫아 주세요` 문구는 바꾸지 않는다. 입력 검사 훅(`hooks/prompt-guard.sh`, G20)이 이 문구로 단계가 끝났는지 안다.

**설계 세션이 자동 실행을 띄웠을 때**(1-6 에서 `dobby_v2_autorun` 이 0 을 돌려줌)는 `다음` 칸만 아래로 바꾼다.

```
다음
  - 구현부터 통합(작업 브랜치 커밋·푸시)까지 자동 실행이 시작됐습니다.
  - 진행 상황은 대시보드 {키} 오더 화면에서 볼 수 있습니다. 이 세션은 닫아도 자동 실행은 계속됩니다.
  - 통합까지 끝나면 배포(/dobby-ship {키} {환경})와 검증(/do {키})은 직접 실행해 주세요.
```

자동 배포 오더면 마지막 줄을 "통합 뒤 {환경} 배포와 검증까지 자동으로 이어 갑니다. 끝나거나 멈추면 대시보드에 알림이 뜹니다."로 바꾼다.

`TASK-` 작업이면 마지막 줄을 "통합에서 기준 브랜치로 PR 까지 만들고 끝납니다. PR 은 직접 머지해 주세요."로 바꾼다.

마무리 명령과 같은 셸 호출 끝에 `dobby_v2_checkpoint {키}; dobby_v2_next_hint {키}` 를 붙인다. 앞의 것은 이 단계가 끝난 상태를 기준점으로 남긴다. 다음 `/do` 가 이 기준점과 비교해 단계 밖 변경을 찾는다. 출력이 있으면 `다음` 칸을 그 출력으로 바꾼다. 없으면 위 형식 그대로다.

**다음 단계를 이어서 하지 않는다.** 이어서 하면 이 스킬을 쓸 이유가 없어진다.

세션을 닫으라고 알린 뒤에 사람이 수정 지시나 새 요청을 하면, 그 요청은 `steps/change.md` 를 읽고 **변경 접수**로 받는다. 그 자리에서 코드를 고치지 않는다.

## 알림 보내는 법 (자동 배포 오더)

알림은 셸 한 줄로 남긴다.

    dobby_v2_notify {키} "{본문}"

이 헬퍼는 본문 첫 줄을 이벤트 로그에 남기기만 한다. 사람에게 띄우는 알림은 대시보드가 상태 문서를 읽어 만든다. 그래서 판단 요청처럼 사람이 읽어야 할 내용은 알림 본문이 아니라 설계 문서 `## 확인이 필요했던 것` 에 자세히 적는다(대시보드가 그 절을 그대로 보여 준다).

슬랙·메일 도구는 찾지도 부르지도 않는다.

## 사람에게 묻지 않는다 (설계 세션의 수정 대화는 예외)

이 스킬은 대시보드가 띄우는 헤드리스 실행(사람과 대화하지 않는 실행)에서도 돌아야 한다. 그래서 **구현부터 검증까지는 세션 안에서 사람의 답을 기다리지 않는다.**

예외는 하나다. `auto` 없이 실행한 설계 세션은 "1-6. 사람과 함께 설계 고치기"대로 사람과 대화한다. 설계가 틀리면 뒤의 모든 세션이 틀리기 때문에, 사람이 볼 수 있는 유일한 자리를 여기에 둔다. 그 대화 중에도 사람만 정할 수 있는 결정은 요약의 "확인이 필요한 것"에 올려 답을 받는다.

판단이 필요한 일이 나오면 둘 중 하나를 한다.

1. **스스로 정할 수 있는 것**: 정하고 `design.md` 의 `## 결정과 근거` 표에 **고른 답과 이유**를 적는다. 이유 없는 결정은 남기지 않는다.
2. **사람만 정할 수 있는 것**(제품 결정, 디자인 결정, 지울지 말지 같은 되돌리기 어려운 선택): 멈춘다. `## 확인이 필요했던 것` 에 **무엇을 왜 못 정했는지와 선택지**를 적고, 세션 종료 알림에 그 사실을 적는다.

## 보드의 상태표 (모든 세션 공통)

대시보드 오케스트레이션 보드는 메타 폴더의 진행 보드 문서(`orchestration.md`)의 `## 에이전트 상태표` 를 읽어 그린다. 상태는 `대기`, `분석`, `구현`, `검증`, `리뷰`, `완료` 여섯 가지다(보드는 `구현` 과 `검증` 을 "진행중" 열에 함께 그린다). 보드는 `분석`, `구현`, `검증`, `리뷰` 상태로 **30분 넘게 갱신이 없으면 "정체"** 로 표시한다.

v2 는 단계 사이에 세션이 없는 시간이 있다. 그래서 **세션을 끝낼 때 자기 행을 `대기` 로 돌린다.** 그러지 않으면 다음 세션을 기다리는 동안 보드가 정체로 경고한다.

| 세션 | 상태표 행 | 시작할 때 | 끝낼 때 |
|---|---|---|---|
| 설계 | 분석 담당 (`analysis-agent`, 이름 "분석") — 개발 담당 행(`{슬러그}`, 이름 "개발자")도 이때 `대기` 로 넣음 | `분석` (행을 새로 넣음) | 확정 전에는 `분석` 유지, 확정하면 `완료` |
| 이어받기 설계 | 분석 담당 | `분석` | 확정 전에는 `분석` 유지, 확정하면 `완료` |
| 변경 접수 | 분석 담당 | `분석` | 확정하면 `완료` |
| 구현 | 개발 담당 | `구현` | `대기` |
| 리뷰 | 리뷰 담당 (`review-agent`, 이름 "리뷰어") | `리뷰` + 라운드 번호 | `완료` |
| 수정 | 개발 담당 | `구현` + 수정 횟수 | `대기` |
| 통합 | 개발 담당 | 바꾸지 않음 | `완료` |
| 검증 | 개발 담당 | `검증` (회차 헬퍼가 바꿈) | 전부 통과면 `완료`, 아니면 `대기` (회차 헬퍼가 바꿈) |
| 배포·검증 실패 분석·판단 답 받기 | 바꾸지 않음 | 바꾸지 않음 | 바꾸지 않음 |

개발 담당 행의 라운드 칸은 **수정 횟수**다(리뷰 지적 수정과 검증 실패 수정을 합친 수, `dobby_fix_count`). 리뷰 담당 행의 라운드 칸은 리뷰 차수다.

검증 동안 개발 담당 행은 이름을 바꾸지 않고 상태만 `검증` 이 된다. 대시보드가 그 카드를 "테스터"로 그린다. 상태는 `dobby_testrun_new`·`dobby_testrun_update` 가 바꾸므로 세션이 따로 부르지 않는다.

개발 담당 슬러그는 세션마다 새로 만들지 않는다. 상태표에서 이름이 "개발자" 인 행의 슬러그를 그대로 쓴다. 나누기 전 오더라 그 행이 없으면 이름이 "분석/개발자" 인 행을 쓴다.

분석 담당 세션은 시작할 때 `dobby_agent_add {키} analysis-agent "분석" "{작업 한 줄}" 분석 0` 을 먼저 부른다. 행이 있으면 아무것도 하지 않으므로, 나누기 전 오더에도 분석 행이 생긴다.

## 세션 기록

세션은 단계마다 새로 열린다. 나중에 어느 단계에서 무슨 일이 있었는지 되짚을 수 있도록 **각 세션은 시작 직후 자기 아이디를 기록한다.** 세션 아이디는 손으로 적지 않는다. 헬퍼가 지금 세션의 아이디(`CLAUDE_CODE_SESSION_ID`)를 읽어 적는다.

```
dobby_session_log {키} {슬러그} {하위 키} {단계 이름} {워크트리경로}
```

이 한 줄이 세 군데에 남긴다.

| 어디에 | 무엇을 | 왜 |
|---|---|---|
| 상태 문서 `## 세션` | 세션 아이디와 작업 경로를 **지금 세션으로 바꿔** 적는다 | 대시보드 "이어가기"가 이 값을 읽어 가장 최근 세션을 연다 |
| 상태 문서 `## 지난 세션` 표 | 시각, 단계, 세션 아이디, 작업 경로 한 줄을 **덧붙인다** | 지나간 세션을 `claude --resume {세션 아이디}` 로 다시 열어 복기한다 |
| 에이전트 기록 목록 `agent-logs.json` | `{슬러그: {하위 키: 대화 기록 파일 경로}}` | 대시보드 콘솔에서 단계별 대화 기록을 골라 본다 |

| 세션 | 슬러그 | 하위 키 | 단계 이름 |
|---|---|---|---|
| 설계 | 분석 담당 | `design` | 설계 |
| 이어받기 설계 | 분석 담당 | `takeover` | 이어받기 설계 |
| 변경 접수 | 분석 담당 | `change-{M}` | 변경 {M} 접수 |
| 구현 | 개발 담당 | `impl` | 구현 |
| 리뷰 | `review-agent` | `round-{N}` | {N}차 리뷰 |
| 수정 | 개발 담당 | `fix-{N}` (검증 실패면 `fix-test-{시각}`) | {N}차 수정 |
| 통합 | 개발 담당 | `integrate` | 통합 |
| 배포 | 개발 담당 | `ship-{시각}` | 배포 |
| 검증 | 개발 담당 | `verify-{묶음}` (예: `verify-V1`) | 검증 {묶음} |
| 검증 실패 분석 | 개발 담당 | `triage-{시각}` | 검증 실패 분석 |
| 판단 답 받기 | 분석 담당 | `answer-{시각}` | 판단 답 |

같은 세션에서 두 번 불러도 표에는 한 줄만 남는다.

`## 지난 세션` 표의 머리는 "세션 아이디"로 쓴다. 대시보드는 문서에서 처음 나오는 `세션 ID:` 꼴을 최신 세션으로 읽기 때문에, 지난 세션 표에는 그 꼴을 쓰지 않는다.

## 메타 파일은 늘리지 않는다

대시보드는 읽을 파일 이름을 코드에 적어 두고 읽는다. **새 이름의 파일을 만들면 대시보드에 보이지 않는다.** 그래서 v2 는 파일을 새로 만들지 않고 기존 문서에 절을 더한다.

| 담는 내용 | 어디에 |
|---|---|
| 개발 작업 지시서 | `design.md` |
| 리뷰 확인 목록 | `design.md` 의 `## 리뷰 항목` 절 |
| 테스트 케이스와 통과 기준 | `test-plan.md` |
| 구현 기록 | `implementation.md` |
| 리뷰 결과 | `reviews/round-{N}/review-agent.md` |
| 지난 세션 아이디 | `status.md` 의 `## 지난 세션` 표 |
| 진행 상태 | `status.md`, `orchestration.md` |

## 글은 한국어로

상태, 로그, 요약, 산출 문서의 진행 서술은 한국어와 존댓말로 쓴다.

사람이 읽는 글에는 오케스트레이션 내부 용어를 쓰지 않는다. 메타 파일은 역할로 부르고(`design.md` → "설계 문서"), 라운드 번호는 "1차 리뷰"로 풀고, 단계 코드와 슬러그는 쓰지 않는다. 심각도 표시(`[blocker]`·`[major]`·`[minor]`·`[nit]`)와 실제 코드 경로는 그대로 쓴다.

# 하지 않는 것

- **다음 단계를 이어서 하지 않는다.** 한 번 실행에 한 단계다.
- **진행 중에 들어온 요청을 그 자리에서 고치지 않는다.** 변경 접수로 설계 문서에 적고, 새 세션이 구현한다.
- **서브 에이전트를 띄우지 않는다.** 서브를 기다리려면 이 세션이 살아 있어야 한다. 영역이 여럿이면 영역마다 세션을 나눈다(동시에 하려면 터미널을 여러 개 연다).
- **정식 배포 브랜치로 PR 을 만들거나 머지하지 않는다.** `dobby-ship` 의 일이다. 자동 배포 오더의 배포 세션만 `dobby-ship` 절차로 한다. `TASK-` 작업은 통합 세션이 기준 브랜치로 PR 을 만들기만 한다(머지하지 않는다).
- **상태를 "해결"로 올리지 않는다.** `dobby-resolve` 의 일이다.
- **`dobby-order` 의 메타를 건드리지 않는다.** 같은 형식을 쓰되 같은 오더를 두 스킬이 번갈아 맡지 않는다. 옮기려면 `dobby-migrate-v2` 를 쓴다.
