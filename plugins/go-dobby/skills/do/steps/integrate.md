# 세션 5 · 통합 (배포담당)

시작 헬퍼의 `설명:` 줄이 `산출물 확정과 문서 올리기` 면 아래 "산출물만 확정할 때"만 한다. 그 밖에는 "하는 일"을 한다.

## 하는 일

1. 리뷰 결과가 0 건인지 다시 확인한다 — `dobby_blocking {키} {N}`.
2. 커밋하고 푸시한다 — `dobby_commit_push {워크트리} {브랜치} "{메시지}"`.
   - 메시지는 `fix: {키} {무엇을 고쳤는가}` 또는 `feat: {키} {무엇을 만들었는가}`.
   - **오케스트레이션 내부 용어를 넣지 않는다**(라운드 번호, 슬러그, 단계 코드, "리뷰 반영").
   - 저장소가 금지하는 서명을 넣지 않는다.
3. 에이전트 브랜치가 루트 브랜치와 다르면 머지한다 — `dobby_merge_root {워크트리} {루트브랜치} {에이전트브랜치}`.
4. `outcome.md` 를 쓴다 — `dobby_scaffold_doc {키} outcome` 후 설계 대비 결과 표와 구현 내용을 채운다. 내부 용어와 줄임말을 쓰지 않는다(`dobby_terms_lint` 로 확인).
5. `dobby-explain {키}` 를 실행해 비전공자용 구현 내용 문서를 만든다.
6. 변경을 통합했으면 설계 문서의 그 `## 변경 {M}` 절 상태를 `통합됨 ({커밋 해시 7자리})` 로 바꾼다. `outcome.md` 는 덮어쓰지 않고 `## 후속 {YYYY-MM-DD} — {변경 요약}` 절을 덧붙인다. 상태를 바꾸지 않으면 다음 변경 때 구현 세션이 이미 통합된 변경을 다시 구현하려 한다.

7. 키가 `TASK-` 로 시작하는 작업이면 작업 브랜치마다 기준 브랜치로 PR 을 만든다 — `dobby_v2_task_pr {키} "{제목}" "{본문}"`. 출력은 저장소마다 `저장소<TAB>PR 주소` 한 줄이다.
   - 기준 브랜치는 설계 때 상태 문서 `- **기준 브랜치**:` 줄에 적힌 값이다. 줄이 없는 옛 작업은 원격에 `cloud_live` 가 있으면 그것, 없으면 원격 기본 브랜치다.
   - 제목은 `{키} {무엇을 했는가}` 로 쓴다. 본문은 `outcome.md` 에서 무엇을 왜 바꿨는지 쉬운 말로 추린다. 내부 용어는 쓰지 않는다.
   - PR 은 만들기만 한다. 머지하지 않는다.
   - 출력이 비면 기준 브랜치보다 앞선 커밋이 없다는 뜻이다(이미 머지됨). 종료 알림에 PR 을 만들 변경이 없었다고 적는다.

8. 산출물이 있는 오더면(설계 문서에 `## 산출물` 표가 있다) 아래 "문서 올리기"를 이어서 한다. 올릴 곳이 적힌 산출물 가운데 산출 기록의 `## 올린 곳` 이 아직 빈 것만 올린다.

**이슈 오더는 정식 배포 브랜치로 PR 을 만들거나 머지하지 않는다.** 그것은 `dobby-ship` 이 할 일이다. `TASK-` 작업은 7번의 PR 생성까지가 끝이고, 배포와 검증을 하지 않는다.

## 산출물만 확정할 때

산출물 리뷰가 끝난 뒤(또는 리뷰어가 없는 오더에서 산출이 끝난 뒤) 열리는 통합이다. 결과 문서(`outcome.md`)와 구현 설명 문서는 만들지 않는다.

1. 리뷰를 거쳤으면 막는 지적이 0건인지 다시 확인한다 — `dobby_blocking {키} {N}`.
2. 산출물이 저장소 문서면 커밋하고 푸시한다 — `dobby_commit_push {워크트리} {브랜치} "docs: {키} {무엇을 썼는가}"`. 메시지 규칙은 위 2번과 같다. 저장소 밖 산출물(`deliverables/`)은 커밋이 없다.
3. 키가 `TASK-` 로 시작하고 커밋이 있으면 위 7번대로 기준 브랜치로 PR 을 만든다.
4. 아래 "문서 올리기"를 한다.

## 문서 올리기

설계 문서 `## 산출물` 표의 `올릴 곳` 칸에 적힌 곳으로 산출물을 올린다. "없음"이면 올리지 않는다.

| 올릴 곳 | 어떻게 |
|---|---|
| Jira 코멘트 | `twg` 로 그 이슈에 코멘트를 단다(`${CLAUDE_PLUGIN_ROOT}/reference/jira-twg.md`) |
| Confluence | 지금 있는 수단(`twg`)으로 해 본다. 자동 실행 세션에는 Atlassian 연결이 붙지 않는다. 안 되면 아래처럼 질문으로 넘긴다 |
| 아티팩트 링크 | 사람 없이 못 한다. 질문으로 넘긴다 |

- 올렸으면 그 산출물의 산출 기록 `## 올린 곳` 절에 `- {종류}: {주소}` 한 줄을 적는다(예: `- Confluence: https://…`). 대시보드가 이 줄을 읽는다.
- 올리기 전에 `dobby_v2_ctx` 로 문맥을 잰다. `DOBBY_REUSE_MAX_CTX`(12만 토큰)를 넘으면 올리지 않고 `dobby_v2_end {키} 넘김 "문서 올리기가 남음"` 으로 새 세션에 넘긴다(커밋·푸시와 결과 문서를 마친 뒤에).
- 올릴 수 없으면(수단이 없음, 권한 없음, 아티팩트) 공통 규칙 "사람에게 묻는 법"대로 질문을 남긴다. 답하는 방식은 "직접 해 주기"로 하고, 올릴 파일 경로와 올릴 곳을 할 일에 적는다. `dobby_v2_end {키} 질문` 으로 끝낸다. 답이 오면 이 세션이 이어서 `## 올린 곳` 을 채우고 끝낸다.

## 마무리

```
dobby_v2_end {키} 완료
```

끝 헬퍼는 저장소마다 커밋하지 않은 변경이 없는지, 끝 커밋이 원격에 푸시됐는지, 결과 문서가 있는지 확인한다. 아니면 `거부:` 를 낸다. 산출물만 확정할 때는 결과 문서 대신 산출 기록이 있는지 본다.

통과하면 다음 차례를 정한다.

| 오더 | 다음 |
|---|---|
| `TASK-` 작업 | 사람이 PR 을 머지한다. 대시보드가 머지를 확인하면 배포담당 행이 완료가 된다 |
| 자동 배포 오더 | 자동 실행이 배포를 잇는다 |
| 그 밖의 오더 | 사람이 `/dobby-ship {키} {환경}` 으로 배포한다 |
| 산출물만 확정한 오더 | 오더가 끝난다. 개발자도 일한 오더에서 검증 뒤에 쓴 산출물이었으면 "검증 통과"로 끝난다 |

세션 종료 알림의 `다음` 칸은 끝 헬퍼 출력을 그대로 옮긴다. `TASK-` 작업이면 `한 일` 칸에 PR 주소를 적는다.
