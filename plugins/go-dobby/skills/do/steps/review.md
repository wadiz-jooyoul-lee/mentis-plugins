# 세션 3 · 리뷰

## 읽을 것

1. `design.md` 의 **`## 리뷰 항목`** 절 — 설계 담당이 넘긴 확인 목록. `구현 대기` 인 `## 변경 {M}` 절이 있으면 그 절의 `### 리뷰 항목` 을 본다.
2. 무엇을 리뷰하는지 본다. 상태 문서 `## 현재 단계` 에 `- **리뷰 대상**: 산출물` 줄이 있으면 **산출물 리뷰**다. 아래 "산출물을 리뷰할 때"를 따른다. 줄이 없으면 코드 리뷰다.
3. (코드 리뷰) `dobby_review_brief {워크트리}` 의 출력 — 바뀐 것, 지운 파일, 변경 본문, 저장소 금지 규칙 검사 결과, 사라진 것들의 소비처 표가 한 번에 나온다.

**직접 `git diff` 를 치기 전에 `dobby_review_brief` 를 먼저 쓴다.** 리뷰 비용은 읽는 양이 아니라 **왕복 횟수**다. 한 번 부를 때마다 그때까지 쌓인 문맥을 다시 읽기 때문이다. 미리 받아 두면 그만큼 왕복이 준다.

## 리뷰 기준

`## 리뷰 항목` 을 먼저 전부 확인하고, 그다음 아래를 본다.

**진행 표시**: 리뷰 항목(표 줄과 목록 줄)을 하나 마칠 때마다 마친 개수를 `dobby_progress {키} {마친 수}` 로 적는다. 따로 부르지 말고 다음 명령 앞에 `&&` 로 붙인다. 사무실 진행 막대가 이 값을 읽는다.

| 보는 것 | 무엇을 |
|---|---|
| 정확성 | 버그, 논리 오류, 빈 값·경계값 처리, 비동기와 오류 처리, 설계와 구현의 불일치 |
| 호출부 영향 | 내보내는 것·반환 형태가 바뀌었으면 부르는 곳마다 어떤 영향인지. **브리프의 소비처 표에 있는 것을 다시 찾지 않는다.** 표가 못 잡는 것(이름을 쪼개 만드는 참조, 물려받은 메서드, 설정 파일이 부르는 것)만 직접 본다 |
| 규약 | 브리프에 검사 결과가 붙은 저장소 금지 규칙은 다시 보지 않는다. 그 밖의 이름·용어·구조 규약만 |
| 재사용 | 새로 적은 타입·유틸·조립이 이미 저장소에 있는지 **찾아본다. 판단이 아니라 절차다** |
| 범위 | 설계의 `## 건드리지 않을 것` 을 지켰는지 |
| 수집 보존 | 마크업이나 이벤트 요소를 바꾸거나 나누거나 옮겼으면, 원래 요소에 있던 수집 장치(수집용 속성, 클릭 처리기, 수집 스크립트 호출, 로깅)가 **모든 조작 경로에 그대로 남았는지**. 화면도 오류도 그대로라 조용히 빠진다. 바꾸기 전 코드나 형제 컴포넌트와 대조한다 |
| 저장 내용 | 저장하거나 보내서 다른 곳이 읽는 값(저장 요청 본문, 변환 결과)을 만들 때, 원본 객체를 통째로 펼쳐 넣지 않고 **약속된 칸만 하나씩 적어 조립했는지**. 통째로 넣으면 필요 없는 값이 조용히 섞여 저장된다 |

## 산출물을 리뷰할 때

리뷰 대상이 산출물이면 위 표 대신 아래를 본다. 볼 것은 산출 기록(`produce.md`, 여럿이면 `produce-{이름}.md`)이 가리키는 산출물과 설계 문서의 `## 산출물` 명세다. 저장소 문서면 `git -C {워크트리} diff` 로 바뀐 것을 본다. `dobby_review_brief` 는 쓰지 않는다.

| 보는 것 | 무엇을 |
|---|---|
| 사실과 맞는가 | 주장과 수치를 출처에서 직접 확인한다. 출처가 없는 주장은 지적한다 |
| 빠진 질문이 없는가 | 명세의 질문 목록이나 목차를 하나씩 대조한다. 답하지 못한 것이 "확인 필요"로 남아 있는지도 본다 |
| 인용한 `파일:줄` 이 실제와 같은가 | 인용한 자리를 열어 본다. 줄이 밀렸거나 내용이 다르면 지적한다 |
| 요청에 맞는가 | 이슈가 요구한 것과 명세의 "다 됐다고 볼 기준"을 채웠는지, 읽을 사람이 이 문서만 보고 판단할 수 있는지 |

## 결과 쓰기

`dobby_review_path {키} {N} review-agent` 가 알려 준 경로에 쓴다. N 은 시작 헬퍼가 알려 준 리뷰 차수다(설명 칸의 "{N}차 리뷰").

각 지적은 **`## [blocker|major|minor|nit] {제목 한 줄}`** 카드로 시작한다. 이 머리글을 `dobby_blocking` 이 센다. 카드 머리글이 없으면 그 파일은 결함 1건으로 세어진다.

본문 첫 줄에는 **설계와 구현** 한 줄을 적는다. 값은 아래 둘 중 하나를 글자 그대로 쓴다. 끝 헬퍼가 `[blocker]`·`[major]` 카드의 이 줄로 다음 차례를 정한다.

```
## [major] 빈 배열일 때 목록이 깨집니다
- 설계와 구현: 설계대로 구현됨
```

| 값 | 언제 | 다음 차례 |
|---|---|---|
| `구현이 설계와 다름` | 설계 문서(산출물이면 명세)가 정한 것과 다르게 만들었다 | 만든 담당자가 고친다 |
| `설계대로 구현됨` | 설계대로 만들었는데 결함이 있다. 설계를 고쳐야 풀린다 | 기획자가 설계를 다시 본다 |

막는 지적 가운데 `설계대로 구현됨` 이 하나라도 있으면 기획자가 먼저다. 설계가 바뀌면 구현도 다시 하기 때문이다. `[blocker]`·`[major]` 카드에 이 줄이 없으면 끝 헬퍼가 `지적` 을 받지 않는다. `[minor]`·`[nit]` 에는 적지 않아도 된다.

그 아래에 근거 `파일:라인`, 재현 조건, 수정 제안을 적는다. 수정 제안은 설계가 정한 동작과 범위 안에서 한다. 본문의 길이와 형식에는 제한이 없다.

**지적이 없는 영역도 적는다** — "확인함 — 문제 없음" 또는 "해당 없음 — {왜 닿지 않는지}". 안 적으면 안 본 것과 구별되지 않는다.

## 마무리

```
dobby_review_lint {키} {N}
dobby_blocking {키} {N}
```

`dobby_blocking` 결과가 0 이면 `dobby_v2_end {키} 통과`, 0 보다 크면 `dobby_v2_end {키} 지적 {건수}` 로 끝낸다. 끝 헬퍼가 리뷰 파일의 지적 수를 다시 세어 맞지 않으면 `거부:` 를 낸다.

| 결과 | 다음 |
|---|---|
| 통과 (코드) | 통합 |
| 통과 (산출물) | 앞 산출물이었으면 구현, 커밋할 문서나 올릴 곳이 있으면 통합, 없으면 오더가 끝난다 |
| 지적, 막는 지적이 모두 `구현이 설계와 다름` | 수정(코드는 개발자, 산출물은 산출자) |
| 지적, `설계대로 구현됨` 인 막는 지적이 있음 | 기획자가 설계를 다시 본다 |
