# 넘김 — 설계·변경 접수를 새 세션으로 넘긴다

시작 헬퍼가 `넘김 권장` 을 냈을 때 읽는다. 이 세션에서 설계(또는 변경 접수)를 시작하지 않는다. 대신 **넘김 문서**를 쓰고 끝낸다.

왜 이 세션이 쓰나: 지금까지의 대화(조사·분석·사람이 한 말)가 이 세션의 캐시에 살아 있어, 요약은 이 세션이 가장 싸고 정확하게 쓴다. 넘기지 않고 여기서 설계하면 호출마다 쌓인 문맥 전체를 다시 읽는다. 근거 수치와 기준 계산은 같은 폴더의 `session-reuse.md` "설계 넘기기" 절이다.

## 1. 사람에게 한 줄로 묻는다

쌓인 문맥이 거의 이 오더를 위한 조사라면 그 자리에서 설계하는 편이 나을 수도 있다. 판정만 믿지 않고 먼저 묻는다.

> 이 세션의 문맥이 커서(늘어난 양 {N} 토큰) 설계를 새 세션으로 넘기기를 권합니다. **넘김** / **그대로 진행** 중 골라 주세요.

- **그대로 진행**: `dobby_v2_begin {키} {원래 인자…} 그대로` 를 부르고, 그 결과의 `지시 문서:` 대로 이 세션에서 진행한다. 이 문서의 나머지는 읽지 않는다.
- **넘김**(또는 넘기자는 취지의 답): 2절로 간다.

## 2. 넘김 문서를 쓴다

```
dobby_v2_handoff {키}            # 변경 접수를 넘기면: dobby_v2_handoff {키} 변경
```

헬퍼가 메타 폴더를 만들고 넘김 문서 경로(`$ORCHESTRATION_META/{키}/handoff.md`), 이 세션의 아이디와 기록 파일 경로, 새 세션 명령을 낸다.

⛔ **`status.md`·`design.md` 는 만들지 않는다.** 단계 판정이 그 파일들로 설계 차례를 가린다 — `design.md` 가 미리 있으면 새 세션이 "설계 확인"으로 잘못 판정된다. 메타 골격(`dobby_bootstrap`)은 새 세션(설계 세션)이 깐다. 변경 접수를 넘길 때도 `design.md` 에 변경 절을 쓰지 않는다 — 접수는 새 세션이 한다.

넘김 문서의 절은 아래로 고정한다. 요약에서 잘 빠지는 것은 결론이 아니라 **조사 과정에서 나온 것**이라서다. 짧게 쓰려 애쓰지 않는다 — 10~20k 토큰이어도 큰 문맥을 끌고 가는 것보다 훨씬 싸다.

| 절 | 내용 |
|---|---|
| `## 목표` | 무엇을 만들거나 고치려는가 |
| `## 정해진 것과 이유` | 결정마다 이유를 함께 적는다. 이유가 없으면 새 세션이 뒤집거나 다시 묻는다 |
| `## 확인하고 배제한 것` | "여기는 봤는데 아니었다". 없으면 새 세션이 같은 곳을 다시 조사한다 |
| `## 사람이 한 말` | 요구와 선호는 요약하지 않고 **그대로 인용**한다 |
| `## 확인하지 못한 것` | 추측은 추측이라고 적는다 |
| `## 근거 위치` | 조사 내용을 다 옮기지 않고 `파일 경로:줄 번호` 로 적는다 |
| `## 옛 세션` | 헬퍼가 낸 세션 아이디와 기록 파일 경로, 그리고 **이 오더와 관련된 대화의 시각 범위**. 며칠 쓴 세션에는 다른 작업이 섞여 있어, 범위가 없으면 새 세션의 서브 에이전트가 엉뚱한 것을 옮긴다 |

변경 접수를 넘길 때는 `## 사람이 한 말` 에 이번 변경 요청을 그대로 인용하고, `## 목표` 에 어느 오더의 몇 번째 변경인지 적는다.

## 3. 마무리

"세션을 닫는 법" 형식으로 알린다. `다음` 칸은 아래로 쓴다. **원래 명령의 인자(`auto`·`env=` 등)를 그대로 붙인다.** 변경 접수를 넘겼으면 `변경` 을 붙인다.

```
다음
  - 이 세션을 닫아 주세요. (/clear 또는 터미널 종료)
  - 새 세션에서: /do {키} {원래 인자…}     ← 넘김 문서를 읽고 설계부터 합니다
```

새 세션이 넘김 문서를 읽고 하는 일(되말하기 · 모자란 것은 서브 에이전트로 옛 기록 조회)은 `steps/design.md` 와 `steps/change.md` 의 "넘김 문서" 규칙에 있다. 넘김 문서는 설계가 확정될 때 헬퍼(`dobby_design_ack`)가 지운다.
