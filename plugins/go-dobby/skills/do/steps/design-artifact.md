# 설계 아티팩트

> 설계의 1-6 과 변경 접수의 5 가 이 파일을 가리킨다.

설계를 사람이 한눈에 확인하는 페이지다. **이 이슈가 무엇을 하려는지, 그것을 어떻게 하려는지**가 분명히 보여야 한다. 설계 문서는 다음 세션의 작업 지시서라 사람이 읽기에 길고 코드가 많다. 이 페이지는 같은 내용을 쉬운 말과 화면, 흐름으로 다시 쓴다.

## 언제 만들고 언제 고치나

| 때 | 할 일 |
|---|---|
| 설계 1-6, 요약을 보여 주기 전 | 처음 게시한다. 요약 맨 위에 링크를 넣는다 |
| 1-6 에서 사람이 설계를 고치라고 했을 때 | 설계 문서를 고친 뒤 이 페이지도 다시 쓰고 같은 링크로 다시 게시한다 |
| 변경 접수 5, 요약을 보여 주기 전 | 변경을 반영해 다시 쓰고 같은 링크로 다시 게시한다. 페이지가 없던 오더면 이때 처음 만든다 |
| `auto` 실행(사람 없는 실행) | 만들지 않는다. 게시 도구가 없다 |

**바뀐 설계는 덧붙이지 않고 최종 상태로 다시 쓴다.** "이전"은 이 이슈 작업 전의 모습, "이후"는 지금까지 확정된 변경을 모두 반영한 모습이다. 변경 이력, 옛 결정, "변경 2에서 바뀜" 같은 문장은 넣지 않는다.

## 근거

설계 문서, 분석 문서, 테스트 계획만 근거로 쓴다. 문서에 없는 내용을 지어내지 않는다. 화면 모양이 문서로 확인되지 않으면 모형에 "모양은 예시"라고 적는다.

## 페이지 구성

아래 순서를 지킨다. 절 제목은 이슈에 맞게 바꿔도 되지만 순서와 내용은 바꾸지 않는다.

| 순서 | 절 | 쓸 내용 |
|---|---|---|
| — | 왼쪽 목차 | 왼쪽에 고정된 칸. 각 절 제목에 `id` 를 달아 눌러 이동하게 한다. 좁은 화면에서는 본문 위로 올린다 |
| 1 | 이 이슈가 하려는 일 | 무엇이 문제이고 무엇을 바꾸는지 3~5줄. 끝에 "이번에 하지 않는 것"을 한두 줄 둔다 |
| 2 | 화면 이전과 이후 | 화면이 바뀌는 변경이면 반드시 넣는다. 아래 "화면 예시" 규칙 |
| 3 | 바뀌는 것 비교 | 항목마다 한 줄인 표: `항목 / 이전 / 이후 / 왜` |
| 4 | 전체 흐름 이전과 이후 | 아래 "흐름" 규칙 |
| 5 | 코드 수준 설계 (접힘) | 맨 아래에 `<details>` 로 접어 둔다. 아래 "코드 수준 설계" 규칙 |

화면이 바뀌지 않는 변경(서버 응답, 수집 태그, 내부 처리)이면 2절 대신 "겉으로 달라지는 것"을 쓴다. 사용자나 운영자가 느끼는 차이가 없으면 그렇다고 한 줄로 적는다.

### 화면 예시

- 이전과 이후를 **나란히** 둔다(좁은 화면에서는 위아래). 각 칸 위에 "이전" "이후" 표지를 단다.
- 갈무리가 있으면 쓴다. 없으면 HTML 과 CSS 로 화면 모형을 그린다. 실제 문구, 버튼 이름, 배치를 설계 문서에서 가져온다.
- 바뀐 부분은 테두리나 배경색으로 표시하고, 옆에 번호를 달아 3절 비교 표의 항목과 맞춘다.
- 상태에 따라 화면이 갈리면(로그인 여부, 국내와 해외, 모바일과 PC) 갈리는 경우마다 한 쌍씩 둔다.

### 흐름

- 사용자의 첫 동작부터 결과가 보일 때까지를 단계로 그린다. 서버나 다른 화면을 거치면 그 단계도 넣는다.
- 이전 흐름과 이후 흐름을 나란히 두고, 달라진 단계는 강조색으로, 없어진 단계는 취소선으로, 새 단계는 "새로" 표지로 보인다.
- 인라인 SVG 나 번호 매긴 상자 목록으로 그린다. mermaid 는 쓰지 않는다(외부 스크립트가 필요하다).
- 갈림길이 있으면(조건에 따라 다른 화면) 갈림을 그림에 넣는다.

### 코드 수준 설계

- 자주 보지 않는 영역이다. 기본으로 접어 둔다.
- 고칠 파일마다 전체 경로, "지금 코드 / 고친 뒤 코드" 조각, 바꾸는 이유 한 줄을 둔다.
- 작업 순서와 건드리지 않을 것을 짧게 덧붙인다.

## 쓰는 법

- 쉬운 말로 쓴다. 전문용어는 처음 나올 때 괄호로 풀이를 단다. 한 문장은 짧게 끊는다.
- 도구 이야기는 넣지 않는다. 이 플러그인과 대시보드 이름, 메타 파일 이름, 단계와 세션 구조, 에이전트, `dobby_*` 헬퍼, 리뷰 차수가 해당한다. 읽는 사람은 이 도구를 쓰지 않는다.
- 외부 주소(글꼴, 스크립트, 이미지)를 쓰지 않는다. CSS 는 모두 인라인이다.
- 밝은 화면과 어두운 화면 모두에서 읽히게 색을 정한다.

## 게시

1. `artifact-design` 스킬을 먼저 불러 그 지침을 따른다.
2. 원고를 `$ORCHESTRATION_META/{키}/artifacts/design.html` 에 쓴다. `<title>` 은 `{키} 설계` 다.
3. `dobby_tooling_lint $ORCHESTRATION_META/{키}/artifacts/design.html` 로 도구 이야기를 검사한다. 걸린 줄을 고쳐 다시 검사한다(최대 2회). 그래도 남으면 게시하지 않고 걸린 줄을 사람에게 보여 준다.
4. Artifact 도구로 게시한다. `icon` 은 `blueprint`, `description` 은 이슈가 하려는 일 한 줄이다.
5. 링크를 기록한다. 파일을 직접 쓰지 않고 헬퍼로만 쓴다.

| 상황 | 게시 | 기록 |
|---|---|---|
| `artifact-share.md` 에 `design` 행이 없다 | `url` 없이 새로 게시 | `dobby_artifact_add {키} design "{키} 설계" {URL}` |
| `design` 행이 있다 | 그 행의 URL 을 `url` 로 넘겨 같은 링크를 갱신 | `dobby_artifact_touch {키} design "{무엇을 바꿨나}"` |

⛔ 다른 슬러그(`i18n`, `outcome` 등)의 URL 로 게시하지 않는다. 그 페이지를 덮어써 링크를 잃는다.
