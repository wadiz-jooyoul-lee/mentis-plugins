# 세션 6 · 검증

## 읽을 것

`test-plan.md` **하나만 읽는다.** 설계 문서도 구현 문서도 읽지 않는다. 테스트 계획이 자족적이지 않으면 그것 자체가 설계 세션의 결함이므로, 그 사실을 기록하고 멈춘다.

## 하는 일

`dobby_session_log {키} {슬러그} verify 검증 {워크트리경로}` 로 세션을 기록한 뒤 `dobby-test {키}` 를 실행한다(자동 배포 오더는 `dobby-test {키} {자동 배포 환경}`). 검증은 보드에 행을 따로 만들지 않는다. 그래서 세션 기록도 개발 담당 슬러그 아래에 남긴다(보드에 없는 슬러그로 기록하면 대시보드가 정체 모를 에이전트로 표시한다). 그 스킬이 브라우저를 열어 시나리오를 돌리고 결과를 `test-runs/{시각}/` 에 남긴다.

## 마무리

```
dobby_phase {키} 검증
```

- 전부 통과: 끝났음을 알리고 `dobby-resolve {키}` 를 안내한다. 배포가 필요하면 `dobby-ship {키} {환경}` 을 안내한다.
- 실패가 있음: 다음은 수정 세션이다. 무엇이 왜 실패했는지 알린다.

**자동 배포 오더는 더 한다.**

1. 테스트 전에 맡은 저장소마다 `dobby_ship_stage {키} {저장소} {환경} "검증 중"`. 전부 통과하면 `"검증 완료"`.
2. 브라우저 도구가 안 보이면 연결이 늦은 것이다. 잠시 뒤 다시 찾는다. 바로 "도구 없음"으로 끝내지 않는다.
3. 알린다(공통 규칙 "알림 보내는 법").
   - 전부 통과: **완료 알림** — 배포 환경, PR·빌드 번호(`## 배포` 표), 통과한 시나리오 수, 남은 일(`/dobby-resolve {키}` 로 해결 표시, Jira 보고). 해결 표시와 Jira 보고는 하지 않는다.
   - 실패가 있음: **실패 알림** — 실패한 시나리오, 몇 번째 시도인지(`dobby_v2_test_fixes {키}` + 1), "원인을 분석해서 고치는 중".
