# 세션 6-2 · 검증 실패 처리 (자동 배포 오더만)

## 읽을 것

1. 마지막 `test-runs/{시각}/` 의 실패 기록
2. 상태 문서 `## 배포` 표
3. `design.md` — 원인이 코드 결함일 때만

## 하는 일

1. `dobby_session_log {키} {슬러그} triage-{YYYYMMDD-HHMM} "검증 실패 분석" {워크트리경로}`
2. **배포부터 의심한다.** 실패한 화면의 번들이 이번 커밋으로 나갔는지 `dobby_ship_verify`, com.wadiz.web 이면 `dobby_ship_argo {키} {환경} check` 로 본다.
3. 원인을 하나로 고르고 처리한다.

| 원인 | 어떻게 알아보나 | 처리 |
|---|---|---|
| 배포가 덜 됐다 | 빠진 번들이 있거나 argocd 가 `OutOfSync`·`Progressing` | `dobby_ship_stage` 로 그 행을 다시 할 단계(번들이 빠졌으면 `빌드 대기`, sync 가 덜 됐으면 `배포 대기`)로 되돌리고 `dobby_phase {키} 통합`. 다음은 배포 세션이다. 수정 횟수에 넣지 않는다 |
| 코드 결함 | 실패가 이번 변경 부분에서 재현된다 | `dobby_v2_test_fixes {키}` 가 2 이상이면 판단 요청으로 간다. 아니면 이 세션에서 세션 4(수정)를 검증 실패로 들어온 경우대로 한다(하위 키 `fix-test-{시각}`). 다음은 리뷰다 |
| 테스트 계획이 틀렸다 | 기대 결과가 설계 문서와 어긋난다 | 판단 요청. 테스트 계획과 설계는 확정된 것이라 고치지 않는다 |
| 환경·데이터 문제 | 이번 변경과 무관한 곳에서 실패한다 | 판단 요청 |
| 원인을 모르겠다 | 위 어느 것에도 확신이 없다 | 판단 요청 |

## 판단 요청

사람이 메타를 열지 않고도 정할 수 있게 자세히 쓴다.

1. 무엇이 실패했는지: 시나리오 이름, 기대한 것, 실제로 본 것
2. 지금까지 한 것: 수정 시도 횟수와 각각 무엇을 바꿨는지
3. 분석: 원인을 무엇으로 보는지와 그 근거, 확인하지 못한 것
4. 선택지와 권장: 2~3개, 각각 무엇이 일어나는지
5. 이어 가는 법: `/do {키}` 로 답하면 된다

같은 내용을 `design.md` 의 `## 확인이 필요했던 것` 에 적고, 알림으로 보내고(공통 규칙 "알림 보내는 법"), `dobby_phase {키} 보류` 로 멈춘다.
