# 세션 6-2 · 검증 실패 분석 (기획자)

검증이 실패하면 기획자가 원인을 가른다. 이 세션은 **코드를 고치지 않는다.** 결론을 설계 문서와 테스트 계획에 남기고 끝낸다. 고치는 일은 다음 구현 세션이 변경 절을 보고 한다. 그래서 왜 실패했고 무엇을 바꾸기로 했는지가 설계 문서에 남는다.

자동 배포 오더든 사람이 돌리는 오더든 같다.

## 읽을 것

1. 마지막 `test-runs/{시각}/` 의 실패 기록
2. 상태 문서 `## 배포` 표
3. `design.md` 와 `test-plan.md` — 실패한 시나리오와 그 시나리오가 확인하는 설계 부분만

## 하는 일

1. **배포부터 의심한다.** 실패한 화면의 번들이 이번 커밋으로 나갔는지 `dobby_ship_verify`, com.wadiz.web 이면 `dobby_ship_argo {키} {환경} check` 로 본다.
2. 원인을 하나로 고르고 아래 표대로 적은 뒤 끝낸다.

| 원인 | 어떻게 알아보나 | 적는 것 | 끝내는 줄 |
|---|---|---|---|
| 코드 결함 | 실패가 이번 변경 부분에서 재현된다 | 설계 문서에 `## 변경 {M} — 검증 실패 {시나리오}` 절(형식은 `steps/change.md`). 테스트 계획의 실패한 시나리오를 다시 검증할 항목으로 돌리고, 필요하면 새 항목을 더한다 | `dobby_v2_end {키} 변경접수` |
| 배포가 덜 됐다 | 빠진 번들이 있거나 argocd 가 `OutOfSync`·`Progressing` | 자동 배포 오더면 `dobby_ship_stage` 로 그 행을 다시 할 단계(번들이 빠졌으면 `빌드 대기`, sync 가 덜 됐으면 `배포 대기`)로 되돌린다 | `dobby_v2_end {키} 재배포` |
| 테스트 계획이 틀렸다 | 기대 결과가 설계 문서와 어긋난다 | 테스트 계획의 그 항목을 고치고, 설계 문서에 `## 변경 {M} — 검증 항목 고침 {시나리오}` 절로 "코드 변경 없음"을 적는다 | `dobby_v2_end {키} 재검증` |
| 환경·데이터 문제, 원인을 모르겠다, 수정 상한 초과 | 이번 변경과 무관한 곳에서 실패한다. 위 어느 것에도 확신이 없다. `dobby_v2_test_fixes {키}` 가 2 이상이다 | 아래 "판단 요청" | `dobby_v2_end {키} 판단요청 "{질문 한 줄}"` |

변경 절 제목의 "검증 실패" 는 바꾸지 않는다. `dobby_v2_test_fixes` 가 이 제목으로 수정 횟수를 센다.

끝 헬퍼는 결론에 맞는 기록이 시작 뒤 남았는지 확인한다. 변경접수면 새 변경 절과 테스트 계획 수정, 재검증이면 테스트 계획 수정, 판단요청이면 `## 확인이 필요했던 것` 절이다. 결론이 옳은지는 확인하지 못한다. 그래서 근거를 변경 절에 `파일:라인` 과 실패 기록으로 남긴다.

변경접수는 사람의 확정 없이 들어간다(실패 분석이 자동 승인을 기록한다). 사람이 돌리는 오더도 같다.

## 판단 요청

사람이 메타를 열지 않고도 정할 수 있게 자세히 쓴다.

1. 무엇이 실패했는지: 시나리오 이름, 기대한 것, 실제로 본 것
2. 지금까지 한 것: 수정 시도 횟수와 각각 무엇을 바꿨는지
3. 분석: 원인을 무엇으로 보는지와 그 근거, 확인하지 못한 것
4. 선택지와 권장: 2~3개, 각각 무엇이 일어나는지
5. 이어 가는 법: `/do {키}` 로 답하면 된다

같은 내용을 `design.md` 의 `## 확인이 필요했던 것` 에 적는다. 자동 배포 오더면 알림도 보낸다(공통 규칙 "알림 보내는 법").
