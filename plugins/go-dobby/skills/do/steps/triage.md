# 세션 6-2 · 설계 다시 보기 (기획자)

다른 담당자가 넘긴 문제를 기획자가 받는다. 이 세션은 **코드를 고치지 않는다.** 원인을 가르고, 결론을 설계 문서(와 필요하면 테스트 계획)에 남기고 끝낸다. 고치는 일은 다음 세션이 변경 절을 보고 한다. 그래서 무엇이 문제였고 무엇을 바꾸기로 했는지가 설계 문서에 남는다.

사람을 부르지 않는다. 변경 절은 사람의 확정 없이 들어간다(끝 헬퍼가 자동 승인을 기록한다). 자동 배포 오더든 사람이 돌리는 오더든 같다.

## 무엇이 넘어왔나

시작 헬퍼의 `설명:` 줄이 알려 준다.

| 설명 줄 | 넘어온 것 | 누가 넘겼나 | 아래 절 |
|---|---|---|---|
| `검증 실패 분석 — {시나리오}` | 검증이 실패했다 | 테스터 | "검증 실패" |
| `설계 다시 보기 — 구현 중 넘김 — {이유}` | 구현 중 설계대로 할 수 없다 | 개발자 | "구현·수정·산출 중 넘어온 것 / 리뷰 지적" |
| `설계 다시 보기 — 수정 중 넘김 — {이유}` | 지적을 설계 안에서 고칠 수 없다. 또는 내부 리뷰가 3번을 넘도록 닫히지 않는다 | 개발자 | 같은 절 |
| `설계 다시 보기 — 산출 중 넘김 — {이유}` | 산출물 명세대로 만들 수 없다 | 산출자 | 같은 절 |
| `설계 다시 보기 — 리뷰 지적 — {N}차 리뷰, …` | 설계대로 만들었는데 결함이 있다 | 리뷰어의 지적 | 같은 절 |
| `설계 다시 보기 — PR 리뷰 지적 — {저장소 #번호}: {요약}` | PR 에 변경요청이 달려 PR 을 닫았다 | 배포담당 | "PR 변경요청" |

## 방향을 고르는 기준 (모든 경우 공통)

순서대로 본다.

1. 문제를 실제로 없애는가
2. 이슈가 요구한 결과를 지키는가
3. 바뀌는 범위가 가장 작은가

고른 안과 이유, 버린 안은 `design.md` 의 `## 결정과 근거` 표에 적는다. `왜` 칸은 **`자동 결정 —` 으로 시작한다**(대시보드가 이 글자로 스스로 정한 결정을 찾는다). 제품 동작이 달라지는 선택이면 같은 칸에 "확인해 보세요"와 무엇이 달라지는지를 함께 적는다.

| 결정한 것 | 고른 답 | 왜 | 검토한 대안 |
|---|---|---|---|
| (무엇을) | (고른 안) | 자동 결정 — (이유. 근거 `파일:줄`) | (버린 안과 버린 이유) |

## 변경 절 제목 (바꾸지 않는다 — 횟수를 이 제목으로 센다)

변경 절의 형식은 `steps/change.md` 의 것을 쓴다. 제목만 아래대로 한다. `steps/change.md` 의 "자동 실행 확인"과 사람 확정, `dobby_v2_change_open` 은 하지 않는다. 그것은 사람이 요청한 변경을 받는 절차다. 다음 리뷰 차수의 빈 폴더는 변경을 구현한 세션의 끝 헬퍼가 연다.

| 넘어온 것 | 변경 절 제목 |
|---|---|
| 구현 중 설계대로 할 수 없음 | `## 변경 {M} — 구현 불가 {요약}` |
| 설계대로 구현됐는데 결함이 있음 | `## 변경 {M} — 리뷰 지적 {요약}` |
| 내부 리뷰가 3번을 넘도록 닫히지 않음 | `## 변경 {M} — 리뷰 미종료 {요약}` |
| PR 에 변경요청이 달림 | `## 변경 {M} — PR 리뷰 지적 {요약}` |
| 검증 실패의 원인이 코드 | `## 변경 {M} — 검증 실패 {시나리오}` |

## 구현·수정·산출 중 넘어온 것 / 리뷰 지적

읽을 것은 넘긴 이유(설명 줄), 설계 문서의 그 부분, 구현 기록(`implementation.md`) 또는 산출 기록, 리뷰 지적이면 최신 차수의 리뷰 결과다. 넘긴 이유를 **코드에서 직접 확인**한다.

| 확인한 결과 | 적는 것 | 끝내는 줄 |
|---|---|---|
| 설계를 바꿔야 한다 | 위 제목의 변경 절(고칠 코드, 리뷰 항목까지). 동작이 바뀌면 테스트 계획도 맞춘다. `## 결정과 근거` 에 자동 결정 줄 | `dobby_v2_end {키} 변경접수` |
| 설계는 맞고 구현이 달랐다 | 변경 절을 쓰지 않는다 | `dobby_v2_end {키} 돌려보냄 "{설계가 맞는 근거와 고칠 방향}"` — 리뷰 지적이 남아 있으면 수정으로, 아니면 구현(산출)으로 돌아간다 |
| 아래 "사람에게 묻는 경우"에 든다 | 질문 | `dobby_v2_end {키} 질문` |

리뷰 지적에 `설계대로 구현됨` 과 `구현이 설계와 다름` 이 섞여 있으면 변경 절 하나에 함께 담는다. 설계가 바뀌면 구현도 다시 하기 때문이다.

내부 리뷰가 3번을 넘겨 넘어왔고, 이미 `## 변경 {M} — 리뷰 미종료` 절이 있는데 또 넘어왔으면(기획자가 다시 설계한 뒤에도 닫히지 않았다) 변경 절을 더 쓰지 않고 질문한다.

일이 없어진 담당자가 생기면(고칠 수 없어 원인만 정리하기로 함 등) `dobby_v2_role_skip {키} {담당자} "{이유}"` 로 "할 일 없음"을 남긴다. 담당자가 더 필요하면 `dobby_v2_set_roles {키} "{담당자}" "{근거}"` 로 켠다(`steps/design.md` 1-1-2 의 표).

## PR 변경요청

읽을 것은 닫힌 PR 의 리뷰 본문(`gh pr view {번호} --repo {저장소} --comments`)과 설계 문서다. 지적을 **코드에서 직접 확인**한다.

| 확인한 결과 | 적는 것 | 끝내는 줄 |
|---|---|---|
| 지적이 타당하다 | `## 변경 {M} — PR 리뷰 지적 {요약}` 절. 닫힌 PR 번호와 지적, 어떻게 고칠지. 새 PR 본문에 실을 "지적과 처리" 표(`\| 지적 \| 처리 \| 근거 \|`)도 이 절에 적어 둔다 | `dobby_v2_end {키} 변경접수` — 구현, 내부 리뷰, 통합을 거쳐 새 PR 로 다시 올린다 |
| 지적이 타당하지 않다 | 같은 제목의 변경 절에 "코드 변경 없음"과 근거(`파일:줄`), 새 PR 본문에 실을 "지적과 처리" 표 | `dobby_v2_end {키} 재배포` — 구현과 내부 리뷰를 건너뛰고 배포 세션이 근거를 실어 새 PR 을 올린다 |
| `dobby_v2_pr_fixes {키}` 가 이미 3이다 | 질문 | `dobby_v2_end {키} 질문` |

변경요청으로 설계를 바꾸는 것은 3번까지다. 센 값은 `## 변경 {M} — PR 리뷰 지적` 절 수다(`dobby_v2_pr_fixes`). 넘으면 끝 헬퍼가 `변경접수`·`재배포` 를 받지 않는다.

## 검증 실패

### 읽을 것

1. 마지막 `test-runs/{시각}/` 의 실패 기록
2. 상태 문서 `## 배포` 표
3. `design.md` 와 `test-plan.md` — 실패한 시나리오와 그 시나리오가 확인하는 설계 부분만

### 하는 일

1. **배포부터 의심한다.** 실패한 화면의 번들이 이번 커밋으로 나갔는지 `dobby_ship_verify`, com.wadiz.web 이면 `dobby_ship_argo {키} {환경} check` 로 본다.
2. 원인을 하나로 고르고 아래 표대로 적은 뒤 끝낸다.

| 원인 | 어떻게 알아보나 | 적는 것 | 끝내는 줄 |
|---|---|---|---|
| 코드 결함 | 실패가 이번 변경 부분에서 재현된다 | 설계 문서에 `## 변경 {M} — 검증 실패 {시나리오}` 절(형식은 `steps/change.md`). 테스트 계획의 실패한 시나리오를 다시 검증할 항목으로 돌리고, 필요하면 새 항목을 더한다 | `dobby_v2_end {키} 변경접수` |
| 배포가 덜 됐다 | 빠진 번들이 있거나 argocd 가 `OutOfSync`·`Progressing` | 자동 배포 오더면 `dobby_ship_stage` 로 그 행을 다시 할 단계(번들이 빠졌으면 `빌드 대기`, sync 가 덜 됐으면 `배포 대기`)로 되돌린다 | `dobby_v2_end {키} 재배포` |
| 테스트 계획이 틀렸다 | 기대 결과가 설계 문서와 어긋난다 | 테스트 계획의 그 항목을 고치고, 설계 문서에 `## 변경 {M} — 검증 항목 고침 {시나리오}` 절로 "코드 변경 없음"을 적는다 | `dobby_v2_end {키} 재검증` |
| 환경·데이터 문제, 원인을 근거로 가를 수 없다, 수정 상한 초과 | 이번 변경과 무관한 곳에서 실패한다. 위 어느 것에도 근거가 없다. `dobby_v2_test_fixes {키}` 가 2 이상이다 | 질문 | `dobby_v2_end {키} 질문` |

변경 절 제목의 "검증 실패" 는 바꾸지 않는다. `dobby_v2_test_fixes` 가 이 제목으로 수정 횟수를 센다.

끝 헬퍼는 결론에 맞는 기록이 시작 뒤 남았는지 확인한다. 변경접수면 새 변경 절과 테스트 계획 수정, 재검증이면 테스트 계획 수정이다. 결론이 옳은지는 확인하지 못한다. 그래서 근거를 변경 절에 `파일:라인` 과 실패 기록으로 남긴다.

## 사람에게 묻는 경우 (이때만)

| 경우 | 왜 |
|---|---|
| 이슈가 요구한 결과 자체를 바꿔야 풀린다 | 이슈의 목적은 세션이 바꿀 수 없다 |
| 되돌아간 횟수가 상한을 넘었다: PR 변경요청 3번, 검증 실패 2번, 기획자가 다시 설계한 뒤에도 내부 리뷰가 안 닫힘 | 같은 자리를 돌고 있다 |
| 사람만 할 수 있는 일이다: 로그인, 시험 데이터 값, 아티팩트로 올리기 | 세션에 수단이 없다 |
| 원인을 근거로 가를 수 없다 | 틀린 방향으로 고치게 된다 |

그 밖은 스스로 정한다. 질문은 공통 규칙 "사람에게 묻는 법"대로 남기고 `dobby_v2_end {키} 질문` 으로 끝낸다. 단계는 그대로 두고 자동 실행이 답을 기다린다. 답이 오면 새 세션이 시작 헬퍼 결과의 `질문과 답:` 으로 받아 이 문서를 처음부터 다시 따른다. 그 답을 `## 결정과 근거` 에 사람의 결정으로 적고(`자동 결정 —` 을 붙이지 않는다) 위 표대로 끝낸다.

사람이 터미널에서 직접 돌리는 대화형 세션이면 질문을 남기지 않고 그 자리에서 묻는다.

옛 방식(`## 확인이 필요했던 것` 에 적고 `dobby_v2_end {키} 판단요청 "{질문 한 줄}"` 으로 끝내 단계를 보류로 바꾸는 것)은 자동 실행 없이 터미널에서만 돌리는 오더를 위해 남아 있다. 자동 실행이 띄운 세션은 쓰지 않는다. 보류가 되면 자동 실행이 끝나고 사람이 `/do {키}` 를 직접 쳐야 하기 때문이다.
