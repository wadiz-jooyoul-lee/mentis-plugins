# 세션 4 · 수정

## 읽을 것

1. 최신 차수의 리뷰 결과 파일 — `$ORCHESTRATION_META/{키}/reviews/round-{N}/review-agent.md`. dobby-order 에서 옮겨 온 오더는 파일 이름이 다를 수 있다(예: `inline-dev.md`). 그 폴더의 `.md` 파일을 전부 읽는다.
2. `design.md` — 설계 기준.

검증 실패는 이 세션으로 오지 않는다. 기획자가 실패를 분석해 설계 문서에 변경 절로 적고, 구현 세션이 그 변경을 구현한다.

## 하는 일

1. 워크트리에서 `[blocker]` 와 `[major]` 를 **전부 반영한다. 기각하지 않는다.** `[minor]` 와 `[nit]` 은 판단해서 처리하고, 안 할 거면 이유를 구현 기록에 적는다.
   - 지적 카드를 하나 처리할 때마다(반영하지 않기로 한 것 포함) 처리한 개수를 `dobby_progress {키} {처리한 수}` 로 적는다. 따로 부르지 말고 다음 명령 앞에 `&&` 로 붙인다. 사무실 진행 막대가 이 값을 읽는다.
2. 반영한 내용을 `implementation.md` 에 덧붙인다.
3. **커밋하지 않는다.**

## 설계 안에서 고칠 수 없을 때

지적을 반영하려면 설계가 정한 동작이나 범위를 바꿔야 하는 경우가 있다. 그때는 그 지적을 고치지 않고 기획자에게 넘긴다. 다른 지적을 이미 반영했으면 그대로 두고 구현 기록에 적는다.

```
dobby_v2_end {키} 설계문제 "{어느 지적이 왜 설계 안에서 안 고쳐지는지}"
```

지적이 틀렸다고 보여도 스스로 기각하지 않는다. 틀렸다는 근거(`파일:라인`)를 이유에 적어 같은 줄로 넘긴다. 설계를 기준으로 맞는지 가르는 것은 기획자다.

## 마무리

```
dobby_v2_end {키} 완료
```

끝 헬퍼가 다음 차수의 빈 리뷰 폴더를 열고 리뷰어 차례로 넘긴다. **반영했으면 반드시 다시 리뷰한다.**

**차수가 3을 넘으면 기획자에게 넘긴다.** 3차 리뷰의 지적을 반영하는 수정 세션이면 반영은 하되 `완료` 대신 `dobby_v2_end {키} 설계문제 "리뷰가 세 번을 넘겨도 닫히지 않습니다 — {무엇이 왜 안 닫히는지}"` 로 끝낸다. 그러면 다음 차수가 열리지 않고 기획자가 설계를 다시 본다. 변경을 리뷰하는 중이면 그 변경 절의 `리뷰 시작 차수` 부터 센다. 예를 들어 시작 차수가 4차면 6차가 마지막이다. 기획자가 설계를 다시 정한 뒤의 리뷰도 세 번을 넘기면 기획자가 사람에게 질문한다.
