# 세션 4 · 수정

## 읽을 것

1. 최신 라운드의 리뷰 결과 파일 — `$ORCHESTRATION_META/{키}/reviews/round-{N}/review-agent.md`. dobby-order 에서 옮겨 온 오더는 파일 이름이 다를 수 있다(예: `inline-dev.md`). 그 폴더의 `.md` 파일을 전부 읽는다.
2. `design.md` — 설계 기준.

검증 실패로 들어온 경우에는 리뷰 파일 대신 `test-runs/{시각}/` 의 실패 기록을 읽는다.

## 하는 일

1. `dobby_session_log {키} {슬러그} fix-{N} "{N}차 수정" {워크트리경로}` 그리고 `dobby_agent_state {키} {슬러그} 구현 "$(dobby_fix_count {키} {슬러그})"`. 검증 실패로 들어왔으면 하위 키를 `fix-test-{시각}`, 단계 이름을 `"검증 실패 수정"` 으로 쓴다.
2. 워크트리에서 `[blocker]` 와 `[major]` 를 전부 반영한다. `[minor]` 와 `[nit]` 은 판단해서 처리하고, 안 할 거면 이유를 적는다.
3. 반영한 내용을 `implementation.md` 에 덧붙인다.
4. **커밋하지 않는다.**

## 지적을 반영하지 않기로 할 때

"드물다"·"엣지 케이스다" 같은 **빈도 추정은 근거가 아니다.** 그 상태를 만드는 코드 경로를 `파일:라인` 으로 전수 확인해 **0건임을 증명**했을 때만 기각한다. 1건이라도 남으면 반영한다. 증명하지 못하면 반영한다.

## 마무리

```
dobby_review_path {키} {N+1} review-agent >/dev/null   # 다음 라운드 빈 폴더를 연다(파일은 만들지 않는다)
dobby_phase {키} 리뷰
dobby_agent_state {키} {슬러그} 대기
dobby_event {키} "{N}차 지적 반영 완료 — 재리뷰 세션으로 넘김"
```

**반영했으면 반드시 다시 리뷰한다.** 다음 세션은 리뷰다(라운드 번호가 하나 올라간다).

**라운드가 3을 넘으면 멈춘다.** 3차 리뷰의 지적을 반영하는 수정 세션이면, 4차 폴더를 열지 않는다. 변경을 리뷰하는 중이면 그 변경 절의 `리뷰 시작 차수` 부터 센다. 예를 들어 시작 차수가 4차면 6차가 마지막이다. 무엇이 왜 안 닫히는지 이벤트 로그에 적고 사람에게 넘긴다. 검증 실패로 들어온 수정은 이 셈에 넣지 않는다.
