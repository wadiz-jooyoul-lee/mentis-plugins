# 변경 접수 (진행 중에 새 요청이 들어왔을 때)

> 이 절은 설계의 1-2, 1-3, 1-5, 1-6 을 가리킨다. 같은 폴더의 `design.md` 를 함께 읽는다.

진행 중에 사람이 아래 같은 요청을 하면, **이 세션에서 바로 코드를 고치지 않는다.** 설계 문서와 상태를 고쳐 두고 끝낸다. 사람이 세션을 닫고 `/do {키}` 를 다시 치면 새 세션이 그 변경만 구현한다.

| 요청 | 예 |
|---|---|
| 수정 지시 | "버튼 문구를 바꿔 줘", "이 경우엔 숨겨 줘" |
| 새 버그 | 테스트나 확인 중에 새로 발견한 결함 |
| 추가 설계 | 디자인 변경, 이벤트(GA·GTM·Braze 수집) 추가 |

바로 고치지 않는 이유는 두 가지다. 이 세션의 문맥이 이미 크다(검증 세션은 끝날 때 10만~23만 토큰). 그리고 설계 문서를 거치지 않은 수정은 리뷰 항목과 테스트 계획에 빠져, 리뷰와 검증이 그 변경을 보지 못한다.

## 1. 기록과 사전 확인

```
dobby_v2_change_open {키} check
dobby_agent_add {키} analysis-agent "분석" "변경 {M} 접수" 분석 0
dobby_session_log {키} analysis-agent change-{M} "변경 {M} 접수" {워크트리경로}
dobby_agent_state {키} analysis-agent 분석 "" "변경 {M} 접수"
```

첫 줄이 거부하면(자동 실행이 돌고 있음) 아무것도 쓰지 않고 그 사실을 알린 뒤 끝낸다. 자동 실행이 상태 문서와 설계 문서를 읽고 있는 중이라, 변경 절을 먼저 쓰면 돌고 있는 리뷰 세션이 구현도 안 된 변경을 리뷰하게 된다.

M 은 설계 문서에 있는 `## 변경 N` 절의 가장 큰 N 에 1 을 더한 값이다. 없으면 1 이다. 이 세션이 이미 다른 단계로 기록돼 있어도 한 줄 더 남긴다.

## 2. 분석

요청이 새 버그면 원인을 코드에서 찾는다. 분석 원칙(`analysis-discipline.md`)을 그대로 따른다. 추가 설계면 디자인이나 이벤트 명세를 먼저 읽는다. A/B 테스트를 넣는 요청이면 1-3 의 A/B 규칙을 따른다. 설계 세션(1-2)과 같은 깊이로 하되, **이번 요청에 닿는 곳만** 본다.

## 3. 설계 문서에 변경 절을 덧붙인다

`design.md` 의 `## 리뷰 항목` 절 **뒤에** 덧붙인다. 앞의 본문은 고치지 않는다. 이미 통합된 내용의 기록이기 때문이다.

```markdown
## 변경 {M} — {한 줄 요약}

- **상태**: 구현 대기
- **종류**: 수정 지시 | 새 버그 | 추가 설계
- **요청**: (사람이 한 말을 그대로, 또는 요청 출처)
- **접수**: {YYYY-MM-DD HH:MM}
- **리뷰 시작 차수**: (5번에서 받은 값)차

### 무엇을 왜
### 고칠 코드
### 작업 순서
### 건드리지 않을 것
### 검증 명령
### 확인하지 못한 것
### 리뷰 항목
```

소절의 규칙은 1-3 의 "반드시 더 적는 것"과 `## 리뷰 항목` 절과 같다. 결정이 바뀌었으면 `## 결정과 근거` 표에 행을 더한다.

## 4. 테스트 계획을 맞춘다

먼저 이 변경이 고칠 파일로 `## 영향 번들` 표를 다시 판정한다(`${CLAUDE_PLUGIN_ROOT}/reference/bundle-scope.md`). 새로 영향이 된 번들이 생기면 표를 고친다. 그다음 이 변경을 확인할 시나리오를 `test-plan.md` 에 더한다. 영향인 번들마다 하나씩 둔다. 제목에 `(변경 {M})` 을 붙인다. 이 변경 때문에 기존 시나리오의 통과 기준이 바뀌면 그 시나리오도 고친다. 검증 세션은 계획 전체를 다시 돌린다. 앞서 고친 것이 깨지지 않았는지도 함께 보기 위해서다.

그다음 1-5 자족성 점검을 이 변경 절에 대해 돈다.

## 5. 확인받고 상태를 되돌린다

1-6 과 같은 형식으로 **변경 절만** 요약해 보여 준다(한 장 요약, 고칠 파일, 테스트 시나리오, 리뷰 항목). 끝의 "자동 실행" 과 "직접 실행" 안내도 1-6 과 같다. 사람이 고칠 곳을 말하면 1-6 의 규칙대로 고친다.

`auto` 실행(사람 없는 실행)에서는 변경 접수를 하지 않는다. 변경은 사람이 요청하는 것이기 때문이다.

사람이 "자동 실행" 이나 "직접 실행" 이라고 하면(옛 낱말 "확정"·"확정만"도 같다) 아래 순서로 부른다.

```
dobby_v2_change_open {키}          # 출력값 = 리뷰 시작 차수. 설계 문서 변경 절에 적는다
dobby_design_ack {키} 사용자         # 변경 절을 적은 뒤에 불러야 한다(설계 지문이 바뀌므로)
dobby_agent_state {키} {슬러그} 대기
dobby_agent_state {키} analysis-agent 완료
dobby_event {키} "변경 {M} 확정 — 구현 세션으로 넘김"
```

`dobby_v2_change_open` 이 하는 일은 아래와 같다.

| 하는 일 | 왜 |
|---|---|
| 자동 실행이 돌고 있으면 거부한다 | 그 실행이 같은 상태 문서를 고치고 있다. 거부되면 사람에게 그대로 전하고 끝낸다. 설계 문서의 변경 절은 남겨 둔다 |
| 단계가 해결이면 해결 표시를 무른다 | 다시 작업하는 오더가 "해결"로 남지 않게 한다 |
| 다음 리뷰 차수의 빈 폴더를 연다 | 안 열면 리뷰 세션이 지난 차수의 결과에 덮어쓰고, 지적 0건인 옛 결과 때문에 리뷰 없이 통합으로 넘어간다 |
| 단계를 분석으로 바꾼다 | 단계 판정이 "분석 + 지금 설계와 같은 승인 = 구현"으로 읽는다 |

**"자동 실행"이면** 1-6 과 같이 `dobby_v2_autorun {키}` 로 자동 실행을 띄운다. **"직접 실행"이면** 띄우지 않는다.

Jira 상태는 건드리지 않는다. 이미 '해결됨'이면 다시 열지는 사람이 정한다. 보고에 지금 Jira 상태를 적는다.

## 6. 마무리

"세션을 닫는 법" 형식으로 알린다. `다음` 칸은 아래로 쓴다.

```
다음
  - 이 세션을 닫아 주세요. (/clear 또는 터미널 종료)
  - 새 세션에서: /do {키}  ← 변경 {M} 을 구현합니다
```

자동 실행을 띄웠으면 "자동 실행을 띄웠을 때" 형식을 쓴다.
