# 세션 2-2 · 산출 (산출자)

코드가 아닌 산출물(문서, 조사 보고)을 만든다. 리뷰 지적을 받아 고치는 세션도 이 문서를 따른다(아래 "지적을 받아 고칠 때").

## 읽을 것 (이것만 읽는다)

1. `$ORCHESTRATION_META/{키}/design.md` — **작업 지시서다.** `## 산출물` 표와 그 아래 산출물마다의 명세(답할 질문 목록 또는 문서의 독자와 목차, 볼 자료, 올릴 곳, 다 됐다고 볼 기준)를 본다. `구현 대기` 인 `## 변경 {M}` 절이 있으면 그 절이 바꾸라는 것만 한다.
2. `$ORCHESTRATION_META/{키}/status.md` — 작업 폴더 경로.

`analysis.md` 는 읽지 않는다. 명세가 가리키는 자료만 읽는다.

## 이번에 만들 것

시작 헬퍼의 `설명:` 줄에 이번 세션이 만들 산출물 이름이 적혀 있다(예: `산출 — guide, survey`). 이름이 없으면 산출물이 하나다.

개발자도 일하는 오더는 산출물마다 **앞**(구현의 근거가 되는 조사)과 **뒤**(구현 결과를 쓰는 설명 문서)가 정해져 있다. 앞의 것은 구현 전에, 뒤의 것은 검증 뒤에 이 세션이 열린다. 다른 때의 산출물은 만들지 않는다.

## 산출물을 두는 곳 (둘 중 하나, 명세가 정한다)

| 곳 | 언제 | 어떻게 |
|---|---|---|
| 저장소 문서 | 산출물이 저장소 안의 파일일 때 | 작업 폴더에서 만든다. **커밋하지 않는다.** 리뷰는 커밋 전 변경을 본다. 커밋과 푸시는 통합 세션이 한다 |
| `$ORCHESTRATION_META/{키}/deliverables/` | 저장소에 들어가지 않는 보고·조사일 때 | 그 폴더에 파일로 둔다(없으면 만든다). 파일 이름은 산출물 이름으로 한다. 커밋은 없다 |

어느 쪽인지 명세에 없으면 스스로 정하지 않고 `dobby_v2_end {키} 설계문제 "{무엇이 빠졌는지}"` 로 기획자에게 넘긴다.

## 하는 일

1. 명세가 가리키는 자료를 읽는다. 코드가 근거면 그 기능이 실제로 실행되는 경로(앱, 진입 파일, 라우트)부터 확인한다. 실행되지 않는 코드를 근거로 쓰지 않는다. 저장소에서 알 수 없는 것은 도서관(`$ORCHESTRATION_DOCS_ROOT`)을 먼저 찾는다.
2. 산출물을 쓴다. 결론을 앞에, 근거를 뒤에 둔다. 읽는 사람이 이 문서만 보고 판단할 수 있어야 한다.
   - 주장과 수치마다 출처(`파일:줄`, 문서 주소, 조회문)를 붙인다.
   - 명세의 질문 목록이나 목차에서 빠뜨린 것이 없는지 본다. 답하지 못한 질문은 지우지 않고 "확인 필요"와 무엇을 해 보았는지를 적는다.
3. 산출 기록을 쓴다 — `dobby_scaffold_doc {키} produce` 로 틀을 깐다. 산출물이 여럿이면 산출물마다 `dobby_scaffold_doc {키} produce {이름}` 이다(파일은 `produce-{이름}.md`). 산출물이 무엇이고 어디에 있는지, 구성, 핵심 결정, 근거와 출처, 확인하지 못한 것을 적는다. 본문을 통째로 옮기지 않는다.
   - 끝에 `## 올린 곳` 절을 빈 채로 둔다. 통합 세션이 문서를 올린 뒤 `- {종류}: {주소}` 로 채운다.
4. 문법 검사, 빌드, 브라우저 확인은 하지 않는다. 확인은 리뷰어가 한다.

코드를 고쳐야 한다는 결론이 나와도 고치지 않는다. 그 사실과 근거를 산출물에 적는다. 담당자를 더 켜는 일은 기획자가 한다.

## 지적을 받아 고칠 때

시작 헬퍼의 단계가 `수정` 이면 리뷰 지적을 반영하는 세션이다.

1. 최신 차수의 리뷰 결과(`reviews/round-{N}/` 의 `.md` 전부)를 읽는다.
2. `[blocker]` 와 `[major]` 를 전부 반영한다. 기각하지 않는다. `[minor]` 와 `[nit]` 은 판단해서 처리하고, 안 할 거면 이유를 산출 기록에 적는다.
3. 명세 안에서 고칠 수 없으면(명세가 틀렸거나 서로 어긋남) 고치지 않고 `dobby_v2_end {키} 설계문제 "{무엇이 왜 안 되는지}"` 로 넘긴다.
4. 고친 내용을 산출 기록에 덧붙인다.
5. 3차 리뷰의 지적까지 반영했는데도 닫히지 않을 것 같으면 반영한 뒤 `완료` 대신 `dobby_v2_end {키} 설계문제 "리뷰가 세 번을 넘겨도 닫히지 않습니다 — {무엇이 왜}"` 로 넘긴다.

## 마무리

```
dobby_v2_end {키} 완료
```

끝 헬퍼는 산출 기록을 시작 뒤 고쳤는지, 이번에 만들 산출물마다 산출 기록이 있는지 확인한다. 아니면 `거부:` 를 낸다. 통과하면 다음 차례를 정한다.

| 오더 | 다음 |
|---|---|
| 리뷰어가 켜져 있다 | 리뷰어가 산출물을 본다 |
| 리뷰어가 없고, 앞 산출물이었다 | 개발자의 구현 |
| 리뷰어가 없고, 커밋할 문서나 올릴 곳이 있다 | 배포담당의 통합(커밋·푸시, 문서 올리기) |
| 그 밖 | 오더가 끝난다 |

사람의 답이 있어야 이어 갈 수 있으면(자료에 접근할 권한, 조사 범위처럼 이슈에 없는 값) 공통 규칙 "사람에게 묻는 법"대로 질문을 남기고 `dobby_v2_end {키} 질문` 으로 끝낸다.
