# 세션 5-2 · 배포 (자동 배포 오더 · 배포담당)

진행은 상태 문서 `## 배포` 표가 나타낸다.

1. `dobby-ship` 스킬 절차를 `{키} {자동 배포 환경}` 으로 따른다. 그 스킬의 **"자동 실행에서"** 절대로 한다 — 머지·빌드·sync 를 묻지 않고, 리뷰봇과 빌드를 기다리지 않고, 검증은 하지 않는다.
2. 아래 자리에 닿으면 끝 헬퍼로 끝낸다. 다음 세션은 자동 실행이 정한다.

| 닿은 자리 | 끝내는 줄 |
|---|---|
| `리뷰 대기`·`빌드 대기`·`배포 대기` | `dobby_v2_end {키} 기다림` |
| 모든 저장소가 `배포 확인` | `dobby_v2_end {키} 배포확인` |
| PR 에 변경요청이 달렸다 | 아래 "변경요청이 달렸을 때"대로 PR 을 닫고 `dobby_v2_end {키} 리뷰지적 "{지적 요약}"` |
| 막혀서 못 나아감 | 그 행의 비고에 무엇이 왜 막혔는지 적고(`dobby_ship_stage` 의 비고 칸) `dobby_v2_end {키} 막힘` |
| 사람의 승인이 꼭 필요함 | `dobby_v2_end {키} 사람승인 "{무엇을 승인받아야 하는지}"` |
| 사람 손이 있어야 이어 갈 수 있음(로그인 등) | 공통 규칙 "사람에게 묻는 법"대로 질문을 남기고 `dobby_v2_end {키} 질문`. 답이 오면 이 세션을 이어 띄운다 |

끝 헬퍼는 고른 결과가 배포 표와 맞는지 확인한다. 맞지 않으면 `거부:` 를 낸다.

테스터가 없는 오더는 `배포확인` 으로 끝내면 검증으로 넘어가지 않는다. 뒤에 쓰는 산출물이 있으면 산출자 차례가 되고, 없으면 오더가 끝난다.

## 변경요청이 달렸을 때

PR 의 리뷰 결정이 변경요청(`CHANGES_REQUESTED`)이면 **고치지 않는다.** 변경요청은 설계 오류로 보고 기획자부터 다시 돈다. 승인에 딸린 지적과 지적이 담긴 코멘트는 지금처럼 `dobby-ship` 4번대로 범위 안에서 고친다.

1. 리뷰 본문을 읽고 지적을 한두 줄로 요약한다. 코드는 건드리지 않는다.
2. PR 을 닫는다. 배포 표의 그 줄도 이 헬퍼가 지운다.

   ```
   dobby_ship_close_pr {키} {워크트리} {환경} {PR 번호} "{지적 요약}"
   ```

3. `dobby_v2_end {키} 리뷰지적 "{지적 요약}"` 으로 끝낸다. 끝 헬퍼는 닫은 PR 기록이 있는지, 이 세션이 작업 폴더를 바꾸지 않았는지 확인한다. 바꿨으면 `거부:` 를 낸다. 그때는 바꾼 것을 되돌리고 다시 부른다.

그 뒤는 기획자가 지적을 확인해 설계를 고치고, 개발자가 구현하고, 리뷰어가 내부 리뷰를 하고, 통합을 거쳐 이 세션이 다시 열린다.

## 변경요청 뒤 다시 올릴 때

배포 표에 이 환경의 줄이 없고 설계 문서에 `## 변경 {M} — PR 리뷰 지적 …` 절이 있으면 변경요청 뒤 다시 올리는 차례다. PR 을 만들 때 그 절에 적힌 "지적과 처리" 표를 일곱째 인자로 준다. 본문 끝에 "이전 PR 의 지적과 처리" 절로 실린다. 표 없이 부르면 헬퍼가 거부한다.

```
dobby_ship_pr {키} {워크트리} {브랜치} {환경} "{제목}" "{본문}" "| 지적 | 처리 | 근거 |
|---|---|---|
| {지적} | 반영 또는 안 함 | {근거} |"
```

기획자가 "코드 변경 없음"으로 정한 경우도 같다. 처리 칸에 "안 함"과 근거를 싣는다.
