# 세션 1 · 설계

**이 세션이 v2 의 전부다.** 뒤따르는 세션들은 여기서 만든 문서만 읽고 일한다. 문서가 부족하면 뒷세션이 코드를 다시 뒤져야 하고, 그러면 세션을 나눈 의미가 사라진다.

## 1-1. 골격과 착수

1. `dobby_bootstrap {키} "{임시제목}" 개발 "{키워드1|키워드2}"` — 폴더·골격·종류·세션·docs 게이트를 한 번에 깐다.
2. Jira 이슈를 조회한다(작업 키 `TASK-` 면 건너뛴다). Jira 는 MCP 가 아니라 `twg` 로 다룬다(`${CLAUDE_PLUGIN_ROOT}/reference/jira-twg.md`).
   - 조회: `twg jira workitem get {키} --fields summary,status,issuetype,parent,labels`
   - 설명: `dobby_jira_desc {키} $ORCHESTRATION_META/{키}/jira-issue.md` 로 파일에 받아 읽는다. 대시보드 Jira 탭도 이 파일을 쓴다.

   조회 직후 **그 자리에서** 두 가지를 한다.
   - `dobby_set_title {키} "{실제 이슈 요약}"` — 임시 제목을 실제 요약으로 바꾼다.
   - `dobby_jira_start_transition {키}` 로 진행 중으로 전환한다. 이어서 `${CLAUDE_PLUGIN_ROOT}/reference/jira-start.md` 를 따라 시작 날짜를 적고 상위 이슈 레이블을 더한다.
3. 워크트리를 준비한다 — `dobby_ensure_worktree {저장소} {키} {prefix} {base}`. `prefix` 는 버그면 `bugfix`, 그 밖은 `feature` 다(빗금은 헬퍼가 붙인다). 이 헬퍼는 상태 문서에 이미 적힌 워크트리가 있으면 그것을 쓰고, 폴더가 지워졌으면 남은 브랜치로 되살리고, 아무것도 없을 때만 새로 만든다. git 에 등록되지 않은 폴더가 같은 자리에 있으면 지우지 않고 멈춘다. 그때는 사람에게 그 폴더를 확인해 달라고 알린다.
4. 상태표에 두 행을 넣는다(공통 규칙 "보드의 상태표"). 개발 담당 슬러그는 `dobby_slug` 로 만들고, 마지막 0 은 수정 횟수다.
   ```
   dobby_agent_add {키} analysis-agent "분석" "{작업 한 줄}" 분석 0
   dobby_agent_add {키} {슬러그} "개발자" "{작업 한 줄}" 대기 0
   ```
5. `dobby_session_log {키} analysis-agent design 설계 {워크트리경로}` — 이 세션의 아이디를 기록한다(공통 규칙 "세션 기록").

## 1-2. 분석 → `analysis.md`

`dobby_scaffold_doc {키} analysis` 로 틀을 깔고 채운다. 틀은 **하한선**이다 — 필요한 만큼 길게 쓰고, 틀에 맞추려고 분석을 줄이지 않는다.

- 코드를 직접 읽어 원인을 `파일:라인` 으로 짚는다. 증상 서술로 끝내지 않는다.
- 현재 저장소에서 알 수 없는 외부 참조가 나오면 **도서관**(`$ORCHESTRATION_DOCS_ROOT`)을 먼저 뒤진다.
- 레거시 앱이나 별도 번들로 뜨는 앱이면 `## 이 앱에 없는 것` 절을 반드시 채운다(국제화 초기화 여부, 같은 주소로 닿는 API 경로, 공용 패키지 재사용 가능 여부).

## 1-3. 설계 → `design.md`

`dobby_scaffold_doc {키} design` 으로 틀을 깔고 채운다. 규칙은 `dobby-design` 스킬의 design.md 규칙을 그대로 따른다.

**v2 에서 달라지는 것은 읽는 사람이다.** 기존에는 사용자가 읽고 승인하는 문서였다. v2 에서는 **다음 세션의 개발 담당이 이것만 보고 코드를 쓰는 작업 지시서**다. 그래서 아래를 더 한다.

### 반드시 더 적는 것

1. **작업 순서** — 고칠 파일이 둘 이상이면 어느 것부터 손대야 하는지와 그 이유. 의존이 있으면(A 를 바꿔야 B 가 컴파일된다) 명시한다.
2. **건드리지 않을 것** — 범위 밖인데 눈에 띌 파일을 미리 적는다. 적지 않으면 개발 담당이 "겸사겸사" 고친다.
3. **검증 명령** — 구현 담당이 자기 작업을 확인할 실제 명령을 적는다. 예: `npm run lint -- {경로}`, `npm run build`, `npx tsc --noEmit`. 저장소마다 다르므로 **실제로 있는 명령인지 확인하고** 적는다.
4. **확인하지 못한 것** — 모른 채 남은 것을 전부 적는다. 각 항목마다 **구현 담당이 어떻게 해야 하는지**까지 적는다(예: "이 값이 null 로 오는 경우가 있는지 확인 못 했다. 방어 코드를 넣고 주석으로 남길 것"). 빈칸으로 두면 뒷세션이 멈춘다.

**A/B 테스트(실험군 분기)를 넣는 요청이면** `ab-test-design` 스킬(wadiz-client 플러그인)을 불러 그 규칙대로 design.md·test-plan.md 의 실험 내용을 채운다. 설치돼 있지 않으면 설계를 확정하지 않고 "ab-test-design 스킬 필요"를 확인할 것으로 남긴다.

### `## 리뷰 항목` 절 (v2 고유 · design.md 맨 끝에 덧붙인다)

리뷰 담당 세션이 읽을 확인 목록이다. **별도 파일로 만들지 않는다** — 대시보드는 파일 이름을 하드코딩해 읽기 때문에 새 파일은 보이지 않는다. design.md 안에 두면 "설계/결과" 탭이 그대로 보여 준다.

설계를 막 끝낸 지금이 **이 변경에서 무엇이 틀리기 쉬운지 가장 잘 아는 시점**이다. 그 지식을 넘긴다.

```markdown
## 리뷰 항목

### 이 변경에서 틀리기 쉬운 곳
| 확인할 것 | 어디를 | 왜 위험한가 |
|---|---|---|
| (한 줄) | `경로:라인` | (설계할 때 망설였던 이유) |

### 영향받는 호출부
| 바뀌는 것 | 부르는 곳 | 확인할 것 |
|---|---|---|
| `함수명`의 반환 형태 | `경로:라인` | (이 호출부가 무엇을 기대하는가) |

- 소비처가 없으면 "소비처 없음 — {어떻게 확인했는지}" 라고 적는다. 안 적으면 안 본 것과 구별되지 않는다.

### 이 저장소에서 지켜야 할 규약
- (CLAUDE.md·NAMING·GLOSSARY 에서 이번 변경에 걸리는 것만)
```

**호출부를 찾는 법**: 내보내는 이름·공개 메서드 이름만으로는 부족하다. 지우는 줄의 **문자열 값**과 **파일 이름**까지 찾는다. 이름을 쪼개 만드는 참조(`'reward-' + name`)와 설정 파일이 간접으로 부르는 것은 이름 검색으로 안 잡히므로 따로 본다.

## 1-4. 테스트 케이스 → `test-plan.md`

`dobby_scaffold_doc` 에 test-plan 틀은 없다. 아래 형식으로 직접 쓴다.

**검증 담당 세션이 이 문서만 보고 브라우저를 열어 테스트하고, 통과인지 실패인지 혼자 판정할 수 있어야 한다.**

**⛔ 시나리오를 쓰기 전에 영향 번들부터 판정한다.** `${CLAUDE_PLUGIN_ROOT}/reference/bundle-scope.md` 를 따라 네 번들(`static`, `static-global`, `static-account`, `studio`)이 이번 변경에 닿는지 가리고, 결과를 `## 영향 번들` 표로 적는다. 그다음 영향인 번들마다 그 번들의 화면에서 확인하는 시나리오를 만든다. 이슈에 적힌 화면 하나만 보고 시나리오를 쓰면, 같은 코드를 쓰는 다른 번들의 화면이 확인 없이 나가기 때문이다.

```markdown
# {키} 테스트 계획

## 사전 준비
- 테스트 환경: {주소}
- 로그인 계정: {아이디} (비밀번호는 config.env 의 TEST_LOGIN_PW)
- 필요한 데이터 상태: (예: 종료된 펀딩 프로젝트 1건, 알림 신청 이력 있는 계정)

## 영향 번들
| 번들 | 판정 | 근거 | 확인 시나리오 |
|---|---|---|---|
| static | 영향 / 제외 / 해당 없음 | (`파일:라인` 또는 찾은 명령과 결과) | S1 |
| static-global | | | |
| static-account | | | |
| studio | | | |

## 검증 묶음
| 묶음 | 시나리오 | 공통 준비 | 묶은 이유 |
|---|---|---|---|
| V1 | S1, S4, S5 | 데스크톱 폭, 로그인, 프로젝트 406114 | 같은 리워드 선택 모달 |

## S1. {시나리오 이름}
- **조건**: C1
- **번들**: static
- **대상 주소**: https://{환경}/{경로}
- **사전 상태**: (이 시나리오를 시작하기 전에 갖춰져야 할 것)
- **조작 단계**:
  1. (사람이 그대로 따라 할 수 있는 동작 하나)
  2. ...
- **통과 기준**: (무엇이 화면에 보이면 통과인가 — 눈으로 판정 가능한 문장으로)
- **실패로 보는 것**: (어떤 모습이면 실패인가)
- **남길 증거**: (화면 캡처 / 개발자 도구 콘솔 / 네트워크 요청 중 무엇을)
```

- **`- **조건**: C1`** 은 `status.md` 의 `## 닫히는 조건 항목` 표에서 가져온다. 대시보드 검증 탭이 "조건 몇 가지 중 몇 가지 확인"을 이 값으로 센다.
- 사전 준비의 데이터(프로젝트 번호, 계정 등)를 dev·rc4 DB 에서 골라야 하면 `wadiz-shared:cloud-db-query` 스킬로 조회한다(`analysis-discipline.md` 6). 고른 값과 그 값을 찾은 조회문을 함께 적는다.
- **통과 기준은 "정상 동작한다" 로 쓰지 않는다.** 무엇이 보이면 통과인지 적는다. 예: "버튼 아래에 '마감된 프로젝트입니다' 라는 회색 문구가 보인다".
- 데이터 수집(수집 태그·수집 스크립트)이나 광고 노출을 건드렸으면 그 시나리오를 반드시 넣는다. 화면에는 안 보이게 깨지기 때문이다.
- 기존 기능이 망가지지 않았는지 보는 **회귀 확인 시나리오를 최소 하나** 넣는다. 영향 번들이 둘 이상이면 회귀 확인도 번들마다 둔다.
- **`- **번들**:`** 은 그 시나리오가 확인하는 번들이다. `## 영향 번들` 표의 "확인 시나리오" 칸과 맞춘다.
- **`## 검증 묶음`** 은 검증 세션 하나가 돌릴 시나리오 묶음이다. 묶음 하나가 세션 하나다.
  - 같은 화면, 같은 로그인 상태, 같은 기기 폭끼리 묶는다. 묶음 안에서 화면 이동과 준비를 다시 하지 않게 하기 위해서다.
  - 묶음 하나는 시나리오 4~6개로 한다. 브라우저 호출이 20회 안팎이 되는 크기다. 너무 잘게 나누면 세션마다 시작 비용(문맥 약 5만 5천)을 다시 낸다.
  - 모든 시나리오가 한 묶음에 들어가야 한다. 표에 빠진 시나리오는 번호 순서로 4개씩 뒤에 붙는다.
  - 검증 세션은 그 묶음의 시나리오 절과 사전 준비만 읽는다. 그래서 여러 시나리오가 함께 쓰는 스크립트와 데이터는 `## 사전 준비` 에 둔다.
  - 앞 묶음의 로그인 상태가 다음 묶음에 남는다. 로그아웃 상태가 필요한 시나리오는 사전 상태에 "로그아웃 상태"를 적는다.
- **로그인·로그아웃은 조작 단계에 버튼으로 적는다.** 로그인 화면이나 로그아웃 주소를 직접 여는 단계는 쓰지 않는다. 검증 담당이 적힌 그대로 따라 하기 때문이다.
  - 로그인: PC 는 메인 화면 헤더의 **로그인** 버튼, 모바일은 **마이 와디즈**의 **로그인**을 눌러 로그인 화면으로 간다.
  - 로그아웃: **마이 와디즈** 맨 아래 **로그아웃** 버튼을 누른다.

## 1-5. 자족성 점검 (이 세션을 닫기 전 필수)

아래를 스스로 묻고, 하나라도 "아니오"면 그 자리를 채운 뒤에 끝낸다.

| 문서 | 점검 질문 |
|---|---|
| design.md | 고칠 파일 경로가 **전부** 적혀 있나 (말줄임·"등" 금지) |
| design.md | 파일마다 "지금 / 고친 뒤 / 왜" 가 **코드로** 있나 |
| design.md | 검증 명령이 **실제로 있는 명령**인가 |
| design.md | `## 확인하지 못한 것` 의 각 항목에 **구현 담당이 어떻게 할지**가 적혀 있나 |
| design.md | `## 리뷰 항목` 의 호출부 표가 비어 있다면 "소비처 없음 + 확인 방법" 이 적혀 있나 |
| test-plan.md | 각 시나리오에 **주소·사전 상태·통과 기준**이 다 있나 |
| test-plan.md | 통과 기준이 **눈으로 판정 가능한 문장**인가 |
| test-plan.md | 회귀 확인 시나리오가 있나 |
| test-plan.md | `## 검증 묶음` 표에 시나리오가 **모두** 들어 있고, 묶음마다 4~6개인가 |
| test-plan.md | `## 영향 번들` 표에 네 번들이 **모두** 있고, 판정마다 근거가 있나 |
| test-plan.md | 영향인 번들마다 **그 번들의 화면**에서 확인하는 시나리오가 있나 |

`dobby_lint {키}` 와 `dobby_terms_lint $ORCHESTRATION_META/{키}/design.md` 를 돌려 걸리는 것을 고친다.

## 1-6. 사람과 함께 설계 고치기 (`auto` 가 없을 때)

자족성 점검까지 마치면 먼저 상태를 적어 둔다. 이 대화가 길어져 세션이 끊겨도, 새 세션이 "설계는 있고 승인은 없다"를 보고 이 절부터 이어가게 하기 위해서다.

```
dobby_phase {키} 분석
dobby_agent_state {키} analysis-agent 분석
dobby_event {키} "설계 초안 완료 — 사람 확인 대기"
```

그다음 사람에게 아래 요약을 보여 준다. 문서를 통째로 붙여 넣지 않는다. 사람이 판단할 수 있을 만큼만 추린다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{키} · 설계 초안

한 장 요약
  (무엇이 문제이고, 어떻게 고치는지 3~5줄)

고칠 파일
  | 파일 | 무엇을 바꾸나 |

결정과 근거
  | 정한 것 | 고른 답 | 이유 |

확인이 필요한 것
  - (사람이 정해 줘야 하는 것. 선택지와 함께)

테스트 시나리오
  | 시나리오 | 통과 기준 |

리뷰 항목
  - (틀리기 쉬운 곳 중 중요한 것)

전체 문서: {설계 문서 경로}, {테스트 계획 경로}
고칠 곳을 말씀해 주세요. 그대로 가도 되면 아래 중 하나로 답해 주세요.
  - "자동 실행" : 구현부터 통합까지 자동으로 진행합니다.
                  통합 단계에서 작업 브랜치({브랜치})에 커밋하고 푸시합니다.
  - "직접 실행" : 설계만 확정합니다. 세션을 닫은 뒤 /do {키} 를 직접 실행해 주세요.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

요약 끝의 자동 실행 안내는 빼지 않는다. 커밋과 푸시는 사람의 동의가 있어야 하는 일이라, 사람이 "자동 실행"이 무엇을 시작하는지 알고 답해야 그 답이 동의가 된다.

사람이 고칠 곳을 말하면 아래를 지킨다.

1. **설계 문서를 고친다.** 결정이 바뀌면 `## 결정과 근거` 표의 해당 줄도 함께 바꾼다.
2. **설계가 바뀌면 딸린 문서도 맞춘다.** 고칠 파일이나 동작이 바뀌면 `## 리뷰 항목` 과 테스트 계획의 시나리오·통과 기준도 같이 고친다. 설계만 바꾸고 두 문서를 두면 뒷세션이 서로 다른 문서를 보고 일한다.
3. **고칠 때마다 1-5 자족성 점검을 다시 돈다.** 대화로 고친 내용은 빠뜨리기 쉽다.
4. 바뀐 곳만 짧게 다시 보여 주고 "자동 실행"인지 "직접 실행"인지 묻는다.

사람이 **"자동 실행"** 이나 **"직접 실행"** 이라고 하면 승인을 기록한다.

옛 낱말도 같은 뜻으로 받는다. "확정"은 "자동 실행", "확정만"은 "직접 실행"으로 본다.

```
dobby_design_ack {키} 사용자
dobby_agent_state {키} analysis-agent 완료
dobby_event {키} "설계 확정 — 구현 세션으로 넘김"
```

**"자동 실행"이면 이어서 자동 실행을 띄운다.** 승인 기록 뒤에 불러야 한다. 대시보드가 시작 전에 "설계가 확정됐는가"를 다시 보기 때문이다.

```
dobby_v2_autorun {키}
```

| 결과 | 할 일 |
|---|---|
| 0 (시작함) | "세션을 닫는 법"의 **자동 실행을 띄웠을 때** 형식으로 알리고 끝낸다. 대시보드 오더 실행 탭이 띄운 세션(`DOBBY_V2_CHAINED`)이면 실제로 띄우지 않고 0 을 돌려준다. 이 세션이 끝나면 같은 잡이 이어서 실행한다 |
| 1 (대시보드가 거부) | 출력된 이유를 그대로 전하고, 기본 형식으로 알리고 끝낸다. 이 세션 자체가 대시보드 잡으로 떠 있으면 "이미 실행 중"으로 거부된다. 그때는 이 세션을 닫은 뒤 오더 화면의 "자동 실행" 버튼을 누르라고 안내한다 |
| 2 (대시보드에 닿지 못함) | 출력된 직접 실행 명령을 그대로 전하고, 기본 형식으로 알리고 끝낸다 |

⛔ **이 세션에서 `run.sh` 를 직접 띄우거나 다음 단계를 이어서 하지 않는다.** 이 세션 아래에서 띄운 프로세스는 세션이 닫힐 때 함께 끝날 수 있고, 이어서 하면 세션을 나눈 의미가 없어진다.

**"직접 실행"이면** 자동 실행을 띄우지 않고 기본 형식으로 알리고 끝낸다.

수정 대화는 확정될 때까지 이 세션에서 그대로 이어간다. 대화 길이 때문에 중간에 끊지 않는다.

사람이 확정하지 않고 세션을 닫았다면, 새 세션은 단계 판정에서 "승인 기록이 없다"를 보고 이 절부터 다시 시작한다. 이때는 1-1 부터 1-5 까지를 다시 하지 않는다. `dobby_session_log {키} analysis-agent design 설계 {워크트리경로}` 로 세션만 기록하고, 설계 문서와 테스트 계획을 읽어 바로 요약을 보여 준다.

## 1-7. 마무리 (`auto` 가 있을 때)

사람에게 묻지 않는다. 사람만 정할 수 있는 결정이 있으면 공통 규칙 "사람에게 묻지 않는다"의 2번대로 멈춘다(승인을 기록하지 않는다). 그런 결정이 없으면 아래를 하고 끝낸다.

```
dobby_phase {키} 분석
dobby_design_ack {키} auto
dobby_agent_state {키} analysis-agent 완료
dobby_event {키} "설계 완료(자동 확정) — 구현 세션으로 넘김"
```

`env=` 가 없으면 그다음 아래 "세션을 닫는 법"대로 알리고 끝낸다.

**`env=` 가 있으면** 승인을 기록하기 전에 아래를 확인한다. 하나라도 안 되면 승인을 기록하지 않고, 무엇이 빠졌고 어떻게 채우는지 알리고 끝낸다. 중간에 사람이 필요해 멈추지 않도록 처음에 다 본다.

| 확인 | 어떻게 |
|---|---|
| 환경이 dev·rc1·rc4 중 하나 | 인자 |
| 고칠 저장소가 wadiz-frontend·com.wadiz.web 안에 있다 | 워크트리 표. 다른 저장소는 배포 절차가 없다 |
| gh 로그인 | `gh auth status` |
| argocd 로그인(고칠 저장소에 com.wadiz.web 이 있을 때만) | `dobby_ship_argo {키} {환경} check` 가 세션 만료로 거부하지 않는다. 재로그인은 브라우저 인증이라 자동으로 못 한다 |
| 테스트 계정 | 테스트 계획 `## 사전 준비` 의 계정이 있고, config.env 에 `TEST_LOGIN_PW` 가 있다 |

통과하면 승인 기록 앞에 `dobby_v2_set_env {키} {환경}` 을 부르고, 승인 기록 뒤에 1-6 과 같이 `dobby_v2_autorun {키}` 를 부른다(결과 처리도 1-6 표와 같다).
