# light · 한 세션 실행 (가벼운 변경)

사람이 미리 분석한 가벼운 변경을 **세션 하나에서** 끝까지 한다. 순서는 착수, 설계 옮겨 적기, 사람 확인, 구현, 커밋·푸시, 배포, 대상 시나리오 검증이다.

일반 실행과 다른 점은 셋이다.

| 일반 실행 | light |
|---|---|
| 단계마다 새 세션 | 세션 하나. 문맥이 상한을 넘으면 그 자리에서 일반 실행으로 넘긴다 |
| 설계 세션이 코드를 깊이 분석한다 | 분석은 사람이 했다고 본다. 사람의 입력과 Jira 내용을 설계 문서로 옮긴다 |
| 별도 세션이 리뷰하고 지적을 고친다 | 리뷰와 자체 점검을 하지 않는다. 설계 문서와 검증 명령을 믿는다. rc1·rc4 의 PR 리뷰봇 반영은 배포 절차라 그대로 한다 |

사람에게 묻는 자리는 2번의 확인 하나뿐이다. 그 답이 커밋·푸시와 그 환경의 머지·빌드·배포 동의가 된다.

## 0. 시작 조건

- 메타 폴더가 없거나 단계가 `착수` 인 오더만 받는다. 이미 설계나 진행 기록이 있는 오더면 아무것도 바꾸지 않고 멈춘다. "이미 진행 중인 오더입니다. `/do {키} 변경 {내용}` 이나 `/do {키}` 로 이어 가 주세요"라고 알린다.
- 키가 `TASK-` 로 시작하면 멈춘다. `TASK-` 작업은 배포하지 않아(`dobby_v2_set_env` 가 거부한다) light 로 끝까지 갈 수 없다. 일반 `/do {키}` 를 안내한다.
- 판정에 쓰는 문맥 상한은 `DOBBY_REUSE_MAX_CTX`(12만 토큰)다. 근거는 `session-reuse.md` 의 "light" 절이다.

## 1. 착수와 설계 옮겨 적기

1. `steps/design.md` 의 1-1 을 그대로 한다. 4번은 `dobby_v2_begin {키}` 로 부른다(`light` 없이). 기획자 행이 작업중이 된다.
2. 무엇을 고칠지는 **사람이 명령에 적은 내용**과 Jira 설명·코멘트에서 가져온다. 코멘트까지 읽는다(`twg jira workitem get {키} --fields comment`). 사람이 미리 적어 둔 원인과 수정안이 코멘트에 있는 경우가 많다.
3. 코드는 **고칠 자리를 확인할 만큼만** 읽는다. 원인을 새로 파고들지 않는다. 사람의 입력이 코드와 맞지 않으면(파일·함수가 없음, 동작이 다름) 고치지 말고 2번 요약의 "확인이 필요한 것"에 올린다.
4. `dobby_scaffold_doc {키} design` 으로 틀을 깔고 아래만 채운다. 틀에 없는 절은 더하고, 나머지 절은 비워 둔다. 분석 문서는 만들지 않는다.
   - `## 고칠 코드` — 파일 경로 전부와 "지금 / 고친 뒤 / 왜"
   - `## 작업 순서` — 파일이 둘 이상일 때만
   - `## 검증 명령` — 그 저장소에 실제로 있는 명령
   - `## 결정과 근거` — 첫 행에 "진행 방식 | light | 사람이 분석을 마치고 light 로 실행"
5. `test-plan.md` 를 `steps/design.md` 1-4 형식으로 쓰되 **이번 변경을 확인하는 시나리오와 회귀 확인 하나만** 둔다. `## 사전 준비`, `## 영향 번들`, `## 검증 묶음` 절은 반드시 둔다. 검증 세션 헬퍼가 이 세 절을 읽는다.
6. 문맥을 잰다(4절 "문맥 점검").

## 2. 사람 확인

```
dobby_v2_end {키} 사람확인
```

아래 요약을 보여 준다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{키} · light 실행 확인

무엇을 고치나
  (2~3줄)

고칠 파일
  | 파일 | 무엇을 바꾸나 |

검증 시나리오
  | 시나리오 | 통과 기준 |

확인이 필요한 것
  - (사람 입력과 코드가 맞지 않는 곳. 없으면 "없음")

배포 환경: {env}          ← env= 가 없었으면 "dev·rc1·rc4 중 어디에 배포할지 알려 주세요"

"실행"이라고 답하면 이 세션에서 끝까지 진행합니다.
  - 작업 브랜치({브랜치})에 커밋하고 푸시합니다.
  - {env} 로 PR 을 만들고 리뷰봇 지적 반영, 머지, 빌드, 배포를 묻지 않고 진행합니다.
  - 배포가 끝나면 위 시나리오만 검증합니다.
고칠 곳이 있으면 말씀해 주세요.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

- 실행 안내 줄은 빼지 않는다. 사람이 무엇이 시작되는지 알고 답해야 그 답이 동의가 된다.
- 사람이 고칠 곳을 말하면 설계 문서와 테스트 계획을 함께 고치고, 바뀐 곳만 다시 보여 준다.
- 환경은 dev·rc1·rc4 만 받는다. stage·cloud_live 를 말하면 받을 수 없다고 알리고 다시 묻는다.

"실행" 답을 받으면 `steps/design.md` 1-7 의 `env=` 확인 표(저장소, gh 로그인, argocd 로그인, 테스트 계정)를 돈다. 하나라도 안 되면 무엇이 빠졌는지 알리고 다시 "실행"을 기다린다. 통과하면 아래를 부른다.

```
dobby_v2_set_env {키} {환경}
dobby_design_ack {키} 사용자
dobby_v2_end {키} 확정
```

`자동 배포 환경` 줄을 적는 이유는 두 가지다. 배포 판정 헬퍼(`dobby_v2_ship_next`)가 이 줄을 읽는다. 그리고 중간에 일반 실행으로 넘어가도 자동 배포 오더로 이어진다.

## 3. 구현 → 커밋·푸시 → 배포 → 검증

### 3-1. 구현

먼저 `dobby_v2_begin {키}` 를 부른다. 개발자 행이 작업중이 된다. 그다음 `steps/impl.md` 의 "하는 일" 1~4번과 "설계대로 할 수 없을 때"를 따른다. 마치면 `implementation.md` 를 짧게 쓴다(바꾼 파일, 검증 명령 결과).

### 3-2. 커밋·푸시

`steps/integrate.md` 의 2·3·4번을 한다. 1번의 리뷰 결과 확인은 하지 않는다(리뷰가 없다). 5번의 구현 설명 문서도 만들지 않는다. 커밋·푸시는 2번의 "실행" 답으로 이미 동의를 받았으니 다시 묻지 않는다.

```
dobby_v2_end {키} 통합완료
```

끝 헬퍼는 설계 문서에 light 결정 행이 있는지, 작업 폴더와 구현 기록이 바뀌었는지, 커밋·푸시와 결과 문서가 있는지 확인한다. 통과하면 단계를 배포로 옮긴다.

문맥을 잰다.

### 3-3. 배포

PR 에 변경요청(`CHANGES_REQUESTED`)이 달리면 이 세션에서 반영하지 않는다. 고치지도 PR 을 닫지도 않고 5절대로 일반 실행으로 넘긴다(`dobby_v2_end {키} 넘김 "light 중단 — PR 변경요청"`). 다음 `/do {키}` 의 배포 세션이 PR 을 닫고 기획자에게 넘긴다(`steps/ship.md` "변경요청이 달렸을 때"). 승인에 딸린 지적과 지적이 담긴 코멘트는 지금처럼 이 세션에서 범위 안에서 반영한다.

먼저 `dobby_v2_begin {키}` 를 부른다. 배포담당 행이 작업중이 된다. `dobby-ship` 스킬 절차를 `{키} {환경}` 으로 따르되, 그 스킬의 **"자동 실행에서"** 절의 light 행대로 한다. 머지·빌드·argocd sync 를 묻지 않는다. 2번의 "실행" 답이 그 동의다.

기다릴 자리(`리뷰 대기`·`빌드 대기`·`배포 대기`)에 닿으면 세션을 끝내지 않고 셸에서 기다린다.

```
dobby_v2_wait {키}
```

이 호출은 최대 8분 걸린다. 도구 호출 제한 시간을 10분(600000)으로 준다. 출력 첫 칸을 보고 고른다.

| 첫 칸 | 할 일 |
|---|---|
| `ship` | 배포 절차를 이어 간다(리뷰가 달렸거나 빌드가 끝났다) |
| `verify` | 모든 저장소가 그 환경에 들어갔다. `dobby_v2_end {키} 배포확인` 을 부르고 3-4 로 간다 |
| `wait-review`·`wait-build` | 아직 기다리는 중이다. 같은 명령을 다시 부른다. 그 행 갱신 뒤 30분이 지났으면 멈추고 5절대로 넘긴다 |
| `blocked` | 비고를 사람에게 알리고 5절대로 넘긴다 |

배포 확인까지 적었으면 문맥을 잰다.

### 3-4. 검증

묶음마다 먼저 `dobby_v2_begin {키}` 를 부른다. 테스터 행이 작업중이 된다. 그다음 `steps/verify.md` 의 "하는 일"과 "마무리"를 따른다. `dobby-test` 는 `{키} {환경} 묶음={묶음} 시나리오={번호}` 로 부른다.

묶음이 둘 이상이면 이 세션에서 이어서 돈다(`묶음남음` 으로 끝낸 뒤 다시 시작 헬퍼를 부른다). 묶음 사이마다 문맥을 잰다.

## 4. 문맥 점검

정해진 자리(1-6, 3-2 끝, 3-3 끝, 검증 묶음 사이)마다 부른다.

```
dobby_v2_ctx
```

출력(지금 문맥 토큰 수)이 `DOBBY_REUSE_MAX_CTX` 를 넘으면 그 자리에서 멈추고 5절대로 넘긴다. 2번 확인 전(1-6)이면 넘기지 않고 그대로 확인을 받는다. 확인 대화는 이 세션에서 해야 하기 때문이다.

## 5. 일반 실행으로 넘기기

문맥 상한을 넘었거나, 30분 넘게 기다렸거나, PR 에 변경요청이 달렸으면 넘긴다. 단계는 이미 일반 실행과 같은 값으로 적혀 있다. 그래서 다음 `/do {키}` 가 그 자리부터 잇는다.

```
dobby_v2_end {키} 넘김 "light 중단 — {이유}"
```

배포가 막혔으면 넘기지 않고 `dobby_v2_end {키} 막힘 "{비고}"` 로 끝낸다. 사람이 풀어야 하기 때문이다.

| 멈춘 자리 | 다음 `/do {키}` 가 하는 일 |
|---|---|
| 구현 중 | 구현을 잇는다. 끝나면 리뷰를 받는다. 문맥이 커질 만큼 큰 변경이면 리뷰를 받는 편이 안전하다 |
| 통합 뒤, 배포 중 | 자동 배포 오더의 배포 세션. 변경요청이 달려 넘겼으면 그 세션이 PR 을 닫고 기획자가 설계를 다시 본다 |
| 검증 묶음 사이 | 남은 묶음 검증 |

## 6. 마무리

"세션을 닫는 법" 형식으로 알린다. `한 일` 칸에 커밋 해시, PR 주소, 빌드 번호, 통과·실패한 시나리오를 적는다. `다음` 칸은 결과에 따라 쓴다.

| 결과 | 다음 칸 |
|---|---|
| 전부 통과 | `/dobby-resolve {키}` 로 해결 처리해 주세요 |
| 실패가 있음 | 이 세션을 닫고 `/do {키}` 를 입력하면 기획자가 실패 원인을 가릅니다. 이 세션에서 고치지 않는다. 브라우저 검증 뒤라 문맥이 크다 |
| 5절로 넘김 | 이 세션을 닫고 `/do {키}` 를 입력하면 멈춘 자리부터 이어 갑니다 |

`다음` 칸에는 마지막 끝 헬퍼가 낸 줄을 옮긴다.
