# light · 한 세션 실행 (가벼운 변경)

사람이 미리 분석한 가벼운 변경을 **세션 하나에서** 끝까지 한다. 순서는 착수, 설계, 확인, 구현, 리뷰, 수정, 통합(커밋·푸시), 배포, 대상 시나리오 검증이다.

**메타 기록과 기능은 일반 실행과 같다.** 문서는 일반 단계 문서(`steps/design.md`, `impl.md`, `fix.md`, `integrate.md`, `integrate-docs.md`)의 규칙과 수준을 그대로 따른다. 다른 것은 돌아가는 방식뿐이다.

| 일반 실행 | light |
|---|---|
| 단계마다 새 세션 | 세션 하나. 리뷰만 새 세션이 한다. 이 세션에서 늘어난 문맥이 30만을 넘을 때만 새 세션이 light 로 이어 간다 |
| 설계 세션이 코드를 깊이 분석한다 | 분석은 사람이 했다고 본다. 사람의 입력과 Jira 내용을 근거로 문서를 쓰고, 코드는 그 근거를 확인한다 |
| 설계 확인은 설계 아티팩트와 대화로 받는다 | 확인은 터미널 요약으로 한 번 받는다. 설계 아티팩트는 리뷰를 기다리는 동안 게시한다 |
| 검증은 영향 범위 전체 | 검증은 이번 변경 시나리오와 회귀 확인 하나 |
| 문서를 단계 안에서 차례로 쓴다 | 구현·배포·검증을 막지 않는 문서는 기다리는 시간에 겹쳐 쓴다(아래 표) |

겹쳐 쓰는 일은 아래와 같다. 겹칠 수 없는 일(설계 문서, 테스트 계획, 구현 기록)은 그 단계 안에서 끝낸다. 설계 문서와 테스트 계획은 확정 뒤에 바뀌면 설계 변경 감지(`dobby_v2_drift`)가 오더를 설계 확인으로 되돌린다. 구현 기록은 구현 끝 헬퍼가 확인한다.

| 겹쳐 쓰는 일 | 누가 | 언제 띄우나 | 언제까지 끝나야 하나 |
|---|---|---|---|
| 분석 문서(`analysis.md`) | 보조 에이전트 하나(백그라운드) | 1-6 | 결과 문서를 쓰기 전(3-5). 구현 설명 문서가 분석 문서를 읽는다 |
| 리뷰 | 리뷰 세션(`dobby_v2_review_session`, 백그라운드) | 3-2 | 수정이나 통합 전 |
| 설계 아티팩트(대화형만) | 이 세션 | 3-2 의 리뷰를 기다리는 동안 | 6절 마무리 전 |
| 결과 문서와 구현 설명 문서(`outcome.md`, `explainer.md`) | 결과 문서 세션(`dobby_v2_docs_session`, 백그라운드) | 3-5 배포를 시작할 때 | 6절 마무리 전. 검증은 기다리지 않는다 |

확인을 받는 방식은 둘이다.

| 명령 | 확인 |
|---|---|
| `/do {키} light [env=] {분석}` | 2-1. 사람에게 요약을 보여 주고 "실행" 답을 받는다. 그 답이 커밋·푸시와 그 환경의 머지·빌드·배포 동의다 |
| `/do {키} light auto [env=] {분석}` | 2-2. 사람에게 묻지 않는다. 스스로 정할 수 있는 것은 정하고 `## 결정과 근거` 에 적는다. 사람만 정할 수 있는 것이 있을 때만 질문을 남기고 끝낸다. 커밋·배포 동의는 실행을 띄운 사람(대시보드·오피스 접수 창의 동의)이 이미 했다 |

단계마다 일반 실행과 같은 시작·끝 헬퍼를 불러 상태 문서를 맞춘다. 그래야 대시보드와 오피스가 지금 누가 무엇을 하는지 일반 오더와 같은 모양으로 보여 준다. 헬퍼를 건너뛰고 일을 이어서 하지 않는다.

## 0. 시작 조건

- 메타 폴더가 없거나 단계가 `착수` 인 오더는 1절부터 한다.
- 단계가 `설계확인` 이고 상태 문서에 `- **진행 방식**: light` 줄이 있으면 **이어받기**다. 앞 light 세션이 확인을 받기 전에 닫혔거나, `auto` 로 돌던 light 가 질문을 남기고 답이 와서 자동 실행이 이 세션을 띄웠다. 1절을 건너뛰고 `dobby_v2_begin {키}` 를 부른 뒤 2절로 간다. 시작 헬퍼 결과에 `질문과 답:` 이 있으면 그 답을 사람의 결정으로 `## 결정과 근거` 에 적고 반영한다. 진행 방식 줄이 `light auto` 면 2-2, `light` 면 2-1 이다(명령에 `auto` 가 있으면 2-2).
- 단계가 `구현`·`수정`·`통합`·`배포`·`검증` 이고 진행 방식 줄이 `light` 또는 `light auto` 이면 **새 세션 이어받기**다. 앞 light 세션이 문맥 때문에 넘겼다(5-1). 1·2절을 건너뛰고 3절의 그 단계 절부터 한다. 시작 헬퍼는 입력 검사 훅이 이미 불렀다. 설계 문서, 테스트 계획, `implementation.md`(있으면)를 읽고 그 단계를 잇는다. 그 단계를 마치면 다음 단계도 이 세션에서 잇는다. 앞 세션의 백그라운드 일은 세션과 함께 끝났을 수 있다. 아래를 먼저 본다.
  - `analysis.md` 가 없으면 1-6 대로 분석 문서 에이전트를 다시 띄운다.
  - 상태 문서의 `- **결과 문서**:` 줄이 `대기` 나 `작성 중` 이면 3-5 대로 결과 문서 세션을 띄운다. 이미 돌고 있으면 헬퍼가 `도는 중` 을 내고 아무것도 하지 않는다.
- 그 밖에 이미 설계나 진행 기록이 있는 오더면 아무것도 바꾸지 않고 멈춘다. "이미 진행 중인 오더입니다. `/do {키} 변경 {내용}` 이나 `/do {키}` 로 이어 가 주세요"라고 알린다.
- 키가 `TASK-` 로 시작하면 멈춘다. `TASK-` 작업은 배포하지 않아(`dobby_v2_set_env` 가 거부한다) light 로 끝까지 갈 수 없다. 일반 `/do {키}` 를 안내한다.
- 새 세션으로 넘기는 기준은 이 세션에서 늘어난 문맥 `DOBBY_LIGHT_MAX_GROWTH`(30만 토큰)다. 근거는 `session-reuse.md` 의 "light" 절이다.

## 1. 착수와 설계

1. `dobby_bootstrap {키} "{임시제목}" 개발 "{키워드1|키워드2}"` 로 골격을 깐다(`steps/design.md` 1-1 의 1번).
2. **light 표지를 적는다.**
   ```
   dobby_v2_light_mark {키}          # auto 면: dobby_v2_light_mark {키} auto
   ```
3. Jira 를 조회하고(`steps/design.md` 1-1 의 2번) 담당자를 정한다(`steps/design.md` 1-1-2). 화면 동작이 바뀌면 `dobby_v2_set_roles {키} "개발자, 테스터" "light — {근거}"`, 주석·타입만 바꾸면 `"개발자"` 와 테스트 계획의 `- **검증**: 필요 없음 — {이유}` 줄이다. 리뷰어와 배포담당은 개발자를 켜면 헬퍼가 함께 켠다.
4. 워크트리를 준비하고(`steps/design.md` 1-1 의 3번) `dobby_v2_begin {키}` 를 부른다(`light` 없이). 기획자 행이 작업중이 되고, 대시보드와 오피스에 "설계" 단계로 보인다.
5. 무엇을 고칠지는 **사람이 명령에 적은 내용**과 Jira 설명·코멘트에서 가져온다. 코멘트까지 읽는다(`twg jira workitem get {키} --fields comment`). 사람이 미리 적어 둔 원인과 수정안이 코멘트에 있는 경우가 많다. 사람의 입력이 코드와 맞지 않으면(파일·함수가 없음, 동작이 다름) 고치지 말고 "확인이 필요한 것"으로 모은다(2절에서 다룬다).
6. **분석 문서 에이전트를 띄운다.** Agent 도구로 보조 에이전트 하나를 백그라운드(`run_in_background`)로 띄우고 기다리지 않는다. 띄우는 에이전트는 이것 하나뿐이다. 지시에는 아래를 모두 넣는다.
   - 할 일: `dobby_scaffold_doc {키} analysis` 로 틀을 깔고 `steps/design.md` 1-2 의 규칙대로 `$ORCHESTRATION_META/{키}/analysis.md` 를 채운다. 원인은 `파일:라인` 으로 짚는다.
   - 근거: 사람이 명령에 적은 분석 원문, Jira 설명·코멘트(5번에서 읽은 내용을 그대로 넘긴다), 워크트리 경로.
   - 금지: `analysis.md` 밖의 파일(설계 문서, 테스트 계획, 상태 문서, 코드)을 고치지 않는다. go-dobby 헬퍼(`dobby_v2_*`)를 부르지 않는다.
   - 끝나면 쓴 파일 경로와 원인 요약 세 줄만 돌려준다.
7. **설계 문서를 쓴다.** `dobby_scaffold_doc {키} design` 으로 틀을 깔고 `steps/design.md` 1-3 그대로 쓴다. "반드시 더 적는 것", 옛 코드를 지우거나 갈아끼울 때의 부수 효과 목록, `## 리뷰 항목` 절을 모두 포함한다. 리뷰 세션이 `## 리뷰 항목` 을 읽는다. `## 결정과 근거` 첫 행에는 "진행 방식 | light | 사람이 분석을 마치고 light 로 실행" 을 적는다(`auto` 면 "light auto | 사람 확인 없이 스스로 판단").
8. **테스트 계획을 쓴다.** `steps/design.md` 1-4 형식 그대로 쓰되 시나리오는 **이번 변경을 확인하는 시나리오와 회귀 확인 하나**다. `## 사전 준비`, `## 영향 번들`, `## 검증 묶음` 절은 반드시 둔다. 검증 세션 헬퍼가 이 세 절을 읽는다.
9. `steps/design.md` 1-5 의 자족성 점검을 한다.
10. 문맥을 잰다(4절 "문맥 점검").

## 2. 확인

### 2-1. 사람 확인 (`auto` 없음)

```
dobby_v2_end {키} 사람확인
```

대시보드와 오피스에는 "터미널의 light 세션이 '실행' 답을 기다립니다"로 보인다(승인 버튼이 없다). 아래 요약을 보여 준다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{키} · light 실행 확인

무엇을 고치나
  (2~3줄)

고칠 파일
  | 파일 | 무엇을 바꾸나 |

검증 시나리오
  | 시나리오 | 통과 기준 |

확인이 필요한 것
  - (사람 입력과 코드가 맞지 않는 곳. 없으면 "없음")

배포 환경: {env}          ← env= 가 없었으면 "dev·rc1·rc4 중 어디에 배포할지 알려 주세요"

"실행"이라고 답하면 이 세션에서 끝까지 진행합니다.
  - 구현한 뒤 별도 세션이 리뷰하고, 지적이 있으면 고칩니다.
  - 작업 브랜치({브랜치})에 커밋하고 푸시합니다.
  - {env} 로 PR 을 만들고 리뷰봇 지적 반영, 머지, 빌드, 배포를 묻지 않고 진행합니다.
  - 배포가 끝나면 위 시나리오만 검증합니다.
고칠 곳이 있으면 말씀해 주세요.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

- 실행 안내 줄은 빼지 않는다. 사람이 무엇이 시작되는지 알고 답해야 그 답이 동의가 된다.
- 사람이 고칠 곳을 말하면 설계 문서와 테스트 계획을 함께 고치고, 바뀐 곳만 다시 보여 준다.
- 환경은 dev·rc1·rc4 만 받는다. stage·cloud_live 를 말하면 받을 수 없다고 알리고 다시 묻는다.

"실행" 답을 받으면 2-3 의 확인 표를 돈다. 하나라도 안 되면 무엇이 빠졌는지 알리고 다시 "실행"을 기다린다. 통과하면 2-4 로 간다.

### 2-2. 스스로 확인 (`auto`)

사람에게 묻지 않는다. 요약을 보여 주며 기다리지 않는다(`사람확인` 을 부르지 않는다).

1. "확인이 필요한 것"을 하나씩 본다. 코드와 Jira 로 답이 나오면 스스로 정하고 `## 결정과 근거` 에 "무엇을 · 어떻게 정함 · 근거"로 적는다. 예: 사람이 적은 함수 이름이 바뀌었지만 같은 일을 하는 함수가 하나뿐이다 → 그 함수를 고친다.
2. 사람만 정할 수 있는 것이 남으면(고칠 곳이 둘 이상이라 고르는 일이 기획 판단이다, 입력이 코드와 정반대다, 고칠 파일이 아예 없다) 질문을 남긴다. `env=` 가 있으면 질문을 남기기 전에 2-3 의 확인 표를 돌고 `dobby_v2_set_env {키} {환경}` 을 먼저 부른다(답 뒤에 이어 갈 때 배포 환경이 남아 있게).
   - 공통 규칙 "사람에게 묻는 법"대로 질문 파일을 만들고 `dobby_v2_ask {키} file {질문 파일}` 로 남긴다. 방법에는 늘 아래 둘을 넣는다.
     - "일반 실행으로 바꾸기" — 기획자가 설계부터 다시 한다
     - "멈추기"
   - `dobby_v2_end {키} 질문` 으로 끝낸다. 답이 오면 자동 실행이 이 세션을 `/do {키} auto` 로 다시 띄우고, 단계 판정이 light 절차로 보낸다(0절 이어받기).
   - 답이 "일반 실행으로 바꾸기"면 `dobby_v2_light_off {키} "사람이 일반 실행을 고름"` 을 부르고 `dobby_v2_end {키} 넘김 "일반 설계로"` 로 끝낸다. 대시보드에 설계 확인 차례로 보이고, 사람이 설계를 확정하면 일반 실행으로 이어진다.
3. 남은 것이 없으면 2-3 의 확인 표를 돈다(`env=` 가 있을 때). 안 되는 것이 있으면 질문으로 남긴다. 방법은 "채웠습니다, 다시 확인" · "환경 없이 통합까지만" · "멈추기"다. 통과하면 2-4 로 간다.
4. `env=` 가 없으면 배포를 하지 않는다. 통합(커밋·푸시)까지 하고 끝난다. 배포는 사람이 `/dobby-ship {키} {환경}` 으로 한다.

### 2-3. 배포 전 확인 표

`steps/design.md` 1-7 의 `env=` 확인 표(환경, 저장소, gh 로그인, argocd 로그인, 테스트 계정)를 돈다.

### 2-4. 확정

```
dobby_v2_set_env {키} {환경}        # 환경이 정해졌을 때만
dobby_design_ack {키} 사용자         # auto 면: dobby_design_ack {키} auto
dobby_v2_end {키} 확정
```

`자동 배포 환경` 줄을 적는 이유는 두 가지다. 배포 판정 헬퍼(`dobby_v2_ship_next`)가 이 줄을 읽는다. 그리고 중간에 일반 실행으로 넘어가도 자동 배포 오더로 이어진다.

## 3. 구현 → 리뷰 → 수정 → 통합 → 배포 → 검증

리뷰를 뺀 단계는 이 세션이 시작 헬퍼로 열고 끝 헬퍼로 닫는다. 같은 세션이 여러 담당자의 일을 차례로 하지만, 상태 문서에는 일반 실행과 같이 담당자 행 하나씩만 작업중으로 보인다.

### 3-1. 구현

`dobby_v2_begin {키}` 를 부른다. 개발자 행이 작업중, 단계가 구현이 된다. 그다음 `steps/impl.md` 의 "하는 일", "설계대로 할 수 없을 때", "마무리"를 그대로 따른다(`implementation.md` 도 그 규칙대로 쓴다).

```
dobby_v2_end {키} 완료
```

단계가 리뷰로 넘어간다. 문맥을 잰다.

### 3-2. 리뷰 (새 세션) — 기다리는 동안 겹쳐 하는 일

리뷰는 이 세션이 하지 않는다. 리뷰 세션을 띄운다. Bash 도구를 **백그라운드(`run_in_background`)** 로 부르고, 끝났다는 알림이 올 때까지 다음 일을 한다.

```
dobby_v2_review_session {키}
```

리뷰 세션은 `/do {키}` 로 떠서 `steps/review.md` 대로 리뷰하고 끝 헬퍼까지 부른다. 기록은 일반 리뷰와 같다.

기다리는 동안 이 세션이 할 일:

1. 대화형 light(`auto` 없음)면 `steps/design-artifact.md` 대로 설계 아티팩트를 게시한다. `auto` 면 만들지 않는다(일반 설계 1-7 과 같다. 게시 도구가 없다).
2. 분석 문서 에이전트가 끝났는지 본다. 끝났으면 `analysis.md` 가 있는지 확인한다. 실패했으면 1-6 대로 다시 띄운다.

리뷰 세션이 끝나면 출력 "지금 단계<TAB>리뷰 세션 아이디<TAB>종료 코드" 의 첫 칸으로 고른다.

| 지금 단계 | 할 일 |
|---|---|
| `수정` | 3-3 |
| `통합` | 3-4 |
| `리뷰` 그대로 | 리뷰 세션이 끝을 맺지 못했다. 한 번 더 부른다. 또 그대로면 멈추고 6절 "리뷰 세션 실패"로 알린다 |
| 그 밖(설계·실패분석 등) | 리뷰가 설계로 넘겼다. 6절 "기획자에게 넘어감"으로 알린다 |

### 3-3. 수정

`dobby_v2_begin {키}` 를 부른다. 개발자 행이 작업중, 단계가 수정이 된다. `steps/fix.md` 를 그대로 따른다(차수가 3을 넘을 때 기획자에게 넘기는 규칙 포함). `완료` 로 끝내면 단계가 리뷰로 돌아간다. 문맥을 재고 3-2 로 간다. `설계문제` 로 끝냈으면 6절 "기획자에게 넘어감"으로 알린다.

### 3-4. 통합(커밋·푸시)

`dobby_v2_begin {키}` 를 부른다. 배포담당 행이 작업중, 단계가 통합이 된다. `steps/integrate.md` 를 그대로 따른다. 시작 헬퍼의 `설명:` 이 `커밋·푸시 (결과 문서는 문서 세션이 씀)` 이면(배포 환경이 있다) 결과 문서는 3-5 의 결과 문서 세션이 쓴다. `커밋·푸시와 결과 문서` 면(배포 환경이 없다) 이 세션이 쓴다. 그때는 분석 문서 에이전트가 끝나기를 먼저 기다린다. 구현 설명 문서가 분석 문서를 읽는다. 커밋·푸시는 2절 확인(사람의 "실행" 답, 또는 auto 실행을 띄운 사람의 동의)으로 이미 동의를 받았으니 다시 묻지 않는다.

```
dobby_v2_end {키} 완료
```

환경이 있으면 단계가 배포로 넘어간다. 환경이 없으면 배포담당이 "통합 끝 — 배포하기" 사람 차례가 되고, 6절 마무리로 간다. 문맥을 잰다.

### 3-5. 배포

**먼저 결과 문서 세션을 띄운다.** 상태 문서의 `- **결과 문서**:` 줄이 `대기` 면, 분석 문서 에이전트가 끝났는지 확인한다(아직이면 끝나기를 기다린다). 그다음 Bash 도구를 백그라운드로 불러 띄우고 기다리지 않는다.

```
dobby_v2_docs_session {키}
```

결과 문서 세션은 `steps/integrate-docs.md` 대로 `outcome.md` 와 `explainer.md` 를 쓰고 `- **결과 문서**:` 줄을 `완료` 로 바꾼다. 배포와 검증은 이 세션을 기다리지 않는다.

PR 에 변경요청(`CHANGES_REQUESTED`)이 달리면 이 세션에서 반영하지 않는다. 고치지도 PR 을 닫지도 않고 5-2 대로 일반 실행으로 넘긴다(이유 "PR 변경요청"). 다음 `/do {키}` 의 배포 세션이 PR 을 닫고 기획자에게 넘긴다(`steps/ship.md` "변경요청이 달렸을 때"). 승인에 딸린 지적과 지적이 담긴 코멘트는 지금처럼 이 세션에서 범위 안에서 반영한다.

`dobby_v2_begin {키}` 를 부른다. 배포담당 행이 작업중이 된다. `dobby-ship` 스킬 절차를 `{키} {환경}` 으로 따르되, 그 스킬의 **"자동 실행에서"** 절의 light 행대로 한다. 머지·빌드·argocd sync 를 묻지 않는다. 2절 확인이 그 동의다.

기다릴 자리(`리뷰 대기`·`빌드 대기`·`배포 대기`)에 닿으면 세션을 끝내지 않고 셸에서 기다린다. 자동 실행 지시에 "리뷰봇이나 빌드를 세션 안에서 기다리지 않는다"가 붙어 있어도 light 는 이 절대로 셸에서 기다린다.

```
dobby_v2_wait {키}
```

이 호출은 최대 8분 걸린다. 도구 호출 제한 시간을 10분(600000)으로 준다. 출력 첫 칸을 보고 고른다.

| 첫 칸 | 할 일 |
|---|---|
| `ship` | 배포 절차를 이어 간다(리뷰가 달렸거나 빌드가 끝났다) |
| `verify` | 모든 저장소가 그 환경에 들어갔다. `dobby_v2_end {키} 배포확인` 을 부르고 3-6 으로 간다 |
| `wait-review`·`wait-build` | 아직 기다리는 중이다. 같은 명령을 다시 부른다. 그 행 갱신 뒤 30분이 지났으면 멈추고 5-2 대로 넘긴다 |
| `blocked` | 비고를 사람에게 알리고 5-2 대로 한다 |

배포 확인까지 적었으면 문맥을 잰다.

### 3-6. 검증

묶음마다 먼저 `dobby_v2_begin {키}` 를 부른다. 테스터 행이 작업중이 된다. 그다음 `steps/verify.md` 의 "하는 일"과 "마무리"를 따른다. `dobby-test` 는 `{키} {환경} 묶음={묶음} 시나리오={번호}` 로 부른다.

묶음이 둘 이상이면 이 세션에서 이어서 돈다(`묶음남음` 으로 끝낸 뒤 다시 시작 헬퍼를 부른다). 묶음 사이마다 문맥을 잰다.

## 4. 문맥 점검

정해진 자리(1-10, 3-1 끝, 3-3 끝, 3-4 끝, 3-5 끝, 검증 묶음 사이)마다 부른다.

```
dobby_v2_ctx_growth
```

출력(이 세션 첫 호출 뒤로 늘어난 문맥 토큰 수)이 `DOBBY_LIGHT_MAX_GROWTH`(30만)를 넘으면 그 자리에서 멈추고 5-1 대로 새 세션에 넘긴다. 넘지 않으면 계속한다. 확인 전(1-10)이면 넘기지 않고 그대로 2절을 한다. 확인 대화는 이 세션에서 해야 하기 때문이다.

## 5. 넘기기

### 5-1. 문맥이 30만 넘게 늘었을 때 — 새 세션이 light 로 잇는다

light 표지를 그대로 둔다.

```
dobby_v2_end {키} 넘김 "light 새 세션 — 늘어난 문맥 {N}"
```

다음 `/do {키}` 는 단계 판정이 light 절차로 보내고, 0절의 새 세션 이어받기로 멈춘 자리부터 잇는다. 단계가 리뷰면(3-1 끝에서 넘김) 다음 `/do {키}` 는 일반 리뷰 세션이 되고, 그 뒤의 `/do {키}` 부터 light 절차로 잇는다. 자동 실행이 띄운 light 면 자동 실행이 바로 새 세션을 띄운다. 이 세션이 띄운 백그라운드 일(분석 문서 에이전트, 결과 문서 세션)은 세션을 닫으면 함께 끝날 수 있다. 새 세션이 0절대로 다시 띄운다.

### 5-2. 오래 기다렸거나 PR 변경요청 — 일반 실행으로 넘긴다

30분 넘게 기다렸거나 PR 에 변경요청이 달렸으면 일반 실행으로 넘긴다. **먼저 light 표지를 정리한다.**

```
dobby_v2_light_off {키} "{이유}"
dobby_v2_end {키} 넘김 "light 중단 — {이유}"
```

`dobby_v2_light_off` 는 표지를 "light (중단)"으로 바꾼다. 남은 배포·검증은 일반 실행이 잇는다.

배포가 막혔으면 넘기지 않고 `dobby_v2_end {키} 막힘 "{비고}"` 로 끝낸다. 사람이 풀어야 하기 때문이다.

| 멈춘 자리 | 다음 `/do {키}` 가 하는 일 |
|---|---|
| 배포 중 | 자동 배포 오더의 배포 세션. 변경요청이 달려 넘겼으면 그 세션이 PR 을 닫고 기획자가 설계를 다시 본다 |

## 6. 마무리

결과 문서 세션을 띄웠으면 끝났다는 알림이 올 때까지 기다린다. 끝났는데 `- **결과 문서**:` 줄이 `완료` 가 아니면 `dobby_v2_docs_session {키}` 를 한 번 더 부른다. 또 `완료` 가 아니면 `다음` 칸에 "결과 문서를 마치지 못했습니다 — `/do {키} 결과 문서` 로 다시 써 주세요"를 더한다.

"세션을 닫는 법" 형식으로 알린다. `한 일` 칸에 커밋 해시, PR 주소, 빌드 번호, 리뷰 차수와 지적 수, 통과·실패한 시나리오를 적는다. `다음` 칸은 결과에 따라 쓴다.

| 결과 | 다음 칸 |
|---|---|
| 전부 통과 | 완성 — 결과를 확인한 뒤 `/dobby-resolve {키}` 로 해결 처리해 주세요 |
| 환경 없이 통합까지 | 배포 차례 — `/dobby-ship {키} {환경}` 으로 배포한 뒤 `/do {키}` 로 검증해 주세요 |
| 실패가 있음 | 이 세션을 닫고 `/do {키}` 를 입력하면 기획자가 실패 원인을 가립니다. 이 세션에서 고치지 않는다. 브라우저 검증 뒤라 문맥이 크다 |
| 기획자에게 넘어감 | 리뷰나 수정이 설계 문제로 넘겼습니다. 이 세션을 닫고 `/do {키}` 를 입력하면 기획자가 설계를 다시 봅니다 |
| 리뷰 세션 실패 | 리뷰 세션이 끝을 맺지 못했습니다. `claude --resume {리뷰 세션 아이디}` 로 확인한 뒤 `/do {키}` 로 이어 가 주세요 |
| 질문을 남김(auto) | 대시보드나 오피스의 질문 창에서 답해 주세요. 답하면 자동 실행이 이어 갑니다 |
| 5-1 로 넘김 | 이 세션을 닫고 `/do {키}` 를 입력하면 새 세션이 light 로 멈춘 자리부터 이어 갑니다(자동 실행이 띄운 light 면 자동 실행이 바로 잇는다) |
| 5-2 로 넘김 | 이 세션을 닫고 `/do {키}` 를 입력하면 일반 실행이 멈춘 자리부터 이어 갑니다(자동 실행이 띄운 light 면 자동 실행이 바로 잇는다) |

`다음` 칸에는 마지막 끝 헬퍼가 낸 줄을 옮긴다.
