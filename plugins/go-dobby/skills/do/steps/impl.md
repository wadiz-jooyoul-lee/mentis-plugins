# 세션 2 · 구현

## 읽을 것 (이것만 읽는다)

1. `$ORCHESTRATION_META/{키}/design.md` — **작업 지시서다. 이 문서가 정본이다.**
2. `$ORCHESTRATION_META/{키}/status.md` — 워크트리 경로와 현재 단계.

**`analysis.md` 는 읽지 않는다.** 설계 문서에 필요한 것이 다 옮겨져 있다. 분석 문서까지 읽으면 문맥만 커진다. 설계 문서를 읽다가 근거가 더 필요할 때만 그 부분을 찾아 읽는다.

**설계 문서에 `## 변경 {M}` 절이 있고 그 상태가 `구현 대기` 면, 그 절들만 구현한다.** 앞의 본문은 이미 통합된 내용이다. 배경으로만 읽고 다시 구현하지 않는다. 아래 2~5번의 `## 고칠 코드`, `## 작업 순서`, `## 건드리지 않을 것`, `## 검증 명령` 은 그 변경 절 안의 같은 이름 소절로 읽는다. 워크트리에 이미 반영된 부분(아직 커밋 전인 앞 변경)이 있으면 다시 하지 않는다.

## 하는 일

1. 워크트리로 이동해 `design.md` 의 `## 고칠 코드` 를 그대로 구현한다.
2. `## 작업 순서` 가 있으면 그 순서를 지킨다.
3. `## 건드리지 않을 것` 에 적힌 파일은 손대지 않는다.
4. `## 검증 명령` 을 돌려 통과시킨다.
5. **커밋하지 않는다.** 리뷰는 커밋 전 변경을 본다.

## 설계대로 할 수 없을 때

구현하다 보면 설계대로는 안 되는 경우가 있다. 둘로 가른다.

| 경우 | 하는 일 |
|---|---|
| **표기만 다르다** — 설계 문서의 줄 번호나 파일 경로가 실제와 다르다. 동작과 범위는 그대로다 | 실제에 맞춰 구현하고, 구현 기록의 "설계와 달라진 점"에 무엇이 어떻게 달랐는지 적는다 |
| **동작이나 범위가 달라진다** — 설계가 고치라는 코드가 없다, 설계대로 하면 다른 곳이 깨진다, 설계에 없는 파일을 고쳐야 한다 | **고치지 않는다.** 아래 줄로 기획자에게 넘긴다. 설계를 바꾸는 것은 기획자다 |

```
dobby_v2_end {키} 설계문제 "{무엇이 왜 설계대로 안 되는지 — 코드 근거(파일:줄)와 함께}"
```

넘기기 전에 한 구현은 되돌리지 않고 작업 폴더에 둔다. 구현 기록에 어디까지 했는지 적는다. 기획자가 설계 문서에 변경 절을 더하면 다음 구현 세션이 그 변경을 구현한다. 더 나은 방법이 보여도 설계와 다르게 구현하지 않는다.

## 마무리

`implementation.md` 를 쓴다(`dobby_scaffold_doc {키} implementation`). 바꾼 파일, 핵심 결정, 설계와 달라진 점, 검증 명령 결과를 적는다. 변경을 구현했으면 덮어쓰지 않고 `## 변경 {M} 구현` 절로 덧붙인다.

```
dobby_v2_end {키} 완료
```

끝 헬퍼는 시작 뒤 작업 폴더가 바뀌었는지와 구현 기록을 고쳤는지 확인한다. 둘 중 하나라도 아니면 `거부:` 를 낸다. 그때는 빠진 일을 하고 다시 부른다. 통과하면 다음 리뷰 차수의 빈 폴더를 열고 리뷰어 차례로 넘긴다.

설계대로 할 수 없으면 위 "설계대로 할 수 없을 때"대로 `설계문제` 로 기획자에게 넘긴다. `막힘` 은 설계와 상관없이 사람 손이 있어야 풀리는 일(작업 폴더가 깨짐, 권한 없음)에만 쓴다.
