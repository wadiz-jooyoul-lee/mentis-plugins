# /do auto 모드 설계

명령 한 번으로 설계부터 배포 환경 테스트 통과까지 사람 없이 이어 가는 실행 방식의 설계다. 구현 전에 합의한 내용을 적었고, 구현하면서 바뀐 곳을 고쳐 두었다. 스킬 본문(`SKILL.md`)에는 지시만 두고 근거는 이 문서에 둔다.

## 지금과 무엇이 다른가

| 구분 | 지금(기본 실행) | auto 모드 |
|---|---|---|
| 설계 확정 | 사람이 "자동 실행"이라고 답한다 | 스스로 확정한다. 결정과 이유는 설계 문서 `## 결정과 근거` 에 남긴다 |
| 끝나는 곳 | 통합(작업 브랜치 커밋·푸시)까지 | 배포 환경 테스트 통과까지 |
| 배포 | 사람이 `/dobby-ship {키} {환경}` 을 실행하고 머지·빌드·argocd sync 를 매번 승인한다 | 배포 세션이 묻지 않고 진행한다. 시작할 때 받은 승인으로 대신한다 |
| 테스트 | 사람이 `/do {키}` 로 검증 세션을 띄운다 | 배포가 확인되면 자동으로 띄운다 |
| 테스트 실패 | 사람이 수정 세션을 띄운다 | 알리고, 원인을 가른 뒤 고칠 수 있으면 고쳐서 다시 배포·테스트한다 |
| 기다리기(리뷰봇·빌드) | 세션이 살아서 기다린다. 기다리는 동안에도 호출마다 문맥을 다시 읽는다 | `run.sh`(셸)가 기다린다. 기다리는 동안 토큰은 0이다 |
| PR 생성 | 하지 않는다 | 배포에 필요한 PR 만 dobby-ship 절차가 만든다 |

`dobby-auto` 와 하는 일이 같다. 차이는 진행 방식이다. `dobby-auto` 는 dobby-order 위에서 세션 하나로 끝까지 가고, 이 모드는 단계마다 새 세션을 띄운다. dobby-order 는 쓰지 않기로 했으므로 `dobby-auto` 도 이 모드를 부르게 바꾼다(아래 "dobby-auto 를 이 모드로 옮긴다").

## 시작하는 법

```
/do {키} auto env={dev|rc1|rc4}
```

- `env` 는 시작할 때 한 번만 받는다. 중간에 묻지 않는다.
- `stage` 는 받지 않는다. dobby-ship 이 stage 는 PR 까지만 만들고 사람이 머지·배포하기 때문이다.
- `cloud_live` 는 어떤 경우에도 가지 않는다(dobby-ship 규칙과 훅 G1 그대로).
- `env` 없이 `auto` 만 주면 지금과 같다. 설계만 스스로 확정하고, 자동 실행은 통합에서 멈춘다.

명령을 친 세션이 설계 세션이다. 설계를 스스로 확정하고, 아래 사전 확인을 통과하면 자동 실행을 띄운 뒤 끝난다. 그다음은 사람이 할 일이 없다.

### 설계 세션이 끝나기 전에 확인하는 것

중간에 멈추지 않으려면 사람이 필요한 준비를 처음에 다 확인한다. 하나라도 안 되면 자동 실행을 띄우지 않고 무엇이 빠졌는지 알린다. 고칠 저장소는 설계를 마쳐야 알 수 있으므로, 이 확인은 설계 뒤 자동 실행을 띄우기 직전에 한다.

| 확인 | 어떻게 | 왜 |
|---|---|---|
| 환경 값이 dev·rc1·rc4 중 하나 | 인자 검사 | 잘못된 환경으로 배포하는 것을 막는다 |
| argocd 로그인 상태(고칠 저장소에 com.wadiz.web 이 있을 때만) | `argocd account get-user-info --server {그 환경의 서버} --grpc-web` | 재로그인은 브라우저 SSO 라 자동으로 못 한다. 마지막 단계에서 막히면 그때까지 쓴 시간이 아깝다 |
| 테스트 계정 | 테스트 계획 `## 사전 준비` 의 계정과 config.env 의 `TEST_LOGIN_PW` | 로그인이 막히면 테스트가 처음부터 실패한다 |
| gh 로그인 | `gh auth status` | PR·머지·빌드를 모두 gh 로 한다 |
| 대시보드 | `dobby_v2_autorun` 이 확인한다 | 대시보드가 띄워야 터미널을 닫아도 실행이 살아 있다 |

통과하면 상태 문서 `## 현재 단계` 에 아래 한 줄을 적고(`dobby_v2_set_env {키} {환경}`), 설계 승인(`dobby_design_ack {키} auto`)을 기록한 뒤 `dobby_v2_autorun {키}` 를 부른다.

```
- **자동 배포 환경**: rc4
```

새 메타 파일을 만들지 않는다는 `/do` 규칙을 지키려고 상태 문서에 한 줄로 둔다. `run.sh` 와 대시보드는 이 줄이 있으면 배포·테스트까지 가고, 없으면 지금처럼 통합에서 멈춘다.

## 전체 흐름

```
[사람] /do {키} auto env=rc4
  설계 세션: 설계·테스트 계획 작성 → 스스로 확정 → 사전 확인 → 자동 실행 띄움 → 끝
                                                          │
[run.sh] ┌────────────────────────────────────────────────┘
         ▼
  구현 → 리뷰 ⇄ 수정 (최대 3차) → 통합(작업 브랜치 커밋·푸시)
         ▼
  배포 세션 ① PR 생성 ─────────────▶ [셸] 리뷰봇 기다림 (10분 알림, 30분 멈춤)
  배포 세션 ② 리뷰 반영·머지·빌드 ──▶ [셸] 빌드 끝날 때까지 기다림
  배포 세션 ③ 배포 확인(·argocd sync)
         ▼
  검증 세션
     통과 → 완료 알림 → 끝
     실패 → 실패 알림 → 실패 처리 세션
               ├ 배포가 덜 됨  → 다시 배포 → 다시 검증 (수정 횟수에 안 셈)
               ├ 코드 결함     → 수정 → 리뷰 → 통합 → 다시 배포 → 다시 검증 (최대 2번)
               └ 그 밖         → 판단 요청 알림 → 보류로 멈춤
```

부모는 지금처럼 `run.sh` 다. 단계마다 새 세션을 띄우고, 세션 이어 쓰기는 `session-reuse.md` 판정을 따른다.

배포 세션이 셋으로 나뉘는 이유는 기다림이다. dobby-ship 은 리뷰봇을 세션 안에서 30초마다 최대 10분, 배포 알림을 1분마다 최대 15분 기다린다. 그동안 호출마다 그 세션 문맥 전체를 다시 읽는다. 기다리는 자리에서 세션을 끝내고 셸이 기다리면 그 비용이 0이 된다.

## run.sh 가 다음 일을 정하는 표

판단이 필요 없도록 셸이 상태 문서와 git 만 보고 정한다. 지금 표에 배포·기다림·실패 처리 줄이 더해진다. `자동 배포 환경` 줄이 없는 오더는 지금 표 그대로다.

| 상태 | 더 보는 것 | 다음 일 |
|---|---|---|
| 분석·구현·리뷰 | — | 지금과 같다(구현, 리뷰, 수정, 통합) |
| 통합 | 표 단계 뒤에 `⚠`(막힘) | 멈춘다. 비고를 알림에 담는다 |
| 통합 | 어느 저장소 행이 `리뷰 대기` 이고, 그 행 갱신 뒤로 새 리뷰가 없다 | **셸이 기다린다** → 리뷰가 달리면 배포 세션 |
| 통합 | 어느 저장소 행이 `빌드 대기`·`배포 대기` 이고, 빌드 칸의 run 이 아직 돈다 | **셸이 기다린다** → 빌드가 끝나면 배포 세션 |
| 통합 | 어느 저장소든 작업 브랜치가 환경 브랜치에 없거나, 표가 `배포 확인` 앞이다 | **배포 세션** |
| 통합 | 모든 저장소의 작업 브랜치가 환경 브랜치에 들어갔고, 표가 `배포 확인` 이후다 | **검증 세션** |
| 검증 | 전부 통과 | 끝난다(완료 알림은 검증 세션이 보낸다) |
| 검증 | 실패가 있다 | **실패 처리 세션** |
| 보류 | — | 셸은 멈춘다. 사람이 `/do {키}` 로 답하면 판단 답 받기 세션이 된다 |

위에서부터 먼저 맞는 줄을 쓴다. 기다림이 배포 세션보다 앞인 이유는 com.wadiz.web 때문이다. wadiz-frontend 가 리뷰나 빌드를 기다리는 동안 com.wadiz.web 은 머지·sync 순서 규칙에 막혀 나아갈 수 없다. 그때 배포 세션을 띄우면 아무것도 못 하고 끝난다.

이 표는 `dobby_v2_ship_next {키}` 하나가 판정한다. `run.sh` 와 `/do` 단계 판정이 같은 함수를 불러서 둘이 다르게 읽을 일이 없다. 결과 첫 칸은 `blocked`·`wait-review`·`wait-build`·`ship`·`verify` 중 하나다.

### 재배포가 필요한지 가르는 법

```bash
git -C {워크트리} fetch -q origin
git -C {워크트리} merge-base --is-ancestor origin/{작업 브랜치} origin/{환경의 실제 브랜치}
```

참이면 작업 브랜치의 마지막 커밋까지 그 환경에 들어가 있다. 수정 커밋이 새로 생기면 다시 거짓이 되므로, 따로 표시하지 않아도 재배포가 필요하다는 것을 안다. 환경의 실제 브랜치는 저장소마다 다르다(com.wadiz.web 의 dev 는 `cloud_dev`). `_ship_branch` 로 옮긴다.

거짓인데 `## 배포` 표의 그 환경 행이 `배포 확인`·`검증 중`·`검증 완료` 로 남아 있으면 옛 배포의 기록이다. `run.sh` 가 다음 일을 정하기 전에 그 행을 **지운다**(`dobby_ship_reopen {키}`, 세션이 아니라 셸이 정해진 규칙대로 한다). 행을 그대로 두면 dobby-ship 0단계 "이어서 할 자리 찾기"가 이미 끝난 배포로 읽는다. 지우면 PR 생성부터 다시 하고, `dobby_ship_pr` 이 같은 브랜치의 열린 PR 이 없으면 새로 만든다.

반대로 작업 브랜치는 환경에 들어갔는데 배포가 덜 된 경우(번들 일부만 빌드됨, sync 안 됨)는 행을 지우지 않는다. 이미 머지된 브랜치로 PR 을 다시 만들면 올릴 커밋이 없어 실패한다. 실패 처리 세션이 행을 다시 할 단계(`빌드 대기`·`배포 대기`)로 되돌린다.

### 셸이 기다리는 것

| 기다리는 것 | 무엇을 보나 | 간격 | 상한 |
|---|---|---|---|
| 리뷰봇(wadiz-frontend 의 rc1·rc4) | `gh pr view {PR} --json reviews` 의 가장 늦은 리뷰 시각이 그 행 갱신 시각 이후인가 | 2분 | 10분에 알림, 30분에 멈춤 |
| 빌드 | `## 배포` 표 빌드 칸의 run id(`static#`·`global#`·`web#`)마다 `gh run view {id} --json status` | 1분 | 30분에 멈춤 |

리뷰는 개수가 아니라 시각으로 본다. 개수로 보면 셸이 기다리기 시작한 때의 개수를 따로 적어 둬야 하는데, 셸이 다시 띄워지면 그 값을 잃는다. 행 갱신 시각은 상태 문서에 이미 있다. 갱신 칸이 분 단위라 같은 분에 달린 옛 리뷰를 새 리뷰로 볼 수 있다. 그때는 배포 세션이 한 번 더 뜨고 리뷰를 다시 읽을 뿐이라 해가 없다. 시간 상한도 같은 갱신 시각부터 잰다.

dev 는 리뷰를 기다리지 않는다(dobby-ship 규칙: dev 는 충돌만 본다). com.wadiz.web 도 리뷰를 기다리지 않는다(리뷰봇이 없다). 빌드가 실패로 끝나면 기다리기를 멈추고 배포 세션을 띄운다. 배포 세션이 dobby-ship 규칙대로 실패를 다룬다.

## 사람이 끼던 자리를 무엇이 대신하나

| 사람이 끼던 자리 | 대신하는 것 |
|---|---|
| 설계 확정 | `auto`. 사람만 정할 수 있는 결정(제품·디자인·지울지 말지)이 나오면 승인을 기록하지 않고 멈춘다 |
| 커밋·푸시 동의 | 지금처럼 대시보드가 `--approve-commit` 을 넘긴다 |
| 머지·빌드·argocd sync 승인 | `run.sh` 가 `자동 배포 환경` 줄을 보고 배포 승인 지시를 덧붙인다(아래). dev·rc1·rc4 만 해당한다 |
| 리뷰봇·빌드 기다리기 | 셸 |
| 배포 뒤 검증 시작 | `run.sh` |
| 검증 실패 뒤 수정 | 실패 처리 세션 |

배포 승인 지시는 `--approve-commit` 과 같은 방식(`--append-system-prompt`)으로 세션마다 덧붙인다.

```
이 실행은 사용자가 {env} 배포를 미리 승인한 자동 실행이다. dev·rc1·rc4 의 머지·빌드·argocd sync 는
이미 동의를 받았으니 다시 묻지 말고 진행한다. stage·cloud_live 는 이 승인에 들어가지 않는다.
리뷰봇이나 빌드를 세션 안에서 기다리지 않는다. `## 배포` 표에 `리뷰 대기`·`배포 대기` 를 적고 세션을 끝낸다.
```

자동 실행에서도 막히는 것은 그대로다. 글이 아니라 훅과 헬퍼가 거부로 막는다.

| 막히는 것 | 무엇이 막나 |
|---|---|
| stage 머지·배포 | 훅 G1, `dobby_ship_argo` |
| cloud_live, 라이브 argocd 앱 | 훅 G1 |
| 반영 안 한 변경요청 | `dobby_ship_merge` |
| 배포 쪽 리뷰 4라운드째 | `dobby_ship_round` |
| wadiz-frontend 머지 전 com.wadiz.web 머지, wadiz-frontend 배포 전 sync | `dobby_ship_merge`, `dobby_ship_argo` |
| argocd 세션 만료 | `dobby_ship_argo` |

## 테스트가 실패했을 때

**실패해도 멈추지 않는다.** 검증 세션이 실패 알림을 보내고 끝나면, 실패 처리 세션이 원인을 가른다.

### 원인 분류

실패 처리 세션은 테스트 기록(`test-runs/{시각}/`)과 `## 배포` 표를 읽고 원인을 아래 중 하나로 고른다. 먼저 배포부터 의심한다(dobby-ship 10단계와 같은 순서 — 사례 FE1-1808 은 반쪽 배포를 코드 결함으로 오진할 뻔했다).

| 원인 | 어떻게 알아보나 | 처리 |
|---|---|---|
| 배포가 덜 됐다 | `dobby_ship_verify` 가 빠진 번들을 내놓거나, `dobby_ship_argo {키} {환경} check` 가 `OutOfSync`·`Progressing` | `## 배포` 표를 그 단계로 되돌린다. 다음은 배포 세션이다. 수정 횟수에 넣지 않는다 |
| 코드 결함 | 실패가 이번 변경 부분에서 재현된다 | 그 자리에서 고친다(수정 세션과 같은 규칙). 다음은 리뷰다 |
| 테스트 계획이 틀렸다 | 기대 결과가 설계 문서와 어긋난다 | 판단 요청 |
| 환경·데이터 문제 | 이번 변경과 무관한 곳에서 실패한다 | 판단 요청 |
| 원인을 모르겠다 | 위 어느 것에도 확신이 없다 | 판단 요청 |

### 판단 요청에 담는 것

사람이 메타를 열어 보지 않고도 결정할 수 있게 자세히 쓴다.

1. 무엇이 실패했는지: 시나리오 이름, 기대한 것, 실제로 본 것
2. 지금까지 한 것: 수정 시도 횟수와 각각 무엇을 바꿨는지
3. 분석: 원인을 무엇으로 보는지와 그 근거, 확인하지 못한 것
4. 선택지와 권장: 2~3개, 각각 무엇이 일어나는지
5. 이어 가는 법: `/do {키}` 로 답하면 된다는 안내

판단 요청을 보낸 뒤에는 설계 문서 `## 확인이 필요했던 것` 에 같은 내용을 적고, 상태 문서의 단계를 `보류` 로 바꾸고 멈춘다. 이 절은 `/do` 공통 규칙 "사람에게 묻지 않는다"가 이미 쓰는 자리다.

## 사람이 답한 뒤 다시 이어 가기

1. 사람이 `/do {키}` 를 실행한다. 단계가 `보류` 이고 `자동 배포 환경` 줄이 있으므로 **판단 답 받기** 세션이 된다(`/do` 세션 6-3).
2. 그 세션이 마지막 판단 요청을 보여 주고 답을 받아 설계 문서 `## 결정과 근거` 에 적는다. 테스트 계획을 고치기로 했으면 고친다. 코드를 고쳐야 하면 변경 접수로 받는다.
3. 단계를 되돌리고 자동 실행을 다시 띄운다(`dobby_v2_autorun {키}`). `자동 배포 환경` 줄은 그대로 있으므로 배포·테스트까지 다시 간다. 대시보드가 통합·검증 단계에서도 띄울 수 있게 고쳤다.

## dobby-auto 를 이 모드로 옮긴다

`/dobby-auto {키} {환경}` 은 명령 이름을 그대로 두고, 속을 `/do {키} auto env={환경}` 으로 바꾼다. 사람이 익힌 명령이 바뀌지 않고, "사람 없이 끝까지"의 진입점이 하나로 남는다.

| 오더 상태 | 처리 |
|---|---|
| 메타가 없다, 또는 v2 오더다(`## 지난 세션` 표가 있다) | `/do {키} auto env={환경}` 과 같은 일을 한다 |
| dobby-order 로 진행한 오더다 | 아무것도 고치지 않고 멈춘다. `/dobby-migrate-v2 {키}` 로 옮긴 뒤 다시 부르라고 알린다. 두 스킬이 한 오더를 번갈아 맡지 않는다 |
| 환경이 stage 다 | 받지 않는다. stage 는 `/dobby-ship {키} stage` 로 PR 까지만 만든다고 알린다 |

dobby-auto 의 충돌 처리(근거로 풀고, 확정 안 되면 해결안을 만들어 알리고 멈춤)는 `skills/dobby-ship/auto-conflict.md` 로 옮겼다. 평소 dobby-ship 은 진짜 충돌이면 거부하고 사람에게 `/merge-branch` 를 안내하므로, 승인 지시만으로는 같은 효과가 나지 않는다. 리뷰 반영 규칙(승인이어도 본문을 읽고, 반영은 지적 범위 안에서만)은 dobby-ship "자동 실행에서" 절에 넣었다. 그 절은 배포 승인 지시가 붙은 세션에만 해당한다.

이미 설계가 확정된 v2 오더에 `/dobby-auto` 를 부르면 설계 세션 없이 사전 확인, `dobby_v2_set_env`, `dobby_v2_autorun` 만 한다.
