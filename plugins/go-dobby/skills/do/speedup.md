# /do 소요 시간 줄이기 — 적용한 것, 남은 설계, 효과 측정

이 문서는 /do 자동 실행의 시간을 줄이는 작업의 설계다. 세 부분으로 나뉜다.

1. 이미 적용한 개선 다섯 가지와 그 근거
2. 아직 하지 않은 개선 세 가지의 설계
3. 개선 효과를 재는 스킬과 대시보드 성능 탭의 설계

## 1. 기준 실측 (2026-11-17)

지난 /do 오더 63개의 세션 기록(`~/.claude/projects/*/{세션아이디}.jsonl`)으로 쟀다. 사람과 대화한 세션(사람이 친 줄이 2개 이상)은 뺐다.

| 단계 | 세션 수 | 세션 하나 평균 | 응답 수 | 캐시 읽기 | 새 입력 | 출력 |
|---|---|---|---|---|---|---|
| 검증 | 90 | 6.3분 | 64 | 838만 | 11만 | 2.6만 |
| 구현 | 130 | 6.0분 | 24 | 235만 | 9만 | 1.5만 |
| 리뷰 | 153 | 3.6분 | 19 | 162만 | 9만 | 1.2만 |
| 배포 | 131 | 2.1분 | 18 | 128만 | 5만 | 0.7만 |
| 통합 | 136 | 1.6분 | 16 | 116만 | 4만 | 0.9만 |

- 타입 검사가 구현 시간의 절반이었다. 오더 13개 기준 약 160분이고, 한 번에 6~10분이었다.
- 검증 세션 하나는 준비 70초, 시험 250초, 마무리 20초였다. 화면 구조 읽기는 6.1번, 화면 갈무리는 2.3번이었다.
- 응답 하나의 시간은 문맥이 커져도 거의 같았다. 문맥 5만~10만일 때 3.3초, 15만~25만일 때 3.7초였다.
- 세션 사이 빈 시간은 3초 안팎이었다. 단계를 고르는 헬퍼는 0.4초 이하였다.
- 배포 세션 사이의 기다림(합계 419분)은 리뷰봇과 빌드라는 바깥 일이다.

측정 기준값은 3절의 측정 스킬이 비교 기준(`baseline`)으로 쓴다. 값을 바꾸면 이 표와 스킬의 기준값을 함께 고친다.

## 2. 적용한 개선

| 개선 | 바꾼 곳 | 기대 효과 | 기록에 남는 표식(측정 스킬이 읽음) |
|---|---|---|---|
| 타입 검사 기본 끔 | `dobby_typecheck`, `steps/design.md`·`impl.md`·`review.md`, `SKILL.md` 의 `타입 검사` 인자 | 오더당 약 12분 | 상태 문서 `- **타입 검사**: 켬 …` 줄(없으면 꺼짐). 세션 기록의 `dobby_typecheck` 호출과 그 출력의 `건너뜀`·`권함`·`검사 N초`·`저장된 결과` |
| 켠 오더의 타입 검사 재사용 | `dobby_typecheck`(지난 검사 기록, 내용 지문별 결과 저장) | 다시 검사 6~10분에서 0~8초로 | 같은 출력 줄의 `검사 N초`·`저장된 결과` |
| 작은 검증 묶음 합치기 | `dobby_verify_next` | 합쳐진 세션 하나당 약 1분 40초 | 지난 세션 표의 단계 이름 `검증 V1+V3` |
| 배포 대기 확인 간격 | `run.sh` 리뷰봇 120초, 빌드 60초를 30초로 | 배포 한 번에 약 1분 | 상태 문서 배포 표의 기다림 표시(`dobby_v2_wait_mark`)와 배포 세션 사이 간격 |
| 검증 묶음 동시 실행 | `dobby_verify_pair`, `run.sh` 의 `run_pair`, `steps/verify.md`, 테스트 계획 `동시 실행` 칸 | 검증하는 오더당 6~13분 | 이벤트 로그 `검증 동시 실행(묶음)` 줄 두 개. 두 세션의 시작·끝 시각이 겹침 |

### 검증 묶음 동시 실행의 규칙

- 첫 묶음은 혼자 돈다. 그 세션이 회차를 연다.
- 회차가 열린 뒤, 남은 두 묶음이 모두 테스트 계획 `## 검증 묶음` 표의 다섯째 칸 `동시 실행` 이 `가능` 이면 함께 띄운다.
- 두 번째 세션은 브라우저 프로필을 따로 쓴다(`$PROFILE-2`). 그래서 로그인부터 한다.
- 두 세션은 환경 변수 `DOBBY_VERIFY_SKIP` 로 상대 묶음을 받는다. `dobby_verify_next` 는 그 묶음을 건너뛰고, `done` 대신 `wait` 를 낸다. 그래서 두 세션 모두 회차를 마감하지 않는다. 마감은 뒤에 띄우는 세션이 한다.
- 동시 실행 세션은 질문을 남기지 않는다. 질문 파일이 오더에 하나뿐이기 때문이다. 사람 손이 필요하면 `넘김` 으로 끝낸다.
- 함께 돈 뒤 그 묶음에 판정이 빈 시나리오가 남으면, 그 실행에서는 다시 동시에 띄우지 않는다.

**잃는 것:** 크롬이 둘 떠서 컴퓨터 부담이 커진다. 두 번째 브라우저의 로그인이 한 번 더 든다. 마지막이 동시 실행이면 마감만 하는 짧은 세션이 하나 더 든다.

## 3. 남은 개선 설계

세 가지는 서로 독립이다. 따로 PR 을 만들어도 된다.

### 3-1. 통합 단계의 문서 쓰기를 배포 기다림과 겹치기

**지금:** 통합 세션(`steps/integrate.md`)이 커밋과 푸시, 결과 문서(`outcome.md`), 구현 내용 설명 문서(`dobby-explain`)를 차례로 한다. 통합 시간의 57%가 모델 시간이고, 대부분 문서 두 개를 쓰는 데 쓴다. 그 뒤 자동 배포 오더는 리뷰봇과 빌드를 5분 넘게 기다린다.

**바꿀 것:**

1. 자동 배포 오더(`- **자동 배포 환경**:` 줄이 있음)의 통합 세션은 다음만 한다.
   - 막는 지적 0건 확인
   - 커밋과 푸시
   - 루트 브랜치 머지
   - 설계 문서 변경 절 상태 고치기
   - 그리고 상태 문서에 `- **결과 문서**: 대기` 줄을 적는다.
2. `run.sh` 는 통합이 끝나 배포 차례가 되면 문서 세션 하나를 백그라운드로 띄운다. 명령은 `claude -p "/do {키} 결과 문서"` 이다.
   - 이 세션은 `outcome.md` 와 `dobby-explain` 만 하고, `- **결과 문서**: 완료 (시각)` 로 바꾼다.
   - 브라우저 도구가 필요 없으므로 MCP 를 붙이지 않는다.
3. `run.sh` 는 끝내기 전(`finish`)과 검증 차례로 넘어가기 전에 문서 세션이 끝났는지 본다. 끝나지 않았으면 기다린다.
4. 완성 판정(`_v2_finished`, `_v2_complete`)은 `결과 문서` 줄이 `대기` 나 `작성 중` 이면 완성으로 옮기지 않는다.
5. 자동 배포가 아닌 오더(통합에서 멈춤)는 겹칠 기다림이 없으므로 지금처럼 통합 세션이 문서까지 쓴다.

**겹칠 때 조심할 것:**
- 상태 문서는 두 세션이 함께 고친다. 줄을 고치는 헬퍼는 모두 `_dobby_locked` 를 거쳐야 한다. 문서 세션이 부르는 헬퍼를 확인한다.
- 문서 세션의 작업 표시가 배포 세션의 시작 검사(`dobby_v2_begin` 의 "다른 세션 작업 중")에 걸리지 않게 한다. 검증 동시 실행처럼 환경 변수(`DOBBY_DOCS_JOB=1`)로 예외를 둔다.
- 통합이 여러 번(변경 N) 도는 오더는 문서 세션도 여러 번 뜬다. 앞 문서 세션이 아직 돌면 새로 띄우지 않고 끝나기를 기다린다.

**효과(예측):** 통합 세션이 1.6분에서 약 0.5분이 된다. 오더당 통합이 평균 2.2번이라 약 2분이 준다.
**토큰(예측):** 문서 세션 시작 문맥 약 5.6만과 근거 문서 읽기가 더 든다. 통합 한 번에 약 50만이고, 대부분 캐시 읽기다.

**성공 기준:**
- 자동 배포 오더 하나를 돌려, 통합 세션 시간이 1분 안쪽인지 본다.
- 문서 세션이 배포 기다림 안에서 끝나는지 본다.
- `outcome.md` 와 `explainer.md` 가 지금과 같은 내용으로 남는지 본다.

### 3-2. 의존성 설치를 설계 단계에서 미리 하기

**지금:** 구현 세션이 `pnpm install` 을 하느라 합계 24분을 썼다(오더당 약 0.4분). 타입 검사가 켜진 오더는 `dobby_typecheck` 도 설치를 한다.

**바꿀 것:**
1. 헬퍼 `dobby_deps_prefetch KEY 작업폴더` 를 만든다.
   - `node_modules` 가 없거나 `pnpm-lock.yaml` 이 마지막 설치보다 새로우면 `CI=true NODE_ENV=development pnpm install --frozen-lockfile` 을 한다.
   - 끝나면 `$META/{키}/.deps-ready` 에 잠금 파일 지문과 시각을 적는다.
2. 설계 안내문(`steps/design.md`)의 1-3 검증 명령 항목에 "wadiz-frontend 작업 폴더면 `dobby_deps_prefetch` 를 백그라운드로 부른다"를 더한다. 타입 검사 기준선과 같은 자리다.
3. 구현 안내문(`steps/impl.md`)에 "`.deps-ready` 가 잠금 파일 지문과 맞으면 설치를 건너뛴다"를 더한다. `dobby_typecheck` 의 설치 단계도 같은 검사를 쓴다.

**효과:** 오더당 약 0.4분. 토큰은 들지 않는다.
**성공 기준:** 설계 뒤 첫 구현 세션 기록에 `pnpm install` 호출이 없다.

### 3-3. 검증 세션의 화면 확인을 스크립트 한 번으로 묶기

**지금:** 검증 세션 하나가 응답을 64번 한다. 세션 시간은 응답 횟수에 비례한다(응답 하나 약 2.6초). 화면 구조 읽기 6.1번, 화면 갈무리 2.3번이 들고, 값 하나를 확인하려고 화면 구조를 통째로 읽는 경우가 많다.

**바꿀 것:**
1. `skills/dobby-test/SKILL.md` 묶음 모드에 확인 방법 규칙을 더한다.
   - 화면의 글자, 요소가 있는지, 속성 값처럼 여러 값을 확인할 때는 `evaluate_script` 한 번으로 모아서 읽는다. 결과는 `{확인 항목: 값}` 꼴로 돌려받는다.
   - 화면 구조 읽기(`take_snapshot`)는 누를 요소를 찾을 때만 쓴다.
   - 화면 갈무리는 시나리오마다 근거용 한 장만 남긴다.
2. 설계 안내문의 시나리오 쓰기 규칙에 "통과 기준에 확인할 선택자나 문구를 적는다"를 더한다. 검증 세션이 화면 구조를 읽지 않고 바로 스크립트로 확인할 수 있게 하기 위해서다.

**효과:** 지난 기록으로는 잴 수 없다. 측정 스킬의 "시나리오 하나당 응답 수"로 바꾼 뒤에 잰다.
**토큰:** 응답이 줄면 캐시 읽기가 함께 준다. 늘지 않는다.
**잃는 것:** 화면 구조를 덜 읽으므로 예상하지 못한 화면 깨짐을 놓칠 수 있다. 그래서 근거용 갈무리 한 장은 유지한다.
**성공 기준:** 바꾼 뒤 오더 두 개 이상에서, 시나리오 하나당 응답 수가 지금(약 13)보다 줄었는지 본다.

## 4. 효과 측정 스킬 — `dobby-perf`

### 목적

오더 하나를 정해 실행하면, 그 오더에 적용된 개선마다 시간과 토큰을 재서 메타 한 곳에 정리한다. 대시보드 성능 탭이 그 파일을 읽어 보여 준다.

### 사용법

```
/dobby-perf FE1-XXXX        # 그 오더를 재서 perf.json 을 새로 쓴다
/dobby-perf FE1-XXXX regen  # 같은 동작(이미 있어도 다시 잰다)
```

- 대화형과 헤드리스 모두 돈다. 숫자는 헬퍼가 직접 쓰고, 모델은 해석 문장만 쓴다.
- 오더가 진행 중이어도 잴 수 있다. 다만 끝나지 않은 단계는 "진행 중"으로 표시한다.
- 파일만 쓰고 커밋·푸시는 하지 않는다.

### 저장 위치

`$ORCHESTRATION_META/{키}/perf.json` 하나다. 다시 재면 덮어쓴다(측정 시각을 파일 안에 남긴다).

### 측정 방법

헬퍼 `dobby_perf_measure KEY` 가 한다. `dobby_retro_measure` 와 같은 방식으로 상태 문서의 `## 지난 세션` 표에서 세션 아이디를 모아 세션 기록을 읽는다.

1. **세션별 기본값:** 단계, 시작·끝 시각, 응답 수(`message.id` 로 하나만 센다), 모델 시간, 도구 시간, 캐시 읽기·새 입력·출력 토큰.
2. **개선별 값:**

| 개선 | 적용 여부 판정 | 재는 값 | 비교 기준 |
|---|---|---|---|
| 타입 검사 기본 끔 | 상태 문서 `타입 검사` 줄 없음, 타입 검사 출력에 `건너뜀` 이 있음. 개선 전처럼 직접 검사한 기록만 있으면 해당 없음. 둘이 섞이면 줄어든 시간은 `null` | 세션 기록의 타입 검사 호출(`dobby_typecheck`, `tsc`) 수와 걸린 시간. `건너뜀` 출력 수 | 기준 실측: 오더당 약 12.3분 |
| 타입 검사 재사용 | `타입 검사` 줄이 켬 | 검사 한 번 시간(`검사 N초`·`저장된 결과`) | 기준: 한 번 6~10분 |
| 묶음 합치기 | 단계 이름에 `+` 가 든 검증 세션 | 합쳐진 세션 수 | 합쳐진 세션 하나당 약 102초 줄어든 것으로 계산 |
| 동시 실행 | 이벤트 로그 `검증 동시 실행` 줄 | 두 세션이 겹친 시간 | 겹친 시간만큼 줄어든 것으로 계산 |
| 배포 대기 간격 | 대시보드 자동 실행 기록(`.mentis-jobs/{키}/run.log`, 마지막 실행분)의 기다림 줄 간격이 1분 이하. 기록이 없으면 `null` | 기다린 일 수(리뷰봇, 빌드) | 기준: 확인 간격의 절반만큼 더 기다렸던 것으로 계산(리뷰봇 45초, 빌드 15초) |
| 통합 문서 분리(3-1) | `결과 문서` 줄이 있음 | 통합 세션 시간과 문서 세션 시간, 둘의 겹침 | 기준: 통합 세션 1.6분 |
| 의존성 미리 설치(3-2) | `.deps-ready` 있음 | 구현 세션의 설치 시간 | 기준: 오더당 0.4분 |
| 화면 확인 묶기(3-3) | 판정 기준은 3-3 을 적용할 때 정한다. 그 전에는 해당 없음 | 시나리오 하나당 응답 수(검증 세션 응답 수 ÷ 시험 결과의 시나리오 행 수) | 기준: 약 13 |

3. **전체 값:** 자동 실행 시간 합계(세션 시간의 합에서 동시 실행으로 겹친 시간을 뺀 실제 걸린 시간), 사람을 기다린 시간(따로 표시하고 합계에 넣지 않음), 토큰 합계.
   - 사람과 대화한 세션(구간 안에서 사람이 친 줄이 2개 이상)은 1절 기준과 같게 합계와 기준에서 뺀다. `interactive` 칸에 모델 시간과 도구 시간의 합만 따로 둔다.
   - 컴퓨터가 잠든 구간은 세션 시간과 합계에서 빼고 `sleepMin` 에 따로 둔다. 잠자기 기록(`pmset -g log`)의 잠듦 줄부터 다음 깨어남 줄까지다. 이 기록은 약 일주일만 남아서, 못 뺀 경우 `sleepLog` 에 이유를 적는다. FE1-2668 은 밤새 잠든 746분이 배포와 검증 세션 안에 들어 있었다.
   - 사람을 기다린 시간은 이벤트 로그의 `사람 차례`, `막힘` 줄부터 같은 담당자의 다음 줄 또는 다음 세션 시작 중 이른 때까지다.
   - 단계 묶기: `N차 리뷰` 는 리뷰다. `구현`, `변경 N 구현`, `N차 수정`, `검증 실패 수정` 은 구현이다. 이름에 `통합` 이 있으면 통합, `배포` 로 시작하면 배포, 나머지 `검증…` 은 검증이다. 그 밖은 기타이고, 기준에 실제 시간을 그대로 넣는다.
4. **기준과 비교:** 1절 표의 단계별 평균으로 "개선 전이었다면 걸렸을 시간"을 계산한다. 단계별로 이번 오더의 세션 수에 기준 평균을 곱한다. 계산식은 파일 안 `method` 칸에 글로 남긴다.

### `perf.json` 모양

```json
{
  "key": "FE1-XXXX",
  "measuredAt": "2026-11-20 10:00",
  "pluginVersion": "0.2.148",
  "status": "완성 | 진행 중",
  "totals": {
    "wallMin": 34.5,
    "baselineMin": 49.8,
    "savedMin": 15.3,
    "humanWaitMin": 12.0,

    "tokens": { "cacheRead": 21000000, "input": 400000, "output": 90000 },
    "baselineTokens": { "cacheRead": 20500000, "input": 380000, "output": 88000 }
  },
  "sleepLog": "",
  "interactive": { "sessions": 2, "min": 40.1, "tokens": { "cacheRead": 0, "input": 0, "output": 0 } },
  "byStage": [
    { "stage": "구현", "sessions": 2, "min": 8.1, "baselineMin": 12.0, "modelMin": 3.2, "toolMin": 4.9 }

  "summary": "모델이 쓰는 해석 3~5문장"
}
```

- 적용되지 않은 개선도 `applied: false` 와 그 이유를 남긴다. 화면이 "이 오더에는 해당 없음"을 보여 줄 수 있게 하기 위해서다.
- 잴 수 없는 값은 `null` 로 두고 `note` 에 이유를 적는다. 추정한 값은 `note` 에 "추정"이라고 적는다.
- 판정을 못 한 개선은 `applied: null` 이다. 화면은 "측정 못 함"으로 보인다.

### 스킬 문서와 검사

- `skills/dobby-perf/SKILL.md`: 사용법, 헬퍼 호출, 해석 문장 쓰는 규칙(쉬운 말, 짧은 문장, 내부 용어 금지).
- 헬퍼 `dobby_perf_put KEY 파일`: 모델이 쓴 `summary` 만 합친다. 다른 칸은 거부한다.
- 헬퍼 `dobby_perf_lint KEY`: 필수 칸, 숫자 형식, `null` 값의 이유, `summary` 3~5문장과 문장 길이, 내부 용어를 검사한다. `dobby_retro_lint` 와 같은 틀이다.
- `reference/config.md` 헬퍼 표에 `dobby_perf_measure`, `dobby_perf_put`, `dobby_perf_lint` 를 더한다.
- 이 스킬 문서에는 다른 스킬 이름을 쓰지 않는다. 필요한 규칙은 직접 적는다.

## 5. 대시보드 성능 탭 (mentis-dashboard-v2)

### 자리

- 오더 화면 탭 목록(`src/components/OrderHeader.tsx`)의 `회고` 다음에 `{ key: "perf", label: "성능" }` 을 더한다. 요약 탭 목록과 기본 탭 목록 둘 다다.
- 경로는 `/orchestration/{키}/perf` 다. 화면은 `src/app/orchestration/[key]/perf/page.tsx` 에 둔다. `retro` 화면과 같은 틀이다.
- 읽는 코드는 `src/lib/perf.ts` 다. `perf.json` 의 타입과 읽기 함수를 둔다(`src/lib/retro.ts` 와 같은 틀).

### 화면 구성 (위에서 아래로)

1. **한 줄 요약 카드**
   - 큰 글씨: "이 오더 자동 실행 34분 — 개선 전 기준이면 50분, 15분 줄었습니다"
   - 작은 글씨: 측정 시각, 플러그인 판, 사람을 기다린 시간(합계에 넣지 않았다는 안내)
2. **전과 후 막대**
   - 단계별(구현, 리뷰, 통합, 배포, 검증)로 가로 막대 두 개를 나란히 그린다. 회색은 기준, 색은 이번 오더다.
   - 막대 끝에 분 숫자를 적는다.
3. **개선 항목 카드**(항목마다 하나)
   - 제목(예: "타입 검사 기본 끔")
   - 상태 표시: 적용됨, 해당 없음, 측정 못 함
   - 줄어든 시간, 토큰 변화(늘면 주황, 줄면 초록)
   - 근거 한 줄(`evidence`)
   - 추정이면 "추정" 표시
4. **시간 흐름 그림**
   - 세션을 시각 순서로 가로 띠로 그린다. 동시 실행으로 겹친 검증 세션은 두 줄로 겹쳐 보인다.
   - 사람을 기다린 구간은 빗금으로 구분한다.
5. **해석**: `summary` 문장
6. **비어 있을 때**: "아직 측정하지 않았습니다"와 실행 명령 `/dobby-perf {키}` 를 복사할 수 있게 보인다. 회고 탭의 빈 화면과 같은 방식이다.

### 표기 규칙

- 숫자는 분 단위 소수 첫째 자리, 토큰은 "만" 단위로 쓴다.
- 내부 용어(단계 코드, 슬러그, 파일 이름)를 화면에 쓰지 않는다. 항목 이름은 `perf.json` 의 `name` 을 그대로 쓴다.
- 밝은 화면과 어두운 화면 모두에서 읽혀야 한다. 대시보드의 기존 색 변수를 쓴다.

### 성공 기준

- 측정을 마친 오더 하나와 측정하지 않은 오더 하나를 열어, 두 화면이 모두 바르게 보인다.
- 대시보드 저장소의 타입 검사와 린트가 통과한다.
