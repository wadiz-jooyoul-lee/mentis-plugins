# dobby-test

브랜치에서 작업한 내용이 실제로 동작하는지 chrome-devtools(브라우저 자동화)로 확인하는 스킬. 변경 분석 → 테스트 시나리오 확보 → 실제 브라우저 테스트 → 결과 리포트(회차별 저장 + 화면 출력)까지 한다.

> chrome-devtools: 브라우저를 열어 이동·클릭·입력·스크린샷·네트워크 확인을 자동으로 하는 도구(MCP). `mcp__chrome-devtools__*`를 쓴다.

**검증 원칙**: **`${CLAUDE_PLUGIN_ROOT}/reference/role-personas.md`의 "테스트 에이전트" 판단 기준**(불신 기본값·직접 실행한 것만 통과·경계/오류/권한을 노려 테스트·재현 가능한 실패 보고)을 따른다.

## 설정 (첫 실행 시 확인)

작업을 시작하기 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md`의 "설정 절차"를 그대로 따른다**: `~/.config/go-dobby/config.env`를 source 해 환경 변수를 **읽기만** 한다. ⛔ **이 스킬은 config.env를 저장·수정·생성하지 않는다**(값 변경은 `dobby-init` 전용 — config.md '비파괴 원칙'). config.env 파일이 아예 없으면 멈추고 `/dobby-init`을 먼저 실행하도록 안내한다. 메타 루트 `ORCHESTRATION_META`, 변수 목록·기본값, 폴더 배치(워크트리 `$ORCHESTRATION_WORKSPACE/subtree/` · 메타 `$ORCHESTRATION_META/`)는 모두 그 문서에 있다. 이하 메타 경로는 `$ORCHESTRATION_META` 기준. **공용 헬퍼(config.md '공용 헬퍼', 이미 source됨)**: 회차 시작은 `dobby_testrun_new 키 [전체시나리오수] [환경]`(회차 자동 계산 + 폴더/result.md 골격 + status.md 이력 표 행 추가, 폴더 경로 반환), 회차 행 갱신은 `dobby_testrun_update 키 {폴더시각} {상태} [성공/실패/skip]`(그 행만 수정 — status.md 통독 금지), 현재 단계 전이는 `dobby_phase 키 검증`.

## 산출물 (단일 이슈 폴더)

이슈/작업 루트: `$ORCHESTRATION_META/{키}/`

- `status.md` — **단일 진행 인덱스**(이슈 폴더에 하나). 테스트 진행 중 현재 단계·`테스트 실행 이력` 표를 실시간 갱신한다.
- `test-plan.md` — **테스트 목록**(dobby-start가 초안 생성). 없으면 이 스킬이 diff로 생성. self-contained.
- `test-runs/{YYYYMMDD-HHMMSS}/result.md` — **테스트 결과**. 실행 시각별 폴더에 저장해 **절대 덮어쓰지 않는다**. 스크린샷 등 근거도 같은 폴더.

## 입력

- `args`: 선택. 키(`FE1-1234`)·브랜치명. 없으면 **현재 브랜치**를 대상으로 한다. 브랜치·키에서 이슈 키를 추출(안 되면 물어봄).
- `묶음={이름} 시나리오={번호들}`: 선택. 주면 아래 **묶음 모드**로 돈다. `/do` 검증 세션이 `dobby_verify_next` 결과를 그대로 넘긴다.

## 묶음 모드 (`묶음=` 을 받았을 때)

한 회차를 여러 세션이 나눠 채운다. 이 세션은 받은 시나리오만 돈다. 아래에 적은 것만 다르고 나머지 절차는 같다.

| 절차 | 묶음 모드에서 |
|---|---|
| 2. 테스트 목록 | 테스트 계획 전체를 읽지 않는다. `dobby_testplan_slice {키} {번호들}` 이 내는 부분만 읽는다 |
| 2의 영향 번들, 3의 배포 반영 확인 | **회차를 새로 열 때만** 한다. 열린 회차(`_testrun_open {키}` 가 폴더를 냄)를 잇는 세션은 앞 묶음이 확인했으므로 건너뛰고, 환경은 그 회차 `result.md` 의 `- **환경**:` 줄을 쓴다 |
| 5. 로그인 | 앞 묶음의 로그인이 남아 있을 수 있다. 먼저 화면 머리의 로그인 상태를 보고, 이미 로그인돼 있으면 다시 하지 않는다. 사전 상태가 "로그아웃 상태"인 시나리오는 5절의 로그아웃 버튼으로 로그아웃한 뒤 시작한다 |
| 6-0 의 1. 회차 폴더 | `dobby_testrun_new` 대신 **`dobby_testrun_current {키} {전체 시나리오 수} {환경}`** — 열린 회차가 있으면 그 폴더, 없으면 새 회차를 연다 |
| 6-1. 시나리오 루프 | 받은 번호만 돈다. 행과 이력 집계는 지금처럼 시나리오마다 바로 채운다. 집계는 이 회차 `result.md` 전체(앞 묶음 포함)로 센다 |
| 7·8. 마감과 정리 | 루프가 끝나면 `dobby_verify_next {키}` 를 부른다. `done` 일 때만 7·8을 한다. 묶음이 남았으면 마감하지 않고, 이번 세션이 연 탭만 닫고 끝낸다(요약 파일·검사·그림 정리는 마지막 묶음이 한다) |

## 절차

### 1. 대상 결정
- 입력이 있으면 그 키/브랜치, 없으면 `git rev-parse --abbrev-ref HEAD`. 키로 Jira를 조회해 맥락 파악(작업 키면 대상 문서·analysis.md로 파악).

### 2. 테스트 목록 확보 — 기존 우선, 없으면 생성
- `$ORCHESTRATION_META/{키}/test-plan.md`가 **있으면**(대개 dobby-start 작성) 기본으로 **재사용**한다. 실제 diff와 대조해 빠진 부분만 보강하고, `미정`으로 남은 환경은 3단계에서 채운다.
- **⛔ 영향 번들을 먼저 맞춘다(있든 없든)**: `${CLAUDE_PLUGIN_ROOT}/reference/bundle-scope.md` 를 따라 **실제 diff**로 네 번들(`static`·`static-global`·`static-account`·`studio`)의 영향을 판정한다. 계획에 `## 영향 번들` 표가 없거나, 표의 판정이 실제 diff 와 다르거나, 영향인데 그 번들 화면의 시나리오(`- **번들**:` 줄)가 없으면 표와 시나리오를 보강한 뒤 진행한다. 설계 때 예상한 파일과 실제로 고친 파일이 달라 영향 번들이 늘어나는 일이 있기 때문이다.
- **없으면**: 베이스 대비 변경 파일 확인(`git diff --name-only origin/{base}...{branch}`) → 위 영향 번들 판정 → 영향인 번들마다 그 번들이 그리는 페이지/기능으로 매핑 → 시나리오(S1, S2…)를 도출해 `test-plan.md`에 저장(self-contained: 대상 URL·사전조건·조작·기대·검증 방법·테스트 데이터+재현 SQL). 재실행 시 최신 분석으로 덮어쓴다.

### ⛔ 2-1. 광고·데이터 수집 — 기계가 가린 뒤 시나리오를 **반드시** 넣는다

```bash
dobby_track_scan {키} {환경}
```

**왜 따로 보나**: 광고와 수집은 **화면에 안 보이게 깨진다.** 배너가 사라지면 눈에 띄지만, `ad.section.view` 가 안 나가거나 `trackingCustomTag` 의 `label` 이 바뀌는 것은 화면이 멀쩡하다. 위 2단계는 "사용자에게 보이는 페이지/기능으로 매핑"해 시나리오를 뽑으므로 **안 보이는 것은 구조적으로 안 잡힌다.**

실측(메타 전수): 분석·구현 문서에 추적·광고 코드가 등장한 오더 **29건 중 검증에서 실제로 확인한 것은 4건**(14%)이다. 나머지 25건은 확인 없이 나갔다. **사람 판단에 맡기면 빠지므로 탐지를 기계로 내렸다.**

헬퍼가 세 갈래로 가른다.

| | 무엇을 보나 |
|---|---|
| **A. 직접** | 그 파일이 수집·광고 코드다 — `packages/core/src/metrics/`·`packages/event-tracker/`·`static/libraries/react-ad-boundary/`·`static/packages/banner/`·`web/WEB-INF/jsp/winclude/tracking*.jsp` 등 |
| **B. 연관** | 바뀐 줄에 `trackingEvent`·`trackingCustomTag`·`trackingBraze`·`@wadiz/metrics`·`@wadiz/event-tracker`·`dataLayer`·`AdBoundary`·`_refer_section_st`·`gaEvt`·`appboy` 가 있다 |
| **C. 화면 경유** | 탐지하지 않는다 — 레이아웃 변경으로 배너가 사라지는 것은 diff 에 안 드러난다. **6-1 의 상시 그물**이 받는다 |

⛔ **`지워짐` 으로 표시된 줄을 그냥 넘기지 않는다.** 추적 호출을 **지운 것**이 가장 조용한 사고다 — 화면은 완벽히 멀쩡하고 데이터만 사라진다. 의도한 것인지 `analysis.md`·`design.md` 로 확인하고, 의도가 아니면 **테스트가 아니라 코드 문제**로 보고한다.

⛔ **`⚠ 확인 불가` 가 뜨면 "없음" 이 아니다.** 워크트리가 지워졌거나 PR 을 못 찾아 **변경을 읽지 못한** 것이다. `gh pr diff {번호} | grep -nE 'tracking|dataLayer|AdBoundary'` 로 직접 본다.

**접촉이 있으면 시나리오를 넣는다.** `확인 항목` 칸에 `[수집]`·`[광고]` 를 적어 표시한다. 7단계에서 `dobby_testrun_lint` 가 **없으면 회차 마감을 거부한다.**

```markdown
| S7 | C1 | /web/social/setting | [수집] 토글 저장 시 GA 이벤트 | ga.custom.tag · category=친구관리 · label=알림토글 | … | | … |
| S8 | —  | /                    | [광고] 메인 팝업 배너 노출·클릭 | ad.section.view 1건 + 링크에 _refer_section_st | … | | … |
```

확인할 수 없는 사정이면 **시나리오를 넣고 판정을 `SKIP(…)`** 으로, 사유를 함께 적는다. ⛔ 빼지 않는다.

### 3. 테스트 환경 결정
- 브랜치가 **머지된 환경**에서 테스트한다. `gh pr list --head {branch} --state all --json number,baseRefName,mergedAt,state`로 머지 대상(base)을 확인해 env를 판단.
- env를 **`ORCHESTRATION_ENV_MAP`**으로 접속 호스트에 대응(기본: dev=dev.wadiz.io, rc=rc.wadiz.kr, rc2=rc2.wadiz.kr, rc4=rc4.wadiz.io). **매핑에 없으면 추측하지 말고** 사용자에게 직접 테스트를 부탁한다.
- PR이 없거나 머지 안 됐거나 환경이 애매하면 **중단하고 사용자에게** 어느 환경에서 테스트할지 묻는다.
- **⛔ 머지 ≠ 배포 — 회차를 열기 전에 배포 반영을 먼저 확인한다**: PR이 머지됐어도 그 뒤 빌드·배포가 돌지 않았으면 환경은 **옛 코드를 서빙한다.** 확인 방법 ⓐ 대상 환경이 서빙하는 번들을 직접 내려받아 이번 변경의 **고유 문자열**(새로 추가한 상수·클래스명·주소 등)이 들어 있는지 검사하고, ⓑ 번들의 `Last-Modified`가 **PR 머지 시각보다 뒤인지** 대조한다. `## 영향 번들` 표에서 **영향인 번들마다 따로** 확인한다(`static`·`static-global`·`static-account`·`studio` 는 각각 따로 빌드·배포된다 — 올라가는 곳은 `bundle-scope.md` 의 번들 표).
- **선확인이 실패하면 회차를 열지 않는다**(`dobby_testrun_new`를 호출하지 않는다). 이벤트 로그에 `배포 미반영 — 재배포 필요`를 남기고 사용자에게 재배포를 요청한 뒤 대기한다. 모르고 실행하면 **수정 전 동작이 관측돼 코드 결함으로 오진**하고, 실패한 회차가 이력에 남아 재실행 회차와 섞인다(사례 FE1-1808: `main.fb101fd1.js` 빌드가 PR 머지보다 68분 앞선 상태로 1회차를 열어 0성공/3실패/4건너뜀 — 재배포 후 2회차는 같은 절차로 9/0/0 통과. 방법이 아니라 **순서**가 문제였다. FE1-1809도 `static/entries/main` 미배포로 1회차 실패 1건).

### 4. 국내/글로벌 판별 + 국가 전환
- 변경이 국내/글로벌 중 무엇인지 판별(`static/*`·레거시 → 국내, `apps/global`의 `korea-routes/` → 국내, `routes/` → 글로벌). 둘 다면 각각 테스트.
- 페이지 진입 후 헤더(GNB) 국가 변경 버튼으로 대상 국가(국내=한국/글로벌=Global)로 전환한 뒤 테스트한다.

### 5. 로그인 (필요 시)
- 자격증명은 `TEST_LOGIN_ID`/`TEST_LOGIN_PW`. 하나라도 없거나, 그 계정으로는 닿지 않는 화면(관리자·메이커·특정 권한)이 필요하면 **사용자에게 계정을 요청한다**. ⛔ 묻지도 않고 SKIP 하지 않는다.
  - 필요한 것을 **한 번에 모아** 묻는다(시나리오마다 끊지 말고, 막히는 것을 모아 두었다가 7단계 직전에 한 번). 답을 받으면 이어서 테스트한다.
  - 사용자가 줄 수 없다고 답한 뒤에야 SKIP 한다. 사유는 `계정 없음`이 아니라 **`{어떤 권한}이 필요해 요청했으나 제공 불가`**로 적는다.
- **⛔ 로그인 화면 주소로 바로 들어가지 않는다.** 사용자가 실제로 밟는 길로 들어간다. 로그인 주소를 직접 열면 돌아갈 주소·국가 같은 진입 정보가 빠져, 사용자가 겪지 않는 화면이 나오거나 로그인 뒤 엉뚱한 곳으로 간다.
  - PC: 메인 화면(`https://{환경}/`)에서 헤더의 **로그인** 버튼을 눌러 로그인 화면으로 간다.
  - 모바일: **마이 와디즈**로 가서 그 안의 **로그인**을 눌러 로그인 화면으로 간다.
- 로그인은 UI 버튼으로. **입력 순서(동시 입력 금지)**: ① 아이디 입력 → ② "이메일로 시작하기" → ③ 비밀번호 입력 → ④ 다시 "이메일로 시작하기". 입력 후 값이 들어갔는지 스냅샷으로 확인.
- **로그아웃**은 **마이 와디즈** 화면 맨 아래의 **로그아웃** 버튼을 눌러서 한다. ⛔ 로그아웃 주소를 직접 열거나 쿠키·저장소를 지워 대신하지 않는다.

### 6-1. 광고·수집은 이렇게 본다 — dataLayer 를 직접 읽는다

**모든 수집이 한 곳으로 모인다.** `trackingCustomTag`·`trackingEvent`·`adTracking` 전부
`window.dataLayer.push({event, …})` 로 끝난다(`packages/core/src/metrics/trackingEvent.ts`).
그러니 **dataLayer 를 읽으면 관측이 끝난다.**

검증 환경에서 실제로 쌓인다 — `tracking-gtm-head.jsp` 가 `environment` 가 `dev`·`rc*` 면 GTM 을
로드한다(제외는 `local` 뿐). rc4 에서 그대로 관측된다.

**조작 전에 표시하고, 조작 뒤 그 사이에 쌓인 것만 본다.**

```js
// ① 조작 직전
window.__dobbyMark = (window.dataLayer || []).length;

// ② 조작 뒤 — 이 조작이 낳은 이벤트만
(window.dataLayer || []).slice(window.__dobbyMark)
  .map(e => ({ event: e.event, cat: e.GACategory, act: e.GAAction, label: e.GALabel }))
```

```
✓ 근거: dataLayer +1 → {event:"ga.custom.tag", cat:"친구관리", act:"클릭", label:"알림토글"}
✗ 근거: GA 이벤트 정상 확인          ← 무엇을 봤는지가 없다
```

### ⛔ 광고 배너는 **스크롤해야** 노출 이벤트가 뜬다

`AdBoundary` 의 `IntersectionObserver` 가 `threshold: 0.75` 다. 배너가 **75% 보일 때까지
스크롤**해야 `ad.section.view` 가 발생한다. 안 스크롤하고 "이벤트 없음" 이라 적으면 오판이다.

링크에 `_refer_section_st=` 가 있는지도 함께 본다 — **없으면 추적 자체가 안 걸리고** 그냥 이동만
한다(`adTracking` 의 조기 반환). 배너는 멀쩡히 눌리는데 집계만 0이 되는 경로다.

```
✓ 근거: 배너까지 스크롤 후 dataLayer +1 → {event:"ad.section.view", "ad.sectionSt":"MAIN_1"}
       링크 href 에 _refer_section_st=MAIN_1 있음
```

**Braze** 는 초기화 여부와 콘솔 에러만 본다(`window.appboy` 존재 · `window.__brazeDiag`).
호출을 가로채기 어렵고, 대부분 `trackingCustomTag` 와 같이 불려 dataLayer 로 잡힌다.

브라우저는 어차피 떠 있으므로 거의 공짜다. 방문한 페이지마다 **깨짐 신호만** 훑는다.
2-1 의 C(레이아웃 변경으로 배너가 사라지는 것처럼 diff 에 안 드러나는 것)를 여기서 받는다.

| 보는 것 | 깨졌다는 뜻 |
|---|---|
| `(window.dataLayer \|\| []).length` 가 0 | 수집이 통째로 죽었다 |
| 콘솔에 `appboy`·`gtm`·`dataLayer` 가 든 에러 | SDK 초기화 실패 |
| 배너·광고 요청이 4xx·5xx | 배너가 안 뜬다 |

하나라도 걸리면 **다른 시나리오의 판정과 무관하게** result.md 본문에 적는다. 시나리오를 통과시키고
조용히 넘어가지 않는다.

### ⛔ 근거 칸에 파일 이름을 적지 않는다

`근거` 칸에는 **관측한 사실**을 적는다 — 응답 본문·이동 경로·번들 시각·화면 문구.

```
✗  s1-dbcredit-toast-server-message.png
✓  응답 `{"status":400,"message":"해당카드 사용불가…"}` · 토스트 문구 일치
✗  s7-step20-loggedin-main.png
✓  문서 요청 기록 step20 302 → /web/main 200
```

**그림은 지금까지 한 번도 화면에 뜬 적이 없다**(실측 회차 76개: result.md 가 이미지로 띄운 것 0개 · 이름만 적힌 것 88개, summary.html 의 `<img>` 0개). 이름만 적힌 근거는 읽는 사람에게 아무것도 알려 주지 않고, 파일이 지워지면 빈 칸이 된다.

화면을 **꼭 보여야 하면**(레이아웃이 깨졌다·겹친다처럼 글로 옮기기 어려운 것) 본문에 그림으로 **띄운다.**

```markdown
| S2 | C2 | /b | 레이아웃 | 안 겹침 | 겹침 | FAIL | 아래 그림 — 버튼이 제목을 덮는다 |

![S2 버튼이 제목을 덮음](s2-overlap.png)
```

띄우면 파일 이름은 그림이 있는 자리에 적히므로 근거 칸에 또 적을 필요가 없다.

   - **`조건` 칸에는 `C` 번호만 적는다**(`C1`, 여럿이면 `C1·C2`). 조건 문장을 옮겨 적지 않는다.
     이 시나리오가 어느 해결 조건을 확인하는지 대는 칸이고, 대시보드가 이 번호로 "조건 3가지 중
     3가지 확인"을 센다.
   - **⛔ 비워 두지 않는다.** 어느 조건도 짚지 않는 회귀 확인이면 **`R`** 로 적는다.
     빈 칸은 "안 적었다"와 구분되지 않아 대시보드가 그 행을 집계에서 떨어뜨린다
     (실측: 75회차 중 조건을 적은 것이 18건(24%)뿐이라, 조건 8개를 선언해 놓고 검증에서
     한 번도 짚지 않은 오더가 있었다). `dobby_testrun_lint` 가 빈 칸을 거부한다.
   - **`판정` 칸은 다섯 낱말만 쓴다** — `PASS` · `FAIL` · `SKIP(환경)` · `SKIP(위험)` · `SKIP(미비)`.
     보류는 **왜 못 했는지로 가른다**. 그래야 "이 회차만 보고 배포를 판단할 수 있나"를 셀 수 있다.

     | 판정 | 언제 | 배포 판단에 |
     |---|---|---|
     | `SKIP(환경)` | 브라우저·외부 시스템 한계 (FedCM 계정 선택창 등) | 쓸 수 있다 — 수동 확인했으면 그 사실도 적는다 |
     | `SKIP(위험)` | 실행하면 되돌릴 수 없다 (실제 결제·운영 데이터 변경) | 쓸 수 있다 — 왜 되돌릴 수 없는지 적는다 |
     | `SKIP(미비)` | 준비가 모자라 못 했다 (테스트 데이터 없음 등) | **못 쓴다** — 하나라도 있으면 배포 판단 불가 |

     여섯 번째 낱말 `SKIP(범위)` 는 세션이 쓰지 않는다. 테스트 계획 `## 검증 범위` 표에서 이번 회차 대상이 아닌 시나리오를, 회차를 여는 헬퍼가 미리 채워 두는 값이다. 그 행은 건드리지 않는다.

     `통과`·`보류` 같은 한글이나 맨 `SKIP` 을 쓰지 않는다(실측 610개 중 79개(13%)가 기계적으로
     안 읽혀 대시보드 집계에서 빠졌다). `dobby_testrun_lint` 가 거부한다.
   - ⛔ **머리글·컬럼·표식을 바꾸지 않는다.** 표를 새로 짓지도 않는다. 회차마다 제멋대로 지어
     대시보드가 칸을 못 읽던 문제가 있었다(75회차에 머리글이 20가지 넘게 나왔다).
   - 적을 것이 없는 칸은 **빈 채로 둔다**(대시보드가 빈 칸만 있는 컬럼은 알아서 감춘다).
     칸을 없애려고 컬럼을 지우지 않는다.
   - 시나리오가 표 행보다 많으면 **행만** 같은 모양으로 덧붙인다.
   - ⛔ **앞 회차의 실패를 다시 확인했으면 그 번호로도 한 행 적는다.**
     대시보드는 시나리오 **번호로 묶어** 그 번호의 마지막 판정만 센다. 그래서 `TC-7` 이 실패한
     뒤 같은 것을 `S9`·`S10` 으로 다시 짜서 통과하면, 번호가 달라 **`TC-7` 은 영원히 실패로
     남는다**(실측 FE1-1953 — 5회차까지 다 통과했는데 모아보기가 "실패 1건"이었다).
     다시 짰으면 새 번호로 적되, **앞 번호 행을 같은 표에 하나 더 적어** 닫는다.

     ```
     | S9   | … | 하나 지우면 나머지 카드가 유지된다 | … | PASS | … |
     | TC-7 | … | 최근 본 목록에서 지울 때 카드가 어떻게 되는가 | … | PASS | 2회차 실패분. S9·S10·S11 로 다시 짜서 확인 |
     ```

     앞 번호를 그대로 쓸 수 있으면 그게 더 낫다 — 그러면 닫는 행이 따로 필요 없다.
   - **판정 칸에는 `PASS`·`FAIL`·`SKIP` 만 적는다.** 다른 말(`정상`·`일치`·`확인됨`)은 판정으로
     읽히지 않는다.
   - 이 표 말고 회차 요약을 따로 적을 때는 **`판정` 이라는 컬럼명을 쓰지 않는다**(`구분 | 건수`).
     쓰면 대시보드가 그 집계표를 시나리오 표로 착각한다.
5. **원래 열려 있던 페이지를 적어 둔다**: `list_pages`로 지금 열린 페이지의 id를 기록한다. 8단계에서 **테스트가 연 것만** 닫기 위해 필요하다 — 사용자가 보고 있던 탭을 닫으면 안 된다.
6. **탭 제목에 이슈 키를 붙이기로 한다**: 아래 6-1의 `initScript` 를 그대로 쓴다. 테스트가 여러 개 동시에 돌 때 **어느 창이 어느 이슈인지** 알 수 없어서다.

#### 6-1. 시나리오 루프 (각 시나리오 4스텝 한 세트)
1. **조작**: `navigate_page`·`take_snapshot`·`click`/`fill`. 리다이렉트·상태코드는 `list_network_requests`(`includePreservedRequests: true`)로 확인. 화면은 `take_screenshot`으로 결과 폴더에 저장(확인용이다 — **근거로 쓰려면 본문에 띄워야 한다.** 띄우지 않은 그림은 마감 때 지워진다).
   - **⛔ `navigate_page` 를 부를 때마다 `initScript` 로 탭 제목에 이슈 키를 붙인다.** 창을 여러 개 띄워 놓으면 어느 것이 어느 이슈의 테스트인지 알 수 없다.

     ```js
     (() => { const K = "[{키}] "; const fix = () => { try { if (document.title && !document.title.startsWith(K)) document.title = K + document.title; } catch (e) {} }; setInterval(fix, 300); fix(); })()
     ```

     탭 제목이 `[FE1-1787] 와디즈` 처럼 된다. **`initScript` 는 `navigate_page` 의 인자라 호출이 늘지 않는다.**
     - 관찰자(`MutationObserver`)를 쓰지 않는다 — 스크립트가 도는 시점에 `document.documentElement` 가 아직 없어 던지면 **그 뒤 줄이 통째로 안 돈다**(실측: 제목이 안 붙었다). `setInterval` 만 쓴다.
     - 페이지가 스스로 제목을 바꿔도 300ms 안에 다시 붙는다. 화면 안에서 경로만 바뀌는 경우(SPA)도 같은 문서라 그대로 유지된다.
     - `new_page` 에는 이 인자가 없다. 새 창을 열었으면 **`navigate_page` 로 주소를 넣을 때** 붙인다.
     - ⛔ **이슈가 문서 제목(`document.title`)을 검증 대상으로 삼으면 붙이지 않는다** — 확인해야 할 값을 우리가 덮어쓰게 된다. 제목·SEO·탭 이름이 완료 조건에 들어 있으면 이 줄을 건너뛰고 그 사실을 `result.md` 에 적는다.
   - **주소를 모르면 코드에서 찾는다.** 라우트 정의(`routes/`·`pages/`·`korea-routes/`·라우터 설정)를 열어 실제 경로를 확인하고 진행한다. "URL을 몰라서"는 SKIP 사유가 아니다.
   - **조건에 맞는 대상이 안 보이면 찾아 나선다.** 목록·검색·필터로 다른 후보를 뒤지고, 필요하면 DB(`config.md`의 접속 정보)로 조건에 맞는 값을 고른다. 첫 번째로 연 화면에 그 조건이 없다는 것은 SKIP 사유가 아니다.
   - **그래도 못 만들면** 무엇이 없어 막혔는지 적어 두었다가 5단계 요령대로 사용자에게 모아 묻는다.
2. **판정**: 기대 vs 실제 → PASS/FAIL/SKIP.

   **SKIP 은 "무슨 수를 써도 못 하는 것"에만 쓴다.** 셋 중 하나에 해당해야 한다.
   - 브라우저 밖의 것을 조작해야 한다 — OS 파일 선택창, 구글 계정 선택(FedCM), 외부 결제창, 문자·앱 푸시 수신
   - 실행하면 되돌릴 수 없다 — 실제 결제·정산, 실제 발송, 운영 데이터 변경
   - **그 코드가 화면에 도달하지 않음을 코드로 증명**했다(아무도 import 하지 않는 파일 삭제 등). 증명을 본문에 남긴다.

   ⛔ 아래는 SKIP 사유가 **아니다.** 해결하고 진행한다(방법은 1번 참조).
   | 이런 말이 떠오르면 | 해야 할 일 |
   |---|---|
   | 주소를 모르겠다 | 라우트 코드에서 찾는다 |
   | 이 화면에 그 조건이 없다 | 다른 대상을 찾는다(목록·검색·DB) |
   | 계정·권한이 없다 | 사용자에게 요청한다(5단계) |
   | 코드를 보니 맞을 것 같다 | 브라우저로 직접 확인한다 |
   | 변경과 무관해 보인다 | 회귀 확인이 목적이므로 그냥 해 본다 |
   | 계획에 적힌 버튼·진입이 화면에 없다 | **계획의 결함이다.** 코드에서 그 화면을 여는 진입을 찾아(라우트, 창을 여는 함수의 호출처) 테스트 계획을 고치고, 고친 기준으로 판정한다. 진입이 어디에도 없으면 그 코드가 화면에 닿지 않는다는 증명을 남기고 시나리오를 실제로 닿는 화면의 확인으로 고쳐 쓴다(`reference/bundle-scope.md` 판정 순서 4). 계획에 "없으면 SKIP" 이 미리 적혀 있어도 그대로 쓰지 않는다. `SKIP(환경)` 은 브라우저·외부 시스템의 한계에만 쓴다 |
3. **result.md 갱신**: 해당 행에 실제값·판정·근거.
4. **이력 행 갱신**: **→ 헬퍼 `dobby_testrun_update {키} {폴더시각} 테스트중 {성공}/{실패}/{skip}`** — 시나리오가 끝날 때마다 집계를 **즉시** 반영한다(그 행만 수정하므로 status.md를 다시 읽지 않는다). 실패 상세·근거 서술은 result.md에 그대로 자세히 남긴다(3번 — 상세도 유지).

### 7. 결과 마감
- **result.md 완성**: "한눈 요약 → 실패 상세 → 전체 표 → 근거" 순(결론 먼저). 어떤 test-plan으로 실행했는지 명시.
- **⛔ 관찰이 계획의 전제를 뒤집으면 그 회차 안에서 테스트 계획을 고친다.** 별도 발견이나 보류 사유가 시나리오의 진입 경로나 데이터 전제와 부딪히면(예: "이 버튼은 다른 화면으로 이동한다", "이 창은 이 주소에서 열리지 않는다") 결과에만 적고 넘어가지 않는다. 테스트 계획의 그 시나리오에 `- **정정 ({날짜})**:` 줄과 근거를 달아 고치고, result.md 에 `계획 정정` 절로 남긴다. 고치지 않으면 다음 회차가 같은 전제로 다시 돈다(사례 FE1-2261: 1회차가 "찜 카드의 참여하기는 상세 화면으로 이동하고 창은 자동으로 열리지 않는다"를 적고도 계획을 그대로 둬서, 5회차가 같은 전제로 보류했다).
- **status.md 마감**: **→ 헬퍼 `dobby_testrun_update {키} {폴더시각} {완료|완료(이슈 있음)|중단} {최종 성공/실패/skip}`**. 현재 단계는 `검증` 그대로 둔다(6-0에서 전이됨 — 정본 8단계에 "검증완료"는 없고, 해결 승격은 dobby-resolve 담당).
- **배포 표 마감**: 실패가 0건이고 `SKIP(미비)` 가 없으면, `status.md` 의 `## 배포` 표에서 **이번 회차가 확인한 (저장소, 환경) 행마다** **→ 헬퍼 `dobby_ship_stage {키} {저장소} {환경} "검증 완료"`** 를 부른다. 3단계에서 배포 반영을 확인한 행이 그 대상이다.
  - ⛔ 빠뜨리지 않는다. 회차 이력이 `완료` 여도 배포 표가 `배포 확인` 에 남아 대시보드에 오더가 배포에서 멈춘 것으로 보인다(실측 FE1-1845: 4회차 8/0/1 통과 뒤 `com.wadiz.web | rc4` 행이 `배포 확인` 으로 남았다).
  - 실패가 있거나 `SKIP(미비)` 가 있으면 바꾸지 않는다. 그 행은 수정과 재배포 뒤 다음 회차에서 마감한다.
  - 이번 회차가 확인하지 않은 행(다른 저장소·환경)은 건드리지 않는다.
- **⛔ 상태를 자동으로 `해결`로 올리지 않는다.** 검증은 여기까지다. `해결` 승격은 **`dobby-resolve`**가 단독으로 담당한다. (테스트가 전부 PASS여도 dobby-resolve를 호출해야 해결로 표시된다.)
- **화면 출력 형식**: 결론부터 보이게 아래 틀로 쓴다. 파일을 열지 않고도 무엇이 됐고 무엇이 안 됐는지 바로 읽혀야 한다.

```
{키} 테스트 {N}회차 — 통과 8 · 실패 1 · 보류 2   ({환경})

■ 실패 1건
  S4  쿠폰 배지 노출
      기대  조건 충족 시 배지가 보인다
      실제  배지 없음 (콘솔 TypeError: coupon is undefined)
      재현  /funding/12345 → 쿠폰 탭 → 새로고침
      화면  test-runs/20260923-0710/s4-fail.png

■ 보류 2건 — 왜 못 했나
  S7  구글 로그인 연동    SKIP(환경)  계정 선택창이 브라우저 밖(FedCM)이라 조작 불가
  S9  결제 완료 화면      SKIP(위험)  실제 결제가 일어나 되돌릴 수 없음

■ 통과 8건
  S1 S2 S3 S5 S6 S8 S10 S11

전체 기록  {결과 폴더}/result.md
작업 정리  /dobby-summary {키} 로 이슈 전체를 아티팩트 한 장으로 정리할 수 있습니다
```

- **보류(SKIP)는 한 줄에 "분류 + 무엇을 못 했는지 + 왜"가 같이 보여야 한다.** `데이터 없음`·`확인 불가` 처럼 뭉뚱그리지 않는다. 사용자에게 계정을 요청했다가 못 받은 경우도 그 사실을 적는다.
- **⛔ `SKIP(미비)` 가 하나라도 있으면 "이 회차로 배포를 판단할 수 있다"고 보고하지 않는다.** 준비가 모자라 못 한 것은 환경 한계와 다르다 — 준비해서 다시 하거나, 왜 준비할 수 없는지 사용자에게 알린다. (실측된 미비 사례: "찜을 걸어야 확인되는 동작이라 같은 이유로 보류" · "부분 — 배너 3장이라 선별 판정 불가". 둘 다 계획 단계에서 테스트 데이터·판정 기준을 정했으면 막을 수 있었다.)
- 보류가 하나도 없으면 그 칸은 통째로 뺀다. 실패가 없으면 마찬가지.
- 같은 내용을 result.md 에도 남긴다(화면 출력은 요약, 파일은 근거까지).

### 8. 브라우저 정리 + 완료 표시 (마감 뒤 반드시)

테스트로 연 페이지를 그대로 두면 회차를 거듭할수록 탭이 쌓인다. **결과를 저장한 뒤** 정리하고, 마지막 한 장에 완료 요약을 띄운다.

1. **요약 화면을 파일로 쓴다**: `{결과폴더}/summary.html` (Write 도구). `{결과폴더}`는 6-0에서 `dobby_testrun_new` 가 돌려준 그 폴더다.
2. **회차를 검사한다**: **→ 헬퍼 `dobby_testrun_lint {결과폴더}`** — 다섯 가지를 본다.
   ① 근거 칸에 파일 이름만 적힌 행 ② **`track-scan` 이 보고한 `[수집]`·`[광고]` 시나리오 누락**
   ③ 조건 칸이 비었거나 형식이 틀린 행
   ④ 판정 칸 어휘(`PASS`·`FAIL`·`SKIP(환경·위험·미비)`) ⑤ **선언한 조건 중 확인한 시나리오가 없는 것**
   ⑤는 앞선 회차까지 합쳐 본다 — 한 회차로 다 못 덮어도 된다. 거부되면 고쳐서 다시 부른다.
   근거 칸에 파일 이름만 적힌 행이 있으면 **거부한다.** 관측한 사실로 고쳐 쓰고 다시 부른다.
   ②는 **이 회차만** 본다(앞 회차로 때우지 않는다) — 이번에 나간 코드의 수집을 이번에 봐야 한다.
   확인할 수 없는 사정이면 시나리오를 넣고 `SKIP(…)` 으로, 사유를 함께 적는다. ⛔ 빼지 않는다.
3. **안 쓰는 그림을 지운다**: **→ 헬퍼 `dobby_testrun_prune {결과폴더}`**
   테스트 중 화면을 확인하려고 찍은 그림이 결과 폴더에 그대로 남는다. **`result.md`·`summary.html` 이 이름으로 가리키지 않는 것만** 지우므로 근거는 하나도 잃지 않는다. 그래서 **요약을 먼저 쓰고 나서** 부른다 — 순서를 바꾸면 요약이 쓸 그림까지 지운다.
4. `list_pages`로 현재 목록을 받는다.
5. **6-0에서 적어 둔 id에 없는 페이지**(= 이번 테스트가 연 것) 중 **한 장만 남기고** 닫는다.
6. 남긴 그 장을 `navigate_page` 로 `file://{결과폴더}/summary.html` 로 보낸다(여기에도 6-1의 `initScript` 를 붙인다 — 마감 뒤에도 어느 이슈의 요약인지 탭에서 보인다).
7. 이번 테스트가 연 페이지가 하나도 없으면 **파일만 쓰고 끝낸다** — 새 탭을 열지 않는다.

⛔ **6-0에 적어 둔 페이지는 닫지도, 덮어쓰지도 않는다** — 사용자가 쓰던 탭이다.
⛔ 마지막 한 장은 닫히지 않는다(도구가 `The last open page cannot be closed`로 거절한다). 그 장이 곧 요약을 띄울 자리다.

**⛔ 임시 폴더에 쓰지 않는다.** 결과 폴더에 result.md 와 나란히 둔다. 임시 폴더에 만들면 탭을 닫는 순간 잃어버려 "그때 뭐가 실패했더라"를 다시 볼 수 없다. 결과 폴더에 있으면 **대시보드 검증 탭이 회차마다 `요약 화면` 링크를 띄워** 언제든 다시 열 수 있다.

**요약 파일** — 통짜 HTML 한 장. `<!doctype html>` 부터 `</html>` 까지 스스로 갖춘다.

```html
<!doctype html>
<html lang="ko">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>{키} 검증 결과 {N}회차</title>
<style>
  :root{color-scheme:light dark}
  body{margin:0;padding:40px;background:#fafafa;color:#1f1f1f;
       font:15px/1.7 -apple-system,"Apple SD Gothic Neo","Malgun Gothic",sans-serif}
  .wrap{max-width:760px;margin:0 auto}
  .verdict{font-size:34px;font-weight:700;margin:0 0 4px}
  .sub{color:#8c8c8c;margin:0 0 20px}
  .bar{display:flex;height:6px;border-radius:3px;overflow:hidden;margin-bottom:28px}
  h2{font-size:15px;margin:24px 0 8px}
  .item{padding:10px 14px;background:#fff;border:1px solid #f0f0f0;border-radius:6px;margin-bottom:6px}
  .item.fail{border-left:3px solid #ff4d4f}
  .k{color:#8c8c8c;margin-right:6px}
  .pass{color:#52c41a}.failc{color:#ff4d4f}
  footer{margin-top:28px;color:#bfbfbf;font-size:12px}
</style>
</head>
<body><div class="wrap">…</div></body>
</html>
```

담을 것과 순서는 **7단계 화면 출력과 같다**(터미널과 브라우저와 파일이 다른 말을 하지 않게).

| 자리 | 내용 |
|---|---|
| 맨 위 | 판정 한 줄 — `통과` 또는 `실패 N건`, 글자를 크게 |
| 그 아래 | `{키} · {N}회차 · {환경}` |
| 막대 | 통과 초록 `#52c41a` · 실패 빨강 `#ff4d4f` · 보류 회색 `#bfbfbf` 비율대로 |
| 실패 | 시나리오 · 기대 · 실제 · 재현 (없으면 이 칸 통째 생략) |
| 보류 | 시나리오 · 왜 못 했나 (없으면 생략) |
| 통과 | `S1 S2 S3 …` 번호만 |
| 맨 아래 | 결과 파일 경로 |

⛔ **바깥에서 무엇도 받아오지 않는다.** 글꼴·스크립트 CDN도 쓰지 않는다 — 인터넷이 끊기면 지연되고, 나중에 대시보드에서 다시 열 때도 깨진다. 위 시스템 글꼴로 충분하다. 그림이 필요하면 같은 폴더의 스크린샷을 상대 경로로 가리킨다.
⛔ 요약 화면을 **따로 찍어(screenshot) 저장하지 않는다.** 파일 자체가 남으므로 그림은 필요 없다(실측: 안 쓰는 그림 3개 중 하나가 이것이었다 — `완료요약-화면.png`).

스크린샷·네트워크 기록·요약 화면이 모두 결과 폴더에 있으므로, 페이지를 닫아도 잃는 것이 없다.

## 주의

- 추측하지 말고 코드·라우트·네트워크 응답 등 사실로 판정한다. 추측이면 추측이라 밝힌다.
- 테스트 환경이 불확실하면 진행하지 말고 사용자에게 묻는다(잘못된 환경 테스트는 무의미).
- 로그인 입력은 아이디·비밀번호를 **동시 입력하지 않는다**(위 순서 준수).
- 로그인 화면은 PC 메인의 로그인 버튼(모바일은 마이 와디즈의 로그인)으로 들어가고, 로그아웃은 마이 와디즈 맨 아래 로그아웃 버튼으로 한다. 주소를 직접 열지 않는다(5단계).
- live(운영)에서 데이터가 바뀌는 조작(작성/결제/삭제)은 하지 않는다. 조회·이동 위주로 검증.
- 결과는 반드시 파일(`test-runs/{시각}/`)과 화면 양쪽에 남긴다. 진행 상태는 `status.md`에 실시간 기록.
