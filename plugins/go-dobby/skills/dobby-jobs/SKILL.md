# dobby-jobs

팀 이슈를 조사해 **누가 무엇을 어디까지 했는지**와 **내 오더와 겹치는 작업**을 도서관에 정리한다.
진행 상황과 결과는 **한국어와 존댓말**로 쓴다.

## 설정

`${CLAUDE_PLUGIN_ROOT}/reference/config.md` 의 "설정 절차"를 따른다(config.env 는 읽기만).
스크립트는 `${CLAUDE_PLUGIN_ROOT}/skills/dobby-jobs/scripts/` 에 있다(아래 `S`).

| 스크립트 | 하는 일 |
|---|---|
| `schedule.py` | 실행할지 판정하고, 한 번에 하나만 돌게 막고, 조사를 백그라운드로 띄운다 |
| `collect.py` | Jira 조회, 저장소 원격 갱신, 브랜치·PR 찾기, 진행도와 겹침 판정, 보고서 쓰기 |

조사 대상 프로젝트는 `DOBBY_JOBS_PROJECTS`(기본 `FE1,FE2,CLIENT`)로 바꿀 수 있다.

## 사용법

```
/dobby-jobs            # = status
/dobby-jobs status     # 마지막 조사, 다음 자동 조사, 실행 중 여부
/dobby-jobs run        # 지금 조사(이미 돌고 있으면 시작하지 않음)
/dobby-jobs summarize  # 마지막 조사 결과에 요약을 덧붙임(조사가 끝나면 자동으로 불림)
```

- `status` 와 `run` 은 `python3 $S/schedule.py status|run` 의 결과를 표로 보여 주면 끝이다.
- `run` 은 백그라운드로 돈다. 기다리지 말고 "시작했다"와 기록 파일 경로를 알린다.

## 실행 규칙 (schedule.py)

- **자동 실행**: 서버가 `schedule.py tick` 을 켜질 때와 1분마다 부른다. 평일, 오전 9시 이후, 오늘 성공 기록이 없을 때만 시작한다.
- **한 번만 돌기**: `$ORCHESTRATION_META/.dobby-jobs/lock` 폴더를 먼저 만든 쪽만 돈다. 대시보드와 오피스가 함께 불러도 한 번만 돈다. 실행한 프로세스가 죽으면 표시는 다음 판정 때 치운다.
- **실패하면**: 성공 기록을 남기지 않는다. 30분 뒤 다시 시도하고, 하루 최대 3번까지만 시도한다.
- **조사 기간**: 지난 성공 시각부터 지금까지다. 주말이나 꺼져 있던 날의 변경도 다음 조사에 들어간다. 성공 기록이 없으면 기준 정리를 한다.
- 실행 기록은 `$ORCHESTRATION_META/.dobby-jobs/` 에 둔다(`state.json`, `run.log`).

## 판정 기준 (collect.py)

**조사 대상**

| 모드 | 대상 |
|---|---|
| 기준 정리 (처음) | 끝나지 않은 이슈 전부 + 지난주 월요일 이후 끝난 이슈 |
| 매일 정리 | 지난 조사 이후 새로 생긴 이슈 + 진행 중·해결됨·종료로 바뀐 이슈 |
| 두 모드 공통 | 지금 진행 중인 이슈 전부(담당자별 진행표용) |

Jira 검색에서 상태는 이름이 아니라 번호로 쓴다(진행 중 `10155`, 해결됨 `5`, 종료 `6`). 이름으로 쓰면 `CHANGED TO` 가 0건이 된다.
twg 조회는 한 번에 100건까지만 오므로 이슈 번호 내림차순으로 끊어 받는다. `key < X` 는 같은 프로젝트 안에서만 비교되므로 **프로젝트마다 따로** 받는다. 여러 프로젝트를 한 번에 끊어 받으면 둘째 쪽부터 한 프로젝트만 남는다.

**진행도**: 이슈 키가 이름에 들어간 원격 브랜치로 정한다.

| 진행도 | 근거 |
|---|---|
| 착수 전 | 브랜치 없음 |
| 개발 중 | 브랜치 있음, 열린 PR 없음 |
| 리뷰 중 | 열린 PR 있음 |
| 검증 환경 반영 | 끝 커밋이 dev·cloud_dev·rc 계열에 들어감(병합된 PR 대상 포함) |
| 배포 대기 | stage 또는 배포용 release 브랜치(release/v20261112, release/26.47.0 처럼 숫자로 시작)에 들어감. release/CLIENT-331_into_dev 같은 병합용은 아님 |
| 라이브 반영 | cloud_live(없으면 master·main)에 들어감 |
| 에픽 | 에픽이고 브랜치가 없음 |

**겹침**: 지금 작업 중인 내 오더와 남의 이슈를 비교한다.

- 내 오더는 `status.md` 단계가 종료·해결·완료가 아니고, **라이브 브랜치에 없는 커밋이 있는** 오더만 센다. 라이브에 다 들어간 오더와 아직 커밋이 없는(작업 시작 전) 오더는 뺀다. Jira 상태가 해결됨·종료인 오더도 뺀다.
- 바뀐 파일은 **그 오더의 이슈 키나 하위 이슈 키가 커밋 메시지에 붙은 커밋**이 고친 파일만 센다. 브랜치 전체 차이로 세면 병합해 들어온 남의 변경까지 잡힌다. 잠금 파일(`pnpm-lock.yaml` 등)은 뺀다.
- 내 이슈끼리는 비교하지 않는다. 담당자가 나인 이슈, 내 오더와 그 하위 이슈는 상대 이슈에서 뺀다.

| 겹침 | 근거 |
|---|---|
| 충돌 주의 | 같은 파일을 고침 |
| 같은 기능 | 같은 상위 이슈, 또는 같은 폴더를 고침 |

## 결과 파일

`$ORCHESTRATION_DOCS_ROOT/_dobby-jobs/`

| 파일 | 내용 | 갱신 |
|---|---|---|
| `latest.json` | 마지막 조사의 전체 데이터. 대시보드와 오피스가 읽는다 | 매번 덮어씀 |
| `daily/{날짜}.md`, `daily/{날짜}.json` | 그날 바뀐 이슈 보고서 | 매일 새 파일 |
| `baseline-{날짜}.md`, `.json` | 기준 정리 | 처음 한 번 |
| `by-person.md` | 담당자별 진행 | 매번 덮어씀 |
| `overlap.md` | 내 오더와 겹치는 작업 | 매번 덮어씀 |

도서관 저장소에 커밋·푸시하지 않는다. 사람이 원할 때 직접 한다.

## summarize

조사가 성공하면 schedule.py 가 헤드리스로 부른다. 사람에게 묻지 않는다.

1. `$ORCHESTRATION_DOCS_ROOT/_dobby-jobs/latest.json` 을 읽는다. `mode` 가 `daily` 면 `picked` 가 참인 이슈와 `overlaps` 를, `baseline` 이면 진행 중 이슈와 `overlaps` 를 본다.
2. 오늘 눈여겨볼 점을 **3~5개** 문장으로 쓴다. 숫자와 이슈 키를 근거로 넣는다. 예:
   - 내 오더와 같은 파일을 고친 남의 이슈와 그 파일
   - Jira는 진행 중인데 브랜치가 없는 이슈가 많은 팀
   - 7일 넘게 커밋이 없는 진행 중 이슈
   - 오늘 라이브나 검증 환경에 들어간 큰 작업
3. 추측은 쓰지 않는다. 데이터에 없는 원인은 적지 않는다.
4. 문장 목록을 `latest.json` 의 `headline` 칸(문자열 배열)에 넣는다. 같은 내용을 그날 보고서(`daily/{날짜}.md` 또는 `baseline-{날짜}.md`) 맨 위 제목 바로 아래에 `## 요약` 절로 넣는다. 이미 `## 요약` 이 있으면 바꿔 쓴다.
5. `latest.json` 은 JSON 으로 다시 읽어 깨지지 않았는지 확인한다.
