# dobby-discard

필요 없어진 오더를 **절차대로** 없앤다. 세 가지 경우를 위한 스킬이다.

- 착수만 하고 접은 오더 — 분석하다 범위가 아니라고 판단해 진행하지 않은 것
- 잘못 만든 키 — 오타·중복으로 만들었다가 안 쓴 것
- 다른 오더로 흡수된 오더 — 사용자 판단으로 기존 오더에 편입해 별도 진행이 없어진 것

> **폐기는 삭제가 아니라 이동이다.** 메타 폴더는 종료된 작업의 유일한 기록이라(워크트리를 지운 뒤에는 `code-changes/*.diff`가 코드 원본이다) 훅 G6이 `rm`을 막는다. 막는 게 맞다. 이 스킬은 **지워도 되는 오더인지를 파일·git으로 전수 확인한 뒤** 휴지통으로 옮긴다. 되돌릴 수 있고, 압축 아카이브도 따로 남는다.

## 설정 (첫 실행 시 확인)

작업을 시작하기 전에 **`${CLAUDE_PLUGIN_ROOT}/reference/config.md`의 "설정 절차"를 그대로 따른다**: `~/.config/go-dobby/config.env`를 source 해 환경 변수를 **읽기만** 한다. ⛔ **이 스킬은 config.env를 저장·수정·생성하지 않는다**(값 변경은 `dobby-init` 전용 — config.md '비파괴 원칙'). config.env 파일이 아예 없으면 멈추고 `/dobby-init`을 먼저 실행하도록 안내한다. 메타 루트 `ORCHESTRATION_META`, 폴더 배치(워크트리 `$ORCHESTRATION_WORKSPACE/subtree/` · 메타 `$ORCHESTRATION_META/`)는 그 문서에 있다.

**공용 헬퍼(config.md '공용 헬퍼', 이미 source됨)** — 판정·이동·복원의 결정론 부분은 전부 함수가 한다. ⛔ **직접 `mv`·`rm`을 치지 않는다.**

| 헬퍼 | 하는 일 |
|------|---------|
| `dobby_discard_check {키}` | 폐기 조건 검사. 위반을 한 줄씩 내고 비0 반환(위반 0건이면 조용히 0) |
| `dobby_discard {키} "사유"` | 검사 통과 시 압축 백업 → 휴지통으로 이동. 새 경로 stdout |
| `dobby_discard_list` | 휴지통 목록 `경로<TAB>키<TAB>폐기시각` |
| `dobby_discard_undo {키}` | 휴지통에서 원래 자리로 복원 |
| `dobby_discard_purge {키}` | 휴지통 안의 그 오더를 영구 삭제(`DOBBY_DISCARD_PURGE_OK=1` 필요) |

## 입력

- `args`: `{키}`(필수, 예 `FE1-1830`·`TASK-image-size-guard`) — 그 오더를 폐기한다.
- `args`: `list` — 휴지통에 무엇이 있는지 본다(키 없이).
- `args`: `undo {키}` — 휴지통에서 되돌린다.
- `args`: `purge {키}` — 휴지통에서 영구 삭제한다.

## ⛔ 폐기 조건 (하나라도 걸리면 거부)

`dobby_discard_check`가 **추정 없이 전부 파일·git에서 읽어** 판정한다. 아래 중 하나라도 있으면 폐기하지 않는다.

| 검사 | 왜 막는가 |
|------|-----------|
| `status.md` 단계가 `해결`·`종료` | 정상 완료한 오더다. 남겨야 하는 기록이라 폐기 대상이 아니다 |
| subtree에 워크트리가 살아 있다 | 미커밋 코드를 잃을 수 있다. **먼저 `/dobby-end`** |
| 그 워크트리에 origin에 없는 커밋이 있다 | 잃으면 되돌릴 방법이 없다 |
| `code-changes/*.diff`가 비어 있지 않다 | 워크트리를 지운 뒤에는 이것이 **유일한 코드 원본**이다 |
| `artifact-share.md`에 게시 링크가 있다 | 공개된 아티팩트가 근거 문서를 잃는다. 링크는 회수할 수 없다 |
| `reviews/`·`agents/`에 `.md`가 있다 | 실제로 리뷰를 받고 진행한 오더다 |

**조건을 무르는 것은 사용자 판단이다.** 헬퍼에 강제 우회 인자는 없다. 위반이 나오면 그 줄을 그대로 보여 주고, 무엇을 먼저 해야 하는지(`/dobby-end` 등)를 안내하고 **멈춘다.** 사용자가 그래도 없애길 원하면 무엇을 잃는지 한 줄로 명시하고 동의를 받은 뒤, 걸린 조건을 실제로 해소하고(워크트리 정리 등) 다시 검사를 통과시킨다.

## 절차

1. **검사부터**: `dobby_discard_check {키}`를 돌린다. 비0이면 출력한 위반 줄을 사용자에게 보여 주고 멈춘다.
2. **무엇을 없애는지 보여 준다**: 통과했더라도 바로 옮기지 않는다. 폴더 경로·`status.md`의 제목·단계·파일 수를 표로 정리해 보여 주고 **사용자 동의를 받는다**(파괴 방향 작업은 항상 동의 후 — dobby-order C1과 같은 원칙).
3. **사유를 받아 폐기**: `dobby_discard {키} "{사유}"`. 사유는 한 줄로 왜 필요 없어졌는지 적는다(예: `사용자 판단으로 FE1-1830에 흡수 — 착수 전 무효`). 헬퍼가 이 순서로 처리한다.
   - `dobby-meta-backup.sh`로 **압축 아카이브를 먼저 만든다**(`$ORCHESTRATION_BACKUP_DIR/{키}--{시각}.tar.zst`). ⛔ 여기서는 백그라운드로 띄우지 않는다 — 다음 줄에서 폴더를 옮기므로 분리 실행하면 압축이 사라진 폴더를 읽어 아카이브가 깨진다(`dobby_resolve`가 분리 실행하는 것과 다른 점).
   - 폐기 사유를 `discard-reason.md`로 폴더 안에 남긴다. 나중에 휴지통을 열었을 때 **왜 없앴는지가 유일한 단서**다.
   - 폴더를 `$ORCHESTRATION_META/.discarded/{키}--{시각}/`로 **이동**한다.
4. **결과를 알린다**: 새 경로, 압축 아카이브 경로, 되돌리는 방법(`/dobby-discard undo {키}`)을 함께 알린다.

## 폐기하면 무엇이 달라지나

- **오케스트레이션 보드에서 사라진다.** 대시보드는 메타 루트에서 **점으로 시작하는 폴더를 건너뛴다**(`orchestration.ts`의 `!d.name.startsWith(".")`). 휴지통이 `.discarded`인 이유다.
- **기록은 두 곳에 남는다.** 휴지통 폴더 원본 + 압축 아카이브. 어느 쪽으로도 되돌릴 수 있다.
- **키를 다시 쓸 수 있다.** 원래 자리가 비므로 같은 키로 새 오더를 착수할 수 있다.

## 되돌리기 · 목록 · 영구 삭제

- **목록**: `dobby_discard_list`. 폐기 시각과 함께 보여 준다. 휴지통이 비어 있으면 그렇게 알린다.
- **되돌리기**: `dobby_discard_undo {키}`. 원래 자리에 이미 폴더가 있으면 거부한다(같은 키로 새 오더를 시작한 경우 — 덮어쓰지 않는다). `discard-reason.md`는 지우지 않고 `- **되돌림**: {일시}` 한 줄을 덧붙인다.
- **영구 삭제**: `dobby_discard_purge {키}`. **사용자가 명시적으로 지시할 때만.** 확인 없이 돌지 않도록 `DOBBY_DISCARD_PURGE_OK=1`을 요구한다. 대상이 휴지통 밖이면 무조건 거부한다. 압축 아카이브는 이때도 남으니, 아카이브까지 없애려면 사용자가 직접 지운다.

> 훅 G6·G5는 `$ORCHESTRATION_META/.discarded/` 아래만 `rm` 대상으로 허용한다. 메타 경로가 여러 개 섞이면 **전부 휴지통 아래일 때만** 통과한다(하나라도 살아 있는 오더면 차단). 이 예외가 있는 이유는 폐기 조건 검사와 백업을 이미 거쳤기 때문이다.

## 휴지통은 자동으로 비우지 않는다

시간이 지나도 스스로 지우지 않는다. 기록을 자동으로 없애는 것이 비파괴 원칙에 어긋나기 때문이다. 쌓인 것이 신경 쓰이면 `/dobby-discard list`로 보고 필요한 것만 `purge`한다.

## 하지 않는 것

- **워크트리를 건드리지 않는다.** 워크트리 정리는 `dobby-end` 소관이다. 살아 있으면 폐기를 거부하고 그쪽으로 안내한다.
- **브랜치·원격을 건드리지 않는다.** 푸시된 브랜치는 그대로 남는다.
- **Jira를 건드리지 않는다.** 이슈 상태 변경은 사용자 판단이다. 오더 폐기와 이슈 종료는 다른 일이다.
- **조건을 스스로 무르지 않는다.** 강제 우회 인자를 만들지 않았다. 걸리면 멈추고 사용자에게 넘긴다.
